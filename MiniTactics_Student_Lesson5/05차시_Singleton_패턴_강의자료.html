1장 / 전체 6장

하나여야 하는 상태와 여러 접근자

이번 차시의 주제는 Singleton 패턴 하나다. 패턴의 이름을 외우기 전에, 어떤 문제가 있을 때 이 구조가 필요해지는지를 먼저 확인한다.

1.1 지금까지의 방법: 참조를 전달한다

이전 차시까지는 한 객체가 다른 객체를 사용해야 할 때 직렬화 필드를 선언하고 Inspector에서 연결했다. 참조는 객체를 가리키는 값이다. 이 방법은 어떤 객체가 어떤 객체를 사용하는지가 필드 선언과 Inspector에 드러난다는 장점이 있다.

// BattleController.cs의 필드 선언 일부
[SerializeField] private BoardView _board;
[SerializeField] private Camera _camera;

이 방법은 이번 차시에도 계속 사용한다. 이 장에서는 이 방법만으로는 보장할 수 없는 조건이 무엇인지를 찾는다.

1.2 새 요구: 여러 곳이 같은 결과를 알아야 한다

경기가 끝나면 입력이 멈추고, 턴 진행이 멈추고, 화면에는 결과가 표시되어야 한다. 경기 결과는 진행 중, 승리, 패배 중 하나를 나타내는 값이다. 이 값을 알아야 하는 곳은 입력을 받는 BattleController, 턴을 진행하는 TurnManager, 화면에 표시하는 PhaseHud의 세 곳이다. 값은 하나인데 그 값을 읽는 곳은 셋이다.

1.3 첫 해결 시도와 그 한계

처음 떠올릴 수 있는 방법은 세 곳이 각자 종료 여부를 필드로 가지는 것이다. 아래는 설계를 검토하기 위한 가상 코드이며 현재 Teacher 구현이 아니다.

// 설계 검토용 가상 코드
// BattleController 안
private bool _isFinished;

// TurnManager 안
private bool _isFinished;

// PhaseHud 안
private bool _isFinished;

결과를 읽는 곳이 한 곳뿐이라면 필드 하나로 충분하다. 그러나 세 곳이 각자 복사본을 가지면 경기가 끝나는 순간에 세 값을 빠짐없이 true로 바꿔야 한다. 아군이 적 거점에 도착해서 승리했는데, 턴 진행이 화면 표시에는 종료를 전달하고 입력에는 전달하지 않은 경우를 추적해 보자.

시점턴 진행의 값화면 표시의 값입력의 값
거점 도착 전falsefalsefalse
턴 진행이 승리를 판정truefalsefalse
화면 표시에만 전달truetruefalse

화면에는 VICTORY가 표시되는데 유닛은 계속 움직인다. 입력의 복사본이 아직 false이기 때문이다. 결과를 읽는 곳이 늘어날 때마다 전달할 곳도 늘어나고, 한 곳을 빠뜨리면 같은 불일치가 다시 생긴다.

1.4 필요한 두 조건

이 문제를 없애려면 두 조건이 필요하다. 첫째, 결과를 가진 객체는 하나여야 한다. 결과를 복사하지 않고 한 객체만 보관하면 서로 다른 값을 볼 수 없다. 둘째, 입력과 턴 진행과 화면 표시가 모두 그 객체에 접근할 수 있어야 한다.

세 곳에 Inspector 참조를 연결해도 둘째 조건은 만족한다. 그러나 누군가 씬에 같은 객체를 하나 더 놓는 것까지 막지는 못한다. 두 번째 객체가 생기면 첫째 조건이 깨진다. 두 조건을 클래스가 스스로 보장하게 만드는 구조가 Singleton이다.

이 장의 핵심 문장

Singleton이 해결하는 문제는 “하나여야 하는 상태에 여러 곳이 접근해야 한다”이다. 접근이 편해서 사용하는 구조가 아니다.

2장 / 전체 6장

Singleton의 구조: 세 부분

Singleton은 어떤 클래스의 인스턴스가 하나만 존재하도록 클래스가 스스로 보장하고, 그 하나에 접근하는 전역 접근 지점을 제공하는 패턴이다. 인스턴스는 클래스로부터 만들어진 실제 객체를 뜻한다. 미니 택틱스에서는 GameManager가 Singleton이다.

2.1 첫째 부분: static Instance

// GameManager.cs
public static GameManager Instance { get; private set; }

일반 속성은 객체마다 하나씩 있다. static 속성은 객체가 아니라 클래스에 하나만 있다. 그래서 객체를 가리키는 참조가 없어도 어느 코드에서든 GameManager.Instance라는 이름으로 읽을 수 있다. get은 누구나 읽을 수 있다는 뜻이고, private set은 GameManager 안에서만 값을 바꿀 수 있다는 뜻이다. 다른 클래스에서 Instance에 다른 객체를 대입하는 코드는 컴파일되지 않는다.

static 속성만으로는 인스턴스가 하나로 제한되지 않는다. 씬에 GameManager가 두 개 있고 Awake에 Instance = this; 한 줄만 있다면, 나중에 Awake가 실행된 쪽이 앞의 등록을 덮어쓴다. Instance는 한 객체를 가리키지만 다른 객체도 씬에 남아 있으므로 결과를 가진 객체가 둘이 된다. this는 지금 코드를 실행하는 객체를 뜻하고, Awake는 객체가 만들어진 직후에 Unity가 한 번 호출하는 메서드다.

2.2 둘째 부분: Awake의 중복 방어와 return

// GameManager.cs
private void Awake()
{
    if (Instance != null && Instance != this)
    {
        Destroy(gameObject);
        return;
    }

    Instance = this;
}

Instance != null은 이미 등록된 인스턴스가 있는지를 묻는다. Instance != this는 그 인스턴스가 자신이 아닌지를 묻는다. 둘 다 참이면 자신은 두 번째 인스턴스이므로 자신이 붙어 있는 게임 오브젝트를 파괴한다. 등록된 인스턴스가 없을 때만 마지막 줄에 도달해서 자신을 등록한다.

Destroy는 객체를 즉시 없애지 않는다. 파괴를 예약하고, 실제 파괴는 현재 프레임의 갱신이 끝난 뒤에 일어난다. 그래서 Destroy를 호출한 다음 줄도 계속 실행된다. return이 없으면 파괴될 객체가 Instance = this를 실행해서 정상 인스턴스의 등록을 덮어쓴다. 그 객체가 파괴되면 Instance는 null로 비워지고, 정상 인스턴스는 살아 있는데도 GameManager.Instance를 읽는 코드에서 NullReferenceException이 발생한다. return을 빠뜨려도 컴파일 오류는 나지 않으므로 주의해야 한다.

2.3 셋째 부분: OnDestroy의 조건부 해제

// GameManager.cs
private void OnDestroy()
{
    if (Instance == this)
    {
        Instance = null;
    }
}

OnDestroy는 객체가 파괴될 때 Unity가 호출하는 메서드다. static 속성은 클래스에 속하므로 객체가 파괴되어도 값이 저절로 비워지지 않는다. 등록된 인스턴스가 파괴될 때 직접 null을 대입해야 파괴된 객체를 가리키는 참조가 남지 않는다.

조건이 필요한 이유는 중복 인스턴스도 파괴되기 때문이다. 조건 없이 Instance = null을 실행하면 중복 객체가 파괴되면서 정상 인스턴스의 등록을 지운다. Awake의 등록과 OnDestroy의 해제는 한 쌍으로 읽는다.

2.4 중복 인스턴스가 사라지는 과정

Play 중에 GameManager가 붙은 게임 오브젝트를 복제했다고 하자. 원본을 A, 복제본을 B라고 부른다.

순서실행되는 판단Instance
1. A의 AwakeInstance가 null이므로 조건은 거짓이다. Instance = this를 실행한다.A
2. B의 AwakeInstance는 A이고 A는 B가 아니므로 조건은 참이다. 파괴를 예약하고 return한다.A
3. B의 OnDestroyInstance == this가 거짓이므로 아무것도 하지 않는다.A
4. 씬이 닫힐 때 A의 OnDestroyInstance == this가 참이므로 null을 대입한다.null

복제본 B는 곧바로 사라지고 원본 A가 남는다. 1번부터 3번까지 Instance는 한 번도 A에서 바뀌지 않는다. Instance를 사용하는 쪽은 중복이 생겼다가 사라진 사실을 알 필요가 없다.

확인 질문과 해설: 중복 객체가 파괴될 때 무엇이 보존되어야 하는가?

처음에 정상으로 등록된 Instance가 보존되어야 한다. 중복의 Awake는 파괴를 예약한 뒤 return하므로 등록을 덮어쓰지 않는다. 중복의 OnDestroy는 Instance == this가 거짓이므로 null을 대입하지 않는다.

3장 / 전체 6장

결과의 확정과 소비자의 코드

Singleton이 보관하는 값과 그 값을 바꾸는 규칙을 확인한 뒤, 그것을 사용하는 쪽의 코드를 읽는다. 마지막으로 Singleton이 아닌 일반 컴포넌트와 비교한다.

3.1 보관하는 값은 경기 결과 하나다

// GameManager.cs
public BattleResult Result { get; private set; } = BattleResult.Playing;
public bool IsPlaying => Result == BattleResult.Playing;

BattleResult는 Playing, PlayerWon, PlayerLost 중 하나를 나타내는 열거형이다. 처음 값은 Playing이다. private set이므로 값을 바꾸는 코드는 GameManager 안에만 있다. IsPlaying은 Result가 Playing인지 계산해서 돌려주는 읽기 전용 속성이다. 별도의 bool 필드를 두지 않았으므로 Result와 어긋날 수 없다. 1장의 첫 해결 시도에서는 세 곳이 bool 복사본을 가졌지만, 이제 결과는 이 속성 하나에만 있고 다른 곳은 읽기만 한다.

3.2 Finish는 첫 번째 결과만 확정한다

// GameManager.cs
public void Finish(BattleResult result)
{
    if (!IsPlaying)
    {
        return;
    }

    Result = result;
}

Finish(PlayerWon)이 호출되면 IsPlaying이 참이므로 Result는 PlayerWon이 된다. 그 뒤에 Finish(PlayerLost)가 호출되면 IsPlaying이 거짓이므로 return하고 Result는 PlayerWon 그대로다. 결과를 확정해 달라는 요청은 여러 곳에서 여러 번 올 수 있다. 확정 규칙이 값을 가진 객체 안에 있으므로, 호출하는 쪽은 경기가 이미 끝났는지 검사하지 않아도 된다. 승리한 뒤에 패배로 덮어쓰이지 않는다.

3.3 소비자의 코드

Instance를 통해 결과를 읽거나 확정을 요청하는 클래스를 이 교재에서는 소비자라고 부른다. 소비자는 BattleController, TurnManager, PhaseHud의 세 클래스다.

// BattleController.CanAcceptInput: 입력을 받을지 판단한다.
return GameManager.Instance.IsPlaying
    && _turnManager.Phase == BattlePhase.Player;

// TurnManager.CheckBase: 결과의 확정을 요청한다.
GameManager.Instance.Finish(result);

// PhaseHud.Update: 표시할 결과를 읽는다.
BattleResult result = GameManager.Instance.Result;

첫 코드는 읽기 쉽게 줄바꿈만 조정했다. 세 클래스에는 GameManager를 담는 필드가 없고 Inspector 연결도 없다. 세 코드는 모두 같은 인스턴스의 같은 Result를 사용한다.

TurnManager: GameManager.Instance.Finish(PlayerWon)
↓
GameManager: Result = PlayerWon
↙　　　　　↘
BattleController: IsPlaying은 false　　PhaseHud: Result는 PlayerWon

확정을 요청한 코드는 입력과 화면 표시에 아무 값도 전달하지 않았다. 그런데도 화면과 동작이 일치한다. 전달할 복사본이 없고 읽을 원본만 있기 때문이다.

3.4 일반 컴포넌트와의 대비: TurnManager

// BattleController.cs와 PhaseHud.cs의 필드: Inspector에서 연결한다.
[SerializeField] private TurnManager _turnManager;

// 사용할 때는 필드를 통해서 접근한다. (CanAcceptInput의 일부)
_turnManager.Phase == BattlePhase.Player
비교GameManagerTurnManager
접근 방법클래스 이름과 static InstanceInspector에서 연결한 필드
의존이 보이는 곳메서드 본문 안필드 선언과 Inspector
인스턴스 수클래스가 하나로 제한한다제한하지 않는다

TurnManager도 씬에 하나만 있다. 그러나 하나만 놓았다는 것과 하나여야 한다고 클래스가 강제하는 것은 다르다. 미니 택틱스는 Singleton을 GameManager 하나에만 사용하고, TurnManager는 의도적으로 일반 컴포넌트로 둔다.

확인 질문과 해설: 승리가 확정된 뒤에 Finish(PlayerLost)가 호출되면 Result는 무엇인가?

PlayerWon이다. IsPlaying이 거짓이므로 Finish는 값을 바꾸지 않고 return한다.

4장 / 전체 6장

Singleton의 대가, 수명, 적용 기준

Singleton은 대가가 있는 구조다. 대가를 알고 있어야 언제 사용하고 언제 사용하지 않을지를 판단할 수 있다.

4.1 숨은 의존

소비자의 필드 선언과 Inspector만 보아서는 어떤 클래스가 GameManager를 사용하는지 알 수 없다. 메서드 본문을 읽어야 보인다. 어디서든 접근할 수 있다는 것은 어디서든 의존할 수 있다는 뜻이다. 3.4의 표에서 “의존이 보이는 곳”의 차이가 이 대가다.

4.2 “하나뿐”이라는 가정의 고착

소비자가 GameManager.Instance라고 적을 때마다 “경기는 동시에 하나뿐이다”라는 가정이 코드의 여러 곳에 반복해서 기록된다. 나중에 두 경기를 동시에 진행해야 한다면 모든 소비자를 고쳐야 한다. 참조로 전달받는 구조였다면 다른 객체를 연결하는 것으로 충분하다.

4.3 실행 순서 의존

// 위험을 보여 주는 가상 코드: 어떤 소비자의 Awake
private void Awake()
{
    bool playing = GameManager.Instance.IsPlaying;
}

Instance는 GameManager의 Awake에서 채워진다. 서로 다른 컴포넌트의 Awake 중 어느 것이 먼저 실행되는지는 보장되지 않는다. 이 소비자의 Awake가 먼저 실행되면 Instance는 아직 null이고 NullReferenceException이 발생한다. Unity는 씬에 있는 컴포넌트의 Awake를 모두 실행한 뒤에 Start를 호출한다. 그래서 Instance는 Start 이후, 즉 Start와 Update와 입력 처리 안에서 사용한다. 실제 소비자도 Update와 입력 처리 안에서만 Instance를 읽는다.

4.4 수명: DontDestroyOnLoad를 사용하지 않는 이유

// GameManager.cs (읽기 쉽게 줄바꿈만 조정)
public void Restart()
{
    SceneManager.LoadScene(
        SceneManager.GetActiveScene().buildIndex);
}

씬을 다시 불러오면 기존 씬의 객체가 모두 파괴된다. 기존 GameManager의 OnDestroy가 Instance를 null로 비우고, 새 씬의 GameManager가 Awake에서 자신을 등록한다. 새 인스턴스의 Result는 처음 값인 Playing이다. 이 Singleton의 수명은 씬 하나다.

DontDestroyOnLoad는 씬이 바뀌어도 객체를 파괴하지 않게 하는 Unity 기능이다. GameManager에 사용하면 기존 인스턴스가 PlayerWon을 가진 채로 남고, 새 씬의 GameManager는 중복으로 판정되어 파괴된다. 재시작해도 이전 결과가 남으므로 사용하지 않는다. 전역 접근 지점을 제공하는 것과 객체를 영구히 보존하는 것은 서로 다른 결정이다.

4.5 적용 기준

질문GameManagerTurnManager
그 상태는 반드시 하나여야 하는가?예. 경기 결과가 둘이면 어느 쪽이 맞는지 정할 수 없다.아니다. 보드와 유닛의 묶음마다 따로 둘 수 있다.
서로 다른 여러 곳이 접근하는가?예. 입력, 턴 진행, 화면 표시가 모두 사용한다.일부만 사용한다.
중복을 클래스가 막아야 하는가?예. 둘이 되는 순간 불일치가 생긴다.아니다. 씬에 하나만 놓는 것으로 충분하다.

세 질문에 모두 “예”일 때만 Singleton을 사용한다. 하나라도 “아니다”라면 Inspector 참조로 전달한다.

흔한 실수

이름에 Manager가 붙은 클래스를 모두 Singleton으로 만드는 것이다. 접근은 쉬워지지만 숨은 의존, 가정의 고착, 실행 순서 의존이 클래스 수만큼 늘어난다.

5장 / 전체 6장

이론 코너: Game Loop

교육과정에서 5차시의 이론 코너로 지정된 엔진 기본 패턴은 Game Loop다. 개념만 짧게 확인한다.

5.1 엔진은 프레임마다 같은 순서를 반복한다

Game Loop는 게임이 실행되는 동안 입력 처리, 상태 갱신, 화면 표시를 계속 반복하는 구조다. 한 번의 반복을 프레임이라고 한다. 사용자가 아무 입력도 하지 않아도 반복은 멈추지 않는다. Unity에서는 엔진이 이 반복을 실행한다. 우리는 반복문을 직접 작성하지 않고, Update처럼 엔진이 매 프레임 호출하는 메서드에 코드를 적는다.

엔진의 프레임 반복: 입력 → 갱신 → 표시 → 입력 → 갱신 → 표시 …
게임 규칙의 턴 반복: 플레이어 차례 ─────────→ 적 차례 ──→ 플레이어 차례

5.2 프레임의 반복과 턴의 반복은 서로 다른 루프다

비교엔진의 프레임 반복게임 규칙의 턴 반복
반복하는 내용입력 처리, 상태 갱신, 화면 표시플레이어 차례, 적 차례
한 번의 길이1초에 수십 번 반복될 만큼 짧다행동을 마칠 때까지이므로 일정하지 않다
다음으로 넘기는 것엔진게임 규칙
작성하는 사람엔진이 제공한다게임을 만드는 사람이 작성한다

플레이어가 다음 행동을 10초 동안 고민하면 프레임은 수백 번 반복되지만 차례는 한 번도 바뀌지 않는다. 턴 반복은 프레임 반복 안에서 실행되지만 별개의 규칙이다. 두 루프를 구분하면 매 프레임 확인할 일과 차례가 바뀔 때 한 번만 할 일을 나눌 수 있다.

6장 / 전체 6장

복습: 확인 질문과 용어

6.1 설명하는 연습

  1. Instance의 private set과 Awake의 중복 검사는 각각 무엇을 막는가?
  2. Awake에서 Destroy 뒤의 return을 지우면 어떤 일이 생기는가?
  3. OnDestroy에서 조건 없이 Instance = null을 실행하면 어떤 일이 생기는가?
  4. 승리가 확정된 뒤에 Finish(PlayerLost)가 호출되면 Result는 무엇인가?
  5. 소비자가 자신의 Awake에서 Instance를 읽으면 안 되는 이유는 무엇인가?
  6. GameManager에 DontDestroyOnLoad를 추가하면 재시작할 때 어떤 일이 생기는가?
  7. TurnManager를 Singleton으로 만들지 않은 이유를 적용 기준의 세 질문으로 설명하라.
핵심 답안 확인

1: private set은 다른 클래스가 Instance에 다른 객체를 대입하는 것을 막고, 중복 검사는 씬에 두 번째 인스턴스가 남는 것을 막는다. 2: 파괴될 객체가 Instance를 덮어쓴다. 그 객체가 파괴되면 Instance가 null이 되어 소비자에서 NullReferenceException이 발생한다. 3: 중복 객체가 파괴되면서 정상 인스턴스의 등록을 지운다. 4: PlayerWon이다. IsPlaying이 거짓이므로 Finish는 return한다. 5: GameManager의 Awake보다 먼저 실행되면 Instance가 아직 null이다. Start 이후에 사용한다. 6: 기존 인스턴스가 이전 결과를 가진 채로 남고 새 씬의 GameManager는 중복으로 파괴된다. 재시작해도 결과가 Playing으로 돌아가지 않는다. 7: 반드시 하나여야 하는 상태가 아니고, 일부 클래스만 사용하며, 씬에 하나만 놓는 것으로 충분하다. 그래서 Inspector 참조로 전달한다.

6.2 용어 사전

Singleton
클래스의 인스턴스가 하나만 존재하도록 클래스가 스스로 보장하고, 그 하나에 접근하는 전역 접근 지점을 제공하는 패턴이다. 객체를 영구히 보존한다는 뜻은 아니다.
인스턴스
클래스로부터 만들어진 실제 객체다.
static 속성
객체가 아니라 클래스에 하나만 있는 속성이다. 클래스 이름으로 접근한다.
전역 접근 지점
참조를 전달받지 않아도 어느 코드에서든 접근할 수 있는 지점이다. 이 수업에서는 GameManager.Instance다.
소비자
Instance를 통해 값을 읽거나 요청을 보내는 클래스다.
직렬화 참조
Inspector에서 연결하여 씬에 저장하는 객체 관계다.
숨은 의존
필드 선언이나 Inspector에 드러나지 않고 메서드 본문 안에서만 보이는 의존이다.
Game Loop
입력 처리, 상태 갱신, 화면 표시를 프레임마다 반복하는 엔진의 구조다.

6.3 요약

Singleton은 “하나여야 하는 상태에 여러 곳이 접근해야 한다”는 문제의 해법이다. static Instance가 전역 접근 지점이 되고, Awake가 중복 인스턴스를 파괴하며, OnDestroy가 자신이 Instance일 때만 해제한다. 그 대가로 의존이 숨고, “하나뿐”이라는 가정이 고정되고, 실행 순서에 의존하게 된다. 같은 문제를 다시 만나면 세 질문으로 판단하고, 하나라도 “아니다”라면 TurnManager처럼 Inspector 참조로 전달한다.
