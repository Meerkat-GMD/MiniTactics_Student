Singleton 패턴

여러 객체가 같은 맥락을 바라봐야 한다면
그 기준 참조는 누가 관리할까?

접근점 하나와 그 참조의 수명을 함께 정한다.

A Small Start

참조 하나로도 함께 일할 수 있다

작은 출발

사용자가 적고 관계가 고정돼 있다면, 각 객체가 필요한 관리자 참조를 직접 받는 방식으로 충분하다.

새로운 요구

여러 소비자가 같은 전투 맥락을 바라봐야 한다. 소비자마다 다른 관리자를 가리키면 같은 질문에도 답이 달라질 수 있다.

맥락은 함께 사용해야 하는 객체와 규칙의 기준이다. 여기서 목표는 모든 객체를 하나로 합치는 일이 아니라 같은 기준을 공유하는 일이다.

A Limited Attempt

정적 필드에 넣기만 하면 될까?

설계 비교용 가상 코드 · 현재 Teacher 구현 아님 · 중복 검사를 생략한 첫 시도; 클래스 경계 생략

public static GameManager Current;

private void Awake()
{
    Current = this;
}

하나만 존재한다는 전제에서는 간단하다. 하지만 A 등록 뒤 B도 실행되면 Current가 B로 덮인다. A와 B가 둘 다 남는 문제도 해결하지 못한다.

Competing Identity

문제는 값보다 어느 객체를 보는가다

상황참조의 결과
소비자 둘이 같은 A 참조같은 관리자를 통해 같은 기준에 접근
소비자 하나는 A, 다른 하나는 B처음 값이 같아도 별도 객체라 이후 어긋날 수 있음
정적 필드에 B를 덮어씀접근점은 하나여도 기존 A의 존재가 사라지지 않음

동일한 값과 동일한 객체는 다르다. 참조를 한곳에 둔다는 약속과 중복 인스턴스를 처리한다는 정책이 함께 필요하다.

Singleton Pattern

하나의 기준 객체와 접근점을 연결한다

정해진 범위에서 한 인스턴스를 기준으로 삼고,
공통 접근점을 통해 그 인스턴스를 찾는다.

이 구현의 접근점

GameManager.Instance는 현재 등록된 GameManager 참조다. 소비자는 같은 입구를 사용한다.

이 구현의 수명

Awake가 중복을 거르고 등록한다. OnDestroy는 자신이 현재 등록자일 때만 참조를 해제한다.

이 코드의 기준은 현재 씬에 속한 관리자다. 프로세스 전체에 영원히 살아 있는 객체를 뜻하지 않는다.

Shared Access

Instance는 객체 자체를 만드는 문장이 아니다

public static GameManager Instance { get; private set; }

현재 실제 코드 발췌 · Teacher5 5612e08 · GameManager.cs L9–9 · 프로퍼티 한 줄; 클래스·다른 멤버 생략

static · 공통 접근

GameManager 타입을 통해 현재 참조를 읽는다. 소비자마다 별도의 Instance 필드를 갖지 않는다.

private set · 쓰기 제한

외부 코드는 읽을 수 있지만 직접 다른 참조를 대입할 수 없다. 등록·해제 책임을 클래스 안에 둔다.

이 선언은 자동 생성이나 중복 방어를 수행하지 않는다. 실제 등록 전에는 아직 사용할 참조가 없다.

Register in Awake

중복이면 파괴를 요청하고 즉시 반환한다

private void Awake()
{
    if (Instance != null && Instance != this)
    {
        Destroy(gameObject);
        return;
    }
    Instance = this;
}

현재 실제 코드 발췌 · Teacher5 5612e08 · GameManager.cs L13–21 · Awake 전체; 다른 멤버 생략

이미 다른 등록자가 있으면 중복 GameObject에 Destroy를 요청한다. Destroy는 즉시 소멸을 뜻하지 않는다. return이 아래 등록문 실행을 막아 살아남는 참조를 보호한다.

Trace Registration

A 다음 B가 깨어나면 누가 남을까?

순서조건과 실행Instance
출발아직 등록자 없음null
A.Awake다른 등록자 없음 → A 등록A
B.AwakeA 존재, A ≠ B → B 파괴 요청 + returnA
B 정리B는 현재 등록자가 아님A

답: A가 기준으로 남는다. 이 표는 A.Awake가 먼저 실행된 경우의 추적이며, 임의의 서로 다른 객체 사이 Awake 순서를 보장한다는 뜻은 아니다.

Release Ownership

파괴되는 모든 객체가 참조를 지우면 안 된다

private void OnDestroy()
{
    if (Instance == this) Instance = null;
}

현재 실제 코드 발췌 · Teacher5 5612e08 · GameManager.cs L23–26 · OnDestroy 전체; 다른 멤버 생략

중복 B의 정리

Instance는 A다. Instance == this가 거짓이므로 A 참조를 유지한다.

등록된 A의 정리

Instance가 A인 동안 A가 파괴되면 조건이 참이다. 자신이 가진 등록을 null로 해제한다.

조건 없이 Instance = null로 쓰면 중복 객체의 정리가 살아남는 관리자의 접근점을 지울 수 있다. 해제도 등록 소유자를 확인해야 한다.

Scene Lifetime

씬 수명과 영구 수명은 다른 선택이다

단계이 구현에서 읽을 의미
씬 안에서 등록Awake에서 현재 관리자를 Instance로 공개
등록된 객체 파괴OnDestroy에서 자신의 등록 해제
씬을 새로 구성새 관리자가 Awake에서 새로 등록
씬을 넘어 보존현재 구현에 DontDestroyOnLoad 없음

Instance가 static이어도 참조 대상의 수명이 자동으로 늘어나지 않는다. 현재 코드는 지연 생성, 씬 간 영구 보존, 범용 Singleton 기반 클래스를 구현하지 않는다.

Reference Only

Turns는 실제 소유자를 가리키는 통로다

[SerializeField] private TurnManager _turns;
public TurnManager Turns => _turns;

GameManager의 책임

현재 맥락의 접근점을 제공한다. Turns는 연결된 TurnManager 참조를 반환한다.

TurnManager의 책임

자신이 맡은 상태와 규칙의 실제 소유자다. GameManager가 같은 상태를 별도 필드로 복사해 보관하지 않는다.

이 두 줄은 참조를 전달한다. 같은 정보를 두 군데에 저장해 서로 맞추는 동기화 장치를 만드는 코드가 아니다.

Short Consumer

소비자는 등록된 참조를 통해 소유자에게 묻는다

internal bool CanSelect(Unit unit) => GameManager.Instance.Turns.CanAct(unit);

현재 실제 코드 발췌 · Teacher5 5612e08 · BattleController.cs L35–35 · 접근을 보여 주는 한 줄; 주변 입력·선택 구현 생략

읽는 순서는 Instance → Turns → CanAct다. 이 발췌의 목적은 접근 경로를 보는 것이다. CanAct의 내부 규칙은 여기서 다루지 않는다.

Initialization Boundary

공통 접근점에도 사용할 수 있는 시점이 있다

등록 후 사용

현재 구현은 GameManager의 Awake 등록 이후 소비자가 접근하는 구성을 전제로 한다. 필수 참조가 연결돼 있어야 한다.

순서에 대한 한계

다른 객체의 Awake가 항상 나중에 실행된다고 가정할 수 없다. 아직 등록되지 않은 시점의 접근을 이 프로퍼티가 해결하지 않는다.

Singleton은 초기화 순서 전체를 자동 조율하는 장치가 아니다. 현재 코드에는 없으면 만드는 지연 생성이나 준비 완료 대기 기능이 없다.

Explicit Alternative

관계가 적다면 참조를 직접 받는 편이 명확하다

설계 비교용 가상 코드 · 현재 Teacher 구현 아님 · 명시적 참조 방식과 비교; 클래스·실제 사용 메서드 생략

[SerializeField] private GameManager _manager;

private TurnManager Turns => _manager.Turns;

명시적 참조

소비자가 무엇을 필요로 하는지 필드에 드러난다. 서로 다른 소비자에 다른 맥락을 줄 수 있다.

공통 접근점

여러 소비자가 하나의 기준에 쉽게 닿는다. 대신 의존성과 수명 전제가 호출문 뒤에 숨어 있다.

Costs

편한 접근에는 결합과 검증 비용이 따른다

이득대가
같은 기준을 쉽게 찾는다소비자가 전역 접근점에 결합된다
호출마다 참조를 전달하지 않아도 된다어떤 의존성이 필요한지 선언에서 덜 드러난다
중복 등록 정책을 한곳에서 읽는다등록·파괴·초기화 시점을 함께 검증해야 한다
하나의 맥락에서는 단순하다동시에 여러 전투를 다루려면 기준을 다시 설계해야 한다

독립 검증에서도 이전 실행의 정적 참조와 객체 수명을 정리해야 한다. 편의만 보고 모든 관리자에 적용할 이유는 없다.

Choose the Boundary

하나여야 하는 이유부터 확인한다

적용을 검토할 때

현재 범위에 기준 맥락이 하나이고, 여러 소비자가 그 동일성을 공유해야 하며, 등록과 해제 정책을 설명할 수 있다.

다른 설계를 검토할 때

동시에 여러 맥락이 필요하거나 소비자를 독립적으로 바꿔 끼워야 한다면, 명시적 참조나 생성 시 의존성 전달을 검토한다.

질문은 “편하게 어디서나 부를까?”에서 끝나지 않는다. 누가 소유하고, 언제 유효하며, 언제 해제하고, 여러 개가 필요하면 어떻게 할지를 함께 정한다.
