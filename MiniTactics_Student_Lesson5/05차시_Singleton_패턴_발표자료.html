New Requirement

이번에는 한 턴의 규칙이 필요하다

“아군은 각자 한 번씩 움직이고,
그다음 적들이 차례로 움직이게 해 주세요.”

필요한 답: 현재 차례와 유닛별 행동 여부를 기억해야 한다. 상대 목표를 점령하면 전투를 끝내고, 적이 행동하는 동안에는 플레이어 입력도 막아야 한다. 이동 가능 범위만 검사해서는 이 요구를 판단할 수 없다.

First Attempt

첫 생각은 차례를 bool 하나로 표시하는 것이다

if (!isPlayerTurn) return;
MovePlayer();
isPlayerTurn = false;
MoveEnemy();
isPlayerTurn = true;

작동하는 범위

bool은 true 또는 false를 담는 값이다. 아군 하나와 적 하나가 즉시 번갈아 움직인다면 이 표시 하나로 차례를 구분할 수 있다.

작은 요구에는 작은 해법이 충분하다. 이제 아군 두 명, 적의 대기 시간, 전투 종료가 추가되어도 이 값 하나로 설명할 수 있는지 살펴보자.

설계 검토용 가상 코드 · 현재 Teacher 구현이 아님

Limit of the First Attempt

유닛과 화면이 늘면 상태도 나눠야 한다

A가 움직인 뒤 B는?

바로 적 차례로 넘기면 B의 기회가 사라진다. 플레이어 차례를 유지하면 A의 재행동을 따로 막아야 한다. 차례와 개인의 행동 여부는 다른 정보다.

화면마다 결과를 보관한다면?

가상으로 UI의 관리자는 승리, 입력의 관리자는 진행 중이라고 하자. 화면은 끝났는데 이동은 계속된다. 여러 곳에서 읽는 결과에는 같은 판단의 기준이 필요하다.

상태를 추가하기 전에, 각 상태의 주인을 정한다.

확장 요구를 설명하는 가상 실패 사례

Role Boundary

결과와 차례와 행동은 맡길 역할이 다르다

전투 결과진행 중인지, 누가 이겼는지 정한다.
현재 차례플레이어와 적의 행동 순서를 관리한다.
유닛 행동이번 턴에 이미 행동했는지 기록한다.
적의 판단갈 수 있는 칸 중 목적지를 고른다.

이 역할을 각각 GameManager, TurnManager, Unit, EnemyAI에 맡긴다. 먼저 여러 코드가 읽을 대표 GameManager를 어떻게 정하는가부터 살펴본다. 역할을 나누는 일과 대표 객체를 하나로 제한하는 일은 별도로 결정한다.

Objects · References · Static

Instance는 대표 객체를 가리키는 참조다

public static GameManager Instance
    { get; private set; }

실제 코드: GameManager.cs · Instance
읽기 쉽게 줄바꿈만 조정

객체와 통로

인스턴스는 실제 객체, 참조는 그 객체를 가리키는 값이다. static은 멤버가 타입에 속한다는 뜻이므로 GameManager.Instance로 읽는다.

Instance는 관례적인 이름이다. get은 읽기, private set은 이 클래스 내부에서만 값 바꾸기를 허용한다. 하지만 참조를 하나 둔다고 GameManager 객체가 저절로 하나만 생기지는 않는다.

Singleton Pattern

Singleton은 대표 하나를 유지하는 규칙이다

if (Instance != null && Instance != this)
{
    Destroy(gameObject);
    return;
}
Instance = this;

대표 접근 + 중복 처리

Singleton은 대표 인스턴스를 하나로 제한하고 접근 통로를 제공하는 패턴이다. 이 예제는 객체가 깨어날 때 호출되는 Awake에서 기존 대표를 검사한다.

this는 지금 코드를 실행하는 객체다. 다른 대표가 있으면 자신을 제거하고 등록을 중단한다. 없으면 자신을 대표로 등록한다. 따라서 static 속성과 중복 처리 규칙이 함께 필요하다.

GameManager.Awake의 실행 중 경로만 남긴 개념용 축약 · 원문에는 편집 중 즉시 제거하는 분기도 있음

Input Guard

행동 입구에서 차례와 유닛을 함께 검사한다

return Phase == BattlePhase.Player
    && IsGamePlaying()
    && unit != null
    && unit.isActiveAndEnabled
    && unit.Team == Team.Player
    && unit.IsTurnUnit
    && !unit.HasMoved;

조건을 통과해야 시작한다

가드는 부적절한 요청을 입구에서 돌려보내는 검사다. &&로 연결한 조건은 모두 참이어야 하고, !는 참과 거짓을 뒤집는다.

BattleController도 진행 중인 GameManager와 Player 차례를 확인한다. 선택할 때뿐 아니라 이동 직전에도 검사하므로, 적이 기다리는 중이거나 이미 행동한 유닛이면 이동을 시작하지 않는다.

다시 행동할 수 있는 이유

State Change

A의 이동은 위치와 행동 여부를 함께 바꾼다

아군 A와 B가 모두 미행동이고, 목표 점령이 없는 유효한 이동이라고 하자. A만 움직였으므로 B의 기회가 남아 있다.

이동 전 · A
(0,0)
HasMoved = false
→
이동 후 · A
(1,0)
HasMoved = true

Phase는 Player를 유지하고 이력에는 A 이동 하나가 남는다. A는 재행동할 수 없다. Undo로 같은 상태를 복원하려면 출발 위치뿐 아니라 A의 행동 기회도 돌려줘야 한다.

One Action · Two Changes

PlayerMoveCommand는 이동과 턴 상태를 묶는다

실행

public void Execute()
{
    _movement.Execute();
    _unit.SetMoved(true);
}

취소

public void Undo()
{
    _movement.Undo();
    _unit.SetMoved(false);
}

안쪽 MoveUnitCommand는 출발·도착 칸을 기억해 위치를 바꾼다. 바깥 PlayerMoveCommand는 행동 여부까지 함께 바꾼다. 현재 이동 입구가 미행동 유닛만 허용하므로 Undo는 행동 여부를 false로 복원할 수 있다.

실제 코드: PlayerMoveCommand.cs · Execute, Undo / MoveUnitCommand.cs · 생성 시 출발 칸 저장

Trace the Undo

A만 이동한 뒤 Undo하면 다시 행동할 수 있다

Undo 직전의 이력

TOP · A: (0,0) → (1,0)

History가 최근 명령을 꺼내 그 명령의 Undo를 호출한다. 기록은 마지막에 넣은 것부터 꺼낸다.

Undo 후의 답

A는 (0,0), HasMoved는 false다. B도 여전히 미행동이고 Phase는 Player다. 명령 이력은 비었으며 A를 다시 선택할 수 있다.

위치만 되돌렸다면 A는 여전히 행동 완료로 남았을 것이다. 한 행동이 바꾼 상태를 함께 복원해야 플레이어가 이동 전과 같은 선택을 할 수 있다.

Undo와 다른 범위

R키 재시작은 장면을 다시 불러와 유닛과 관리자를 새로 만든다. 원문은 먼저 유효한 buildIndex인지 검사한다. 최근 명령 하나를 취소하는 Undo보다 초기화 범위가 크다.

GameManager.TryFinish는 진행 중일 때만 새 승패를 적용한다. 이 GameManager에는 장면을 넘어 보존하는 코드가 없어, 재시작하면 기존 대표가 사라지고 새 대표가 생긴다. Singleton도 객체의 수명을 따져야 한다.

Trace the Occupancy

중간 칸이 막히면 뒤의 빈 칸도 못 간다

x       0   1   2   3
배치    S   X   .   G
비용    0   -   -   -

예제 조건

한 줄 평지 보드, 칸 진입 비용 1, 예산 3이다. S는 이동 유닛, X는 다른 유닛, G는 목표다. 위아래 우회로는 없다.

답: (2,0)과 (3,0)도 도달할 수 없다. (1,0)을 점유 검사에서 제외하므로 그 뒤로 탐색이 이어지지 않는다. X가 사라지면 세 칸의 비용이 1, 2, 3이 되어 모두 후보가 된다. 빈 목적지만 검사해서는 이 차이를 설명할 수 없다.

Separate Reachability and Choice

AI는 갈 수 있는 칸 중 목적지를 고른다

첫 생각: 곧바로 목표로 이동

목표가 예산 안에 있고 길도 비었다면 충분하다. 하지만 목표가 멀거나 길이 막히면 목적지를 고르는 판단에 이동 규칙이 필요해진다.

현재 코드의 역할 분리

MovementRange는 어디까지 갈 수 있는가를 답한다. EnemyAI는 그 결과를 받아 그중 어디가 좋은가를 비교한다.

EnemyAI는 출발 칸을 제외하고 목표 거리, 이동 비용, y, x 순으로 비교한다. 후보가 없거나 최상위 후보도 현재보다 가까워지지 않으면 제자리에 남는다. 이동 예산을 반드시 다 쓰는 규칙은 아니다.

첫 생각은 설계 검토용 가정 / 실제 코드: EnemyAI.ChooseDestination

Distance to the Goal

맨해튼 거리는 좌표 차이의 크기를 더한다

목표 (3,3)까지 거리 = |x − 3| + |y − 3|

맨해튼 거리는 가로·세로 차이를 더한 값이다. 절댓값 기호 | |는 부호를 없애 차이의 크기만 취한다. (1,1)에서는 2 + 2 = 4다.

후보목표 (3,3)까지 계산거리
(1,2)2 + 13
(2,2)1 + 12
(1,3)2 + 02

이 값은 목표 쪽으로 가까워졌는지 보는 간단한 평가값이다. 숲의 비용이나 막힌 길을 고려한 실제 남은 경로 비용을 뜻하지 않는다.

실제 계산식: EnemyAI.ManhattanDistance · 표는 계산 예제

입력값

현재 목표 거리는 4다. 목표까지 바로 갈 수 없으므로 예산 안의 후보를 먼저 구한다. (2,2)는 숲을 거쳐야만 갈 수 있을까? 다음 화면에서 실제 비용을 비교한다.

AI Trace · Cost Before Ranking

숲을 피해도 (2,2)에 비용 2로 도달한다

답: 숲을 거칠 필요가 없다. (1,1) → (1,2) → (2,2)는 1 + 1 = 2다. 숲 (2,1)을 거치는 비용 3보다 싸므로 예산 안에 들어간다.

주요 후보최소 이동 비용목표 (3,3)까지 거리
(1,3)22
(2,2)22
(1,2)13
(2,1), 숲23

나머지 도달 칸은 목표 거리가 4 이상이다. AI는 목표 거리를 먼저 비교하므로 비용 1인 (1,2)보다 거리 2인 두 칸을 앞세운다. 이제 최상위 둘의 동률을 풀면 된다.

Deterministic Selection

거리와 비용이 같으면 y와 x로 순서를 정한다

var orderedCandidates = movementRange.Costs
    .Where(pair => pair.Key != start)
    .OrderBy(pair => ManhattanDistance(pair.Key, goalCell))
    .ThenBy(pair => pair.Value)
    .ThenBy(pair => pair.Key.y)
    .ThenBy(pair => pair.Key.x);

각 pair는 칸(Key)과 비용(Value)의 쌍이다. =>는 pair를 받아 오른쪽 값을 계산하는 짧은 함수 표현이다. Where는 출발 칸을 빼고, OrderBy는 첫 기준을, ThenBy는 앞 기준이 같은 경우의 다음 기준을 정한다.

앞 예제의 답은 (2,2)다. (1,3)과 거리·비용이 같지만 y=2가 더 작다. 같은 보드·점유·예산·시작점·목표에서 같은 목적지를 고르는 성질을 결정적이라고 한다.

Tie Break and Greedy Limit

동률을 풀어도 우회로에서 멈출 수 있다

별도 평지 예제다. x=0~2, y=0~3이고 S=(1,0), G=(1,3), 예산 2다. (1,1)은 통과 불가이며 다른 유닛은 없다. 좌우 우회 후보를 비교해 보자.

최상위 후보목표 거리 / 비용 / y / x순위
(0,1)3 / 2 / 1 / 0x가 작아 1위
(2,1)3 / 2 / 1 / 22위

실제 목적지는 출발 칸 (1,0)이다. 현재 거리도 3이어서 1위 후보가 더 가깝지 않기 때문이다. 이번 선택에서 좋아지는 칸만 고르는 탐욕적 선택은 돌아가는 길이 있어도 멈출 수 있다. 같은 답을 고른다는 결정성만으로 목표 도달까지 보장하지는 않는다.

Asynchronous Waiting

await는 다음 줄을 미루고 프레임 처리를 이어 간다

적의 대기가 끝날 때까지
게임 화면도 멈춰야 할까?

메인 실행 흐름을 붙잡는 대기

대기가 끝나기 전까지 실행권을 돌려주지 않으면 화면 갱신까지 멈출 수 있다.

UniTask.Delay를 await

답: 화면은 계속 갱신된다. 비동기 작업을 기다리며 실행권을 돌려주고, 완료 뒤 이 함수의 다음 줄을 이어 간다.

비동기는 기다리는 동안 실행 흐름을 계속 붙잡지 않는 방식이다. await가 자동으로 별도 스레드를 만드는 것은 아니다. 화면이 갱신되어도 Phase는 Enemy이므로 플레이어 입력 가드는 계속 동작한다.

Read async and await

UniTask의 완료 뒤 목표를 검사한다

async UniTask Run(CancellationToken token)
{
    await enemyAi.TakeTurnAsync(enemy, goal, token);
    CheckGoal(enemy);
}

코드에서 읽는 뜻

async는 함수 안에서 await를 사용할 수 있게 한다. UniTask는 작업의 완료를 나타내는 타입이고, await는 완료를 기다린 뒤 다음 줄로 진행한다.

TakeTurnAsync 안에 이동 후 지연이 있다. 따라서 실제 TurnManager의 목표 검사는 적의 이동과 지연이 모두 끝난 뒤에 실행된다. token은 취소 요청을 전달하는 값이며, 뒤에서 작업의 수명과 연결한다.

실제 TurnManager.RunEnemyPhaseAsync의 호출 관계를 짧게 쓴 개념용 코드 · 함수명과 지역 이름은 축약

Trace the Sequential Turn

E1이 끝난 뒤 E2의 행동을 시작한다

활성 적 E1, E2가 이 순서로 등록되어 있고 둘 다 목표를 점령하지 않는다고 하자. 반복문 안의 await가 다음 적으로 넘어가는 시점을 정한다.

시점실행Phase
E1 시작E1 즉시 이동 → 지연Enemy
E1 지연 완료E1 목표 검사 → E2 이동 → 지연Enemy
E2 지연 완료E2 목표 검사 → 새 아군 턴Player

E2는 E1이 이동한 뒤의 점유 상태로 후보를 구한다. E1이 목표를 점령했다면 지연 뒤 전투를 끝내므로 E2는 행동하지 않는다. 보장하는 것은 순서이며, 350ms 설정이 정확한 벽시계 재개 시각을 뜻하지는 않는다.

실제 코드: TurnManager.RunEnemyPhaseAsync / EnemyAI.TakeTurnAsync, ChooseDestination

Prevent Reentry

진행 중인 적 턴은 다시 실행하지 않는다

if (!TryEnterEnemyPhase() || _isEnemyPhaseRunning)
{
    return;
}
_isEnemyPhaseRunning = true;
finally
{
    _isEnemyPhaseRunning = false;
}

기다림도 실행 중이다

대기 중 다시 호출하면 별도 실행이 겹칠 수 있다. 실행 표시로 중복을 막고, finally에서 표시를 해제한다. finally는 정상 완료, 중간 return, 예외 뒤에도 정리를 실행한다.

입력 가드는 플레이어 행동의 입구를 지키고, 실행 표시는 비동기 적 턴의 중복을 막는다. 원문의 진입 검사는 Phase와 전투 결과도 확인한다.

실제 코드: TurnManager.RunEnemyPhaseAsync · 시작 부분과 finally 부분을 발췌, 사이 반복문 생략

CancellationToken

취소 토큰은 작업에 중단 요청을 전달한다

await UniTask.Delay(
    TimeSpan.FromMilliseconds(_turnDelayMilliseconds),
    cancellationToken: cancellationToken);

요청을 확인해야 반응한다

CancellationToken은 취소 요청을 확인하는 수단이다. 작업이 토큰을 검사하거나, 이처럼 취소를 지원하는 기다림에 전달해야 중단에 반응한다.

TurnManager는 적 순회를 시작하기 전에도 토큰을 검사한다. 취소가 관찰되면 취소 예외로 현재 흐름을 빠져나온다. 이미 실행한 이동을 되감거나 이전 상태를 자동으로 복원하는 요청은 아니다.

실제 코드: EnemyAI.TakeTurnAsync / TurnManager.RunEnemyPhaseAsync · ThrowIfCancellationRequested

Trace the Cancellation

대기 중 취소해도 이미 끝낸 이동은 남는다

E1이 이동한 뒤 지연 중에 취소가 관찰되었다고 하자. 객체는 살아 있고, 토큰만 취소한 상황을 추적한다.

시점상태와 다음 흐름
취소 전E1은 도착 칸, HasMoved=true, 지연 중
취소 관찰지연에서 취소 예외로 빠져나옴
정리 후finally가 실행 표시 해제, E2는 시작하지 않음

답: E1의 위치와 HasMoved는 그대로다. 목표 검사와 새 플레이어 턴 시작에도 도달하지 않으므로 이 취소만으로 Phase가 Player로 돌아가지 않는다. 현재 구현은 취소를 장면이 사라질 때 후속 작업을 중단하는 데 연결한다.

현재 EnemyAI.TakeTurnAsync와 TurnManager.RunEnemyPhaseAsync의 실행 순서에 따른 추적

Lifetime and Forget

장면 객체의 수명과 적 턴의 기다림을 연결한다

CancellationToken lifetimeToken = destroyCancellationToken;
RunEnemyPhaseForLifetimeAsync(lifetimeToken).Forget();

객체가 사라지면

destroyCancellationToken은 TurnManager 파괴 때 취소된다. 장면 재시작으로 이전 객체가 사라지면 이전 적 턴의 기다림도 중단한다.

호출 지점은 기다리지 않는다

Forget()은 여기서 완료를 기다리지 않게 한다. 내부 래퍼가 수명 토큰의 취소 예외를 처리하고, 적들의 순서는 내부 await가 유지한다.

래퍼는 해당 토큰이 취소된 경우의 취소 예외만 처리한다. 모든 예외를 무조건 숨기는 코드가 아니다. 새 장면의 새 관리자는 자신의 전투 흐름을 시작한다.

실제 코드: TurnManager.RequestEndPlayerPhase, RunEnemyPhaseForLifetimeAsync

Takeaway

상태의 주인과 행동의 순서를 구분한다

GameManager결과를 보관한다. Singleton 규칙이 대표와 중복을 관리한다.
TurnManager일반 참조로 연결하며 차례와 행동 허용을 정한다.
명령·이력위치와 행동 기회를 복원한다. Undo는 현재 플레이어 턴 안에 머문다.
AI·await갈 수 있는 목적지를 고르고, 각 적의 완료 뒤 다음 적으로 간다.

한 턴을 만들려면 이동뿐 아니라,
누가 어떤 상태를 언제 바꾸는지 정해야 한다.

대표가 필요한 곳에 Singleton을 쓰고, 다른 역할은 일반 참조로 연결할 수 있다. 목표 도달을 보장하려면 AI의 우회 판단을 더 설계해야 하며, 작업을 중단할 때는 이미 실행한 상태와 아직 실행하지 않은 흐름을 구분해야 한다.
