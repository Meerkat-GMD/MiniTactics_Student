Yesterday's Success

지금까지는 필요한 객체를 참조로 전달했다

[SerializeField] private BoardView _board;
[SerializeField] private Camera _camera;

실제 코드: BattleController.cs · 필드 선언 일부

당시에는 충분한 설계

[SerializeField]는 private 필드를 Inspector에 표시한다. Inspector에서 객체를 연결하면 그 객체의 참조, 즉 객체를 가리키는 값이 필드에 저장된다. 어떤 객체가 어떤 객체를 사용하는지 필드 선언과 Inspector에서 확인할 수 있다.

이 방법은 오늘도 계속 사용한다. 오늘은 이 방법과 다른 선택을 하나 배우고, 두 방법을 언제 구분해서 쓰는지 판단한다.

New Requirement

이번에는 여러 곳이 같은 결과를 알아야 한다

“경기가 끝나면 입력도 멈추고 턴도 멈추고,
화면에는 결과가 나와야 해요.”

경기 결과는 진행 중, 승리, 패배 중 하나를 나타내는 값이다. 이 값을 알아야 하는 곳은 입력을 받는 BattleController, 턴을 진행하는 TurnManager, 화면에 표시하는 PhaseHud의 세 곳이다. 값은 하나인데 그 값을 읽는 곳은 셋이다.

First Attempt

첫 생각은 각자 종료 여부를 필드로 가지는 것이다

// BattleController 안
private bool _isFinished;

// TurnManager 안
private bool _isFinished;

// PhaseHud 안
private bool _isFinished;

작동하는 범위

bool은 true 또는 false를 담는 값이다. 결과를 읽는 곳이 한 곳뿐이라면 필드 하나로 충분하다.

세 곳이 각자 복사본을 가지면 경기가 끝나는 순간에 세 값을 빠짐없이 true로 바꿔야 한다.

확장 요구를 설명하는 가상 실패 사례

Required Boundary

필요한 것은 하나뿐인 값과 그 값에 접근하는 방법이다

조건 1 · 결과를 가진 객체는 하나다

결과를 복사하지 않고 한 객체만 보관한다. 다른 곳은 필요할 때마다 그 객체에서 읽는다. 값이 하나이므로 서로 다른 값을 볼 수 없다.

조건 2 · 여러 곳에서 그 객체에 접근한다

입력, 턴 진행, 화면 표시가 모두 같은 객체를 찾을 수 있어야 한다. 두 번째 객체가 생기면 조건 1이 깨지므로 중복도 막아야 한다.

하나여야 하는 상태에 여러 곳이 접근해야 한다.

세 곳에 Inspector 참조를 연결해도 조건 2는 만족한다. 그러나 누군가 씬에 같은 객체를 하나 더 놓는 것까지 막지는 못한다. 두 조건을 클래스가 스스로 보장하게 만드는 구조가 있다.

Singleton Pattern

이 구조의 이름이 Singleton 패턴이다

Singleton은 어떤 클래스의 인스턴스가 하나만 존재하도록 클래스가 스스로 보장하고, 그 하나에 접근하는 전역 접근 지점을 제공하는 패턴이다. 인스턴스는 클래스로부터 만들어진 실제 객체를 뜻한다.

Instance 속성어느 코드에서든 유일한 인스턴스에 접근하는 지점이다.
Awake의 중복 방어두 번째 인스턴스는 만들어진 직후에 스스로 파괴된다.
OnDestroy의 해제자신이 등록된 인스턴스일 때만 Instance를 비운다.
소비자BattleController, TurnManager, PhaseHud가 Instance로 결과를 읽거나 확정을 요청한다.

미니 택틱스에서는 GameManager가 Singleton이다. 경기 결과를 보관하고 결과의 확정과 재시작을 맡는다. 다음 장부터 세 부분을 코드로 하나씩 확인한다.

실제 클래스: GameManager.cs

Part 1 · Global Access Point

첫째 부분: static Instance가 전역 접근 지점이다

public static GameManager Instance { get; private set; }

실제 코드: GameManager.cs · Instance

static의 뜻

일반 속성은 객체마다 하나씩 있다. static 속성은 객체가 아니라 클래스에 하나만 있다. 그래서 객체를 가리키는 참조가 없어도 GameManager.Instance라는 이름만으로 읽을 수 있다.

get은 누구나 읽을 수 있다는 뜻이고, private set은 GameManager 안에서만 값을 바꿀 수 있다는 뜻이다. 다른 클래스에서 Instance에 다른 객체를 대입하는 코드는 컴파일되지 않는다.

Predict the Result

static 속성만으로는 인스턴스가 하나로 제한되지 않는다

씬에 GameManager가 A와 B 두 개 있고 Awake가 아래 한 줄뿐이라면,
Instance는 어느 쪽을 가리킬까?

private void Awake()
{
    Instance = this;   // this는 지금 이 코드를 실행하는 객체다.
}

답: 나중에 Awake가 실행된 쪽이다. Awake는 객체가 만들어진 직후에 Unity가 한 번 호출하는 메서드다. A가 먼저 등록하고 B가 덮어쓰면 Instance는 B를 가리키지만 A도 씬에 남아 있다. 결과를 가진 객체가 둘이 되어 조건 1이 깨진다.

설계 비교용 가상 코드 · 현재 Teacher 구현이 아님

Part 2 · Duplicate Guard

둘째 부분: Awake에서 중복 인스턴스를 파괴한다

private void Awake()
{
    if (Instance != null && Instance != this)
    {
        Destroy(gameObject);
        return;
    }

    Instance = this;
}

조건문이 묻는 것

Instance != null은 이미 등록된 인스턴스가 있는지를 묻는다. Instance != this는 그 인스턴스가 자신이 아닌지를 묻는다. 둘 다 참이면 자신은 두 번째 인스턴스다.

두 번째 인스턴스는 Destroy(gameObject)로 자신이 붙어 있는 게임 오브젝트를 파괴하고 return으로 메서드를 끝낸다. 등록된 인스턴스가 없을 때만 마지막 줄에 도달해서 자신을 Instance에 등록한다.

실제 코드: GameManager.cs · Awake

Why return Matters

Destroy 뒤의 return이 잘못된 등록을 막는다

Destroy는 객체를 즉시 없애지 않는다. 파괴를 예약하고, 실제 파괴는 현재 프레임의 갱신이 끝난 뒤에 일어난다. 그래서 Destroy를 호출한 다음 줄도 계속 실행된다.

return이 있을 때

B는 파괴를 예약하고 Awake를 끝낸다. Instance = this에 도달하지 않으므로 Instance는 A로 유지된다.

return이 없을 때

B는 파괴를 예약한 뒤 Instance = this를 실행한다. Instance는 곧 파괴될 B를 가리킨다. B가 파괴되면서 Instance는 null로 비워진다.

return이 없어도 컴파일 오류는 나지 않는다. 그러나 A는 살아 있는데 Instance는 비어 있게 되어, GameManager.Instance.IsPlaying을 읽는 코드에서 NullReferenceException이 발생한다.

왼쪽은 실제 코드의 동작 · 오른쪽은 return을 지운 가상 상황

Part 3 · Release

셋째 부분: 자신이 Instance일 때만 해제한다

private void OnDestroy()
{
    if (Instance == this)
    {
        Instance = null;
    }
}

실제 코드: GameManager.cs · OnDestroy

조건이 필요한 이유

OnDestroy는 객체가 파괴될 때 Unity가 호출하는 메서드다. 중복 인스턴스 B도 파괴되므로 B의 OnDestroy도 실행된다. 조건이 없으면 B가 A의 등록을 지운다.

static 속성은 클래스에 속하므로 객체가 파괴되어도 값이 저절로 비워지지 않는다. 등록된 인스턴스가 파괴될 때 직접 null을 대입해야 파괴된 객체를 가리키는 참조가 남지 않는다. Awake의 등록과 OnDestroy의 해제는 한 쌍이다.

Trace the Instance

중복 B가 사라지는 동안 Instance는 A로 유지된다

Play 중에 GameManager가 붙은 게임 오브젝트를 복제했다고 하자. 원본을 A, 복제본을 B라고 부른다.

순서실행되는 판단Instance
1. A의 AwakeInstance가 null이므로 조건은 거짓이다. Instance = this를 실행한다.A
2. B의 AwakeInstance는 A이고 A는 B가 아니므로 조건은 참이다. 파괴를 예약하고 return한다.A
3. B의 OnDestroyInstance == this가 거짓이므로 아무것도 하지 않는다.A
4. 씬이 닫힐 때 A의 OnDestroyInstance == this가 참이므로 null을 대입한다.null

결과: 복제본 B는 곧바로 사라지고 원본 A가 남는다. 1번부터 3번까지 Instance는 한 번도 A에서 바뀌지 않는다. 소비자는 중복이 생겼다가 사라진 사실을 알 필요가 없다.

The Single State

Singleton이 보관하는 값은 경기 결과 하나다

public BattleResult Result { get; private set; } = BattleResult.Playing;
public bool IsPlaying => Result == BattleResult.Playing;

Result

BattleResult는 Playing, PlayerWon, PlayerLost 중 하나를 나타내는 열거형이다. 처음 값은 Playing이다. private set이므로 값을 바꾸는 코드는 GameManager 안에만 있다.

IsPlaying

Result가 Playing인지 계산해서 돌려주는 읽기 전용 속성이다. 별도의 bool 필드를 두지 않았으므로 Result와 어긋날 수 없다.

첫 해결 시도에서는 세 곳이 bool 복사본을 가졌다. 이제 결과는 이 속성 하나에만 있고, 다른 곳은 읽기만 한다.

실제 코드: GameManager.cs · Result, IsPlaying / BattleResult.cs

Confirm Once

Finish는 첫 번째 결과만 확정한다

public void Finish(BattleResult result)
{
    if (!IsPlaying)
    {
        return;
    }

    Result = result;
}

실제 코드: GameManager.cs · Finish

두 번 호출되면

  1. Finish(PlayerWon): IsPlaying이 참이므로 Result는 PlayerWon이 된다.
  2. Finish(PlayerLost): IsPlaying이 거짓이므로 return한다. Result는 PlayerWon 그대로다.

결과를 확정해 달라는 요청은 여러 곳에서 여러 번 올 수 있다. 확정 규칙이 값을 가진 객체 안에 있으므로, 호출하는 쪽은 경기가 이미 끝났는지 검사하지 않아도 된다. 승리한 뒤에 패배로 덮어쓰이지 않는다.

소비자는 클래스 이름으로 같은 인스턴스에 접근한다

Cost 1 · Cost 2

Singleton의 대가: 의존이 숨고 가정이 고정된다

숨은 의존

필드 선언과 Inspector만 보아서는 어떤 클래스가 GameManager를 사용하는지 알 수 없다. 메서드 본문을 읽어야 보인다. 어디서든 접근할 수 있다는 것은 어디서든 의존할 수 있다는 뜻이다.

“하나뿐”이라는 가정의 고착

소비자가 GameManager.Instance라고 적을 때마다 “경기는 동시에 하나뿐이다”라는 가정이 코드의 여러 곳에 반복해서 기록된다. 나중에 두 경기를 동시에 진행해야 한다면 모든 소비자를 고쳐야 한다.

Singleton은 편해서 쓰는 구조가 아니다.
대가를 알고 선택하는 구조다.

Cost 3 · Execution Order

Singleton의 대가: 실행 순서에 의존한다

// 어떤 소비자의 Awake
private void Awake()
{
    bool playing = GameManager.Instance.IsPlaying;
}

위험을 보여 주는 가상 코드 · 현재 Teacher 구현이 아님

왜 위험한가

Instance는 GameManager의 Awake에서 채워진다. 서로 다른 컴포넌트의 Awake 중 어느 것이 먼저 실행되는지는 보장되지 않는다. 이 소비자의 Awake가 먼저 실행되면 Instance는 아직 null이고 NullReferenceException이 발생한다.

Unity는 씬에 있는 컴포넌트의 Awake를 모두 실행한 뒤에 Start를 호출한다. 그래서 Instance는 Start 이후, 즉 Start와 Update와 입력 처리 안에서 사용한다. 실제 소비자도 Update와 입력 처리 안에서만 Instance를 읽는다.

씬을 다시 불러오면

  1. 기존 씬의 객체가 모두 파괴된다. A의 OnDestroy가 Instance를 null로 비운다.
  2. 새 씬의 GameManager C가 Awake에서 자신을 등록한다.
  3. C의 Result는 처음 값인 Playing이다.

DontDestroyOnLoad는 씬이 바뀌어도 객체를 파괴하지 않게 하는 Unity 기능이다. GameManager에 사용하면 A가 PlayerWon을 가진 채로 남고, 새 씬의 C는 중복으로 판정되어 파괴된다. 재시작해도 이전 결과가 남으므로 사용하지 않는다. 전역 접근과 영구 보존은 서로 다른 결정이다.

그 상태는 반드시 하나여야 하는가?예. 경기 결과가 둘이면 어느 쪽이 맞는지 정할 수 없다.아니다. 보드와 유닛의 묶음마다 따로 둘 수 있다.
서로 다른 여러 곳이 접근하는가?예. 입력, 턴 진행, 화면 표시가 모두 사용한다.일부만 사용한다.
중복을 클래스가 막아야 하는가?예. 둘이 되는 순간 불일치가 생긴다.아니다. 씬에 하나만 놓는 것으로 충분하다.

흔한 실수는 이름에 Manager가 붙은 클래스를 모두 Singleton으로 만드는 것이다. 접근은 쉬워지지만 숨은 의존, 가정의 고착, 실행 순서 의존이 클래스 수만큼 늘어난다. 질문 중 하나라도 “아니다”라면 Inspector 참조로 전달한다.

Game Loop는 게임이 실행되는 동안 입력 처리, 상태 갱신, 화면 표시를 계속 반복하는 구조다. 한 번의 반복을 프레임이라고 한다. 사용자가 아무 입력도 하지 않아도 반복은 멈추지 않는다.

Unity에서는 엔진이 이 반복을 실행한다. 우리는 반복문을 직접 작성하지 않고, Update처럼 엔진이 매 프레임 호출하는 메서드에 코드를 적는다.

Theory Corner · Two Loops

프레임의 반복과 턴의 반복은 서로 다른 루프다

비교엔진의 프레임 반복게임 규칙의 턴 반복
반복하는 내용입력 처리, 상태 갱신, 화면 표시플레이어 차례, 적 차례
한 번의 길이1초에 수십 번 반복될 만큼 짧다행동을 마칠 때까지이므로 일정하지 않다
다음으로 넘기는 것엔진게임 규칙
작성하는 사람엔진이 제공한다게임을 만드는 사람이 작성한다

플레이어가 다음 행동을 10초 동안 고민하면 프레임은 수백 번 반복되지만 차례는 한 번도 바뀌지 않는다. 턴 반복은 프레임 반복 안에서 실행되지만 별개의 규칙이다. 두 루프를 구분하면 매 프레임 확인할 일과 차례가 바뀔 때 한 번만 할 일을 나눌 수 있다.

Takeaway

하나여야 하는 상태에만 Singleton을 사용한다

Instancestatic 속성이 유일한 인스턴스에 대한 전역 접근 지점이 된다.
Awake중복 인스턴스는 자신을 파괴하고 return한다.
OnDestroy자신이 Instance일 때만 null로 비운다.
대가숨은 의존, “하나뿐”이라는 가정의 고착, 실행 순서 의존이 따른다.

Singleton은 “하나여야 하는 상태에 여러 곳이 접근해야 한다”는 문제의 해법이다.

같은 문제를 다시 만나면 세 질문으로 판단한다. 모두 “예”라면 Singleton을 사용하고, 하나라도 “아니다”라면 TurnManager처럼 Inspector 참조로 전달한다.
