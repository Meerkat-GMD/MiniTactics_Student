Unity가 초당 약 60번 반복하는 한 바퀴다.

프레임이란

Unity는 입력을 읽고, 스크립트를 실행하고, 화면을 한 번 그린다. 이 한 바퀴가 프레임이다. 60fps라면 한 바퀴는 약 16.7ms다.

스크립트가 끝나야 화면이 그려진다. 스크립트가 1초 동안 끝나지 않으면 그 1초 동안 화면은 멈춘다.

지금까지 작성한 메서드는 모두 “호출되면 끝까지 실행되고 돌아오는” 메서드였다. 이동 명령, Undo, 상태 전환은 한 프레임 안에서 끝났기 때문에 문제가 없었다.

New Requirement

적은 한 명씩, 간격을 두고 움직여야 한다

경과 시간플레이어가 보아야 하는 장면
0ms적 1이 이동한다.
350ms적 2가 이동한다.
700ms적 3이 이동한다.
1050ms플레이어의 차례가 다시 시작된다.

원하는 것

“이동한다 → 기다린다 → 다음 적”을 읽히는 순서 그대로 작성하고 싶다.

지켜야 하는 것

기다리는 1초 동안에도 화면은 계속 그려지고 게임은 멈추지 않아야 한다.

First Attempt · 설계 비교용 가상 코드

첫 시도: 기다리는 동안 스레드를 재운다

private void RunEnemyPhase()
{
    foreach (Unit unit in _spawner.Units)
    {
        MoveEnemy(unit);
        Thread.Sleep(350);
    }
    BeginPlayerPhase();
}

실행하면 벌어지는 일

  1. Thread.Sleep은 이 메서드를 실행하는 스레드 전체를 멈춘다.
  2. Unity의 스크립트와 화면은 모두 같은 스레드(메인 스레드)에서 실행된다.
  3. 적이 세 명이면 1050ms 동안 게임이 완전히 멈춘다.
  4. 멈춘 뒤 한 번에 그려지므로 세 명이 동시에 움직인 것처럼 보인다.

코드는 원하는 순서대로 읽히지만 결과는 원하는 것과 정반대다. “기다린다”가 “게임 전체를 멈춘다”가 되었다.

Second Attempt · 설계 비교용 가상 코드

두 번째 시도: Update에서 시간을 직접 잰다

private int _index = -1;
private float _timer;

private void Update()
{
    if (_index < 0) return;
    _timer -= Time.deltaTime;
    if (_timer > 0f) return;
    MoveEnemy(_spawner.Units[_index++]);
    _timer = 0.35f;
    if (_index == _spawner.Units.Count) { _index = -1; BeginPlayerPhase(); }
}

이 방법은 동작한다

매 프레임 조금씩 시간을 줄이다가 0 이하가 되면 한 명을 움직인다. 한 프레임은 금방 끝나므로 화면이 멈추지 않는다.

요구가 이 정도로 단순하다면 충분히 쓸 수 있는 방법이다.

적 팀인지 확인하는 조건은 생략했다. 이해를 돕기 위한 가상 코드이며 수업 코드에는 없다.

Observe the Limit

요구가 늘면 “순서”가 필드와 조건문으로 흩어진다

새 요구Update 방식에서 해야 하는 일
적이 이동한 뒤 공격도 한다.“이동 중인가, 공격 중인가”를 나타내는 필드를 추가하고 Update에 분기를 추가한다.
적이 목표에 도착하면 즉시 멈춘다.모든 분기에서 종료 조건을 검사하고 _index를 되돌린다.
이동과 공격의 대기 시간이 다르다._timer에 넣을 값을 분기마다 따로 정한다.

읽는 사람이 겪는 일

“적 1 이동 → 대기 → 공격 → 대기 → 적 2 …”라는 순서가 코드 어디에도 한 줄로 적혀 있지 않다. 필드의 값을 머릿속으로 따라가야 순서가 보인다.

실제로 원하는 코드

순서는 위에서 아래로 적고, “기다린다”라는 줄에서만 잠시 멈췄다가 다음 프레임 이후에 이어서 실행되는 메서드다.

Built-in Option · 설계 비교용 가상 코드

Unity의 코루틴은 순서를 되살리지만 제약이 있다

private IEnumerator RunEnemyPhase()
{
    foreach (Unit unit in _spawner.Units)
    {
        MoveEnemy(unit);
        yield return new WaitForSeconds(0.35f);
    }
    BeginPlayerPhase();
}
// 시작: StartCoroutine(RunEnemyPhase());

코루틴이 해결한 것

yield return에서 메서드가 멈추고, Unity가 0.35초 뒤에 그 다음 줄부터 이어서 실행한다. 순서가 코드에 그대로 보인다.

코루틴의 제약구체적인 모습
결과 값을 돌려줄 수 없다.IEnumerator는 “다 끝났다”는 것 외의 값을 호출한 쪽에 돌려주지 못한다.
예외 처리가 어렵다.C#은 catch가 있는 try 블록 안에 yield return을 허용하지 않는다.
MonoBehaviour가 필요하다.StartCoroutine은 MonoBehaviour의 메서드다. 일반 class에서는 시작할 수 없다.

Find the Boundary

필요한 기능을 네 가지로 정리한다

1. 순서대로 작성한다

이동, 대기, 다음 적의 순서가 코드에 위에서 아래로 보인다.

2. 기다려도 멈추지 않는다

기다리는 동안 메서드만 잠시 빠져나가고 프레임은 계속 돈다.

3. 결과를 기다리고 받을 수 있다

“적 한 명의 행동이 끝날 때까지” 기다렸다가 다음 줄을 실행한다. 필요하면 값도 돌려받는다.

4. 도중에 멈출 수 있다

기다리는 사이에 씬이 사라지면 남은 작업을 실행하지 않고 끝낸다.

C#에는 1~3을 위한 문법 async/await가 이미 있다. 4를 위한 도구는 CancellationToken이다. UniTask는 이것들을 Unity에 맞게 사용하게 해 주는 라이브러리다.

async · await · UniTask

네 가지 역할에 이름을 붙인다

await를 만나면 메서드는 잠시 빠져나가고, 기다리던 일이 끝나면 그 다음 줄부터 다시 실행된다.

async“이 메서드 안에서 await를 쓰겠다”는 표시다. 메서드 선언에 붙인다.
await기다리는 지점이다. 여기서 메서드를 빠져나가 프레임을 돌려주고, 끝나면 돌아와 이어서 실행한다.
UniTask“아직 끝나지 않았을 수도 있는 작업”을 나타내는 반환 타입이다. 호출한 쪽은 이것을 await한다.
CancellationToken“그만하라”는 신호를 전달하는 값이다. 신호가 오면 기다리던 작업이 취소된다.

C# 표준의 반환 타입은 Task다. UniTask는 Cysharp가 만든 Unity용 대체 타입이며, Unity의 프레임 반복(PlayerLoop) 위에서 동작하고 메모리 할당을 줄이도록 설계되었다.

Setup

패키지를 추가하고 네임스페이스를 가져온다

"com.cysharp.unitask": "https://github.com/Cysharp/UniTask.git?path=src/UniTask/Assets/Plugins/UniTask#2.5.11",

Packages/manifest.json의 dependencies에 들어 있는 한 줄이다. 끝의 #2.5.11은 사용할 버전이다.

using System.Threading;          // CancellationToken
using Cysharp.Threading.Tasks;   // UniTask, UniTask.Delay, Forget

두 using의 역할

CancellationToken은 UniTask가 아니라 .NET 표준에 있다. 그래서 두 네임스페이스가 모두 필요하다.

EnemyAI.cs와 TurnManager.cs의 맨 위에 이 두 줄이 있다. 오른쪽 주석은 설명을 위해 덧붙였다.

Actual Code · EnemyAI.cs

적 한 명의 행동: 이동하고 기다린다

public async UniTask TakeTurnAsync(
    Unit enemy, Vector2Int goalCell, CancellationToken token)
{
    enemy.MoveTo(_board, ChooseDestination(enemy, goalCell));
    await UniTask.Delay(_delayMilliseconds,
        cancellationToken: token);
}

한 줄씩 읽기

  1. async UniTask: 끝날 때까지 시간이 걸리는 메서드다. 호출한 쪽이 끝나기를 기다릴 수 있다.
  2. 첫 줄은 평소처럼 즉시 실행된다. 적이 목적지로 옮겨진다.
  3. UniTask.Delay: _delayMilliseconds(기본 350)ms가 지나면 끝나는 작업이다.
  4. await: 그 시간이 지날 때까지 이 메서드는 빠져나가 있는다.

EnemyAI.cs의 메서드 전체다. 화면에 맞추려고 긴 줄 두 곳만 나누었다.

이름 끝의 Async는 “await해서 쓰는 메서드”라는 C#의 관례다. 문법이 아니다.

Actual Code · TurnManager.cs

적의 차례 전체: 한 명씩 await한다

private async UniTask RunEnemyPhaseAsync(CancellationToken token)
{
    Vector2Int goalCell = _board.WorldToCell(_playerBase.position);
    foreach (Unit unit in _spawner.Units)
    {
        if (unit.Team != Team.Enemy) continue;

        await _enemyAi.TakeTurnAsync(unit, goalCell, token);
        if (CheckBase(unit)) return;
    }
    BeginPlayerPhase();
}

읽히는 순서 = 실행되는 순서

적 한 명의 행동(이동 + 대기)이 완전히 끝나야 다음 줄로 넘어간다. 그래서 적은 한 명씩 움직인다.

목표에 도착한 적이 있으면 return으로 끝낸다. 기다림이 중간에 있어도 평소의 return, foreach, if를 그대로 쓴다.

5차시 TurnManager.cs의 발췌다. 한 줄짜리 if 블록은 읽기 편하게 중괄호를 줄였다.

Actual Code · TurnManager.cs

일반 메서드에서 async 메서드를 시작한다

public void EndPlayerPhase()
{
    Phase = BattlePhase.Enemy;
    RunEnemyPhaseAsync(destroyCancellationToken).Forget();
}

Forget()

EndPlayerPhase는 일반 메서드라서 await할 수 없다. Forget은 “시작만 하고 끝나기를 기다리지 않는다”는 뜻이다. 이 줄은 즉시 돌아온다.

destroyCancellationToken

MonoBehaviour가 제공하는 토큰이다. 이 컴포넌트가 파괴되는 순간 “그만하라” 신호를 보낸다.

Forget 없이 호출만 해도 작업은 시작된다. 그러나 반환된 UniTask를 그냥 버리면 기다리지 않은 것이 실수인지 의도인지 알 수 없고, 작업 안에서 발생한 예외를 놓치기 쉽다. Forget은 “의도적으로 기다리지 않는다”는 표시이자, 예외를 로그로 남겨 주는 장치다.

빠져나가 있는 동안

메서드의 지역 변수와 “어디까지 실행했는가”는 UniTask가 보관한다. Unity는 그동안 다른 Update와 화면 그리기를 계속한다. 60fps라면 350ms는 약 21프레임이다.

새 스레드가 아니다

재개된 코드도 Unity의 메인 스레드에서 실행된다. 그래서 transform 같은 Unity API를 그대로 쓸 수 있다. 다만 무거운 계산을 await 없이 실행하면 그 계산 동안은 여전히 화면이 멈춘다.

Cancellation

기다리는 도중에 씬이 사라지면 어떻게 되는가

토큰이 없다면

적 2가 기다리는 사이에 씬을 다시 불러온다. TurnManager와 보드는 파괴된다. 350ms 뒤 메서드가 재개되어 파괴된 _board를 사용한다. MissingReferenceException이 발생하거나, 사라진 게임의 규칙이 새 게임에 끼어든다.

Think · Remove await

RunEnemyPhaseAsync에서 await만 지우면 어떻게 되는가?

foreach (Unit unit in _spawner.Units)
{
    if (unit.Team != Team.Enemy) continue;

    _enemyAi.TakeTurnAsync(unit, goalCell, token);
    if (CheckBase(unit)) return;

BeginPlayerPhase();

설계 비교용 가상 코드다. 실제 코드에서 await 한 단어만 지웠다.

답

세 적의 MoveTo가 같은 프레임에 모두 실행된다. 각 적의 350ms 대기는 아무도 기다리지 않은 채 따로 흘러간다. 그리고 곧바로 BeginPlayerPhase가 실행되어 0ms에 플레이어의 차례가 된다.

컴파일러는 “이 호출을 await하지 않았다”는 경고(CS4014)를 표시한다. async 메서드를 호출하는 것만으로는 기다리지 않는다. 기다리는 것은 await다.

Cost

UniTask를 쓸 때 조심해야 하는 것

주의할 점구체적인 모습대응
토큰을 빠뜨린다.대기 중에 오브젝트가 파괴되어도 메서드가 재개되어 파괴된 참조를 사용한다.async 메서드는 CancellationToken을 받아서 아래로 계속 전달한다.

시간 배율에 영향을 받는다.기본 UniTask.Delay는 Time.timeScale이 0이면 흐르지 않는다.일시 정지 중에도 흘러야 하면 ignoreTimeScale: true를 준다.

Judgment

적용 기준: 여러 프레임에 걸친 순서가 있는가?

UniTask가 이득인 경우

“한다 → 기다린다 → 한다”가 여러 프레임에 걸쳐 이어진다. 순서 중간에 조건 검사, 반복, 조기 종료가 섞인다. 기다린 결과 값을 받아서 다음 줄에 써야 한다.

예: 적의 차례 진행, 연출이 끝난 뒤 다음 행동, 씬 불러오기, 네트워크 요청.

필요하지 않은 경우

한 프레임 안에서 끝나는 계산이다. 매 프레임 같은 일을 반복하는 것이 전부다.

예: 이동 범위 계산, 피해 계산은 일반 메서드로 충분하다. 매 프레임 따라가는 카메라는 Update가 더 단순하다.

판단하는 질문은 하나다. “이 순서를 필드와 타이머로 흩어 놓지 않고, 위에서 아래로 읽히게 쓰고 싶은가?” 그렇다면 async 메서드로 작성한다.

Check Yourself

이해 확인: 답을 먼저 예측한 뒤에 확인한다

질문 1

적이 4명이고 _delayMilliseconds가 500이다. 아무도 목표에 도착하지 않는다면, EndPlayerPhase가 호출된 뒤 몇 ms 뒤에 플레이어의 차례가 시작되는가?

답: 2000ms다. 적 한 명의 행동은 “이동 + 500ms 대기”이고, 마지막 적의 대기도 포함된다. 4 × 500 = 2000이다.

질문 2

위 상황에서 두 번째 적이 이동하고 기다리는 동안 씬을 다시 불러왔다. 세 번째 적은 이동하는가? BeginPlayerPhase는 실행되는가?

답: 둘 다 아니다. TurnManager가 파괴되며 토큰이 취소되고, 두 번째 적의 Delay가 취소로 끝난다. 그 뒤의 CheckBase, 세 번째 적, BeginPlayerPhase는 실행되지 않는다.

질문 1은 await가 순서를 만든다는 것을, 질문 2는 토큰이 그 순서를 멈춘다는 것을 확인한다.

Takeaway

순서는 await로 쓰고, 멈춤은 토큰으로 전달한다

  1. 한 프레임은 빨리 끝나야 한다. Thread.Sleep은 게임 전체를 멈춘다.
  2. async 메서드는 await에서 빠져나갔다가 기다리던 일이 끝나면 다음 줄부터 재개된다. 그동안 프레임은 계속 돈다.
  3. 기다리는 것은 await다. 일반 메서드에서 시작만 할 때는 .Forget()을 적는다.
  4. CancellationToken을 끝까지 전달하면 오브젝트가 파괴될 때 남은 작업이 실행되지 않는다.
  5. 기다리는 동안에도 입력과 다른 Update는 계속 실행된다. 상태 값으로 막아야 할 것을 막는다.
