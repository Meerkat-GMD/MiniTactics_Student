Mini Tactics · Lesson 11

Service Locator 패턴

Service Locator
요청은 같게, 제공자는 교체

직접 호출의 작은 성공에서 출발해
계약 · 제공자 · 공통 접근점의 책임을 나눈다.

같은 소리 요청이 실제 재생과 의도적인 무음 중 어디로 가는지 코드로 따라간다.

A Small Success

직접 호출은 작은 시작에 충분하다

하나의 호출부

선택할 때 같은 소리 하나를 재생한다. 호출하는 곳이 적고 재생 방식이 고정이면 직접 연결이 읽기 쉽다.

직접 의존

호출부가 재생 객체와 클립을 안다. “소리를 요청한다”와 “어떻게 재생한다”가 함께 놓인다.

요구가 단순할 때 직접 호출 자체가 잘못된 설계는 아니다.

A Concrete Change

무음으로 바꾸어도 요청은 유지하고 싶다

선택 소리를 내던 호출부를 고치지 않고
다음 요청부터 무음으로 바꿀 수 있을까?

요청의 뜻은 그대로다. 달라지는 것은 요청을 받아 실제로 수행하는 쪽이다.

여기서 제공자(provider)는 계약에 적힌 일을 실제로 수행하는 객체다.

Limited First Attempt

호출부마다 무음 조건을 넣어 본다

설계 비교용 가상 코드 · 현재 Teacher 구현의 결함을 인용한 코드가 아니다.

if (!muted)
    audioSource.PlayOneShot(selectionClip);

한 곳에서는 충분

조건 하나를 확인하고 재생하면 된다. 분기와 효과를 함께 읽을 수 있다.

여러 곳으로 늘어나면

모든 호출부가 muted와 재생 객체를 알아야 한다. 제공자 선택 규칙이 반복된다.

Observe the Cost

반복되는 것은 소리가 아니라 선택 책임이다

변경 요구각 호출부가 고르는 방식
무음 정책 변경선택 조건을 여러 곳에서 수정
다른 재생 제공자로 교체재생 방식에 의존한 호출부 수정
호출부 하나 누락일부 요청만 다른 정책 적용

요청하는 책임과 제공자를 선택·등록하는 책임을 나누면 변경 지점이 모인다.

Responsibility Boundary

세 가지 경계를 먼저 세운다

계약어떤 요청을 받을 수 있는가
제공자그 요청을 어떻게 수행하는가
접근점현재 제공자를 어디서 얻는가
소비자언제 무엇을 요청하는가

제공자를 선택하는 초기화 주체는 소비자의 호출 전에 실제 객체를 등록한다.

Name the Pattern

Service Locator는 현재 서비스를 찾는 공통 접근점이다

소비자는 공통 접근점에서
계약 타입의 현재 제공자를 얻는다.

Locator는 위치를 찾는 역할이다. 소비자가 구체 제공자를 매번 생성하거나 선택하지 않게 한다.

의존성이 사라진 것은 아니다. 소비자는 계약과 전역 접근점에 의존하고, 실행은 현재 등록 상태에도 의존한다.

Actual Roles

인터페이스는 호출 약속이고, 클래스는 그 약속을 수행하는 구현이다.

계약은 요청의 모양을 약속한다

Locator

Services는 두 제공자의 현재 참조를 보관한다

public static IAudioService Audio { get; set; } = new NullAudioService();
public static ISaveService Save { get; set; } = new NullSaveService();

get

소비자가 현재 등록된 참조를 읽는다. 타입은 인터페이스이므로 같은 계약의 제공자를 받을 수 있다.

set

등록 주체가 제공자를 교체한다. 이 구현은 두 속성을 가진 작은 전역 접근점이다.

기본값은 null 참조가 아니라 실제 Null Object다. 그렇다고 필수 등록이 불필요해지지는 않는다.

Concrete Audio Provider

실제 재생은 구체 제공자가 맡는다

public ClipAudioService(AudioSource source, AudioClip[] clips)
{
    _source = source;
    _clips = clips;
}

public void Play(SoundCue cue) => _source.PlayOneShot(_clips[(int)cue]);

실제 코드 발췌 · ClipAudioService.cs 16–16행 · 주변 코드 생략 · SHA-256 58c7a6437535

생성자는 AudioSource와 AudioClip 배열을 보관한다. Play는 SoundCue를 인덱스로 삼아 클립을 고르고 PlayOneShot에 전달한다.

소비자는 클립 배열이나 재생 API를 알 필요가 없다. 필수 AudioSource와 클립은 등록 전에 준비되어 있어야 한다.

Unchanged Consumer

소비자는 선택할 때 계약으로 요청한다

if (!CanAcceptInput()) return;
if (CanSelect(unit)) Services.Audio.Play(SoundCue.Selection);

실제 코드 발췌 · BattleController.cs 33–34행 · 주변 코드 생략 · SHA-256 3f09aa79ee85

Select 내부의 실제 두 줄이다. 입력 가능 여부와 선택 가능 여부를 통과하면 Selection 요청을 보낸다.

Services.Audio를 읽어 현재 제공자의 Play를 호출한다. 이 호출문에는 무음 조건이나 구체 재생 클래스 선택이 없다.

NullAudio는 의도적으로 아무 일도 하지 않는다

null 참조

호출할 객체가 없다. Play를 호출할 수 있는 제공자가 아니다.

NullAudioService 객체

IAudioService를 구현한 실제 객체다. Play를 받아 영구적으로 아무 일도 하지 않는다.

미완성 임시 스텁이 아니다. 무음이라는 의도된 동작을 가진 완성된 제공자다.

Registration Before Use

실제 제공자는 첫 사용 전에 등록한다

Services.Save = new PlayerPrefsSaveService();
_state = Services.Save.Load();
_sound = new ClipAudioService(_source, _clips);
Services.Audio = _state.Muted ? new NullAudioService() : _sound;

실제 코드 발췌 · CampaignController.cs 31–34행 · 주변 코드 생략 · SHA-256 cc8413de82b5

초기화에서 실제 저장 제공자를 등록한 뒤 Load한다. 읽은 Muted에 따라 오디오 제공자를 고른다.

인터페이스가 자동으로 제공자를 찾아 주지 않는다. NullSave 기본값이 있어도 필수 저장 제공자 등록을 빠뜨려도 된다는 뜻은 아니다.

Provider Replacement

음소거는 현재 오디오 참조를 교체한다

public void SetMuted(bool muted)
{
    _state.Muted = muted;
    Services.Save.Save(_state);
    Services.Audio = muted ? new NullAudioService() : _sound;
    _view.SetMuted(muted);

실제 코드 발췌 · CampaignController.cs 117–122행 · 주변 코드 생략 · SHA-256 cc8413de82b5

SetMuted 내부 발췌다. Muted 값을 반영하고 저장 요청을 보낸 뒤, Audio에 NullAudioService 또는 기존 _sound를 등록한다.

교체는 이후 Play 요청에 적용된다. 이미 PlayOneShot으로 재생 중인 소리를 멈추는 명령은 이 코드에 없다.

Trace One Request

같은 호출문이 다른 객체에 도착한다

시점 / 등록된 Audio같은 Selection 요청의 결과
① ClipAudioServicePlay → PlayOneShot으로 클립 재생 요청
② NullAudioService로 교체Play → 빈 본문, 새 재생 요청 없음
③ 기존 ClipAudioService로 교체다음 Play → 다시 클립 재생 요청

BattleController의 호출문은 세 경우 모두 같다. 달라진 것은 Services.Audio가 가리키는 객체다.

Save Contract

저장도 같은 계약과 제공자의 경계다

public sealed class NullSaveService : ISaveService
{
    public CampaignSave Load() => default;
    public void Save(CampaignSave state) { }
}

NullSaveService는 저장하지 않는다. Save 뒤에 Load해도 default를 돌려준다. 메모리 저장 버퍼가 아니다.

CampaignSave는 네 필드의 값 타입이다. default이면 HasProgress·Completed·Muted는 false, StartingStageIndex는 0이다.

같은 Save 계약을 실제로 수행하는 제공자는 PlayerPrefsSaveService다. 가운데 생략한 부분에서 네 필드 값을 PlayerPrefs에 기록하고 Save를 호출한다.

이 발췌는 구현의 앞·뒤만 보여 준다. 저장 키·구현 순서 대신 “계약은 같아도 제공자에 따라 효과가 다르다”를 읽는다.

Predict and Check

NullSave에 저장하면 무엇이 남을까?

HasProgress가 true인 값을 NullSaveService에 저장한 뒤 Load하면?

답: HasProgress는 false다. Save는 값을 보관하지 않고 Load는 언제나 default를 반환한다. 재시작 여부와 무관하게 비저장이다.

실제 저장이 필요한 경로는 첫 사용 전에 실제 저장 제공자를 등록해야 한다.

Lifetime and Reset

전역 참조의 수명도 설계해야 한다

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void Reset()
{
    Audio = new NullAudioService();
    Save = new NullSaveService();
}

실제 코드 발췌 · Services.cs 10–15행 · 주변 코드 생략 · SHA-256 5486b0c3314a

SubsystemRegistration 시 Reset이 Audio와 Save를 새 Null 제공자로 되돌린다. 이전 세션의 정적 제공자 참조를 그대로 두지 않는 경계다.

Reset은 두 참조를 바꾼다. 모든 런타임 객체의 해제·씬 정리·오디오 중지를 대신하지 않는다.

Global Mutable Dependency

편리한 접근에는 숨은 의존성이 따른다

얻는 것

소비자 곳곳의 제공자 선택 분기를 줄이고, 같은 계약을 지키는 구현으로 교체하기 쉽다.

치르는 것

함수 인수만 보면 서비스 의존성이 드러나지 않는다. 전역의 변경 가능한 등록 상태와 호출 순서에 영향을 받는다.

검증에서 제공자를 바꾸었다면 다음 검증 전에 복원·초기화해야 한다. 테스트 격리는 Locator가 자동으로 보장하지 않는다.

Application Criteria

지역 의존성은 명시적으로 전달할 수도 있다

상황판단
한 객체만 쓰는 협력자생성자나 메서드 인수로 전달하면 의존성이 드러난다.
넓게 공유하며 교체할 소수 서비스등록 책임과 수명을 정하고 Locator를 검토한다.
호출마다 다른 제공자가 필요전역 교체가 다른 호출에도 영향을 줄 수 있다.
필수 연결이 빠짐Null 기본값으로 누락을 숨기지 말고 초기화 경로를 확인한다.

전역 접근이 편리하다는 이유만으로 모든 객체를 Services에 넣지는 않는다.

Contract and Limits

교체 가능한 범위는 계약이 정한다

가능한 교체

IAudioService.Play를 지키는 제공자라면 소비자의 같은 요청을 받을 수 있다. ISaveService도 Load와 Save를 지켜야 한다.

자동으로 해결되지 않는 것

제공자의 올바른 초기화, 데이터의 의미, 필수 참조의 준비와 해제, 이미 시작한 작업의 중지는 별도 책임이다.

이 예시는 두 속성의 Locator다. 별도 등록 프레임워크 없이도 역할과 비용을 설명할 수 있다.
