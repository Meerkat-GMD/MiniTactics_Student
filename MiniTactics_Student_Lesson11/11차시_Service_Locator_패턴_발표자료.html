Mini Tactics · Lesson 11

미니 택틱스로 이해하는
Service Locator 패턴

서비스를 사용하는 코드와
그 서비스를 제공할 객체를 고르는 코드를 나눈다.

Starting point

직접 참조는 필요한 대상을 드러낸다

class Notice
{
    private ConcreteAudio audio;

    public void Report()
    {
        audio.Play();
    }
}

설계 비교용 가상 코드 · 구체적인 소리 제공자를 직접 참조하는 첫 설계다.

필드의 형식을 보면 어떤 객체가 필요한지 알 수 있다. 제공자가 고정되고 참조를 전달하기 쉽다면 충분히 단순하다.

New requirement

같은 요청을 다른 제공자에게 보내고 싶다

호출하는 코드는 그대로 두고,
실제로 처리하는 객체만 바꿀 수 있을까?

예를 들어 실제 소리를 내는 제공자와 아무 소리도 내지 않는 제공자가 같은 요청을 받을 수 있다.

First attempt

호출하는 곳마다 제공자를 선택한다

if (silent)
    silentAudio.Play();
else
    realAudio.Play();

설계 비교용 가상 코드 · 같은 선택 분기가 여러 소비자에 들어간다고 가정한다.

작은 범위의 장점

선택 조건과 실행 결과를 한곳에서 읽을 수 있다.

요청하는 곳이 늘어나면

모든 소비자가 제공자의 종류와 선택 조건을 알아야 한다.

Observe the limit

선택 규칙이 여러 곳에서 반복된다

바뀌는 요구각 호출부가 선택하는 구조
제공자를 하나 추가여러 분기를 찾아 바꾼다.
선택 조건을 수정모든 소비자가 같은 기준을 사용하게 맞춘다.
한 호출부를 빠뜨림같은 요청이 서로 다른 정책으로 처리될 수 있다.

사용자는 무엇을 요청할지 알면 된다. 어떤 구현을 쓸지 고르는 책임까지 각 사용자에게 둘 필요가 있는지 살펴본다.

Find the boundary

사용하는 책임과 선택하는 책임을 나눈다

소비자

서비스에 어떤 일을 요청할지 안다.

요청을 수행할 구체적인 class는 선택하지 않는다.

초기화 코드

현재 사용할 제공자를 고른다.

소비자가 요청하기 전에 접근 지점에 등록한다.

계약은 요청의 모양을 정하고,
제공자는 그 요청을 수행한다.

Service Locator

현재 제공자를 찾는 접근 지점을 둔다

계약 · IAudioService요청할 수 있는 메서드를 선언한다.
제공자ClipAudioService와 NullAudioService가 계약을 구현한다.
Locator · Services현재 등록된 계약 형식의 참조를 보관한다.
소비자Services.Audio에서 얻은 서비스에 요청한다.

Locator는 의존을 없애지 않는다. 소비자는 서비스 계약과 접근 지점을 알아야 한다.

Actual code · Contract

인터페이스가 요청의 모양을 정한다

public interface IAudioService
{
    void Play(SoundCue cue);
}

실제 제공자가 계약을 구현한다

Actual code · Locator

Services는 현재 제공자의 참조를 보관한다

public static IAudioService Audio { get; set; } = new NullAudioService();
public static ISaveService Save { get; set; } = new NullSaveService();

속성의 형식은 구체적인 제공자가 아니라 계약이다. 다른 구현도 같은 계약을 지키면 등록할 수 있다. 기본값은 아무 작업도 하지 않는 제공자다.

Actual code · Registration

초기화 코드가 제공자를 만들고 등록한다

Services.Save = new PlayerPrefsSaveService();
_state = Services.Save.Load();
_sound = new ClipAudioService(_source, _clips);
Services.Audio = _state.Muted ? new NullAudioService() : _sound;

실제 코드 · CampaignController.cs 31–34행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

저장 계약으로 상태를 읽고 실제 소리 제공자를 준비한다. 선택 조건은 이 등록 코드에 모인다. 소비자는 Play를 요청할 때 같은 조건을 반복하지 않는다.

Actual code · Consumer

소비자는 조회한 계약에 요청한다

Services.Audio.Play(SoundCue.Result);

실제 코드 · CampaignController.cs 69–69행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

소비자
→
Services.Audio 조회
→
IAudioService 참조
→
등록된 구현의 Play

현재 등록된 객체의 메서드가 실행된다. 전역 접근이 편해져도 소비자의 서비스 의존성은 남아 있다.

Actual code · Null Object

아무 일도 하지 않는 제공자도 계약을 지킨다

public sealed class NullAudioService : IAudioService
{
    public void Play(SoundCue cue) { }
}

실제 코드 · NullAudioService.cs 3–6행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

null 참조와 다르다. 호출할 수 있는 객체가 존재하고, 그 객체가 의도적으로 빈 작업을 수행한다. 소비자는 매번 켜짐 여부를 분기하지 않아도 된다.

Trace · Replace

교체 뒤의 조회는 새 제공자를 얻는다

순서현재 등록된 제공자같은 Play 요청의 결과
1. 실제 제공자 등록ClipAudioService아직 요청하지 않음
2. Play 두 번ClipAudioService실제 제공자에게 두 번 전달
3. Null 제공자로 교체NullAudioService이후 조회부터 새 제공자를 얻음
4. Play 한 번NullAudioService의도적으로 아무 작업도 하지 않음

이 추적은 각 요청 때 Services.Audio를 다시 읽는 소비자를 전제로 한다. 이미 다른 변수에 보관한 이전 제공자 참조까지 자동으로 바뀌지는 않는다.

Actual code · Select

호출부를 고치지 않고 제공자를 바꾼다

Services.Audio = muted ? new NullAudioService() : _sound;

실제 코드 · CampaignController.cs 119–119행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

muted가 true

muted가 false

준비한 _sound가 다음 요청을 받는다. 실제 제공자의 Play가 실행된다.

Initialization

등록과 첫 호출 사이의 순서가 필요하다

기본 Null 제공자
→
실제 제공자 준비
→
Services에 등록
→
소비자 요청

기본 Null 제공자는 초기 참조를 안전하게 만들지만 등록을 올바르게 끝냈다는 증거가 아니다. 필수 기능이 조용히 빠지지 않았는지 초기화 경계를 확인해야 한다.

Actual code · Reset

전역 참조의 수명도 정해야 한다

private static void Reset()
{
    Audio = new NullAudioService();
    Save = new NullSaveService();
}

실제 코드 · Services.cs 11–15행 · 해당 메서드 전체다.

이 구현은 실행 초기화 시 제공자 참조를 기본값으로 돌린다. 이전 실행에서 등록한 객체가 다음 실행에도 남는 문제를 피하려는 경계다. 이후 초기화 코드가 사용할 제공자를 다시 등록한다.

Another contract

서비스마다 필요한 계약을 작게 둔다

public interface ISaveService
{
    CampaignSave Load();
    void Save(CampaignSave state);
}

실제 코드 · ISaveService.cs 3–7행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

저장은 Load와 Save라는 별도 계약을 가진다. 한 거대한 서비스 인터페이스에 모든 기능을 모으기보다 소비자가 요구하는 기능을 구분한다.

Singleton and locator

전역 접근이 같아도 맡은 책임은 다르다

비교SingletonService Locator
핵심 책임특정 종류의 인스턴스와 접근 관리서비스 계약과 현재 제공자 연결
주요 질문그 인스턴스를 어디서 얻는가?이 계약을 지금 누가 제공하는가?
제공자 교체이름만으로 보장되지 않음계약을 지키는 구현을 등록
공통 비용전역 상태와 수명전역 상태와 숨은 의존

static class를 썼다는 사실만으로 Service Locator가 되는 것은 아니다. 계약과 제공자를 연결하는 책임을 본다.

Alternative · Direct injection

직접 전달하면 의존이 선언에 드러난다

class Notice
{
    private IAudioService audio;

    public Notice(IAudioService audio)
    {
        this.audio = audio;
    }
}

설계 비교용 가상 코드 · 같은 계약을 생성자로 직접 받는 대안이다.

객체를 만드는 코드가 필요한 참조를 전달한다. 사용 범위가 좁고 전달하기 쉽다면 이 방식이 의존을 찾기 더 쉽다.

Costs

숨은 의존과 등록 순서가 비용이다

비용읽고 확인할 곳
겉에서 보이지 않는 의존소비자의 본문에서 Services 조회를 찾는다.
전역 상태누가 등록·교체·정리하는지 확인한다.
초기화 순서첫 호출보다 등록이 먼저인지 확인한다.
조용한 누락Null 제공자가 필수 기능 실수를 감추지 않는지 확인한다.

매개변수가 줄었다는 이유만으로 구조가 단순해졌다고 판단하지 않는다.

Judgment

참조 전달과 제공자 선택의 범위를 비교한다

적용할 이득이 있는 경우

여러 소비자가 작은 공통 계약을 사용하고, 사용할 제공자를 중앙에서 선택할 이유가 있다.

직접 전달이 단순한 경우

소비자가 적고 의존 관계를 선언에 드러내기 쉽다. 제공자를 고르는 위치도 이미 명확하다.

중앙에서 제공자를 선택하는 이득과, 소비자의 의존을 찾는 비용을 함께 비교한다.

Check

교체되는 것과 남는 의존을 구분한다

질문

Services.Audio가 NullAudioService로 바뀌었다. 다음 Play에서 소비자의 조건문을 바꿔야 하는가?

답: 아니다. 같은 계약의 Play를 호출하면 새 제공자가 받는다.

한 가지 더

그러면 소비자는 아무것에도 의존하지 않는가?

답: 아니다. IAudioService, 요청 데이터, Services 접근 지점에 의존한다.

Takeaway

제공자 선택을 모으고 의존의 비용을 관리한다

  1. 소비자가 요구하는 작은 계약을 정한다.
  2. 제공자는 같은 계약을 각자의 방식으로 구현한다.
  3. 등록 코드는 제공자를 고르고 소비자는 조회해 요청한다.
  4. 등록 순서·전역 수명·숨은 의존을 함께 살핀다.
