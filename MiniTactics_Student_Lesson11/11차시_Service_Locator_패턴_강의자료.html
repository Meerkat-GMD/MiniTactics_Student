Chapter 01

직접 호출에서 반복되는 제공자 선택

패턴 이름부터 외우기보다 바뀌는 책임을 관찰한다. 요청자는 소리를 내야 할 시점을 알고, 제공자는 실제 재생 방식을 안다. 처음에는 같은 곳에 있어도 충분하지만 여러 요청자가 동일한 무음 정책을 직접 판단하면 변경 지점이 늘어난다.

직접 호출은 작은 시작에 충분하다

하나의 호출부

선택할 때 같은 소리 하나를 재생한다. 호출하는 곳이 적고 재생 방식이 고정이면 직접 연결이 읽기 쉽다.

직접 의존

호출부가 재생 객체와 클립을 안다. “소리를 요청한다”와 “어떻게 재생한다”가 함께 놓인다.

요구가 단순할 때 직접 호출 자체가 잘못된 설계는 아니다.

무음으로 바꾸어도 요청은 유지하고 싶다

선택 소리를 내던 호출부를 고치지 않고
다음 요청부터 무음으로 바꿀 수 있을까?

요청의 뜻은 그대로다. 달라지는 것은 요청을 받아 실제로 수행하는 쪽이다.

여기서 제공자(provider)는 계약에 적힌 일을 실제로 수행하는 객체다.

호출부마다 무음 조건을 넣어 본다

설계 비교용 가상 코드 · 현재 Teacher 구현의 결함을 인용한 코드가 아니다.

if (!muted)
    audioSource.PlayOneShot(selectionClip);

한 곳에서는 충분

조건 하나를 확인하고 재생하면 된다. 분기와 효과를 함께 읽을 수 있다.

여러 곳으로 늘어나면

모든 호출부가 muted와 재생 객체를 알아야 한다. 제공자 선택 규칙이 반복된다.

반복되는 것은 소리가 아니라 선택 책임이다

변경 요구각 호출부가 고르는 방식
무음 정책 변경선택 조건을 여러 곳에서 수정
다른 재생 제공자로 교체재생 방식에 의존한 호출부 수정
호출부 하나 누락일부 요청만 다른 정책 적용

요청하는 책임과 제공자를 선택·등록하는 책임을 나누면 변경 지점이 모인다.

Chapter 02

계약·제공자·접근점·소비자

계약은 호출 가능한 모양이고 제공자는 실제 객체다. Service Locator는 현재 제공자를 얻는 공통 접근점이다. 등록은 그 접근점에 실제 객체를 연결하는 행위다. 소비자는 요청할 때 계약을 사용한다. 역할을 나누어도 의존성은 남는다.

세 가지 경계를 먼저 세운다

계약어떤 요청을 받을 수 있는가
제공자그 요청을 어떻게 수행하는가
접근점현재 제공자를 어디서 얻는가
소비자언제 무엇을 요청하는가

제공자를 선택하는 초기화 주체는 소비자의 호출 전에 실제 객체를 등록한다.

Service Locator는 현재 서비스를 찾는 공통 접근점이다

소비자는 공통 접근점에서
계약 타입의 현재 제공자를 얻는다.

Locator는 위치를 찾는 역할이다. 소비자가 구체 제공자를 매번 생성하거나 선택하지 않게 한다.

의존성이 사라진 것은 아니다. 소비자는 계약과 전역 접근점에 의존하고, 실행은 현재 등록 상태에도 의존한다.

Chapter 03

인터페이스와 현재 서비스 참조

Chapter 04

Chapter 05

등록과 제공자 교체를 따라가기

첫 사용 전 등록 순서가 중요하다. 초기화 주체는 저장 제공자를 먼저 연결하고 Load한 결과로 오디오 제공자를 고른다. SetMuted는 이후 요청이 향할 참조를 바꾼다. 동일 소비자의 디스패치란, 같은 호출문이 런타임의 실제 객체 메서드로 전달되는 일이다.

실제 제공자는 첫 사용 전에 등록한다

_state = Services.Save.Load();

Services.Audio = _state.Muted ? new NullAudioService() : _sound;

Chapter 06

저장 계약과 영구 비저장 Null Object

Chapter 07

전역 등록의 수명과 초기화

정적 접근점의 참조는 일반 객체의 지역 변수보다 넓은 범위에 영향을 준다. Services.Reset은 새 Null 제공자로 두 속성을 되돌리는 일만 한다. 제공자의 외부 자원과 다른 객체의 수명은 각 소유자의 책임으로 남는다. 검증 간 전역 상태를 관리해야 서로의 결과를 오염시키지 않는다.

전역 참조의 수명도 설계해야 한다

[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void Reset()
{
    Audio = new NullAudioService();
    Save = new NullSaveService();
}

실제 코드 발췌 · Services.cs 10–15행 · 주변 코드 생략 · SHA-256 5486b0c3314a

SubsystemRegistration 시 Reset이 Audio와 Save를 새 Null 제공자로 되돌린다. 이전 세션의 정적 제공자 참조를 그대로 두지 않는 경계다.

Reset은 두 참조를 바꾼다. 모든 런타임 객체의 해제·씬 정리·오디오 중지를 대신하지 않는다.

편리한 접근에는 숨은 의존성이 따른다

얻는 것

소비자 곳곳의 제공자 선택 분기를 줄이고, 같은 계약을 지키는 구현으로 교체하기 쉽다.

치르는 것

함수 인수만 보면 서비스 의존성이 드러나지 않는다. 전역의 변경 가능한 등록 상태와 호출 순서에 영향을 받는다.

검증에서 제공자를 바꾸었다면 다음 검증 전에 복원·초기화해야 한다. 테스트 격리는 Locator가 자동으로 보장하지 않는다.

Chapter 08

비용을 알고 적용하기

간단한 지역 협력자는 인수나 생성자로 명시적으로 전달하는 편이 더 읽기 쉬울 수 있다. 넓게 공유하는 소수 서비스를 교체할 이유가 있고 등록 책임과 수명을 정할 수 있을 때 Locator를 검토한다. 모든 의존성을 전역으로 옮기는 것이 목표는 아니다.

지역 의존성은 명시적으로 전달할 수도 있다

상황판단
한 객체만 쓰는 협력자생성자나 메서드 인수로 전달하면 의존성이 드러난다.
넓게 공유하며 교체할 소수 서비스등록 책임과 수명을 정하고 Locator를 검토한다.
호출마다 다른 제공자가 필요전역 교체가 다른 호출에도 영향을 줄 수 있다.
필수 연결이 빠짐Null 기본값으로 누락을 숨기지 말고 초기화 경로를 확인한다.

전역 접근이 편리하다는 이유만으로 모든 객체를 Services에 넣지는 않는다.

교체 가능한 범위는 계약이 정한다

가능한 교체

IAudioService.Play를 지키는 제공자라면 소비자의 같은 요청을 받을 수 있다. ISaveService도 Load와 Save를 지켜야 한다.

자동으로 해결되지 않는 것

제공자의 올바른 초기화, 데이터의 의미, 필수 참조의 준비와 해제, 이미 시작한 작업의 중지는 별도 책임이다.

이 예시는 두 속성의 Locator다. 별도 등록 프레임워크 없이도 역할과 비용을 설명할 수 있다.

핵심 질문에 현재 코드로 답한다

질문답과 이유
인터페이스가 실제 제공자를 선택하나?아니다. 등록 주체가 Services 속성에 객체를 대입한다.
무음은 null인가?아니다. Play가 아무 일도 하지 않는 객체다.
음소거가 재생 중인 소리를 끄나?아니다. 교체 뒤의 요청이 새 제공자로 간다.
NullSave는 잠깐 값을 기억하나?아니다. Load는 언제나 default다.
Locator로 의존성이 없어졌나?아니다. 전역 접근과 등록 상태에 의존한다.
