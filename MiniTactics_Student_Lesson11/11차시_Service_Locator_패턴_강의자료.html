CHAPTER 01

직접 참조에서 제공자 선택 분리로

학습 목표: 직접 참조의 장점을 설명하고 선택 규칙이 반복되는 상황을 구분한다.

참조를 직접 받는 방식의 장점

어떤 객체가 작업을 하려면 다른 객체의 기능이 필요할 수 있다. 이때 필요한 참조를 필드나 생성자로 직접 전달하면 의존 관계가 선언에 드러난다. 객체를 만드는 코드를 읽는 사람은 무엇을 준비해야 하는지 알 수 있다. 필요한 참조를 전달하기 쉬운 구조라면 이 방식은 명확하고 간단하다.

공통 기능의 제공자를 여러 곳에서 사용하거나 바꾸어야 할 때, 모든 호출부가 구체적인 제공자를 선택하면 선택 규칙이 흩어질 수 있다. 예를 들어 실행 환경마다 기능을 실제로 수행하는 제공자가 다르더라도, 소비자는 “이 작업을 요청한다”는 같은 계약을 사용할 수 있다.

계약과 제공자

서비스는 여러 코드가 필요로 하는 기능이다. 계약은 그 기능을 어떻게 요청할지 정한 메서드의 모양이다. 제공자는 그 계약을 실제로 구현한 객체다. 인터페이스가 같은 제공자들은 같은 요청을 받을 수 있지만 요청을 수행하는 방법은 다를 수 있다.

Service Locator는 현재 사용할 제공자를 보관하고 꺼내 주는 접근 지점이다. 초기화 코드는 제공자를 골라 Locator에 등록한다. 소비자는 Locator에서 계약 형식으로 서비스를 얻고 요청한다. 선택하는 코드와 사용하는 코드를 나눈 것이다.

나누어진 두 책임소비자는 서비스의 계약을 안다. 초기화 코드는 어떤 제공자를 등록할지 안다. Locator는 현재 등록된 제공자를 전달한다. 이 경계를 지나도 소비자가 그 서비스에 의존한다는 사실은 남는다.

등록이 먼저다

소비자가 조회하기 전에 사용할 제공자가 준비되어야 한다. 인터페이스는 “무엇을 호출할 수 있는가”를 설명하지만 “언제부터 호출해도 되는가”까지 자동으로 보장하지 않는다. 등록 위치와 첫 호출 위치를 함께 읽는 이유다.

class Notice
{
    private ConcreteAudio audio;

    public void Report()
    {
        audio.Play();
    }
}

설계 비교용 가상 코드 · 구체적인 소리 제공자를 직접 참조하는 첫 설계다.

가상 코드의 ConcreteAudio는 구체적인 제공자다. 소비자가 이 형식에 직접 의존하면 해당 구현을 교체할 때 소비자도 영향을 받을 수 있다. 그렇다고 모든 필드를 Locator로 바꾸어야 하는 것은 아니다. 제공자가 고정되어 있고 전달 경로가 짧다면 직접 참조가 더 명확하다.

CHAPTER 02

계약, 제공자, Locator와 소비자

학습 목표: 네 역할을 실제 코드에 대응하고 인터페이스의 약속을 읽는다.

계약은 요청할 수 있는 일을 정한다

계약은 서비스의 사용 방법이다. IAudioService는 Play라는 메서드와 SoundCue 매개변수를 선언한다. 이 선언을 따르는 객체라면 소비자는 같은 메서드 호출을 사용할 수 있다.

public interface IAudioService
{
    void Play(SoundCue cue);
}

인터페이스는 요청의 이름과 매개변수 형식을 정하지만 실제 처리 방법을 구현하지 않는다. 계약이 같은 두 객체가 서로 다른 동작을 수행할 수 있는 이유다. 소비자는 계약이 약속한 일만 사용해야 교체 가능성을 유지할 수 있다.

CHAPTER 03

등록, 조회, 요청의 실행 순서

학습 목표: 현재 등록된 객체가 실제 요청을 받는 과정을 따라간다.

Locator가 기억하는 것은 참조다

public static IAudioService Audio { get; set; } = new NullAudioService();
public static ISaveService Save { get; set; } = new NullSaveService();

실제 코드 · Services.cs 7–8행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

Audio와 Save의 속성 형식은 계약이다. 구체적인 제공자 형식에 고정하지 않으므로 같은 계약을 구현한 다른 객체를 대입할 수 있다. static 접근이므로 소비자는 Services 인스턴스를 먼저 전달받지 않고 속성을 읽는다. 이것이 접근을 편하게 하는 부분이면서 의존을 숨기는 부분이기도 하다.

선택은 초기화에서 한다

Services.Save = new PlayerPrefsSaveService();
_state = Services.Save.Load();
_sound = new ClipAudioService(_source, _clips);
Services.Audio = _state.Muted ? new NullAudioService() : _sound;

실제 코드 · CampaignController.cs 31–34행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

초기화 코드는 사용할 저장 제공자를 등록하고 계약을 통해 상태를 읽는다. 이어 실제 소리 제공자를 준비하고 현재 설정에 맞는 제공자를 Audio에 등록한다. 이 코드는 구체적인 제공자의 class를 안다. 반면 서비스를 사용하는 코드는 그 class를 직접 선택하지 않는다.

소비자는 현재 참조를 얻어 요청한다

Services.Audio.Play(SoundCue.Result);

실제 코드 · CampaignController.cs 69–69행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

먼저 Services.Audio를 읽어 IAudioService 형식의 참조를 얻는다. 그다음 Play를 호출한다. 실행되는 메서드의 본문은 실제로 등록된 객체의 구현이다. 등록된 객체가 ClipAudioService인지 NullAudioService인지에 따라 결과가 달라져도 호출 문장은 같다.

간접 접근 한 단계소비자에서 실제 제공자로 바로 가지 않고 Locator를 거친다. 호출을 조사할 때는 소비자 문장만 읽지 말고 마지막으로 어떤 객체를 등록했는지도 확인한다.

CHAPTER 04

Null Object와 제공자 교체

학습 목표: null 참조와 빈 제공자를 구분하고 다음 요청의 결과를 예측한다.

빈 동작도 의도된 구현이다

public sealed class NullAudioService : IAudioService
{
    public void Play(SoundCue cue) { }
}

실제 코드 · NullAudioService.cs 3–6행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

NullAudioService는 존재하는 객체다. IAudioService 계약을 지키므로 소비자가 Play를 호출할 수 있다. 단지 메서드 본문에 실행할 일이 없다. 참조가 없어서 호출할 수 없는 null과 구별한다.

선택적으로 기능을 끄는 상태가 정상이라면 이 빈 구현이 조건문을 줄일 수 있다. 소비자마다 켜짐 여부를 확인할 필요 없이 같은 요청을 계속 사용한다. 그러나 필수 서비스를 연결하지 않은 실수까지 빈 구현이 조용히 넘기면 문제를 발견하기 어려워진다.

선택 분기가 한곳에 남는다

Services.Audio = muted ? new NullAudioService() : _sound;

실제 코드 · CampaignController.cs 119–119행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

조건문이 세상에서 사라진 것은 아니다. 어떤 제공자를 쓸지 선택하는 위치에 한 번 남았다. muted가 true면 빈 제공자, false면 준비한 실제 제공자를 등록한다. 소비자들은 같은 Play 요청을 유지한다.

순서현재 등록된 제공자같은 Play 요청의 결과
1. 실제 제공자 등록ClipAudioService아직 요청하지 않음
2. Play 두 번ClipAudioService실제 제공자에게 두 번 전달
3. Null 제공자로 교체NullAudioService이후 조회부터 새 제공자를 얻음
4. Play 한 번NullAudioService의도적으로 아무 작업도 하지 않음

교체의 적용 범위

이 추적에서는 요청할 때마다 Services.Audio를 읽는다. 이전 제공자를 지역 변수나 필드에 따로 보관했다면 그 참조는 교체 뒤에도 같은 객체를 가리킨다. Locator의 속성을 바꾸는 것은 그 속성에 저장한 참조를 바꾸는 일이며 모든 참조 변수를 찾아 수정하는 일이 아니다.

교체와 진행 중 작업새 제공자를 등록했다고 이전 제공자가 이미 시작한 작업이 자동으로 취소되지는 않는다. 교체할 수 있는 시점과 진행 중 작업의 종료는 각 서비스의 계약과 수명 정책으로 정해야 한다.

CHAPTER 05

작은 계약과 서로 다른 서비스

학습 목표: 서비스 접근점과 모든 일을 하는 거대한 객체를 구분한다.

기능별로 필요한 요청이 다르다

public interface ISaveService
{
    CampaignSave Load();
    void Save(CampaignSave state);
}

실제 코드 · ISaveService.cs 3–7행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

ISaveService는 상태를 읽고 쓰는 계약이다. IAudioService의 Play와 성격이 다르므로 별도 인터페이스로 둔다. Services에 둘 다 접근할 수 있어도 실제 저장과 소리를 Services가 직접 수행하지 않는다. 이 class는 현재 제공자를 연결한다.

데이터와 수행 방법을 나눈다

CampaignSave는 저장 계약이 주고받는 데이터다. 데이터를 사용해야 하는 소비자가 실제 저장 매체의 API까지 알 필요는 없다. PlayerPrefsSaveService는 현재 구현에서 사용하는 저장 방법을 감싼다. 다른 제공자로 바꾸려면 같은 Load와 Save의 의미를 유지해야 한다.

Null 저장 제공자의 의미

public sealed class NullSaveService : ISaveService
{
    public CampaignSave Load() => default;
    public void Save(CampaignSave state) { }
}

실제 코드 · NullSaveService.cs 3–7행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

Load는 기본값을 돌려주고 Save는 아무것도 쓰지 않는다. 같은 계약을 호출할 수 있게 하는 기본 동작이다. 따라서 이 제공자가 등록되어 있다는 사실을 실제 저장이 되었다는 증거로 볼 수 없다. 필요한 기능의 제공자가 제대로 등록되었는지 별도로 확인해야 한다.

서비스 계약을 너무 넓게 만들면 소비자가 필요하지 않은 작업까지 한 묶음으로 의존하게 된다. 인터페이스는 사용할 요청을 이해할 수 있을 만큼 작게 유지한다. Locator라는 이름을 붙였다는 이유로 모든 게임 상태를 이곳에 모으지 않는다.

CHAPTER 06

초기화 순서와 전역 참조의 수명

학습 목표: 등록 전 호출과 이전 실행의 참조가 남는 문제를 설명한다.

인터페이스는 시작 시점을 보장하지 않는다

메서드의 이름과 형식이 올바르더라도 필요한 제공자가 준비되기 전에 호출하면 의도한 작업이 수행되지 않을 수 있다. 이 구현은 기본 Null 제공자를 먼저 두고 실행 초기화에서 참조를 되돌린 뒤, 사용할 제공자를 등록한다.

private static void Reset()
{
    Audio = new NullAudioService();
    Save = new NullSaveService();
}

실제 코드 · Services.cs 11–15행 · 해당 메서드 전체다.

Reset 본문은 서비스 참조를 기본값으로 돌린다. 이전 실행의 객체가 남지 않도록 하는 초기화 경계다. 기본 제공자로 돌아왔다는 사실과 실제 서비스 준비가 끝났다는 사실은 다르다. 첫 요청 전에 초기화 코드의 등록이 끝나야 한다.

정적 접근과 대상 객체의 수명

전역 속성은 여러 곳에서 읽을 수 있지만 그 속성이 참조한 객체의 수명까지 자동으로 늘려 주거나 정리하지는 않는다. 제공자가 내부에서 장면 객체를 사용한다면 장면이 사라질 때 그 참조도 유효하지 않을 수 있다. 등록한 쪽은 어떤 범위에서 객체를 유지할지 알아야 한다.

교체 책임을 흩뜨리지 않는다

여러 소비자가 제각각 전역 속성을 바꾸기 시작하면 마지막으로 등록한 객체를 추적하기 어렵다. 요청하는 코드와 제공자를 선택하는 코드의 경계를 유지한다. 수명이 끝난 제공자를 남기지 않고 어떤 기본 상태로 돌아갈지도 정한다.

읽는 순서서비스 요청이 기대대로 동작하지 않으면 계약, 소비 문장, 등록한 실제 객체, 등록 시점, 객체의 수명을 차례로 확인한다. 호출 문장만 맞는 것으로 충분하지 않다.

CHAPTER 07

Singleton과 직접 전달의 비교

학습 목표: 전역 접근, 인스턴스 관리, 의존성 전달의 차이를 구분한다.

전역 접근은 겉모습의 공통점이다

Singleton과 Service Locator는 모두 전역 접근 형태로 구현할 수 있다. 하지만 Singleton은 특정 종류의 인스턴스와 그 접근을 관리한다. Service Locator는 서비스 계약에 대해 현재 사용할 제공자를 연결한다. 하나의 인스턴스에 접근할 수 있다는 사실만으로 제공자 교체가 설계되는 것은 아니다.

    }

설계 비교용 가상 코드 · 소비자 생성 시 계약 형식의 참조를 전달하는 대안이다.

객체를 만드는 쪽은 생성자의 매개변수를 보고 서비스를 준비한다. 소비자는 Locator를 조회하지 않고 받은 참조를 사용한다. 인터페이스를 통한 제공자 교체는 Service Locator만의 기능이 아니다. Locator가 추가하는 것은 서비스를 얻는 접근 방식이다.

직접 전달은 의존이 잘 드러나지만 여러 계층을 통과해 참조를 전달해야 할 수 있다. Locator는 조회가 편하지만 객체가 겉으로 드러내지 않는 준비 조건을 갖게 된다. 선택할 때는 코드의 규모와 제공자 선택 위치, 의존을 찾기 쉬운 정도를 함께 비교한다.

CHAPTER 08

비용과 적용 판단

학습 목표: 서비스 선택을 모으는 이득과 의존을 숨기는 비용을 함께 판단한다.

편리한 전역 접근에는 숨은 의존이 생긴다

생성자로 참조를 받는 객체는 생성자의 매개변수만 보아도 필요한 기능을 알 수 있다. Locator를 내부에서 조회하는 객체는 겉보기에는 매개변수가 없어도 등록된 서비스를 필요로 한다. 그 객체를 다른 환경에서 실행하려면 본문을 읽고 어떤 서비스와 등록 순서가 필요한지 찾아야 한다.

따라서 Locator는 의존을 없애지 않는다. 구체적인 제공자에 대한 결합을 계약으로 바꾸고 제공자 선택을 한 곳에 모으지만, Locator 자체와 서비스 계약에 대한 의존이 남는다. 사용하기 쉬워졌다는 이유로 모든 참조를 전역 조회로 바꾸면 의존을 파악하기 어려워질 수 있다.

Singleton과의 비교

전역으로 접근할 수 있다는 점 때문에 두 패턴을 혼동하기 쉽다. Singleton은 특정 종류의 인스턴스와 그 접근을 관리하는 데 초점이 있다. Service Locator는 서비스 계약에 대해 어느 제공자를 사용할지 연결하는 데 초점이 있다. Locator를 정적 class로 구현할 수 있지만, 정적 접근 자체가 서비스 계약과 제공자 교체를 만들어 주지는 않는다.

아무 일도 하지 않는 제공자

Null Object는 같은 계약을 구현하되 의도적으로 아무 일도 하지 않는 객체다. 기능을 끄는 것이 정상적인 상태라면 소비자가 매번 조건문을 작성하지 않고도 같은 요청을 할 수 있다. 다만 필수 서비스를 잘못 등록한 실수까지 조용히 감추면 오류를 찾기 어려워진다. 선택적으로 꺼도 되는 기능과 반드시 있어야 하는 기능을 먼저 구분한다.

직접 전달과 비교해서 결정한다

필요한 참조를 생성자나 Inspector로 전달하기 쉽고 사용 범위가 좁다면 직접 전달이 더 명확하다. 넓은 범위에서 공통 계약을 사용하고 제공자를 중앙에서 선택해야 한다면 Locator를 검토할 수 있다. 그 경우에도 등록과 정리의 책임, 서비스의 수명, 사용할 수 있는 시점을 문서와 코드에서 분명히 해야 한다.

남는 비용호출부에서 보이지 않는 의존, 전역 상태의 수명, 초기화 순서가 주요 비용이다. “전달할 매개변수가 줄었다”만으로 적용을 결정하지 않는다. 의존을 찾고 바꾸는 사람이 어떤 코드를 읽어야 하는지까지 비교한다.

CHAPTER 09

복습 질문과 용어

학습 목표: 계약·등록·조회·교체의 결과를 자신의 말로 설명한다.

질문과 해설

1. Services.Audio의 형식이 IAudioService인 이유는?
소비자가 요청할 계약을 고정하면서 그 계약을 구현한 서로 다른 제공자를 등록하기 위해서다.

2. NullAudioService는 null과 같은가?
아니다. 존재하는 객체가 계약을 구현하며 Play를 호출해도 의도적으로 작업하지 않는다. null은 객체 참조가 없는 상태다.

3. 제공자를 교체하면 소비자의 모든 참조가 자동으로 바뀌는가?
아니다. Services.Audio에 저장한 참조만 바뀐다. 다음 요청 때 이 속성을 다시 읽으면 새 제공자를 얻지만 미리 보관한 이전 참조는 그대로다.

4. 인터페이스가 같으면 초기화 순서를 무시해도 되는가?
아니다. 올바른 제공자가 등록되어야 기대한 작업이 실행된다. 기본 Null 제공자는 등록 완료의 증거가 아니다.

5. Locator를 사용하면 의존성이 없어지는가?
아니다. 구체적인 제공자 선택이 분리될 뿐 계약과 Locator에 대한 의존이 남는다. 그 의존은 생성자만 읽어서는 보이지 않을 수 있다.

6. 참조를 직접 전달하기 쉬운 두 객체 사이에도 Locator가 필요한가?
보통 직접 전달부터 검토한다. 중앙에서 제공자를 선택할 이득이 등록 순서와 전역 상태 관리 비용보다 커야 한다.
