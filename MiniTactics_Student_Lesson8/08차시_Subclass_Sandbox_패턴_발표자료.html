Mini Tactics · Lesson 08

미니 택틱스로 이해하는
Subclass Sandbox 패턴

스킬이 30개가 되어도 피해 공식은 한 곳에만 있어야 한다.
부모가 도구를 제공하고, 자식은 도구를 조합하기만 한다.

Starting Point

지금까지 “효과”는 일반 공격 하나뿐이었다

public void Attack(Unit attacker, Unit defender, int bonusDamage)
{
    Vector2Int cell = _board.WorldToCell(defender.transform.position);
    int terrainDefense = _board.GetDefenseBonus(cell);
    int damage = CombatCalculator.CalculateDamage(attacker.AttackPower, defender.Defense, terrainDefense);
    defender.TakeDamage(damage + bonusDamage);
}

TurnManager.cs의 Attack이다. 7차시까지는 bonusDamage 매개변수가 없었고 마지막 줄이 defender.TakeDamage(damage);였다. 지금은 일반 공격이 bonusDamage에 0을 넘겨 이 메서드를 호출한다.

이 방식으로 충분했던 이유

효과의 종류가 하나였다. 피해를 주는 절차가 메서드 하나에 모여 있어서 공식을 고칠 곳도 하나였다.

이 메서드가 알고 있는 것

보드, 지형 방어, 피해 공식, 유닛의 체력이다. 피해 한 번에 네 가지 시스템이 관여한다.

오늘은 효과의 종류가 여럿이고 앞으로 계속 늘어나는 상황을 다룬다.

New Requirement

스킬은 종류마다 하는 일이 다르다

스킬대상효과
강타사거리 안의 적 하나일반 공격의 피해에 4를 더한다.
치유사거리 안의 부상당한 아군 하나(자기 자신 포함)HP를 5 회복한다. 최대 HP를 넘지 않는다.
화염구, 독, 밀치기, 흡혈 …스킬마다 다르다.아직 없지만 앞으로 추가된다.

7차시와 다른 점

병종은 값만 달랐다. 그래서 데이터로 만들었다. 스킬은 실행되는 코드가 다르다. 강타는 피해를 주고 치유는 회복시킨다.

그래서 필요한 것

스킬마다 class가 하나씩 필요하다. 동작이 다르면 class로 나눈다는 7차시의 기준 그대로다.

class가 많아지는 것은 피할 수 없다. 문제는 그 많은 class를 어떻게 작성하게 할 것인가다.

First Attempt

첫 시도: 스킬 class가 필요한 시스템을 직접 사용한다

public sealed class PowerStrikeSkill : Skill
{
    public override void Use(Unit user, Unit target, BoardView board)
    {
        Vector2Int cell = board.WorldToCell(target.transform.position);
        int terrainDefense = board.GetDefenseBonus(cell);
        int damage = CombatCalculator.CalculateDamage(user.AttackPower, target.Defense, terrainDefense);
        target.TakeDamage(damage + 4);
    }
}

설계 비교용 가상 코드다. 실제 프로젝트에는 이런 코드가 없다.

이 코드는 동작한다. 스킬이 두세 개로 고정되어 있다면 이 방식으로도 충분하다. 본문 네 줄 가운데 강타만의 내용은 마지막 줄의 + 4뿐이고, 나머지는 일반 공격에서 복사한 것이다.

Observe the Limit

첫 시도에서는 스킬의 수만큼 같은 코드가 복사된다

새 요구첫 시도에서 해야 하는 일
피해를 주는 스킬이 20개로 늘어난다.지형 방어를 읽고 공식을 호출하는 세 줄이 20곳에 복사된다.
피해 공식에 “치명타”를 추가한다.20개의 class를 모두 열어 같은 수정을 한다. 한 곳이라도 빠뜨리면 그 스킬만 다르게 동작한다.
보드의 API가 바뀐다.BoardView를 직접 사용하는 모든 스킬 class가 컴파일되지 않는다.

스킬 class 하나가 알고 있는 것

BoardView, CombatCalculator, Unit.TakeDamage다. 스킬이 30개면 이 세 시스템에 대한 의존이 30번 반복된다.

스킬을 만드는 사람은 “무엇을 하는 스킬인가”만 정하고 싶다. 그런데 첫 시도에서는 “어떻게 피해를 주는가”까지 매번 다시 작성해야 한다.

Find the Boundary

스킬마다 다른 것과 모든 스킬에 공통인 것을 나눈다

스킬마다 다른 것

누구를 대상으로 하는가.
어떤 효과를 어떤 값으로 주는가.

강타: 사거리 안의 적에게 공격 + 4
치유: 사거리 안의 부상당한 아군에게 회복 5

모든 스킬에 공통인 것

사거리 안의 유닛을 찾는 방법.
피해를 주는 방법(지형 방어와 공식).
회복시키는 방법(최대 HP 제한).

공통인 것은 부모 class에 한 번만 작성해서 “도구”로 제공한다. 자식 class는 도구를 골라서 호출하기만 한다. 다른 시스템을 아는 것은 부모 하나로 끝난다.

Subclass Sandbox Pattern

이 구조의 이름이 Subclass Sandbox 패턴이다

부모 class가 제공하는 도구만 사용해서 자식 class가 자신의 동작을 정의한다.

부모 class · Skill도구를 구현한다. 다른 시스템(TurnManager)과의 연결은 이 class에만 있다.
도구 · protected 메서드EnemiesInRange, WoundedAlliesInRange, Strike, Restore다. 자식만 호출할 수 있다.
샌드박스 메서드 · abstract 메서드FindTargets와 Activate다. 자식이 반드시 작성해야 하는 빈칸이다.
자식 class · PowerStrikeSkill, HealSkill빈칸을 도구의 조합으로 채운다. 다른 시스템을 알지 못한다.

샌드박스(sandbox)는 아이들이 안전하게 노는 모래 놀이터다. 자식 class는 부모가 마련한 놀이터 안에서 주어진 도구만 가지고 논다. 놀이터 밖의 시스템에는 손을 대지 않는다.

Actual Code · Skill.cs

부모: 자식이 채울 빈칸을 abstract로 선언한다

public abstract class Skill : ScriptableObject
{
    [SerializeField] private string _displayName;
    [SerializeField, Min(1)] private int _range = 1;

    private Unit _user;
    private TurnManager _turns;

    protected abstract List<Unit> FindTargets();
    protected abstract void Activate(Unit target);
}

abstract의 뜻

본문이 없는 메서드다. “자식이 반드시 작성해야 한다”는 약속이다. 작성하지 않은 자식은 컴파일되지 않는다.

abstract 메서드를 가진 class도 abstract여야 한다. Skill 자체로는 에셋을 만들 수 없고 자식으로만 만들 수 있다.

축약한 발췌다. 속성, 공개 메서드 두 개, 도구 네 개를 생략했다. 이어지는 장에서 다룬다.

Actual Code · Skill.cs

부모: 바깥에서 부르는 입구는 공개 메서드 두 개다

public List<Unit> GetTargets(Unit user, TurnManager turns)
{
    _user = user;
    _turns = turns;
    return FindTargets();
}

public void Use(Unit user, Unit target, TurnManager turns)
{
    _user = user;
    _turns = turns;
    Activate(target);
}

실행 순서

  1. 누가 사용하는지와 TurnManager를 private 필드에 적어 둔다.
  2. 자식이 작성한 메서드를 호출한다.
  3. 자식이 도구를 호출하면 도구가 적어 둔 값을 사용한다.

바깥(BattleController)은 GetTargets와 Use만 안다. 자식의 메서드는 protected여서 바깥에서 직접 호출할 수 없다. 반드시 부모의 입구를 지나가므로 도구가 사용할 값이 항상 준비되어 있다.

Skill.cs의 공개 메서드 두 개 전체다.

Actual Code · Skill.cs

부모: 도구가 다른 시스템과의 연결을 감춘다

protected List<Unit> EnemiesInRange()
{
    Team enemyTeam = _user.Team == Team.Player
        ? Team.Enemy : Team.Player;
    return _turns.GetUnitsInRange(
        _user, _range, enemyTeam);
}
protected void Strike(Unit target, int bonusDamage)
{
    _turns.Attack(_user, target, bonusDamage);
}

protected void Restore(Unit target, int amount)
{
    target.Heal(amount);
}

Strike의 본문은 한 줄이지만 그 뒤에 2장의 Attack 전체가 있다. 지형 방어, 피해 공식, 체력 감소, 체력바 갱신, 전멸 판정이 모두 이 한 줄로 실행된다. 자식은 Strike라는 이름만 알면 된다.

Skill.cs의 도구 세 개다. 왼쪽은 읽기 편하게 줄을 나누었다. 부상당한 아군을 찾는 WoundedAlliesInRange는 생략했다.

protected

protected는 자식 class에게만 호출을 허용한다

접근 수준Skill에서의 예호출할 수 있는 곳
publicGetTargets, Use, DisplayName어디에서나 호출할 수 있다. BattleController가 사용한다.
protectedStrike, Restore, EnemiesInRange, FindTargets, ActivateSkill과 Skill의 자식 class 안에서만 호출할 수 있다.
private_user, _turns, _range, _displayNameSkill 안에서만 사용할 수 있다. 자식도 볼 수 없다.

도구가 protected인 이유

BattleController가 skill.Strike(...)를 직접 호출하면 입구를 지나지 않아 _user가 준비되지 않는다. 도구는 스킬을 작성하는 자식만 사용해야 한다.

_turns가 private인 이유

자식이 _turns를 볼 수 있으면 도구를 거치지 않고 TurnManager를 직접 사용할 수 있다. 그러면 첫 시도와 같아진다.

Actual Code · PowerStrikeSkill.cs

자식: 강타는 도구 두 개를 고른 것이 전부다

[CreateAssetMenu(menuName = "Mini Tactics/Skills/Power Strike")]
public sealed class PowerStrikeSkill : Skill
{
    [SerializeField, Min(0)] private int _bonusDamage = 4;

    protected override List<Unit> FindTargets() => EnemiesInRange();
    protected override void Activate(Unit target) => Strike(target, _bonusDamage);
}

읽는 방법

  1. 대상: 사거리 안의 적이다.
  2. 효과: 추가 피해를 더해서 공격한다.
  3. 이 스킬만의 값: 추가 피해 4다.

첫 시도의 본문 네 줄이 도구 호출 한 줄이 되었다. 이 파일에는 BoardView도, CombatCalculator도, TurnManager도 등장하지 않는다.

PowerStrikeSkill.cs의 class 전체다.

Actual Code · HealSkill.cs

자식: 치유는 다른 도구 두 개를 고른다

[CreateAssetMenu(menuName = "Mini Tactics/Skills/Heal")]
public sealed class HealSkill : Skill
{
    [SerializeField, Min(1)] private int _healAmount = 5;

    protected override List<Unit> FindTargets() => WoundedAlliesInRange();
    protected override void Activate(Unit target) => Restore(target, _healAmount);
}

강타와 비교한다

class의 모양이 같다. 다른 것은 고른 도구와 값뿐이다.

두 class를 나란히 놓으면 “이 스킬이 무엇을 하는가”만 남아 있다.

7차시의 기준을 다시 확인한다. 강타와 치유는 값이 아니라 동작이 다르므로 class로 나누었다. 같은 강타라도 추가 피해가 다른 스킬은 에셋을 하나 더 만들면 된다. 그 차이는 값이기 때문이다.

HealSkill.cs의 class 전체다.

호출이 오가는 방향

부모(Use) → 자식(Activate) → 부모(Strike)의 순서다. 부모가 자식을 부르고 자식이 다시 부모의 도구를 부른다.

호출하는 쪽이 아는 것

BattleController는 그 스킬이 강타인지 치유인지 알지 못한다. Skill 타입의 Use를 호출할 뿐이다. 어떤 자식의 Activate가 실행될지는 에셋이 정한다.

Trace the Numbers

추적: 기사의 강타와 마법사의 치유

출발 상태: 기사는 공격력 6이다. 적 궁수는 방어력 1, HP 9 / 9다. 피해 공식은 max(1, 공격력 − 방어력 − 지형 방어)다.

단계평지의 궁수에게 강타숲(지형 방어 1)의 궁수에게 강타
공식의 결과max(1, 6 − 1 − 0) = 5max(1, 6 − 1 − 1) = 4
추가 피해를 더한다5 + 4 = 94 + 4 = 8
궁수의 HPmax(0, 9 − 9) = 0, 쓰러진다.max(0, 9 − 8) = 1, 살아남는다.
단계HP 6 / 14인 기사를 치유HP 12 / 14인 기사를 치유
Heal(5)min(14, 6 + 5) = 11min(14, 12 + 5) = 14
체력바11 / 14 ≈ 79%14 / 14 = 100%

지형 방어는 강타에도 적용된다. 강타의 class에는 지형에 대한 코드가 한 줄도 없지만 Strike가 일반 공격과 같은 길을 지나가기 때문이다.

Think · New Skill

화염구를 추가하려면 무엇을 작성해야 하는가?

화염구: 사거리 안의
모든 적에게
추가 피해 2의 공격을 한다.
대상 하나를 클릭하면 발동한다.

public sealed class FireballSkill : Skill
{
    [SerializeField] private int _bonusDamage = 2;

    protected override List<Unit> FindTargets()
        => EnemiesInRange();

    protected override void Activate(Unit target)
    {
        foreach (Unit enemy in EnemiesInRange())
        {
            Strike(enemy, _bonusDamage);
        }
    }
}

답: 새 class 하나다. 기존 파일은 한 줄도 고치지 않는다. 도구는 여러 번 호출해도 되고 반복문 안에서 호출해도 된다. 자식은 도구를 “조합”한다.

설계 비교용 가상 코드다. 실제 프로젝트에는 FireballSkill이 없다. CreateAssetMenu 줄을 생략했다.

With Type Object

7차시의 Type Object와 함께 쓰인다

[SerializeField] private Skill _skill;
public Skill Skill => _skill;

UnitClass.cs에 추가된 두 줄이다. 실제 파일에서는 필드와 속성이 떨어져 있다.

Type Object · 값의 차이

병종의 HP, 공격력, 사거리는 값이다. UnitClass 에셋에 적는다.

스킬의 추가 피해 4, 회복량 5도 값이다. 스킬 에셋에 적는다.

Subclass Sandbox · 동작의 차이

강타와 치유는 실행되는 코드가 다르다. class로 나누고 도구로 작성한다.

7차시에 남았던 “값으로 표현할 수 없는 차이”의 답이다.

기사 에셋의 Skill 칸에 강타 에셋을 끼우면 기사가 강타를 쓴다. 궁수의 칸은 비어 있다. 스킬이 없는 병종은 정상적인 상태이므로 사용하는 쪽이 skill != null을 확인한다.

Subclass Sandbox에는 대가가 있다

대가구체적인 모습대응
부모 class가 계속 커진다.스킬이 다양해질수록 도구가 늘어난다. 도구가 50개가 되면 Skill.cs가 가장 크고 가장 자주 바뀌는 파일이 된다.도구를 주제별 class로 나누고 부모가 그것을 꺼내 주게 한다.
모든 자식이 부모에 묶인다.Strike의 매개변수를 바꾸면 Strike를 호출하는 모든 자식이 컴파일되지 않는다.도구의 이름과 매개변수를 신중하게 정하고 쉽게 바꾸지 않는다.
부모가 상태를 잠시 보관한다._user와 _turns는 호출할 때마다 다시 적는다. 스킬 에셋은 여러 유닛이 공유하므로 이 값을 나중에 다시 읽으면 다른 유닛의 값일 수 있다.도구는 입구가 실행되는 동안에만 사용한다.

결합이 사라진 것이 아니다. 자식 30개에 흩어져 있던 결합을 부모 한 곳으로 모은 것이다. 그래서 부모는 더 무거워진다.

Judgment

적용 기준: 비슷한 자식이 많고, 같은 시스템을 반복해서 쓰는가?

Subclass Sandbox가 이득인 경우

자식 class가 많거나 앞으로 늘어난다. 자식들이 같은 시스템을 비슷한 방법으로 사용한다. 자식을 작성하는 사람이 다른 시스템을 몰라도 되게 하고 싶다.

예: 스킬, 아이템 효과, 적의 행동 방식.

필요하지 않은 경우

자식이 두세 개로 고정되어 있다. 자식마다 사용하는 시스템이 전혀 달라서 공통 도구를 뽑을 수 없다.

예: 4차시부터 만든 입력 상태들. 상태의 수가 적고, BattleController의 메서드를 직접 호출해도 복사되는 코드가 거의 없다.

판단하는 질문은 하나다. “자식 class들에 같은 코드가 복사되고 있는가?” 복사되고 있다면 그 코드를 부모의 도구로 올린다.

Check Yourself

이해 확인: 답을 먼저 예측한 뒤에 확인한다

질문 1

PowerStrikeSkill.cs와 HealSkill.cs에서 “TurnManager”, “BoardView”, “CombatCalculator”를 검색하면 몇 번 나오는가?

답: 0번이다. 자식은 다른 시스템을 알지 못한다. 그 시스템들이 바뀌어도 자식 파일은 바뀌지 않는다.

질문 2

공격력 8인 마법사가 추가 피해 4의 강타 에셋을 끼우고, 산(지형 방어 2) 위에 있는 방어력 3, HP 14인 기사를 공격한다. 남는 HP는 얼마인가?

답: max(1, 8 − 3 − 2) = 3이고 3 + 4 = 7이다. 14 − 7 = 7이 남는다. 강타의 코드는 그대로이고 병종 에셋의 Skill 칸만 바꾸었다.

질문 2가 두 패턴이 함께 동작하는 모습이다. 누가 어떤 스킬을 쓰는지는 데이터(Type Object)가 정하고, 스킬이 무엇을 하는지는 도구의 조합(Subclass Sandbox)이 정한다.

Takeaway

부모는 도구를 만들고, 자식은 도구를 조합한다

  1. 동작이 다른 종류는 class로 나눈다. 그 class들에 복사되는 코드는 부모의 protected 도구로 올린다.
  2. 자식이 채울 빈칸은 abstract 메서드로 선언한다. 바깥은 부모의 공개 입구만 호출한다.
  3. 자식은 다른 시스템을 알지 못한다. 다른 시스템과의 연결은 부모 한 곳에만 있다.
  4. 도구가 부족하면 자식이 밖으로 나가지 않고 부모에 도구를 추가한다.
  5. 대가는 커지는 부모, 부모에 묶이는 자식, 잠시 보관하는 상태다.

새 스킬을 작성할 때
부모의 도구 말고 다른 시스템을 열어 보아야 하는가?
답이 “아니다”라면 Subclass Sandbox가 제 역할을 하고 있다.
