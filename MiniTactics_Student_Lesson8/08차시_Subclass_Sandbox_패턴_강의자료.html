Chapter 01

행동별 코드에서 공통 작업을 찾기

서로 다른 행동을 코드로 표현할 수 있다

각 행동의 알고리즘

대상을 찾고 효과를 적용한다. 행동마다 선택 기준과 수행할 작업이 다를 수 있다.

처음의 단순한 선택

행동 클래스에서 필요한 객체를 직접 조회하고 작업을 호출하면 된다. 행동이 적을 때는 이해하기 쉽다.

알고리즘은 목적을 이루기 위한 작업 순서다. 이제 행동 종류가 늘어도 공통 작업의 규칙을 한곳에서 바꾸고 싶다.

자식마다 엔진 호출을 직접 적는다면?

설계 비교용 가상 코드 · 현재 Teacher 구현에 없는 비교 예시

class ExampleSkill : ExampleBase
{
    protected override void Run()
    {
        var all = UnityEngine.Object.FindObjectsByType<Transform>(
            FindObjectsSortMode.None);
        // 조회·분류·작업을 각 행동 안에 직접 적는다.
    }
}

한 행동 안에서는 흐름이 눈에 보인다. 그러나 다른 행동도 같은 조회·분류 규칙을 반복하면 여러 자식이 엔진 사용 방식까지 알아야 한다. ExampleSkill·ExampleBase·Run은 가상 이름이다.

같은 공통 작업이 여러 자식에 퍼진다

중복 · 같은 규칙의 반복

대상을 고르는 공통 규칙을 자식마다 쓰면 수정할 위치가 늘어난다. 일부만 바꾸면 행동별 기준이 달라진다.

결합 · 알아야 하는 관계

자식이 엔진 조회와 세부 작업을 직접 알면 엔진 사용 방식의 변경에도 영향을 받는다.

앞 발췌의 가상 설계에서 관찰한 한계다. 현재 Teacher가 전역 조회를 반복한다는 뜻이 아니다. 반복되는 작업과 행동별 판단을 나눌 경계가 필요하다.

Chapter 02

책임 경계와 Subclass Sandbox의 뜻

부모는 도구, 자식은 도구를 조합하는 판단

부모 Skill의 책임자식의 책임
공통 대상 조회와 효과 적용을 도구로 제공어떤 대상 도구와 효과 도구를 쓸지 선택
호출에 필요한 문맥을 준비자기 알고리즘을 짧게 표현
공통 작업의 세부 협력자를 관리부모가 제공한 도구의 의미를 이해

도구 어휘는 자식이 사용할 수 있는 의미 있는 작업 묶음이다. 단순한 “실행하라”보다 EnemiesInRange·Strike 같은 구체적인 말을 제공한다.

부모의 도구로 자식 알고리즘을 작성한다

Subclass Sandbox는 부모가 제공한
protected 도구를 사용해
자식이 알고리즘을 구현하는 패턴이다.

protected · 상속 경계

부모와 파생 클래스에서 사용할 수 있는 멤버다. 일반 호출자에게 모든 도구를 공개하지 않는다.

abstract · 구현할 자리

부모가 선언하고 자식이 구현할 작업이다. 이 선언만으로 충분한 도구 어휘가 생기지는 않는다.

추상 훅과 공통 도구를 구별한다

역할실제 코드와 책임
부모 Skill문맥 준비와 공통 작업 제공
추상 훅FindTargets / Activate · 자식이 채울 알고리즘 자리
protected 도구EnemiesInRange / Strike 등 · 공통 작업의 어휘
구체 자식PowerStrikeSkill / HealSkill · 도구를 골라 알고리즘 구현

훅(hook)은 부모의 흐름에서 자식 구현을 호출하는 확장 지점이다. 훅만 선언한 추상 클래스와 자식이 쓸 공통 도구까지 제공한 설계를 구별한다.

부모는 무엇이 공통 작업인지 정하고 자식에게 적절한 이름으로 제공한다. 자식은 그 이름을 사용해 자기 행동의 순서를 표현한다. protected는 상속 관계 안에서 도구를 사용할 수 있게 하는 접근 수준이다. abstract는 구현을 자식에게 요구하는 선언이다. 이 두 역할을 구별해야 추상 메서드 한 개만으로 패턴을 설명하는 실수를 피할 수 있다.

현재 Teacher8 실제 코드 발췌 · Skill.cs:11–12 · 문맥 필드만 발췌, 다른 필드·멤버 생략

Skill은 ScriptableObject 정의를 공유할 수 있다. _user·_turns는 부모 내부의 호출 문맥이다. 개체별 현재 HP나 행동 상태를 Skill에 보관하지 않는다.

현재 도구는 동기 호출 안에서 문맥을 사용한다. 문맥을 바꾸는 중첩 호출이나 비동기 실행까지 안전하게 만드는 구조는 아니다.

문맥은 현재 작업을 해석하는 데 필요한 사용자와 협력자의 참조다. 이 구현에서 GetTargets와 Use는 모두 전달받은 문맥을 private 필드에 넣고 나서 자식의 훅을 호출한다. 문맥을 공개 속성으로 꺼내 자식에게 넘기는 대신, 부모의 도구가 내부에서 읽는다. 두 진입점은 독립적인 호출이며 이전 호출의 문맥을 전제로 삼지 않는다.

알고리즘을 넣을 자리와 다형성

자식이 구현할 두 자리를 선언한다

protected abstract List<Unit> FindTargets();
protected abstract void Activate(Unit target);

현재 Teacher8 실제 코드 발췌 · Skill.cs:30–31 · 추상 훅 전체, 다른 멤버·클래스 외곽 생략

FindTargets

List<Unit>을 돌려준다. 어떤 대상 도구를 사용할지는 구체 자식이 결정한다.

Activate

받은 target에 어떤 효과 도구를 적용할지 결정한다. 이 자리는 구현을 요구하는 계약이다.

다형성은 같은 호출이 실제 자식 구현으로 이어지는 성질이다. Sandbox의 핵심은 여기에 알고리즘을 쓰기 좋은 protected 도구를 더하는 것이다.

FindTargets는 목록을 구하는 자리를, Activate는 대상을 받아 적용할 자리를 제공한다. 실제 자식은 두 자리를 모두 override한다. 부모의 메서드 안에서 이 훅을 호출하면 런타임의 구체 자식 구현으로 이어진다. 다형성은 이 연결을 설명한다. Subclass Sandbox는 그 구현을 쓸 때 공통 도구를 이용하도록 설계를 돕는다.

EnemiesInRange는 상대 팀을 판별하고 TurnManager의 GetUnitsInRange에 문맥을 전달한다. WoundedAlliesInRange는 같은 팀 목록을 얻은 다음 Unit.CurrentHp와 Unit.MaxHp를 비교해 새 목록을 만든다. 자식은 이 세부 단계를 복사하지 않고 자기 목적에 맞는 도구를 선택한다. 이 장은 대상 계산 방법을 연습하는 장이 아니라 반복되는 지식을 어느 책임에 둘지 읽는 장이다.

WoundedAlliesInRange 코드는 앞부분과 뒷부분으로 나누어 발췌했다. 앞부분의 if 조건에 이어 뒷부분의 중괄호와 targets.Add가 실행된다. 두 발췌를 연결하면 원본 메서드 전체가 된다.

Chapter 06

효과 도구와 실제 자식 알고리즘

Strike와 Restore는 효과 적용을 감싼다

protected void Strike(Unit target, int bonusDamage)
{
    _turns.Attack(_user, target, bonusDamage);
}

protected void Restore(Unit target, int amount)
{
    target.Heal(amount);
}

현재 Teacher8 실제 코드 발췌 · Skill.cs:54–62 · 두 도구 메서드 전체, 다른 멤버 생략

Strike는 _turns.Attack에 사용자와 대상을 전달하고, Restore는 대상의 Heal을 호출한다. 구체 자식은 이 협력자 호출 대신 효과의 의도를 나타내는 도구를 선택한다.

한 자식은 조회와 효과를 이렇게 고른다

public sealed class PowerStrikeSkill : Skill
{
    [SerializeField, Min(0)] private int _bonusDamage = 4;

    protected override List<Unit> FindTargets() => EnemiesInRange();
    protected override void Activate(Unit target) => Strike(target, _bonusDamage);

현재 Teacher8 실제 코드 발췌 · PowerStrikeSkill.cs:7–12 · 클래스 앞부분·필드·두 override, 닫는 외곽 생략

FindTargets는 EnemiesInRange, Activate는 Strike를 선택한다. override는 부모의 추상 훅을 구현한다는 표시다. 숫자 필드는 이 자식의 매개변수이며, 여기서는 수치 조정보다 도구를 선택하는 두 문장을 읽는다.

다른 자식은 다른 도구 조합을 쓴다

public sealed class HealSkill : Skill
{
    [SerializeField, Min(1)] private int _healAmount = 5;

    protected override List<Unit> FindTargets() => WoundedAlliesInRange();
    protected override void Activate(Unit target) => Restore(target, _healAmount);

현재 Teacher8 실제 코드 발췌 · HealSkill.cs:7–12 · 클래스 앞부분·필드·두 override, 닫는 외곽 생략

부모의 같은 두 훅을 구현하지만 WoundedAlliesInRange와 Restore를 선택한다. 자식은 단순히 이름만 다른 데이터가 아니라 서로 다른 도구를 고르는 실행 코드다.

PowerStrikeSkill과 HealSkill은 같은 부모를 상속하지만 선택하는 도구가 다르다. 한쪽은 EnemiesInRange와 Strike, 다른 쪽은 WoundedAlliesInRange와 Restore를 사용한다. 각 자식의 숫자 필드는 도구에 전달할 매개변수다. 패턴의 핵심은 숫자 자체보다 부모의 어휘로 알고리즘의 뜻을 드러내는 구조에 있다.

부모는 TurnManager.Attack이나 Unit.Heal과 연결되는 세부 호출을 보관한다. 자식의 override에서는 그 협력자를 직접 호출하는 문장 대신 의미 있는 도구 호출을 읽을 수 있다. 이 경계가 공통 작업의 수정 위치를 모은다.

Skill 참조의 실제 대상이 PowerStrikeSkill이면 Strike로, HealSkill이면 Restore로 이어진다. 호출자는 이 한 줄에서 구체 자식마다 분기하지 않는다.

같은 진입점, 다른 자식 구현을 따라간다

문맥 준비 → 훅 → 도구실제 구현의 연결
PowerStrikeSkill.GetTargets(A, T)_user=A, _turns=T → FindTargets → EnemiesInRange
PowerStrikeSkill.Use(A, X, T)문맥 재대입 → Activate(X) → Strike(X, _bonusDamage)
HealSkill.GetTargets(B, T)_user=B, _turns=T → FindTargets → WoundedAlliesInRange
HealSkill.Use(B, Y, T)문맥 재대입 → Activate(Y) → Restore(Y, _healAmount)

A/B는 사용자, X/Y는 대상, T는 TurnManager를 뜻하는 설명용 이름이다. 실제 멤버 이름이 아니다. 현재 코드의 호출 경로를 추적한 표이며 게임 진행 절차가 아니다.

발췌한 호출 한 줄은 실제 BattleController.UseSkill 내부에 있다. 앞뒤의 허용 검사, 화면 표현과 정리 코드는 패턴 설명 범위 밖이므로 생략했다. Skill.Use는 대상의 구체 타입에 맞는 Activate로 이어지고 그 자식이 선택한 부모 도구를 실행한다. 호출자는 이 문장에서 구체 자식을 분기하지 않는다.

추적의 답: PowerStrikeSkill이면 Use → Activate → Strike → TurnManager.Attack, HealSkill이면 Use → Activate → Restore → Unit.Heal이다. 조회도 GetTargets → FindTargets → 선택한 조회 도구로 이어진다.

Chapter 08

공유 정의의 순차 호출과 보장 범위

왜 조회와 적용 모두 문맥을 새로 넣을까?

같은 정의를 순서대로 호출호출 뒤 부모 문맥
GetTargets(A, T1)A / T1
GetTargets(B, T2)B / T2로 덮어씀
Use(A, X, T1)A / T1을 다시 넣고 Activate(X) 실행

답: Use가 문맥을 갱신하지 않는 가상 변경을 하면 마지막 조회의 B/T2를 사용할 수 있다. 실제 Use는 A/T1을 재대입하므로 이 순차 호출에서 이번 사용자를 기준으로 작업한다.

이 추적은 각 호출이 끝난 뒤 다음 호출이 시작되는 동기 범위다. 공유 상태를 모든 실행 방식에서 안전하게 만든다는 보장이 아니다.

T1과 T2는 서로 다른 협력자 참조를 가정한 설명용 이름이다. 같은 Skill 정의의 문맥은 마지막 호출이 대입한 값으로 바뀐다. 그래서 Use도 자기 인수를 필드에 다시 넣어야 한다. GetTargets를 한 번 실행했다는 사실만으로 뒤의 적용 문맥이 보존된다고 가정하면 안 된다.

이 구조의 설명 범위는 현재의 동기 호출이다. 실행 도중 다른 호출이 끼어들어 필드를 바꾸는 재진입이나, 나중에 이어지는 비동기 작업의 문맥 보존을 보장하지 않는다. 공유 정의와 개체별 상태를 구분하는 것과 모든 공유 상태 사용이 안전하다는 주장은 다르다.

Chapter 09

설계 규칙, 상속 결합과 도구 표면의 비용

protected는 보안 장벽이 아니다

얻는 것

중복된 공통 작업을 한곳에서 고친다. 자식 코드는 의도를 나타내는 도구 조합으로 읽힌다.

치르는 것

자식은 부모 도구의 의미와 계약에 결합된다. 도구가 커지거나 의미가 바뀌면 여러 자식이 영향을 받는다.

C# 자식은 여전히 공개 Unity API를 직접 호출할 수 있다. protected 도구 사용은 설계 규칙이다. 외부 코드를 격리하거나 권한을 제한하는 보안 Sandbox가 아니다.

Sandbox라는 이름은 이 자료에서 자식 알고리즘이 활용할 도구 집합을 뜻한다. 보안 격리나 가상 실행 환경을 뜻하지 않는다. C#에서 자식은 공개 Unity API를 여전히 호출할 수 있다. 팀이 공통 도구를 사용하기로 정하고 코드 검토로 경계를 지키는 설계다.

부모 도구의 동작이나 전제가 바뀌면 같은 도구를 쓰는 여러 자식의 결과가 바뀔 수 있다. protected 멤버도 자식과 맺는 계약이다. 특수한 자식 하나를 위해 공통 부모에 도구를 계속 추가하면 부모의 책임과 변경 영향 범위가 커진다. 도구를 추가할 때는 여러 알고리즘에 공통 의미가 있는지 확인한다.

Chapter 10

적용 판단과 이해 확인

같은 도구로 다른 알고리즘을 쓸 때 검토한다

상황판단
여러 자식이 같은 공통 작업을 반복안정된 도구 어휘로 묶을 만하다.
부모 도구로 자식의 의도를 짧게 표현 가능행동별 알고리즘을 읽고 바꾸기 쉽다.
자식 하나의 특수 요구 때문에 도구가 계속 증가부모의 책임과 protected 표면을 다시 검토한다.
작업을 상속 관계 밖에서도 조합·교체해야 함별도 협력 객체를 조합하는 구성 방식을 검토한다.

도구가 적을수록 무조건 좋은 것은 아니다. 공통 작업의 의미가 일관되고, 실제 자식의 알고리즘을 표현할 만큼 충분한지 본다.

정의보다 호출 경로로 이해를 확인한다

질문답과 이유
추상 메서드만 있으면 Subclass Sandbox인가?충분하지 않다. 자식이 사용할 공통 도구가 핵심이다.
왜 GetTargets 뒤 Use도 문맥을 대입하는가?같은 정의에 다른 사용자의 조회가 끼어들 수 있다.
자식은 엔진 API를 전혀 호출할 수 없는가?아니다. C# 접근 권한이 공개 API를 차단하지 않는다.
부모 수정은 자식에게 항상 투명한가?아니다. 도구 계약 변경은 모든 자식에 영향을 준다.
같은 Skill이 개체별 현재 HP를 보관하는가?아니다. 공유 정의와 개체별 상태를 구별한다.

행동별 알고리즘은 다르지만 공통 작업이 안정적으로 반복된다면 Subclass Sandbox를 검토할 수 있다. 반대로 도구를 상속 관계 밖에서 재사용하거나 독립적으로 교체해야 한다면 별도 협력 객체를 조합하는 구성이 더 적절할 수 있다. 패턴 이름보다 바뀌는 부분과 함께 유지할 부분을 먼저 찾는다.
