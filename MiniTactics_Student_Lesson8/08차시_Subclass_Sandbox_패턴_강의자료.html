CHAPTER 01 · 문제

동작이 다른 종류가 늘어날 때

학습 목표: 효과가 일반 공격 하나뿐일 때 피해를 주는 코드가 한 곳에 모여 있을 수 있었던 이유를 설명한다. 스킬은 값이 아니고 실행되는 코드가 다르므로 class로 나누어야 한다는 점을 설명한다. 각 스킬 class가 필요한 시스템을 직접 사용하는 첫 시도의 한계를 표와 코드로 확인한다.

1.1 지금까지 “효과”는 일반 공격 하나뿐이었다

이 교재에서 효과는 한 유닛의 행동이 다른 유닛의 상태를 바꾸는 일을 뜻한다. 지금까지 미니 택틱스에 있던 효과는 일반 공격 하나였다. 일반 공격으로 피해를 주는 절차는 다음 메서드 하나에 모여 있다.

실제 코드 · TurnManager.cs에서 매개변수가 세 개인 Attack 전체

public void Attack(Unit attacker, Unit defender, int bonusDamage)
{
    Vector2Int cell = _board.WorldToCell(defender.transform.position);
    int terrainDefense = _board.GetDefenseBonus(cell);
    int damage = CombatCalculator.CalculateDamage(attacker.AttackPower, defender.Defense, terrainDefense);
    defender.TakeDamage(damage + bonusDamage);
}

TurnManager.cs에는 매개변수가 두 개인 Attack(attacker, defender)도 있다. 일반 공격은 그 메서드를 호출하고, 그 메서드는 bonusDamage에 0을 넘겨 위의 메서드를 호출한다. 7차시까지는 bonusDamage가 없었고 마지막 줄이 defender.TakeDamage(damage);였다. 나머지 세 줄은 7차시와 같다.

본문 네 줄을 순서대로 읽는다. 첫째 줄은 방어하는 유닛이 서 있는 칸을 구한다. 둘째 줄은 그 칸의 지형 방어를 보드에서 읽는다. 셋째 줄은 피해 공식을 호출한다. 피해 공식은 max(1, 공격력 − 방어력 − 지형 방어)다. 넷째 줄은 계산한 피해에 추가 피해를 더해서 방어하는 유닛의 HP를 줄인다.

이 메서드는 네 가지를 알고 있다. 보드(BoardView), 지형 방어, 피해 공식(CombatCalculator), 유닛의 체력(Unit.TakeDamage)이다. 피해 한 번에 네 가지가 관여하지만 문제가 되지 않았다. 효과의 종류가 하나였기 때문이다. 피해를 주는 절차가 메서드 하나에 모여 있으므로 공식을 고칠 곳도 하나였다. 이 장에서는 이 전제가 맞지 않는 상황을 살펴본다. 효과의 종류가 여럿이고 앞으로 계속 늘어나는 경우다.

1.2 새 요구: 스킬은 종류마다 하는 일이 다르다

스킬은 일반 공격과 별도로 병종이 사용하는 특별한 행동이다. 스킬은 종류마다 대상과 효과가 다르다.

스킬의 대상과 효과
스킬대상효과
강타사거리 안의 적 하나일반 공격의 피해에 4를 더한다.
치유사거리 안의 부상당한 아군 하나HP를 5 회복한다. 최대 HP를 넘지 않는다.
화염구, 독, 밀치기, 흡혈 등스킬마다 다르다.아직 없지만 앞으로 추가된다.

7차시와 비교해 본다. 7차시의 병종은 값만 달랐다. 기사와 궁수는 HP와 공격력의 숫자가 다를 뿐이고 피해를 받고 이동하는 코드는 같았다. 그래서 병종을 class로 나누지 않고 데이터로 만들었다. 스킬은 사정이 다르다. 강타는 피해를 주고 치유는 회복시킨다. 두 스킬은 숫자가 다른 것이 아니고 실행되는 코드가 다르다.

핵심 관찰스킬마다 다른 것은 값이 아니고 동작이다. 7차시의 기준은 “동작이 다르면 class로 나눈다”였다. 그 기준에 따라 스킬마다 class가 하나씩 필요하다. class가 많아지는 것은 피할 수 없다. 이번 차시의 문제는 그 많은 class를 어떻게 작성하게 할 것인가다.

1.3 첫 시도: 스킬 class가 필요한 시스템을 직접 사용한다

가장 먼저 떠올릴 수 있는 방법은 다음과 같다. 공통 부모 class Skill에는 Use라는 메서드의 이름만 정해 둔다. 각 스킬 class는 Use를 다시 정의하고, 그 안에서 필요한 시스템을 직접 사용한다. 여기에서 시스템은 보드, 피해 공식, 턴 관리처럼 스킬의 바깥에 있으면서 게임의 규칙을 맡고 있는 class를 뜻한다.

설계 비교용 가상 코드 · 프로젝트에 있었던 코드가 아니다

// 첫 시도: 스킬 class가 보드와 피해 공식을 직접 사용한다.
public sealed class PowerStrikeSkill : Skill
{
    public override void Use(Unit user, Unit target, BoardView board)
    {
        Vector2Int cell = board.WorldToCell(target.transform.position);
        int terrainDefense = board.GetDefenseBonus(cell);
        int damage = CombatCalculator.CalculateDamage(user.AttackPower, target.Defense, terrainDefense);
        target.TakeDamage(damage + 4);
    }
}

이 코드는 동작한다. 스킬이 두세 개로 고정되어 있다면 이 방식으로도 충분하다. 다만 본문 네 줄을 1.1절의 Attack과 비교해 보면 강타만의 내용은 마지막 줄의 + 4뿐이다. 나머지는 일반 공격의 코드를 복사한 것이다.

1.4 첫 시도의 한계

첫 시도에서는 피해를 주는 스킬을 만들 때마다 지형 방어를 읽고 공식을 호출하는 세 줄을 복사한다. 화염구처럼 여러 적에게 피해를 주는 스킬도 피해를 주는 부분에서는 같은 세 줄을 그대로 복사한다. 스킬의 수만큼 같은 코드가 복사되므로 다음과 같은 문제가 생긴다.

새 요구가 생겼을 때 첫 시도에서 해야 하는 일
새 요구첫 시도에서 해야 하는 일
피해를 주는 스킬이 20개로 늘어난다.지형 방어를 읽고 공식을 호출하는 세 줄이 20곳에 복사된다.
피해 공식에 “치명타”를 추가한다.20개의 class를 모두 열어 같은 수정을 한다. 한 곳이라도 빠뜨리면 그 스킬만 다르게 동작한다.
보드의 API가 바뀐다.BoardView를 직접 사용하는 모든 스킬 class가 컴파일되지 않는다.

API는 한 class가 다른 class에게 공개한 메서드와 속성의 이름, 매개변수를 뜻한다. GetDefenseBonus의 이름이나 매개변수가 바뀌는 것이 API가 바뀌는 예다.

첫 시도의 스킬 class 하나는 세 가지를 알고 있다. BoardView, CombatCalculator, Unit.TakeDamage다. 한 class가 다른 class를 알고 사용하는 것을 의존이라고 한다. 스킬이 30개이면 이 세 가지에 대한 의존이 30번 반복된다.

한계의 요약스킬을 만드는 사람은 “무엇을 하는 스킬인가”만 정하고 싶다. 그런데 첫 시도에서는 “어떻게 피해를 주는가”까지 스킬마다 다시 작성해야 한다. 같은 코드가 스킬의 수만큼 복사되고, 다른 시스템에 대한 의존도 스킬의 수만큼 반복된다.
생각할 문제첫 시도의 방식으로 피해를 주는 스킬을 20개 만들었다. 지형 방어를 읽고 공식을 호출하는 세 줄은 프로젝트 전체에 몇 줄 있는가? 피해 공식에 치명타를 추가하면서 20개 가운데 19개만 고쳤다면 어떤 일이 일어나는가?
해설 보기

세 줄이 20곳에 있으므로 3 × 20 = 60줄이다. 일반 공격의 Attack에 있는 세 줄까지 세면 63줄이다. 19개만 고치면 고치지 않은 스킬 하나만 치명타가 적용되지 않는다. 그 스킬의 코드는 문법에 맞으므로 컴파일러는 이 실수를 알려 주지 않는다. 게임을 실행해서 그 스킬을 사용해 보아야 알 수 있다.

CHAPTER 02 · 구조

도구와 빈칸으로 나누는 구조

학습 목표: 스킬마다 다른 것과 모든 스킬에 공통인 것을 구분한다. 부모 class, 도구, 샌드박스 메서드, 자식 class의 역할을 실제 class와 대응시킨다. 패턴의 이름에 있는 샌드박스의 뜻을 설명한다.

2.1 스킬마다 다른 것과 모든 스킬에 공통인 것을 나눈다

1장의 한계는 서로 성격이 다른 두 가지가 스킬 class 하나에 섞여 있어서 생겼다. 두 가지를 나누어 적어 본다.

스킬마다 다른 것

누구를 대상으로 하는가. 어떤 효과를 어떤 값으로 주는가. 강타는 사거리 안의 적에게 공격 + 4를 준다. 치유는 사거리 안의 부상당한 아군에게 회복 5를 준다.

모든 스킬에 공통인 것

사거리 안의 유닛을 찾는 방법. 피해를 주는 방법(지형 방어와 공식). 회복시키는 방법(최대 HP 제한).

공통인 것은 부모 class에 한 번만 작성한다. 자식 class는 부모가 작성해 둔 메서드를 골라서 호출하기만 한다. 그러면 다른 시스템을 아는 class는 부모 하나로 끝난다. 자식 class에는 “이 스킬이 무엇을 하는가”만 남는다.

2.2 Subclass Sandbox 패턴의 역할

이 구조의 이름이 Subclass Sandbox 패턴이다. 정의는 다음과 같다. 부모 class가 제공하는 도구만 사용해서 자식 class가 자신의 동작을 정의한다. Subclass는 자식 class를 뜻하는 영어다.

이 교재에서 사용하는 말 두 개를 먼저 정한다. 도구는 부모 class가 자식을 위해 작성해 둔 메서드다. 자식은 도구를 호출해서 자신의 동작을 만든다. 샌드박스 메서드는 부모가 이름과 매개변수만 선언하고 본문은 자식이 작성하게 한 메서드다. 자식이 채워야 하는 자리이므로 이 교재에서는 빈칸이라고도 부른다.

Subclass Sandbox의 역할과 미니 택틱스의 코드
역할미니 택틱스에서책임
부모 classSkill도구를 구현한다. 다른 시스템(TurnManager)과의 연결은 이 class에만 있다.
도구(protected 메서드)EnemiesInRange, WoundedAlliesInRange, Strike, Restore공통인 일을 한 번만 구현한다. 자식만 호출할 수 있다.
샌드박스 메서드(abstract 메서드)FindTargets, Activate자식이 반드시 작성해야 하는 빈칸이다.
자식 classPowerStrikeSkill, HealSkill빈칸을 도구의 조합으로 채운다. 다른 시스템을 알지 못한다.

protected와 abstract는 C#의 키워드다. 뜻은 3장과 4장에서 코드와 함께 설명한다. 지금은 protected가 “자식만 호출할 수 있다”, abstract가 “자식이 반드시 작성해야 한다”를 코드로 표현하는 키워드라는 것만 알면 된다.

바깥이 부모의 공개 메서드를 호출한다→부모가 자식의 빈칸을 호출한다→자식이 부모의 도구를 호출한다→도구가 다른 시스템을 사용한다

2.3 이름의 유래: 모래 놀이터

샌드박스(sandbox)는 아이들이 안전하게 노는 모래 놀이터다. 놀이터에는 울타리가 있고, 안에는 놀이에 쓸 도구가 준비되어 있다. 자식 class는 부모가 마련한 놀이터 안에서 주어진 도구만 가지고 자신의 동작을 만든다. 놀이터 밖에 있는 시스템에는 손을 대지 않는다. 패턴의 이름은 이 제한을 가리킨다. 자식이 할 수 있는 일의 범위를 부모가 도구로 정해 준다는 뜻이다.

2.5 흔한 오해

주의상속을 사용했다고 해서 모두 Subclass Sandbox인 것은 아니다. 1.3절의 첫 시도도 Skill을 상속했다. 이 패턴의 핵심은 자식이 부모가 제공한 도구만 사용한다는 제한이다. 자식이 다른 시스템을 직접 사용하기 시작하면 상속 구조는 그대로여도 첫 시도와 같아진다.

7차시의 첫 시도도 상속이었다는 점을 떠올릴 수 있다. 7차시에는 병종마다 값만 달랐기 때문에 상속이 맞지 않았다. 이번에는 스킬마다 동작이 다르므로 class로 나누는 것이 맞다. 상속은 그대로 사용하고, 자식 class를 작성하는 방법을 정하는 것이 이번 차시의 내용이다.

생각할 문제스킬이 30개이고 그중 20개가 피해를 주는 스킬이다. BoardView의 GetDefenseBonus의 이름이 바뀌었다. 첫 시도에서는 고쳐야 하는 스킬 파일이 몇 개인가? Subclass Sandbox에서는 몇 개인가?
해설 보기

첫 시도에서는 피해를 주는 스킬 20개가 모두 board.GetDefenseBonus를 호출하므로 스킬 파일 20개를 고쳐야 한다. Subclass Sandbox에서는 고쳐야 하는 스킬 파일이 0개다. GetDefenseBonus를 호출하는 곳은 1.1절의 TurnManager.Attack 한 곳뿐이므로 TurnManager.cs 하나만 고친다. 자식 class는 물론이고 부모 Skill도 보드를 직접 사용하지 않는다.

CHAPTER 03 · 부모 ①

부모 Skill: abstract 빈칸과 공개 입구

학습 목표: abstract 메서드와 abstract class의 뜻을 설명하고 virtual과 구분한다. 바깥에서 호출하는 공개 메서드 두 개가 하는 일을 순서대로 읽는다. 자식의 메서드가 반드시 부모의 공개 메서드를 거쳐서 실행되는 이유를 설명한다.

3.1 Skill의 뼈대

실제 코드 · Skill.cs · 축약한 발췌이며 속성 한 개, 공개 메서드 두 개, 도구 네 개를 생략했다

public abstract class Skill : ScriptableObject
{
    [SerializeField] private string _displayName;
    [SerializeField, Min(1)] private int _range = 1;

    private Unit _user;
    private TurnManager _turns;

    protected abstract List<Unit> FindTargets();
    protected abstract void Activate(Unit target);
}

필드는 네 개다. _displayName과 _range는 모든 스킬이 공통으로 가지는 값이며 Inspector에서 입력한다. 스킬의 이름과 사거리다. _user와 _turns는 “지금 이 스킬을 사용하는 유닛”과 TurnManager를 적어 두는 자리다. 이 두 필드는 3.4절에서 값이 들어가고 4장의 도구에서 사용된다.

Skill은 7차시의 UnitClass와 같이 ScriptableObject를 상속한다. 스킬도 프로젝트에 에셋으로 저장하는 객체라는 뜻이다. _range = 1의 1은 새 에셋을 만들었을 때 처음 들어 있는 기본값이다.

3.2 abstract 메서드: 본문이 없는 메서드

아래쪽 두 줄을 본다. FindTargets와 Activate에는 중괄호로 둘러싼 본문이 없고 세미콜론으로 끝난다. abstract는 “이 메서드의 이름, 매개변수, 반환 형식은 부모가 정하고, 본문은 자식이 반드시 작성한다”는 뜻의 키워드다. 자식 class가 부모의 메서드를 다시 정의하는 것을 override라고 하며, 자식은 같은 이름의 메서드 앞에 override 키워드를 붙여서 작성한다.

FindTargets는 “이 스킬의 대상이 될 수 있는 유닛의 목록을 돌려준다”는 빈칸이다. Activate는 “대상 하나에게 이 스킬의 효과를 준다”는 빈칸이다. 2.1절에서 찾은 “스킬마다 다른 것” 두 가지가 그대로 abstract 메서드 두 개가 되었다.

7차시의 첫 시도에서 본 virtual과 비교하면 차이가 분명해진다.

virtual과 abstract
구분virtual 메서드abstract 메서드
부모의 본문기본 본문이 있다.본문이 없다.
자식의 override선택이다.필수다.
자식이 override를 빠뜨리면부모의 기본 본문이 실행된다.자식 class가 컴파일되지 않는다.

빈칸을 virtual과 빈 본문으로 선언할 수도 있다. 그러면 Activate를 작성하지 않은 스킬은 사용해도 아무 일도 일어나지 않고, 컴파일러는 이 실수를 알려 주지 않는다. abstract로 선언하면 같은 실수가 컴파일 오류가 된다. 게임을 실행하기 전에 실수를 발견할 수 있다.

3.3 abstract class: 그 자체로는 객체를 만들 수 없는 class

abstract 메서드를 하나라도 가진 class는 class 선언에도 abstract를 붙여야 한다. 첫 줄의 public abstract class Skill이 그것이다. abstract class는 그 자체로는 객체를 만들 수 없다. 본문이 없는 메서드를 가진 객체가 만들어지면 그 메서드를 호출했을 때 실행할 코드가 없기 때문이다.

그래서 “Skill 에셋”은 만들 수 없다. 만들 수 있는 것은 빈칸을 모두 채운 자식 class의 에셋이다. 실제로 Skill.cs에는 7차시에서 배운 [CreateAssetMenu]가 없고, 5장에서 볼 자식 class에만 있다.

객체는 만들 수 없지만 변수의 형식으로는 사용할 수 있다. Skill 형식의 변수에는 PowerStrikeSkill 에셋도, HealSkill 에셋도 담을 수 있다. 이 점은 6장과 8장에서 사용한다.

3.4 바깥에서 부르는 입구는 공개 메서드 두 개다

실제 코드 · Skill.cs의 공개 메서드 두 개 전체

public List<Unit> GetTargets(Unit user, TurnManager turns)
{
    _user = user;
    _turns = turns;
    return FindTargets();
}

public void Use(Unit user, Unit target, TurnManager turns)
{
    _user = user;
    _turns = turns;
    Activate(target);
}

스킬의 바깥에 있는 코드가 호출하는 메서드는 이 두 개다. 이 교재에서는 이 두 메서드를 입구라고 부른다. 두 메서드는 같은 순서로 일한다.

  1. 누가 사용하는지(user)와 TurnManager(turns)를 private 필드 _user와 _turns에 적어 둔다.
  2. 자식이 작성한 메서드를 호출한다. GetTargets는 FindTargets()를, Use는 Activate(target)을 호출한다.
  3. 자식이 그 안에서 도구를 호출하면, 도구는 1번에서 적어 둔 값을 사용한다.

Use가 _user와 _turns를 다시 적는다는 점을 눈여겨본다. GetTargets에서 이미 적었더라도 Use는 그 값을 믿지 않고 새로 적는다. 스킬 에셋 하나는 여러 유닛이 함께 사용하므로 두 호출 사이에 다른 유닛이 같은 에셋의 입구를 지나갔을 수 있기 때문이다. 이 점은 8장의 대가에서 다시 다룬다.

3.5 자식의 메서드는 반드시 입구를 거쳐서 실행된다

FindTargets와 Activate는 protected로 선언되어 있다. protected의 자세한 뜻은 4.4절에서 다룬다. 여기에서 필요한 사실은 하나다. Skill과 그 자식이 아닌 class는 이 두 메서드를 직접 호출할 수 없다. 바깥의 코드가 skill.Activate(target)이라고 적으면 컴파일 오류가 된다.

입구가 보장하는 것바깥은 GetTargets와 Use만 호출할 수 있다. 자식의 메서드는 반드시 부모의 입구를 지나서 실행된다. 입구는 항상 _user와 _turns를 먼저 적는다. 그러므로 자식이 도구를 호출하는 시점에는 도구가 사용할 값이 항상 준비되어 있다.
연습5장에서 볼 HealSkill은 FindTargets와 Activate를 모두 override한다. HealSkill에서 Activate를 override한 줄을 지우면 어떤 일이 일어나는가? 빈칸을 abstract가 아니고 “virtual과 빈 본문”으로 선언했다면 같은 실수는 어떻게 나타나는가?
해설 보기

HealSkill이 컴파일되지 않는다. 컴파일러는 HealSkill이 상속받은 abstract 메서드 Skill.Activate(Unit)을 구현하지 않았다고 알려 준다. 프로젝트에 컴파일 오류가 있으면 Unity는 Play를 시작하지 않으므로 이 실수는 게임에 들어갈 수 없다. virtual과 빈 본문이었다면 컴파일은 통과한다. 치유를 사용하면 부모의 빈 본문이 실행되어 HP가 회복되지 않고, 오류 메시지도 나오지 않는다. 직접 플레이해서 회복되지 않는다는 것을 발견해야 한다.

부모 Skill: protected 도구

학습 목표: 도구 네 개가 각각 어떤 시스템과의 연결을 감추는지 설명한다. public, protected, private의 차이를 Skill의 멤버로 설명한다. 도구가 protected이고 _turns가 private인 이유를 설명한다.

4.1 도구는 네 개다

Skill이 제공하는 도구
도구하는 일도구가 사용하는 것
EnemiesInRange()사거리 안에 있는 살아 있는 적의 목록을 돌려준다.TurnManager.GetUnitsInRange
WoundedAlliesInRange()사거리 안에 있는 살아 있는 아군 가운데 부상당한 유닛의 목록을 돌려준다.TurnManager.GetUnitsInRange

앞의 두 개는 대상을 찾는 도구이고 뒤의 두 개는 효과를 주는 도구다. 3.2절의 빈칸 두 개와 짝이 맞는다. FindTargets는 대상을 찾는 도구로 채우고, Activate는 효과를 주는 도구로 채운다.

4.2 대상을 찾는 도구

실제 코드 · Skill.cs의 EnemiesInRange와 WoundedAlliesInRange 전체

protected List<Unit> EnemiesInRange()
{
    Team enemyTeam = _user.Team == Team.Player ? Team.Enemy : Team.Player;
    return _turns.GetUnitsInRange(_user, _range, enemyTeam);
}

protected List<Unit> WoundedAlliesInRange()
{
    List<Unit> allies = _turns.GetUnitsInRange(_user, _range, _user.Team);
    List<Unit> targets = new List<Unit>();
    foreach (Unit unit in allies)
    {
        if (unit.CurrentHp < unit.MaxHp)
        {
            targets.Add(unit);
        }
    }

    return targets;
}

EnemiesInRange의 첫 줄은 상대 진영을 구한다. 조건 ? A : B는 조건이 참이면 A를, 거짓이면 B를 값으로 가지는 연산자다. 사용하는 유닛이 아군(Player)이면 상대 진영은 Enemy이고, 그렇지 않으면 Player다. 둘째 줄은 TurnManager에게 사거리 안에 있는 그 진영의 유닛을 요청한다.

WoundedAlliesInRange는 먼저 사거리 안의 같은 진영 유닛을 요청한다. 그 목록에서 현재 HP가 최대 HP보다 작은 유닛만 골라서 돌려준다. HP가 가득 찬 유닛은 회복시킬 필요가 없으므로 대상에서 뺀다.

두 도구는 모두 _user, _range, _turns를 사용한다. 자식은 이 값들을 넘기지 않는다. 자식은 EnemiesInRange()라고 인수 없이 호출하고, 필요한 값은 부모가 입구에서 적어 둔 것을 도구가 읽는다.

실제 코드 · TurnManager.cs의 GetUnitsInRange 전체

public List<Unit> GetUnitsInRange(Unit user, int range, Team team)
{
    List<Unit> targets = new List<Unit>();
    Vector2Int origin = _board.WorldToCell(user.transform.position);
    foreach (Unit unit in _spawner.Units)
    {
        Vector2Int cell = _board.WorldToCell(unit.transform.position);
        int distance = Mathf.Abs(cell.x - origin.x) + Mathf.Abs(cell.y - origin.y);
        if (unit.IsAlive && unit.Team == team && distance <= range)
        {
            targets.Add(unit);
        }
    }

    return targets;
}

도구의 뒤에서 실제로 일하는 메서드다. 전장의 모든 유닛을 하나씩 확인하여 살아 있고, 요청한 진영이고, 거리가 사거리 이하인 유닛을 목록에 담는다. 거리는 7차시와 같이 가로 차이와 세로 차이를 더한 값이다. 이 메서드는 보드(_board)와 유닛 목록(_spawner)을 사용한다. 자식 class는 이 둘의 존재를 알지 못한다.

조건에 거리의 아래쪽 제한이 없다. 사용하는 유닛 자신은 거리가 0이고 자신과 같은 진영이므로, 아군을 찾을 때에는 자신도 목록에 들어간다. 그래서 부상당한 마법사는 치유의 대상으로 자기 자신을 고를 수 있다. 적을 찾을 때에는 자신의 진영이 다르므로 자신이 들어가지 않는다.

4.3 효과를 주는 도구

실제 코드 · Skill.cs의 Strike와 Restore 전체

protected void Strike(Unit target, int bonusDamage)
{
    _turns.Attack(_user, target, bonusDamage);
}

protected void Restore(Unit target, int amount)
{
    target.Heal(amount);
}

Strike의 본문은 한 줄이지만 그 뒤에 1.1절의 Attack 전체가 있다. 칸을 구하고, 지형 방어를 읽고, 피해 공식을 호출하고, HP를 줄인다. HP가 줄면 6차시에서 배운 대로 Unit.TakeDamage가 HpChanged와 Died 알림을 발행하므로 체력바 갱신과 전멸 판정도 이어서 실행된다. 이 모든 일이 Strike 한 줄로 실행된다. 자식은 Strike라는 이름과 매개변수 두 개만 알면 된다.

실제 코드 · Unit.cs의 Heal 전체

public void Heal(int amount)
{
    CurrentHp = Mathf.Min(MaxHp, CurrentHp + amount);
    HpChanged?.Invoke(this);
}

Restore의 뒤에는 이 메서드가 있다. Mathf.Min은 두 값 가운데 작은 쪽을 돌려준다. 회복한 뒤의 HP가 최대 HP를 넘으면 최대 HP로 제한된다. 둘째 줄은 6차시의 HpChanged 알림을 발행하므로 체력바가 회복된 HP로 갱신된다.

Restore는 한 줄을 그대로 전달할 뿐인데도 도구로 만들었다. 이유는 Strike와 같다. “회복시키는 방법”을 한 곳에 두기 위해서다. 나중에 회복에 공통 규칙이 추가되더라도 Restore 한 곳만 고치면 회복시키는 모든 스킬에 반영된다.

4.4 접근 수준: public, protected, private

접근 수준은 class의 멤버(필드, 속성, 메서드)를 어디에서 사용할 수 있는지를 정하는 표시다. Skill은 세 가지 접근 수준을 모두 사용한다.

Skill의 멤버와 접근 수준
접근 수준Skill에서의 예사용할 수 있는 곳
publicGetTargets, Use, DisplayName어디에서나 사용할 수 있다. BattleController가 사용한다.
protectedStrike, Restore, EnemiesInRange, WoundedAlliesInRange, FindTargets, ActivateSkill과 Skill의 자식 class 안에서만 사용할 수 있다.
private_user, _turns, _range, _displayNameSkill 안에서만 사용할 수 있다. 자식도 사용할 수 없다.

지금까지의 차시에서는 public과 private 두 가지만 사용했다. protected는 그 사이에 있다. 바깥에는 private처럼 닫혀 있고, 자식 class에게만 열려 있다. 부모와 자식 사이에서만 사용할 멤버에 붙인다. Subclass Sandbox에서 도구가 바로 그런 멤버다.

4.5 도구가 protected이고 _turns가 private인 이유

도구가 public이 아닌 이유

도구가 public이면 BattleController가 skill.Strike(...)를 직접 호출할 수 있다. 이 호출은 입구를 지나지 않으므로 _user와 _turns가 준비되지 않았거나 이전 호출의 값이 남아 있다. 도구는 스킬을 작성하는 자식만 사용해야 한다.

_turns가 protected가 아닌 이유

자식이 _turns를 사용할 수 있으면 도구를 거치지 않고 _turns.Attack(...)처럼 TurnManager를 직접 사용할 수 있다. 그러면 자식이 다시 다른 시스템을 알게 되고 첫 시도와 같아진다.

두 결정은 방향이 반대다. 도구는 private보다 넓혀서 자식에게 열었고, 필드는 protected보다 좁혀서 자식에게도 닫았다. 결과는 하나다. 자식이 할 수 있는 일은 도구를 호출하는 것뿐이다. 2.3절에서 말한 놀이터의 울타리를 코드에서는 접근 수준이 만든다.

흔한 실수자식 class를 작성하다가 필요한 값에 접근할 수 없으면 부모의 private 필드를 protected로 바꾸고 싶어진다. 컴파일은 통과하지만 그 순간부터 자식이 시스템을 직접 사용할 수 있게 된다. 필요한 것은 필드를 여는 일이 아니고 도구를 추가하는 일이다. 7장에서 다룬다.
연습어떤 자식 class가 Activate 안에서 _turns.Attack(_user, target, 4);를 호출하려고 한다. 현재 코드에서 이 줄은 어떻게 되는가? _turns와 _user를 protected로 바꾸면 어떻게 되고, 그때 잃는 것은 무엇인가?
해설 보기

현재 코드에서는 컴파일 오류다. _turns와 _user가 private이므로 자식은 사용할 수 없다. 두 필드를 protected로 바꾸면 컴파일되고 강타와 같은 결과가 나온다. 그러나 이 자식은 이제 TurnManager의 Attack이라는 이름과 매개변수 세 개를 알고 있다. Attack의 매개변수가 바뀌면 이 자식도 컴파일되지 않는다. 다른 시스템과의 연결이 부모 한 곳에만 있다는 이 패턴의 이득을 잃는다. 올바른 코드는 Strike(target, 4)다.

CHAPTER 05 · 자식

자식 class: 강타와 치유

학습 목표: override 키워드로 빈칸을 채운 자식 class를 한 줄씩 읽는다. 강타와 치유의 코드에서 같은 부분과 다른 부분을 구분한다. 새 class가 필요한 차이와 새 에셋으로 충분한 차이를 구분한다.

5.1 강타는 도구 두 개를 고른 것이 전부다

실제 코드 · PowerStrikeSkill.cs의 class 전체

[CreateAssetMenu(menuName = "Mini Tactics/Skills/Power Strike")]
public sealed class PowerStrikeSkill : Skill
{
    [SerializeField, Min(0)] private int _bonusDamage = 4;

    protected override List<Unit> FindTargets() => EnemiesInRange();
    protected override void Activate(Unit target) => Strike(target, _bonusDamage);
}

이 class는 세 줄로 읽는다.

  1. 이 스킬만의 값은 추가 피해이고 기본값은 4다.
  2. 대상은 사거리 안의 적이다. FindTargets를 도구 EnemiesInRange()로 채웠다.
  3. 효과는 추가 피해를 더한 공격이다. Activate를 도구 Strike(target, _bonusDamage)로 채웠다.

override는 부모가 선언한 메서드를 자식이 다시 정의한다는 표시다. 부모의 abstract 메서드와 이름, 매개변수, 반환 형식이 같아야 한다. 접근 수준도 같아야 하므로 부모가 protected로 선언한 메서드는 자식도 protected override로 작성한다. =>는 본문이 식 하나인 메서드를 짧게 적는 문법이다. 중괄호 안에 그 식 하나를 적은 것과 같다.

: Skill은 Skill을 상속한다는 뜻이다. sealed는 이 class를 더 이상 상속할 수 없게 한다. [CreateAssetMenu]는 7차시에서 배운 대로 Create 메뉴에 항목을 추가한다. abstract인 Skill에는 없고 객체를 만들 수 있는 자식에만 있다.

1.3절의 첫 시도와 비교한다. 첫 시도의 본문 네 줄이 도구 호출 한 줄이 되었다. 첫 시도에 코드로 적혀 있던 숫자 4는 Inspector에서 조정할 수 있는 값이 되었다.

5.3 자식 파일에 없는 것

두 파일에는 BoardView도, CombatCalculator도, TurnManager도 등장하지 않는다. 자식이 사용하는 이름은 부모의 도구 이름과, 매개변수의 형식으로 쓰인 Unit뿐이다. 자식은 Unit의 메서드를 하나도 호출하지 않는다. 받은 대상을 도구에 그대로 넘길 뿐이다.

자식이 모르는 것지형 방어가 있다는 사실, 피해 공식의 모양, 유닛의 목록이 어디에 있는지, 거리를 어떻게 계산하는지, 최대 HP 제한. 자식은 이 가운데 어느 것도 알지 못한다. 그래서 이것들이 바뀌어도 자식 파일은 바뀌지 않는다.

CHAPTER 06 · 흐름

호출 흐름과 수치 추적

학습 목표: 스킬을 사용하는 호출 한 줄이 입구, 빈칸, 도구를 차례로 지나가는 과정을 설명한다. 호출하는 쪽이 스킬의 종류를 알지 못한다는 점을 설명한다. 강타의 피해와 치유의 회복을 실제 값으로 직접 계산한다.

6.1 호출하는 쪽의 코드는 한 줄이다

실제 코드 · BattleController.UseSkill의 첫 줄

user.UnitClass.Skill.Use(user, target, _turnManager);

왼쪽에서부터 읽는다. user.UnitClass는 7차시에서 배운 대로 그 유닛의 타입 객체, 즉 병종 에셋이다. .Skill은 그 병종 에셋에 연결된 스킬 에셋이다. 이 연결은 8장에서 다룬다. .Use(...)는 3.4절의 입구다. 사용하는 유닛, 대상, TurnManager를 넘긴다.

6.2 호출 한 번이 입구, 빈칸, 도구를 차례로 지나간다

기사가 강타를 사용한 경우를 따라간다.

Skill.Use · 사용자와 TurnManager를 적는다→PowerStrikeSkill.Activate · 자식이 작성한 빈칸→Skill.Strike · 부모의 도구→TurnManager.Attack · 실제 피해 처리
  1. Skill.Use가 실행된다. _user에 기사를, _turns에 TurnManager를 적고 Activate(target)을 호출한다.
  2. 이 에셋은 PowerStrikeSkill의 객체이므로 PowerStrikeSkill.Activate가 실행된다. 본문은 Strike(target, _bonusDamage)이고 _bonusDamage는 4다.
  3. Skill.Strike가 실행된다. 1번에서 적어 둔 값을 사용하여 _turns.Attack(_user, target, 4)를 호출한다.
  4. TurnManager.Attack이 지형 방어를 읽고, 공식으로 피해를 계산하고, 4를 더해서 대상의 HP를 줄인다.

호출이 오가는 방향을 본다. 부모(Use)에서 자식(Activate)으로 갔다가 다시 부모(Strike)로 돌아온다. 부모가 자식을 부르고, 자식이 다시 부모의 도구를 부른다. 흐름의 시작과 끝을 부모가 맡고 있고, 자식은 가운데에서 “어떤 도구를 어떤 값으로 부를 것인가”만 정한다.

6.3 호출하는 쪽은 스킬의 종류를 알지 못한다

6.1절의 한 줄에는 “강타”도 “치유”도 없다. user.UnitClass.Skill의 형식은 부모인 Skill이다. C#에서는 부모 형식의 변수로 메서드를 호출해도 그 변수에 담긴 실제 객체의 class에 있는 override가 실행된다. 이 성질을 다형성이라고 한다. 같은 호출이 객체에 따라 다른 동작을 한다는 뜻이다.

그래서 같은 한 줄이 기사에게서는 강타를, 마법사에게서는 치유를 실행한다. 어떤 자식의 Activate가 실행될지는 코드가 아니고 병종 에셋에 연결된 스킬 에셋이 정한다. 스킬이 30개로 늘어나도 호출하는 쪽의 이 한 줄은 바뀌지 않는다.

6.4 추적: 기사의 강타

출발 상태는 다음과 같다. 기사의 공격력은 6이다. 적 궁수는 방어력 1, HP 9 / 9다. 강타 에셋의 추가 피해는 4다. 피해 공식은 max(1, 공격력 − 방어력 − 지형 방어)다. 평지의 지형 방어는 0이고 숲의 지형 방어는 1이다. 궁수가 평지에 있을 때와 숲에 있을 때를 나란히 계산한다.

7.1 화염구를 추가하려면 무엇을 작성해야 하는가

7.2 자식은 도구를 조합한다

화염구의 Activate는 강타와 같은 도구 Strike를 사용하지만 호출하는 방법이 다르다. 반복문 안에서 적의 수만큼 호출한다. 도구는 여러 번 호출해도 되고, 반복문이나 조건문 안에서 호출해도 되고, 여러 도구를 차례로 호출해도 된다. 자식은 도구를 고르기만 하는 것이 아니고 조합한다. 도구는 네 개뿐이어도 조합의 수는 그보다 훨씬 많다.

화염구를 수치로 확인한다. 출발 상태는 다음과 같다. 화염구 에셋의 사거리는 2이고 추가 피해는 2다. 이 에셋을 마법사(공격력 8)의 병종 에셋에 연결했다고 가정한다. 사거리 안에 적이 둘 있다. 평지의 궁수(방어력 1, HP 9 / 9)와 숲의 기사(방어력 3, HP 14 / 14)다.

Strike가 두 번 호출되었고, 호출마다 대상이 서 있는 칸의 지형 방어가 따로 적용되었다. 화염구의 코드에는 지형에 대한 내용이 없다.

7.3 도구가 부족하면 부모에 도구를 추가한다

“밀치기” 스킬을 만들려고 한다. 대상을 한 칸 뒤로 이동시켜야 하는데 그런 도구가 없다. 이때 하지 말아야 할 일이 있다. 밀치기 class 안에서 BoardView를 찾아 대상을 직접 이동시키는 것이다. 이것은 2.3절의 놀이터 밖으로 나가는 일이다. 첫 시도의 문제가 그 class에서 다시 시작된다. 올바른 방법은 부모에 도구를 추가하는 것이다.

설계 비교용 가상 코드 · 실제 프로젝트에는 Push 도구, PushSkill, TurnManager.PushAway가 없다 · CreateAssetMenu 줄을 생략했다

// Skill.cs에 도구를 하나 추가한다.
protected void Push(Unit target)
{
    _turns.PushAway(_user, target);
}

// 새 자식은 새 도구를 호출하기만 한다.
public sealed class PushSkill : Skill
{
    protected override List<Unit> FindTargets() => EnemiesInRange();
    protected override void Activate(Unit target) => Push(target);
}

PushAway는 “사용자의 반대 방향으로 대상을 한 칸 이동시킨다”는 일을 TurnManager가 맡는다고 가정한 이름이다. 빈 칸인지, 지도 밖인지를 확인하는 코드는 그 메서드 안에 들어간다.

Skill에 Push 도구를 추가한다→Push가 보드와의 연결을 감춘다→PushSkill은 Push를 호출한다→이후의 모든 스킬이 Push를 쓸 수 있다

새 도구는 한 번 만들면 모든 자식의 것이 된다. Strike와 Push를 차례로 호출하는 “충격 화살”처럼 조합할 수 있는 재료가 늘어난다. 이때 기존 자식 class는 고칠 필요가 없다. 도구를 추가하는 일은 기존 도구의 이름과 매개변수를 바꾸지 않기 때문이다.

7.4 도구 한 곳을 고치면 모든 스킬에 반영된다

“피해를 주는 모든 스킬이 기록을 남기게 한다”는 요구가 생겼다고 가정한다.

설계 비교용 가상 코드 · 실제 Strike에는 로그를 남기는 줄이 없다

protected void Strike(Unit target, int bonusDamage)
{
    Debug.Log($"{_user.name} → {target.name} : {DisplayName}");
    _turns.Attack(_user, target, bonusDamage);
}

Debug.Log는 Unity의 Console 창에 글을 출력하는 메서드다. $"..."는 중괄호 안의 값을 문자열에 끼워 넣는 문법이다.

같은 변경을 두 구조에서 할 때
변경첫 시도Subclass Sandbox

공통인 코드가 한 곳에만 있기 때문이다. 자식이 30개여도 다른 시스템과 연결된 곳은 부모 하나다. 1.4절의 표에 있던 한계가 이 표에서 풀렸다.

생각할 문제“흡혈” 스킬을 만들려고 한다. 사거리 안의 적 하나를 추가 피해 0으로 공격하고, 사용한 유닛 자신의 HP를 3 회복한다. 현재의 도구 네 개만으로 Activate를 작성할 수 있는가? 작성할 수 없다면 무엇을 해야 하는가?
해설 보기

공격은 Strike(target, 0)으로 작성할 수 있다. 회복은 작성할 수 없다. Restore에는 회복시킬 유닛을 넘겨야 하는데, 사용한 유닛을 담고 있는 _user는 private이어서 자식이 사용할 수 없다. _user를 protected로 바꾸는 것은 4.5절에서 본 대로 울타리를 허무는 일이다. 부모에 도구를 추가한다. 예를 들어 Skill에 protected void RestoreUser(int amount)를 추가하고 본문을 _user.Heal(amount);로 작성한다. 그러면 흡혈의 Activate는 Strike(target, 0);과 RestoreUser(3); 두 줄이 된다. 새 도구는 이후에 만드는 모든 스킬이 사용할 수 있다.

CHAPTER 08 · 결합과 판단

Type Object와의 결합, 대가, 적용 기준

학습 목표: 7차시의 Type Object와 이번 차시의 Subclass Sandbox가 각각 어떤 차이를 맡는지 설명한다. Subclass Sandbox의 대가 세 가지를 구체적인 모습으로 설명한다. 이 패턴을 적용할지 판단하는 질문을 사용한다.

8.1 병종 에셋이 스킬 에셋을 참조한다

실제 코드 · UnitClass.cs에 추가된 두 줄 · 축약한 발췌이며 필드 한 줄과 속성 한 줄만 옮겼다. 파일에서는 두 줄이 서로 떨어져 있다

[SerializeField] private Skill _skill;
public Skill Skill => _skill;

7차시의 타입 객체 UnitClass에 값이 하나 늘었다. 그 병종이 사용하는 스킬이다. 필드의 형식이 부모인 Skill이므로 Inspector에서 PowerStrikeSkill 에셋도, HealSkill 에셋도 연결할 수 있다. 3.3절에서 말한 “abstract class는 변수의 형식으로 사용할 수 있다”는 점이 여기에서 쓰인다.

현재 프로젝트의 병종과 스킬
병종 에셋Skill에 연결된 에셋결과
KnightPowerStrike기사는 강타를 쓴다.
Archer없다.궁수는 스킬이 없다.

6.1절의 user.UnitClass.Skill.Use(...)가 이 연결을 따라간다. 유닛에서 병종 에셋으로, 병종 에셋에서 스킬 에셋으로 간다.

8.2 스킬이 없는 병종은 정상적인 상태다

궁수의 Skill은 비어 있다. 코드에서는 null이다. 7차시에서 병종이 연결되지 않은 유닛은 실수였지만, 스킬이 없는 병종은 의도한 상태다. 그래서 사용하는 쪽이 이 경우를 확인한다.

실제 코드 · BattleController.HasSkillTargets의 본문 두 줄

Skill skill = user.UnitClass.Skill;
return skill != null && skill.GetTargets(user, _turnManager).Count > 0;

&&는 왼쪽이 거짓이면 오른쪽을 실행하지 않는다. 궁수는 skill != null이 거짓이므로 GetTargets를 호출하지 않고 false를 돌려준다. 기사와 마법사는 3.4절의 입구 GetTargets를 호출하여 대상이 하나 이상 있는지 확인한다. 이 코드에도 강타와 치유라는 단어는 없다.

8.3 두 패턴이 맡는 차이

Type Object · 값의 차이

병종의 HP, 공격력, 사거리는 값이다. UnitClass 에셋에 적는다. 스킬의 추가 피해 4, 회복량 5, 사거리도 값이다. 스킬 에셋에 적는다. 어떤 병종이 어떤 스킬을 쓰는지도 에셋의 연결로 정한다.

Subclass Sandbox · 동작의 차이

강타와 치유는 실행되는 코드가 다르다. class로 나누고 부모의 도구로 작성한다. 7차시의 대가였던 “값으로 표현할 수 없는 차이”를 이 패턴이 맡는다.

7차시 교재의 8장에서 “동작의 차이가 필요해지면 다른 구조를 함께 사용한다”고 했다. 그 구조가 이것이다. 누가 어떤 스킬을 쓰는지는 데이터(Type Object)가 정하고, 스킬이 무엇을 하는지는 도구의 조합(Subclass Sandbox)이 정한다.

8.4 Subclass Sandbox의 대가

대가와 대응
대가구체적인 모습대응
부모 class가 계속 커진다.스킬이 다양해질수록 도구가 늘어난다. 도구가 50개가 되면 Skill.cs가 가장 크고 가장 자주 바뀌는 파일이 된다.도구를 주제별 class로 나누고 부모가 그것을 꺼내 주게 한다.
모든 자식이 부모에 묶인다.Strike의 매개변수를 바꾸면 Strike를 호출하는 모든 자식이 컴파일되지 않는다.도구의 이름과 매개변수를 신중하게 정하고 쉽게 바꾸지 않는다.
부모가 상태를 잠시 보관한다._user와 _turns는 호출할 때마다 다시 적는다. 스킬 에셋은 여러 유닛이 공유하므로 이 값을 나중에 다시 읽으면 다른 유닛의 값일 수 있다.도구는 입구가 실행되는 동안에만 사용한다.

셋째 대가를 예로 확인한다. 전장에 기사 A와 기사 B가 있다. 두 기사는 같은 Knight 에셋을 참조하고, Knight 에셋은 PowerStrike 에셋 하나를 참조한다. 그러므로 두 기사는 같은 스킬 객체 하나를 사용한다. A가 입구를 지나가면 _user는 A가 되고, 이어서 B가 입구를 지나가면 _user는 B가 된다. 7차시의 규칙은 “공유하는 객체에는 실행 중에 바뀌는 값을 두지 않는다”였다. _user는 이 규칙의 예외에 가깝다. 예외가 안전한 이유는 두 가지다. 입구가 매번 값을 새로 적고, 도구는 protected여서 입구가 실행되는 동안에만 호출된다. 3.4절과 4.5절의 결정이 이 대가에 대한 대응이다.

_user와 _turns에는 [SerializeField]가 없다. 그래서 이 값은 에셋 파일에 저장되지 않고 실행 중에만 잠시 존재한다.

대가의 요약결합이 사라진 것이 아니다. 결합은 한 class가 바뀌면 다른 class도 함께 바뀌어야 하는 관계를 뜻한다. 자식 30개에 흩어져 있던 다른 시스템과의 결합을 부모 한 곳으로 모은 것이다. 그래서 부모는 더 무거워지고, 자식은 모두 부모에 결합된다.

8.5 적용 기준: 비슷한 자식이 많고 같은 시스템을 반복해서 쓰는가

Subclass Sandbox가 이득인 경우

자식 class가 많거나 앞으로 늘어난다. 자식들이 같은 시스템을 비슷한 방법으로 사용한다. 자식을 작성하는 사람이 다른 시스템을 몰라도 되게 하고 싶다. 예: 스킬, 아이템 효과, 적의 행동 방식.

필요하지 않은 경우

자식이 두세 개로 고정되어 있다. 자식마다 사용하는 시스템이 전혀 달라서 공통 도구를 뽑을 수 없다. 예: 4차시부터 만든 입력 상태들. 상태의 수가 적고, BattleController의 메서드를 직접 호출해도 복사되는 코드가 거의 없다.

판단하는 질문“자식 class들에 같은 코드가 복사되고 있는가?” 복사되고 있다면 그 코드를 부모의 도구로 올린다. 복사되는 코드가 없다면 도구로 올릴 것이 없으므로 이 패턴은 필요하지 않다. 패턴은 실제로 해결할 문제가 있을 때에만 도입한다.
손으로 계산하기Archer 에셋의 Skill에 PowerStrike 에셋(사거리 1, 추가 피해 4)을 연결했다. 궁수(공격력 5, 공격 사거리 2)가 산(지형 방어 2) 위의 적 기사(방어력 3, HP 14 / 14)에게 강타를 사용한다. 적 기사가 거리 1에 있을 때 남는 HP는 얼마인가? 적 기사가 거리 2에 있다면 어떠한가? 이 변경을 위해 고친 코드는 몇 줄인가?
해설 보기

거리 1일 때: 공식의 결과는 max(1, 5 − 3 − 2) = max(1, 0) = 1이다. 추가 피해를 더하면 1 + 4 = 5이고 14 − 5 = 9가 남는다. 거리 2일 때: 강타의 대상이 아니다. 궁수의 공격 사거리는 2이지만 EnemiesInRange는 스킬 에셋의 사거리 1을 사용하기 때문이다. 일반 공격은 할 수 있고 그때의 피해는 1이다. 고친 코드는 0줄이다. 병종 에셋의 Skill 연결만 바꾸었다. 누가 어떤 스킬을 쓰는지는 Type Object가 정하고, 강타가 무엇을 하는지는 Subclass Sandbox가 정한다.

CHAPTER 09 · 복습

복습 질문과 용어

학습 목표: 다섯 질문에 자신의 말로 답한다. 이번 차시의 용어를 정확한 뜻으로 사용한다.

9.1 스스로 설명하는 다섯 질문

  1. PowerStrikeSkill.cs와 HealSkill.cs에서 “TurnManager”, “BoardView”, “CombatCalculator”를 검색하면 몇 번 나오는가? 그것은 무엇을 뜻하는가?
  2. abstract, protected, override는 Skill과 그 자식에서 각각 어떤 일을 하는가?
  3. 도구는 왜 public이 아니고 protected인가? _turns는 왜 protected가 아니고 private인가?
  4. 공격력 8인 마법사의 병종 에셋에 추가 피해 4의 강타 에셋을 연결했다. 이 마법사가 산(지형 방어 2) 위에 있는 방어력 3, HP 14인 기사에게 강타를 사용한다. 남는 HP는 얼마인가? 이를 위해 고친 코드는 몇 줄인가?
  5. “밀치기” 스킬을 만들려는데 필요한 도구가 없다. 무엇을 해야 하고 무엇을 하지 말아야 하는가? 이 패턴의 대가 세 가지와 적용을 판단하는 질문은 무엇인가?
답 확인

1. 0번이다. 자식은 다른 시스템을 알지 못한다는 뜻이다. 그 시스템들이 바뀌어도 자식 파일은 바뀌지 않는다. 2. abstract는 자식이 반드시 작성해야 하는 빈칸 FindTargets와 Activate를 선언한다. 작성하지 않은 자식은 컴파일되지 않는다. protected는 도구와 빈칸을 Skill과 그 자식만 사용할 수 있게 한다. override는 자식이 부모의 abstract 메서드를 다시 정의한다는 표시다. 3. 도구가 public이면 바깥의 코드가 입구를 지나지 않고 도구를 호출할 수 있고, 그때에는 _user와 _turns가 준비되어 있지 않다. _turns가 protected이면 자식이 도구를 거치지 않고 TurnManager를 직접 사용할 수 있어서 첫 시도와 같아진다. 4. max(1, 8 − 3 − 2) = 3이고 3 + 4 = 7이다. 14 − 7 = 7이 남는다. 고친 코드는 0줄이다. 강타의 코드는 그대로이고 병종 에셋의 Skill 연결만 바꾸었다. 5. 부모 Skill에 Push 도구를 추가하고 새 자식은 그 도구를 호출한다. 자식 class 안에서 BoardView를 직접 사용하지 않는다. 대가는 커지는 부모, 부모에 묶이는 자식, 부모가 잠시 보관하는 상태다. 판단하는 질문은 “자식 class들에 같은 코드가 복사되고 있는가”다.

9.2 용어 사전

용어이번 차시에서의 뜻
Subclass Sandbox 패턴부모 class가 제공하는 도구만 사용해서 자식 class가 자신의 동작을 정의하는 구조.
샌드박스(sandbox)모래 놀이터. 자식이 부모가 정해 준 범위 안에서 주어진 도구만 사용한다는 제한을 가리킨다.
도구부모가 자식을 위해 작성해 둔 protected 메서드. EnemiesInRange, WoundedAlliesInRange, Strike, Restore.
샌드박스 메서드(빈칸)부모가 abstract로 선언하고 자식이 본문을 작성하는 메서드. FindTargets, Activate.
입구바깥에서 호출하는 부모의 public 메서드. GetTargets, Use. 사용자와 TurnManager를 적은 뒤에 자식의 메서드를 호출한다.
abstract메서드에 붙이면 본문이 없고 자식이 반드시 override해야 한다는 뜻. class에 붙이면 그 자체로는 객체를 만들 수 없다는 뜻.
override자식이 부모의 virtual 또는 abstract 메서드를 다시 정의한다는 표시.
protected그 class와 자식 class 안에서만 사용할 수 있는 접근 수준.
접근 수준멤버를 어디에서 사용할 수 있는지를 정하는 표시. public, protected, private.

9.3 요약

이번 차시의 기준동작이 다른 종류는 class로 나눈다. 그 class들에 복사되는 코드는 부모의 protected 도구로 올린다. 자식이 채울 빈칸은 abstract 메서드로 선언하고, 바깥은 부모의 공개 입구만 호출한다. 자식은 다른 시스템을 알지 못하고, 다른 시스템과의 연결은 부모 한 곳에만 있다. 도구가 부족하면 자식이 시스템을 직접 사용하지 않고 부모에 도구를 추가한다. 값의 차이는 7차시의 Type Object가, 동작의 차이는 Subclass Sandbox가 맡는다. 대가는 커지는 부모, 부모에 묶이는 자식, 잠시 보관하는 상태다. 새 스킬을 작성할 때 부모의 도구 말고 다른 시스템을 열어 보지 않아도 된다면 Subclass Sandbox가 제 역할을 하고 있는 것이다.
