A Small Success

같은 구조의 객체 여러 개는 이미 만들 수 있다

개체 · 실제 하나

Unit 하나는 자기 현재 HP와 소속을 갖는다. 같은 C# 클래스로 만든 두 객체도 각각의 상태가 있다.

작은 시작점

모두 같은 공통 값을 쓴다면 Unit 클래스 한 곳에 정의해도 충분하다. 아직 종류를 표현하는 별도 객체는 필요하지 않을 수 있다.

객체는 하나의 실체다. 클래스는 객체의 코드 구조를 정한다. 이제 코드 구조는 같고 공통 값만 다른 종류가 늘어난다고 생각하자.

New Requirement

동작 구조가 같아도 종류의 값은 달라진다

“검사와 궁수는 공통 값을 다르게 쓰되,
같은 종류의 개체는 같은 정의를 읽고 싶어요.”

종류에 속하는 것

이름, 최대 HP 같은 기본 정의다. 같은 종류라면 여러 개체가 함께 사용할 수 있다.

개체에 속하는 것

현재 HP는 겪은 일에 따라 달라진다. 같은 종류라는 이유로 함께 바뀌면 안 된다.

First Attempt

종류마다 C# 클래스를 하나씩 만든다면?

A Limited Solution

값 한 줄이 달라도 코드 종류가 늘어난다

첫 시도가 잘하는 일

서로 다른 구현을 코드의 타입으로 구분한다. 종류마다 고유한 동작을 구현하고 검사하기 쉽다.

지금 요구에서 드는 비용

동작은 같고 숫자·이름만 달라도 C# 파일이 늘어난다. 새 종류나 값 조정이 코드 변경과 결합된다.

상속 자체가 문제는 아니다. 차이가 데이터인가, 서로 다른 알고리즘인가를 먼저 구별한다. 값의 차이를 코드 타입의 차이로 표현할 필요가 있는가?

Responsibility Boundary

공유 기준은 “값이 우연히 같다”가 아니라 같은 종류의 정의를 함께 사용하는가다. 현재 HP가 우연히 같아도 각 개체에 둔다.

Type Object

종류 자체를 하나의 객체로 표현한다

Type Object는 종류의 정의를 객체로 만들고,
개체가 그 정의를 참조하게 한다.

코드 타입 · Unit

여러 종류의 개체가 같은 Unit 코드를 사용한다. 무엇을 읽을지는 참조한 정의가 결정한다.

데이터 타입 · UnitClass

검사와 궁수는 서로 다른 C# 하위 클래스가 아니라 서로 다른 UnitClass 객체로 표현된다.

Roles

현재 코드의 역할을 네 관점으로 읽는다

종류의 공통 값과 참조

어느 정의를 읽는지 연결

Unity에서는 UnitClass를 ScriptableObject 에셋으로 저장한다. Type Object는 설계 패턴이고, ScriptableObject는 그 정의를 보관하는 Unity의 수단이다. 둘은 같은 용어가 아니다.

Shared Definition

UnitClass는 공통 값을 보관한다

[SerializeField] private string _displayName;
[SerializeField, Min(1)] private int _maxHp;
[SerializeField, Min(0)] private int _attackPower;
[SerializeField, Min(0)] private int _defense;

값의 주인

이름과 최대 HP는 개체마다 복사해 둔 규칙이 아니라 정의 객체가 보관하는 데이터다.

없는 것의 의미

현재 HP는 여기에 없다. 개체의 경험으로 달라지는 상태는 공유 정의에 넣지 않는다.

UnitLook는 외형 데이터의 타입이다. PlayerLook와 EnemyLook는 그 데이터의 참조다. 같은 UnitClass를 읽으면서도 각 Unit은 자기 소속에 맞는 참조를 선택할 수 있다.

Individual Object

Unit은 정의 참조와 현재 상태를 갖는다

public UnitClass UnitClass { get; private set; }
public Team Team { get; private set; }
public bool HasMoved { get; set; }
public int CurrentHp { get; private set; }

현재 Teacher7 실제 코드 발췌 · Unit.cs:11–14 · 연속한 속성 일부, 나머지 멤버·클래스 외곽 생략

UnitClass 속성은 “어느 종류인가”를 가리킨다. CurrentHp·Team·HasMoved는 Unit 인스턴스마다 별도로 저장된다. Unit.UnitClass는 이 코드에서 참조 속성이며 C# 상속 선언이 아니다.

Delegated Reads

공통 값은 참조한 정의에서 읽는다

예를 들어 Unit.MaxHp는 매번 UnitClass.MaxHp를 읽는다. Unit마다 별도 최대 HP 필드를 보관하지 않으므로 같은 정의를 읽는 개체의 기준값이 한곳에 모인다.

Initialization

정의를 먼저 연결하고 현재 HP를 정한다

public void Initialize(Team team, UnitClass unitClass)
{
    UnitClass = unitClass;
    Team = team;
    HasMoved = false;
    _animator.SetLook(team == Team.Player ? unitClass.PlayerLook : unitClass.EnemyLook);
    CurrentHp = MaxHp;
    HpChanged?.Invoke(this);
}

현재 Teacher7 실제 코드 발췌 · Unit.cs:25–33 · Initialize 전체, 다른 메서드·클래스 외곽 생략

UnitClass 참조를 보관한 뒤 CurrentHp = MaxHp로 초기 값을 복사한다. 외형과 개별 상태를 정한 다음 HpChanged로 알린다. 이 메서드는 공유 정의를 복제하지 않는다.

Initial Trace

두 개체가 한 정의를 받아 시작한다

시점 · 설명용 이름 A/B공유 정의 참조A.CurrentHpB.CurrentHp
같은 Swordsman 정의 준비MaxHp = 14아직 초기화 전아직 초기화 전
A.Initialize에 그 정의 전달A → 같은 정의14아직 초기화 전
B.Initialize에 그 정의 전달A/B → 같은 정의1414

A와 B는 설명용으로 붙인 두 Unit의 이름이다. 공개 A/B API가 아니다. 각 호출은 자신의 CurrentHp에 14를 대입한다. 정의 하나를 공유해도 HP 저장 공간은 둘이다.

Individual Change

개별 변화는 그 Unit의 CurrentHp에 쓴다

public void TakeDamage(int damage)
{
    if (!IsAlive || damage <= 0) return;
    CurrentHp = Mathf.Max(0, CurrentHp - damage);
    HpChanged?.Invoke(this);

현재 Teacher7 실제 코드 발췌 · Unit.cs:35–39 · TakeDamage 앞부분만 발췌, 뒤의 종료 처리·닫는 중괄호 생략

여기서 쓰는 곳은 Unit의 CurrentHp다. UnitClass의 최대 HP를 바꾸지 않는다. 입력 damage는 이미 정해진 수이며, 이 장은 개별 상태의 저장 위치를 읽는 예시다.

Worked Result

A만 변하면 B의 현재 HP는 그대로다

추적 · 두 객체는 같은 정의를 참조정의 MaxHpA.CurrentHpB.CurrentHp
둘 다 초기화 완료141414
A.TakeDamage(4) 호출141014
A/B의 MaxHp를 다시 조회둘 다 1410 그대로14 그대로

왜 A만 10인가?

14 − 4 = 10을 A.CurrentHp에 대입했다. B의 필드에 대입한 문장은 없다.

공유한 것은 무엇인가?

UnitClass 참조와 그 정의다. CurrentHp가 정의에 있다면 독립 상태를 표현할 수 없게 된다.

Reference Identity

같은 값과 같은 객체는 다르다

경우값의 모습공유 여부
A/B가 한 UnitClass 에셋 참조두 MaxHp 모두 14정의 객체 하나를 공유
서로 다른 두 에셋에 각각 14두 MaxHp 모두 14정의 객체는 별개
한 UnitClass와 두 CurrentHp현재 HP가 둘 다 14일 수도 있음현재 HP 저장 공간은 개체별

숫자만 비교해서 공유를 판정하지 않는다. 어느 객체를 참조하는지 본다. Type Object의 핵심은 값의 우연한 일치보다 종류 정의와 개체의 관계다.

Shared Mutable Data

공유 에셋은 자동으로 불변이 되지 않는다

읽기 전용 속성의 범위

MaxHp에 public setter가 없어도 에셋 데이터 전체가 불변인 것은 아니다. 에셋을 변경하면 모든 참조가 같은 정의를 읽는다.

상태를 넣을 때의 위험

한 개체의 현재 HP나 임시 효과를 공유 에셋에 기록하면 같은 정의를 참조한 다른 개체까지 영향을 받을 수 있다.

공유 정의의 변경 권한과 변경 시점을 관리한다. 개체별로 달라지는 가변 상태는 Unit에 둔다. 에셋을 참조한다는 사실 자체가 안전한 변경 정책을 보장하지 않는다.

Copy at Initialization

MaxHp 조회와 CurrentHp 초기화는 다르다

상황MaxHp 조회이미 초기화된 CurrentHp
공유 정의 MaxHp가 14참조한 정의의 14A=10, B=14
정의가 15로 바뀐다고 가정A/B 모두 15를 읽음자동 대입이 없으므로 10/14 유지
그 정의로 새 개체를 초기화15새 개체는 15에서 시작

값 변경의 영향을 설명하는 가정이다. CurrentHp = MaxHp는 초기화 시점의 대입이다. MaxHp를 바꿨다고 기존 CurrentHp가 자동 회복·비례 조정되지는 않는다.

Data and Algorithms

새 데이터가 임의의 새 동작을 만들지는 않는다

같은 알고리즘에 다른 값을 주는 것과,
서로 다른 알고리즘을 구현하는 것은 다르다.

Type Object가 돕는 범위

이미 구현된 코드가 이름·수치·참조를 읽어 종류를 구분한다. 같은 데이터 구조로 새로운 정의를 표현하기 쉽다.

별도 설계가 필요한 범위

숫자나 이름만 추가해도 전혀 새로운 행동이 생기지는 않는다. 동작 차이는 실행 코드와 그 연결 구조가 필요하다.

UnitClass에는 임의의 동작 알고리즘을 담는 메서드가 없다. 이름이 어떤 역할을 암시하더라도 이름만으로 새 동작을 구현했다고 해석하지 않는다.

Benefits and Costs

코드 종류를 줄이는 대신 데이터 연결을 관리한다

얻는 것

  • 같은 동작 구조에서 값이 다른 종류를 표현한다.
  • 공통 정의를 한곳에서 읽는다.
  • 종류 정의와 개체 상태의 책임이 분명해진다.

치르는 것

  • 필수 정의 참조와 유효한 값이 필요하다.
  • 공유 데이터 변경의 영향 범위를 관리한다.
  • 데이터와 개체를 함께 추적해야 한다.

Type Object는 C# 타입 검사를 없애는 방법이 아니다. UnitClass라는 코드 타입 안에서 여러 데이터 정의를 표현하는 선택이다.

When to Apply

차이가 값인가, 코드 동작인가?

판단할 상황선택의 근거
동작은 같고 이름·수치 조합이 자주 늘어남Type Object로 공유 정의를 분리할 만하다.
종류마다 서로 다른 알고리즘이 핵심상속·구성 등 동작을 표현하는 별도 설계를 검토한다.
종류가 하나이며 변화 요구도 작음현재의 단순한 필드 구조로 충분할 수 있다.
개체마다 바뀌는 임시 값개별 인스턴스에 둔다. 공유 정의와 섞지 않는다.

패턴을 먼저 고르기보다 어떤 변경이 반복되고, 무엇이 함께 바뀌어야 하는지 찾는다.

Visible Review Answers

이해 확인은 참조와 대입 위치로 답한다

질문답과 이유
같은 정의를 참조하면 CurrentHp도 같은가?아니다. 초기 값은 같을 수 있지만 각 Unit에 저장한다.
MaxHp는 어디에서 읽는가?UnitClass.MaxHp를 통해 공유 정의를 읽는다.
이름과 수치가 같은 에셋 둘은 하나인가?아니다. 값이 같아도 별도 정의 객체다.
데이터 추가로 임의의 새 행동이 생기는가?아니다. 그 데이터를 실행하는 코드가 필요하다.
공유 에셋은 읽기 전용 속성만 있으면 불변인가?아니다. 공유 데이터의 변경 정책을 따로 관리한다.

Prototype · 복제로 생성

기존 객체를 본보기로 새 객체를 만든다. 핵심 질문은 “무엇을 복제하고 무엇을 계속 참조하는가?”다.

개념 비교다. 복제본의 참조 필드까지 깊게 복제되는지는 복제 정책에 달려 있다. 같은 값으로 시작했다는 사실만으로 원본과 독립인지 판단할 수 없다.
