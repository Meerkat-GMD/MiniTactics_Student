미니 택틱스로 이해하는
Type Object 패턴

기사, 궁수, 마법사는 서로 다른 class여야 할까?
유닛의 “종류”를 class가 아니라 데이터로 만든다.

Starting Point

지금까지는 Unit이 자신의 능력치를 직접 가지고 있었다

[SerializeField, Min(0)] private int _moveBudget = 4;
[SerializeField, Min(1)] private int _maxHp = 10;
[SerializeField, Min(0)] private int _attackPower = 6;
[SerializeField, Min(0)] private int _defense = 1;

6차시 Unit.cs의 필드다. 읽기 편하게 네 줄만 옮겼다.

이 방식으로 충분했던 이유

모든 유닛을 같은 프리팹 하나로 만들었다. 프리팹에 적힌 값이 곧 모든 유닛의 값이므로 아군과 적의 능력치가 모두 같았다.

이 방식의 전제

유닛의 종류가 하나뿐이다. 값을 바꾸려면 프리팹 하나만 고치면 된다.

오늘은 이 전제가 맞지 않는 상황을 다룬다. 유닛의 종류가 여럿이고 앞으로 더 늘어날 수 있는 경우다.

New Requirement

병종이 생기면 유닛마다 능력치가 달라져야 한다

병종최대 HP공격력방어력이동력사거리
기사146331
궁수95142
마법사78031

병종마다 다른 것

숫자 다섯 개와 이름, 그림이다.

병종이 달라도 같은 것

피해를 받으면 HP가 줄고, 0이 되면 쓰러진다. 이동하고 공격하는 방법도 같다.

다른 것은 값이고, 같은 것은 동작이다. 이 구분이 오늘 내용 전체의 출발점이다.

First Attempt

첫 시도: 병종마다 class를 하나씩 만든다

public class Unit : MonoBehaviour
{
    public virtual int MaxHp => 10;
    public virtual int AttackRange => 1;
}

public class Knight : Unit
{
    public override int MaxHp => 14;
}

public class Archer : Unit
{
    public override int MaxHp => 9;
    public override int AttackRange => 2;
}

이 방법의 생각

“기사는 유닛의 한 종류다”라는 말을 상속으로 그대로 옮겼다. 객체지향을 배우면 가장 먼저 떠올리는 방법이다.

병종이 두세 개로 고정되어 있다면 이 방법으로도 동작한다.

설계 비교용 가상 코드다. 실제 프로젝트에는 이런 class가 없다.

Observe the Limit

첫 시도에서는 값 하나를 바꾸는 일이 코드 수정이 된다

새 요구첫 시도에서 해야 하는 일
기사의 HP를 14에서 16으로 조정한다.Knight.cs를 열어 숫자를 고치고 다시 컴파일한다. 프로그래머만 할 수 있다.
새 병종 “도적”을 추가한다.새 class 파일을 만들고, 그 class를 붙인 새 프리팹을 만들고, 생성하는 코드에 도적을 추가한다.
병종이 30개로 늘어난다.class 30개와 프리팹 30개가 생긴다. 그런데 class들의 내용은 숫자만 다르다.

class는 동작이 다를 때 나누는 도구다. 기사와 궁수는 동작이 같고 값만 다르다. 값의 차이를 표현하려고 class를 늘리고 있다.

enum과 switch로 바꾸어도 사정은 같다. 병종을 추가할 때마다 모든 switch에 case를 추가해야 한다.

Find the Boundary

병종마다 다른 값만 떼어 내어 별도의 객체로 만든다

첫 시도의 구조

Knight, Archer, Mage

종류 하나가 class 하나다. 종류를 추가하려면 코드를 작성해야 한다.

바꾼 구조

Unit + “병종 정보” 객체

Unit class는 하나다. 병종마다 다른 값은 병종 정보 객체가 가진다. Unit은 자신의 병종 정보를 참조한다.

“이 유닛은 기사다”를 “이 유닛은 Knight class의 객체다”로 표현하지 않는다. “이 유닛은 기사라는 병종 정보를 가리킨다”로 표현한다. 종류가 class에서 객체로 바뀌었다.

Type Object Pattern

이 구조의 이름이 Type Object 패턴이다

종류를 나타내는 객체를 따로 만들고, 각 개체가 자신의 종류 객체를 참조한다.

타입 객체(Type Object) · UnitClass병종 하나를 나타낸다. 그 병종의 모든 유닛이 공유하는 값을 가진다.
타입 객체의 실물 · 에셋 3개Knight, Archer, Mage 에셋이다. class는 UnitClass 하나이고 객체가 셋이다.
개체(Typed Object) · Unit전장에 있는 유닛 하나다. 현재 HP처럼 개체마다 다른 상태를 가진다.
연결 · Unit.UnitClass개체가 자신의 타입 객체를 가리키는 참조다. 개체는 공유 값을 이 참조를 통해 읽는다.

Type Object는 “타입 역할을 하는 객체”라는 뜻이다. C#의 class가 하던 “종류를 정의하는 일”을 우리가 만든 객체가 대신한다.

Actual Code · UnitClass.cs

타입 객체: UnitClass는 값과 읽기 전용 속성만 가진다

[CreateAssetMenu(menuName = "Mini Tactics/Unit Class")]
public sealed class UnitClass : ScriptableObject
{
    [SerializeField] private string _displayName;
    [SerializeField, Min(1)] private int _maxHp;
    [SerializeField, Min(1)] private int _attackRange = 1;
    [SerializeField] private Sprite _sprite;

    public string DisplayName => _displayName;
    public int MaxHp => _maxHp;
    public int AttackRange => _attackRange;
    public Sprite Sprite => _sprite;
}

읽는 방법

  1. 필드는 Inspector에서 입력하는 값이다.
  2. 속성은 =>로 값을 읽어 주기만 한다. 바깥에서 값을 바꿀 수 없다.
  3. 메서드가 없다. 이 class는 동작을 하지 않고 값을 보관한다.

축약한 발췌다. 실제 파일에는 같은 모양의 _attackPower, _defense, _moveBudget 필드와 속성이 더 있다.

ScriptableObject

ScriptableObject

개체: Unit은 능력치를 자신의 타입 객체에게 물어본다

바뀐 점

능력치 필드 네 개가 사라지고 UnitClass 참조 하나가 생겼다.

unit.MaxHp를 읽으면 Unit은 자신의 값을 돌려주지 않고 타입 객체의 값을 돌려준다.

속성의 이름은 6차시와 같다. 그래서 unit.MaxHp, unit.AttackPower를 읽던 체력바와 피해 계산 코드는 한 줄도 바뀌지 않는다.

Unit.cs의 속성 부분이다. 중간의 CanMove 한 줄을 생략했다.

Actual Code · Unit.cs

연결: Initialize가 유닛에게 타입 객체를 알려 준다

public void Initialize(Team team, UnitClass unitClass)
{
    Team = team;
    UnitClass = unitClass;
    CurrentHp = unitClass.MaxHp;
    SpriteRenderer renderer = GetComponent<SpriteRenderer>();
    renderer.sprite = unitClass.Sprite;
    renderer.color = team == Team.Player ? PlayerColor : EnemyColor;
}

실행 순서

  1. 전달받은 타입 객체를 기억한다.
  2. 현재 HP를 그 병종의 최대 HP로 채운다.
  3. 그림을 그 병종의 그림으로 바꾼다.

유닛은 만들어진 직후에는 종류가 없다. Initialize에 어떤 에셋을 넘기는가에 따라 기사가 되기도 하고 궁수가 되기도 한다. 종류가 실행 중에 정해진다.

Unit.cs의 Initialize 전체다.

Shared vs Own

공유하는 값은 타입 객체에, 개체마다 다른 값은 Unit에 둔다

값두는 곳이유
MaxHp, AttackPower, Defense, MoveBudget, AttackRange, SpriteUnitClass같은 병종이면 모두 같다. 한곳에 두면 한 번만 고쳐도 그 병종 전체에 반영된다.
CurrentHpUnit같은 기사라도 받은 피해가 다르다.
Team, HasMovedUnit같은 기사라도 아군일 수도 적일 수도 있고, 이번 턴에 행동했는지도 다르다.
위치Unit의 Transform유닛마다 서 있는 칸이 다르다.

판단하는 질문은 하나다. “같은 병종의 다른 유닛과 이 값이 달라질 수 있는가?” 달라질 수 있으면 Unit에 두고, 달라질 수 없으면 UnitClass에 둔다.

Think · Shared State

CurrentHp를 UnitClass에 두면 어떤 일이 일어나는가?

아군 기사 A와
적 기사 B가 있다.
A가 피해 5를 받으면
B의 HP는 얼마인가?

답을 순서대로 확인한다

  1. A와 B는 같은 Knight 에셋을 참조한다. 에셋은 하나다.
  2. CurrentHp가 에셋에 있다면 A가 받은 피해는 에셋의 값을 14에서 9로 바꾼다.
  3. B도 같은 에셋의 값을 읽으므로 B의 HP도 9가 된다. 맞지 않은 유닛의 HP가 줄었다.

현재 코드에서는 CurrentHp가 Unit에 있다. A는 14 − 5 = 9가 되고 B는 14 그대로다. 타입 객체에는 실행 중에 바뀌지 않는 값만 둔다.

질문은 CurrentHp를 잘못된 곳에 두었다고 가정한 것이다.

Trace the Numbers

추적: 같은 조건문이 병종에 따라 다른 결과를 낸다

출발 상태: 공격하는 유닛이 (2, 3)에 있다. 적 X는 (3, 3)에, 적 Y는 (4, 3)에 있다. 거리는 가로 차이와 세로 차이를 더한 값이다.

단계공격하는 유닛이 기사일 때공격하는 유닛이 궁수일 때
attacker.AttackRangeKnight 에셋의 값 1Archer 에셋의 값 2
적 X까지의 거리|3 − 2| + |3 − 3| = 11
적 X 판정1 ≥ 1 이고 1 ≤ 1 이므로 대상이다.1 ≥ 1 이고 1 ≤ 2 이므로 대상이다.
적 Y까지의 거리|4 − 2| + |3 − 3| = 22
적 Y 판정2 ≤ 1 이 아니므로 대상이 아니다.2 ≥ 1 이고 2 ≤ 2 이므로 대상이다.
공격 대상X 하나X와 Y 둘

Think · Live Edit

실행 중에 Knight 에셋의 MaxHp를 14에서 20으로 바꾸면?

전장에 기사가 둘 있다.
A는 HP 14 / 14,
B는 HP 9 / 14다.
체력바는 언제 바뀌는가?

답을 순서대로 확인한다

  1. A와 B의 MaxHp는 모두 즉시 20이 된다. 둘 다 같은 에셋의 값을 읽기 때문이다.
  2. CurrentHp는 Unit에 있으므로 14와 9 그대로다.
  3. 체력바는 바로 바뀌지 않는다. 체력바는 HpChanged 알림을 받았을 때만 다시 계산한다.
  4. B가 피해 2를 받으면 그때 7 / 20 = 0.35로 계산되어 35%가 된다.

에디터에서 실행 중에 바꾼 ScriptableObject 에셋의 값은 Play를 끝내도 되돌아가지 않는다. 씬의 오브젝트와 다른 점이다.

Flyweight vs Type Object

3차시의 Flyweight와 모양이 비슷하지만 목적이 다르다

Flyweight · “같은 데이터를 몇 번 저장하는가”

수많은 칸이 같은 지형 정보를 각자 복사해서 가지는 낭비를 없앤다. 목적은 중복 제거다.

칸 120개가 TerrainType 객체 4개를 공유한다.

Type Object · “종류를 어디에 정의하는가”

종류를 class로 정의하지 않고 객체로 정의한다. 목적은 코드를 고치지 않고 종류를 추가하고 조정하는 것이다.

유닛들이 UnitClass 에셋 3개를 참조한다.

두 패턴 모두 여러 개체가 하나의 객체를 공유한다. 그래서 한 구조가 두 패턴의 이득을 함께 얻는 경우가 많다. 기사가 100명이어도 기사의 능력치는 메모리에 한 번만 저장된다.

Cost

Type Object에는 대가가 있다

대가구체적인 모습대응
값은 바꿀 수 있지만 동작은 바꿀 수 없다.“마법사의 공격은 방어력을 무시한다”는 숫자 하나로 표현할 수 없다. 데이터에는 if문을 적을 수 없기 때문이다.동작의 차이가 필요해지면 다른 구조를 함께 사용한다.
연결을 빠뜨려도 컴파일러가 알려 주지 않는다.배치 목록에서 병종 칸을 비워 두면 실행 중에 placement.UnitClass.DisplayName에서 NullReferenceException이 발생한다.에셋을 만든 뒤 Inspector의 연결을 확인한다.
값을 찾으려면 한 단계를 더 거친다.unit.MaxHp의 실제 값은 Unit.cs에 없다. 그 유닛이 참조하는 에셋을 열어야 알 수 있다.속성 이름을 에셋의 필드 이름과 같게 유지한다.

class 상속에서는 컴파일러가 검사해 주던 것을 이제는 사람이 확인해야 한다. 유연함을 얻은 만큼 검사를 잃었다.

Judgment

적용 기준: 종류마다 다른 것이 값인가, 동작인가?

Type Object가 이득인 경우

종류가 많거나 앞으로 늘어난다. 종류 사이의 차이가 대부분 값이다. 프로그래머가 아닌 사람이 값을 조정해야 한다.

예: 병종, 아이템, 몬스터, 지형.

class로 나누는 편이 나은 경우

종류가 두세 개로 고정되어 있다. 종류마다 실행되는 코드 자체가 다르다.

예: 4차시의 IdleState와 UnitSelectedState. 두 상태는 같은 클릭에 서로 다른 코드를 실행한다.

4차시의 상태들을 데이터로 바꾸지 않는 이유가 여기에 있다. 상태마다 다른 것은 값이 아니고 동작이다. 패턴은 실제로 해결할 문제가 있을 때에만 도입한다.

Check Yourself

이해 확인: 답을 먼저 예측한 뒤에 확인한다

질문 1

전장에 기사 2명, 궁수 3명, 마법사 1명이 있다. Unit 객체와 UnitClass 객체는 각각 몇 개인가?

답: Unit은 2 + 3 + 1 = 6개이고 UnitClass는 3개다. 유닛이 60명으로 늘어나도 병종이 그대로라면 UnitClass는 3개다.

질문 2

“이동하면 이번 턴의 이동력이 줄어든다”는 규칙을 추가하려고 한다. 남은 이동력은 어디에 두어야 하는가?

답: Unit이다. 같은 기사라도 이미 이동한 기사와 아직 이동하지 않은 기사의 값이 다르다. UnitClass에 두면 기사 하나가 이동했을 때 모든 기사의 이동력이 줄어든다.

두 질문 모두 12장의 기준으로 풀 수 있다. “같은 병종의 다른 유닛과 이 값이 달라질 수 있는가?”

Theory Corner · Prototype

이론 코너: Instantiate(prefab)은 Prototype 패턴이다

Unit unit = Instantiate(_unitPrefab, transform);

UnitSpawner.Spawn의 실제 코드다.

Prototype 패턴

새 객체를 new로 처음부터 조립하지 않고, 미리 만들어 둔 원본을 복제해서 만든다. 원본을 프로토타입이라고 부른다.

Unity의 프리팹

프리팹이 프로토타입이다. Instantiate는 프리팹에 붙어 있는 컴포넌트, 자식 오브젝트, Inspector 값을 모두 복제한다. 체력바가 유닛마다 따라오는 이유다.

오늘의 유닛은 두 패턴으로 만들어진다. 프리팹을 복제하여 모든 유닛에 공통인 구조를 얻고(Prototype), 타입 객체를 넘겨받아 병종을 얻는다(Type Object).

Takeaway

종류가 값으로만 구분된다면, 종류를 객체로 만든다

  1. 병종마다 다른 값은 UnitClass에, 개체마다 다른 상태는 Unit에 둔다.
  2. Unit은 자신의 타입 객체를 참조하고, 능력치를 물으면 타입 객체의 값을 돌려준다.
  3. 사용하는 쪽은 병종을 확인하지 않고 attacker.AttackRange처럼 값을 읽는다.
  4. 새 종류를 추가하거나 값을 조정할 때 코드를 고치지 않는다. 에셋을 만들거나 고친다.
  5. 대가는 데이터로 표현할 수 없는 동작, 컴파일러가 검사하지 않는 연결, 한 단계 멀어진 값이다.
