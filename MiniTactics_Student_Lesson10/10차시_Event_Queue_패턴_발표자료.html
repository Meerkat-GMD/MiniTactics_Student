Mini Tactics · Lesson 10

미니 택틱스로 이해하는
Event Queue 패턴

발생한 일을 기록해 두고,
소비자가 정한 시점에 순서대로 처리한다.

Starting point

직접 호출은 지금 처리할 때 단순하다

void Report(string message)
{
    display.Show(message);
    history.Add(message);
}

설계 비교용 가상 코드 · 호출한 순간 두 작업을 직접 처리한다고 가정한 첫 시도다.

호출 흐름 안에서 표시와 기록을 끝낸다. 결과가 지금 필요하고 작업이 짧다면 읽기 쉬운 방식이다.

New requirement

발생 속도와 처리 속도를 나누고 싶다

짧은 순간에 여러 일이 발생했다.
각 사실을 잃지 않고,
처리하는 쪽이 순서와 시간을 관리할 수 있을까?

무엇이 발생했는지 기록하는 일과, 그것을 지금 처리하는 일을 분리해야 한다.

First attempt

첫 시도는 발생한 곳에서 작업을 끝낸다

void Changed(int before, int after)
{
    display.Show(after);
    display.ShowDifference(after - before);
}

설계 비교용 가상 코드 · 변경을 알린 호출 흐름에서 즉시 표시한다고 가정한 코드다.

장점

어디서 어떤 처리가 일어나는지 따라가기 쉽다.

새 요구와 만나는 지점

여러 변경을 시간을 두고 처리하려면 호출자도 표시 작업의 진행을 알아야 한다.

Observe the limit

즉시 통지도 처리 시점을 함께 묶을 수 있다

상태 변경
→
알림 발생
→
수신자 처리
→
호출자 계속 진행

누가 받는가

Observer는 구독자를 등록해 수신자를 나눌 수 있다.

언제 받는가

일반적인 즉시 이벤트는 같은 호출 흐름에서 구독자의 코드를 실행한다.

수신자를 몰라도 처리 시점은 묶여 있을 수 있다. 시간 분리에는 별도의 보관 지점이 필요하다.

Find the boundary

발생 기록과 처리 시점을 나눈다

생산자의 책임

무슨 일이 생겼는지 필요한 값을 기록해서 보낸다.

받는 쪽의 작업이 끝날 때까지 기다릴 필요가 줄어든다.

소비자의 책임

기록을 꺼낼 시점과 처리 방법을 정한다.

처리 중에도 새 기록은 큐의 뒤에 쌓일 수 있다.

전송을 마쳤다는 사실과 처리를 마쳤다는 사실은 다르다.

Event Queue

큐가 아직 처리하지 않은 기록을 보관한다

생산자 · Unit 등발생 시점의 값을 기록하고 큐에 넣는다.
데이터 · PresentationEvent종류·대상·위치·변경 전후 값을 보관한다.
큐 · Queue아직 처리하지 않은 항목을 순서대로 보관한다.
소비자 · PresentationQueue앞에서 하나씩 꺼내 처리를 끝낸다.

역할은 네 개여도 class가 반드시 네 개여야 하는 것은 아니다. 이 구현에서는 큐의 보관과 소비를 한 컴포넌트가 맡는다.

FIFO

먼저 넣은 항목을 먼저 꺼낸다

앞 · A가 먼저 들어왔다
B
뒤 · C가 나중에 들어왔다
private readonly Queue<PresentationEvent> _events = new Queue<PresentationEvent>();

A, B, C 순서로 넣었다면 꺼내는 순서도 A, B, C다. 이것이 FIFO다. 최근 항목부터 꺼내는 Stack과 구분한다.

위치와 HP는 처리 시점에 이미 달라졌을 수 있다. 발생 당시의 값을 기록한 스냅샷을 사용한다. 스냅샷은 어떤 시점의 상태를 복사해 둔 데이터다.

Actual code · Snapshot

생성할 때 현재 값을 이벤트 데이터에 복사한다

Actual code · Producer

규칙 값은 지금 바뀌고 기록은 큐로 간다

int before = CurrentHp;
CurrentHp = Mathf.Max(0, CurrentHp - damage);
bool queued = before != CurrentHp && TryPresent(PresentationEvent.HealthChanged(this, before, CurrentHp));
HpChanged?.Invoke(this);

CurrentHp는 즉시 바뀐다. BeforeHp와 AfterHp를 가진 기록을 보낸 뒤 알림을 발행한다. 규칙 상태와 표시의 진행 상태를 별도로 다룬다.

Actual code · Enqueue

첫 전송이 소비자를 한 번 시작한다

_events.Enqueue(item);
if (!IsBusy)
{
    IsBusy = true;
    _cancellation = CancellationTokenSource.CreateLinkedTokenSource(destroyCancellationToken);
    ConsumeAsync(_cancellation.Token).Forget();
}

처리 중이면 뒤에 넣기만 한다. 아직 처리 중이 아니면 IsBusy를 먼저 true로 바꾸고 소비를 시작한다. 같은 큐를 동시에 여러 소비자가 처리하지 않게 하는 경계다.

Actual code · Dequeue

현재 항목이 끝난 뒤 다음 항목을 꺼낸다

await UniTask.Yield(token);
while (_events.Count > 0)
    await PlayAsync(_events.Dequeue(), token);
ResetUnits();
IsBusy = false;
_cancellation.Dispose();
_cancellation = null;

while은 대기 중인 항목이 있는 동안 반복한다. PlayAsync가 끝날 때까지 다음 항목을 꺼내지 않는다. 큐가 처리 스레드를 자동으로 만드는 것은 아니다.

Pending and running

대기열이 비어도 처리는 끝나지 않았을 수 있다

상태큐 안의 항목IsBusy
처음Atrue
A를 꺼내 처리 중없음true
A의 처리까지 완료없음false

Dequeue는 항목을 목록에서 꺼낸다. 그 항목을 처리하는 시간은 그 뒤에 남아 있다. Count가 0이라는 사실만으로 전체 완료를 판단하면 이 시간을 놓친다.

Trace · FIFO

전송과 처리를 번갈아 따라간다

순서작업큐의 앞에서 뒤처리한 항목
0빈 큐로 시작없음없음
1A 전송A없음
2B 전송A, B없음
3한 항목 처리BA
4C 전송B, CA
5한 항목 처리CA, B

이 표는 한 항목을 처리할 때마다 멈춰 본 상태다. 현재 구현은 앞 항목의 처리가 끝나면 남은 항목을 계속 소비한다.

Trace · Values

현재 값 하나로는 중간 변화가 사라진다

출발 HP는 12다. 같은 호출 흐름에서 5 감소, 3 감소, 5 증가가 차례로 발생했다고 가정한다.

발생한 변경기록한 Before / After나중에 표시할 값
12에서 5 감소12 / 7HP 7, 변화 −5
7에서 3 감소7 / 4HP 4, 변화 −3
4에서 5 증가4 / 9HP 9, 변화 +5

규칙 HP는 이미 9여도 첫 기록은 7을 표시해야 한다. 모든 기록에서 현재 HP 9를 읽으면 중간 값 7과 4를 잃는다.

Actual code · Consumer

소비자는 기록된 전후 값으로 계산한다

item.Actor.GetComponentInChildren<UnitHealthBar>(true).Show(item.AfterHp, item.MaxHp);
int change = item.AfterHp - item.BeforeHp;

item.AfterHp가 표시할 값이고 AfterHp − BeforeHp가 실제 변화량이다. 최대 HP에서 회복이 잘렸다면 잘린 뒤의 실제 차이를 표시한다.

Values and references

복사한 값과 보관한 참조를 구분한다

값을 복사한 기록

BeforeHp, AfterHp, From, To는 그 시점의 값이다. 원래 객체가 나중에 달라져도 기록의 값은 변하지 않는다.

객체를 찾는 참조

Actor는 표시할 객체를 찾는 참조다. readonly 기록 안에 있어도 대상 객체 자체가 불변이 되는 것은 아니다.

참조 대상이 먼저 사라지면 늦은 처리가 실패할 수 있다. 기록의 내용과 대상 객체의 수명을 함께 설계한다.

취소는 남은 처리를 버리는 결정이다

진행 중인 처리를 취소하고 대기 항목을 비운다. ResetUnits는 표시를 현재 규칙 상태와 맞춘다. 이전 HP나 위치로 되돌리는 Undo가 아니다.

Observer and queue

수신자 분리와 시간 분리를 비교한다

방식누가 처리하는가언제 처리하는가
직접 호출호출자가 참조한 대상호출 흐름 안
즉시 Observer등록한 구독자일반적으로 알림을 발행한 흐름 안
Event Queue큐의 소비자소비자가 꺼내는 시점

세 방식은 함께 사용할 수 있다. 현재 규칙의 즉시 알림과 나중에 처리할 기록은 맡은 시간이 다르다.

Event and command

같은 큐에도 데이터의 의미는 다를 수 있다

이벤트 기록

이미 생긴 변경이나 처리할 알림을 전달한다. 여기서는 규칙이 바뀐 결과를 화면에 표현한다.

명령 요청

무언가를 실행하라고 요청한다. 실행을 거부하거나 실패했을 때의 의미를 따로 정해야 한다.

둘 다 큐에 넣을 수 있지만 큐라는 자료구조만으로 기록의 의미가 정해지지는 않는다.

Costs

지연과 적체, 수명 관리가 비용이다

비용생기는 이유
처리 지연전송 뒤에 기다리는 시간이 있다.
큐 적체생산량이 처리량보다 많으면 항목이 쌓인다.
데이터 수명참조 대상과 값이 처리할 때 달라질 수 있다.
추적의 어려움발생 위치와 처리 위치·시간이 나뉜다.

순서를 지켰다고 충분하지 않다. 얼마나 늦어져도 괜찮은지, 언제 비울지까지 정해야 한다.

Judgment · Check

지금 결과가 필요한 호출인지 먼저 판단한다

질문

지금 행동 가능한지 bool을 받아 바로 분기해야 한다. 큐가 단순해질까?

답: 보통 직접 반환이 더 단순하다. 큐를 쓰면 답을 기다리는 흐름까지 만들어야 한다.

반대로 이득인 경우

발생한 여러 일을 순서대로, 소비자의 처리 시간에 맞춰 전달해야 한다. 생산자는 처리 완료를 즉시 알 필요가 없다.

Takeaway

기록할 사실과 처리할 시간을 함께 정한다

  1. 생산자는 필요한 발생 당시 값을 기록한다.
  2. 큐는 대기 항목을 FIFO로 보관한다.
  3. 소비자는 현재 처리를 끝낸 뒤 다음 항목을 꺼낸다.
  4. 지연·적체·참조 수명·취소의 의미를 정한다.

시간을 나누었을 때에도 기록의 뜻이 유지되어야 한다.
