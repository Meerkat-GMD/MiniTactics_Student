Chapter 01

즉시 피드백과 과거 값의 소실

현재 값을 보여 주는 일과 여러 변화의 과정을 보여 주는 일은 다르다. 동기 알림은 즉시 갱신에 유용하지만, 스스로 시간을 저장하거나 이전 값을 복원하지 않는다. 아래의 가상 첫 시도는 현재 Teacher 구현의 결함을 인용한 것이 아니다.

즉시 알림은 현재 상태를 빠르게 전달한다

간단한 피드백

값 하나가 바뀔 때 화면 하나를 즉시 갱신한다면 직접 호출이나 동기 알림으로 충분하다.

연속 변화

같은 대상의 HP가 짧은 순간에 10 → 7 → 8로 바뀐다. 화면에서는 −3 다음 +1의 과정을 읽고 싶다.

동기 알림은 호출 중에 처리한다는 뜻이다. 알림을 보냈다는 사실만으로 표현 시간이 따로 확보되지는 않는다.

값 변경 직후 화면을 직접 부르면?

설계 비교용 가상 코드 · 현재 Teacher에 없는 첫 시도

hp = 7;
ShowHp(hp);
ShowNumber(-3);
hp = 8;
ShowHp(hp);
ShowNumber(+1);

한 번만 바뀌면 단순하다. 연속 호출이면 뒤 갱신이 앞 표현을 덮거나 여러 표현이 겹칠 수 있다. 호출 순서만으로 각 표현이 기다릴 시간까지 정해지지는 않는다.

나중에 현재 HP만 읽는 것도 충분하지 않다

// 나중에 표현할 때
ShowHp(pendingUnit.CurrentHp);

어느 Unit인지는 기억한다. 하지만 나중에 읽는 CurrentHp는 이미 8일 수 있다.

Chapter 02

이벤트·저장소·소비자의 책임

이벤트는 이미 일어난 사실을 전달한다. 이 자료의 이벤트는 표현을 위한 기록이며 게임 규칙을 다시 실행할 명령이 아니다. 생산자는 모델 변경을 끝내고, 소비자는 당시 기록으로 화면을 차례대로 갱신한다.

변경 사실과 표현 작업의 시간을 나눈다

생산자
규칙 즉시 변경
→
이벤트
당시 값 보관
→
FIFO 큐
순서 보관
→
소비자
하나씩 표현

생산자(producer)는 기록을 넣는 쪽, 소비자(consumer)는 꺼내 처리하는 쪽이다. 규칙을 계산하는 책임과 화면의 재생 순서를 관리하는 책임이 달라진다.

Event Queue는 사실의 전달과 처리를 분리한다

먼저 발생한 사실을 저장하고,
소비자가 나중에 순서대로 처리한다.

Event · 일어났다

“HP가 10에서 7로 바뀌었다.” 표현에 필요한 당시 값을 가진 기록이다.

Queue · 보관 순서

First In, First Out = FIFO. 먼저 넣은 기록을 먼저 꺼낸다. 이벤트 자체가 규칙을 다시 실행하지 않는다.

현재 클래스가 맡은 역할

역할현재 이름맡은 일
생산자Unit / 작업 호출부모델을 바꾸고 PresentationEvent 생성
값 기록PresentationEvent종류·대상·위치·HP·표현 정보 보관
저장소PresentationQueue의 _eventsQueue<PresentationEvent>에 FIFO 보관
단일 소비자ConsumeAsync → PlayAsync하나씩 꺼내 정해진 대기와 표현 수행

PresentationQueue 안에 저장소와 소비자가 함께 있다. 역할을 구분한다고 반드시 클래스 수를 늘려야 하는 것은 아니다.

Chapter 03

복사하는 값과 공유하는 참조

스냅샷은 필요한 당시 값을 남긴다는 뜻이다. 이 구현은 모든 객체의 깊은 복사본을 만드는 방식이 아니다. 좌표·정수·시간은 값으로 잡고 Unit 정체성과 전투 중 바꾸지 않는 프레임 에셋은 공유한다. readonly의 범위를 참조 대상까지 확대해서 읽지 않는다.

Chapter 04

생성 시점과 모델의 즉시 변경

기록을 만들 때 어떤 값을 넘겼는지가 이후 표현의 정확도를 결정한다. 위치를 먼저 잃어버리거나 HP의 전 값을 덮어쓴 뒤 현재 값만 넘기면 과정을 재생하기 어렵다. 현재 생산자는 필요한 이전 값을 지역 변수로 보관한다.

이동·행동 기록의 생성 지점

public static PresentationEvent Moved(Unit unit, Vector3 from, Vector3 to) =>
    new PresentationEvent(EventKind.Move, unit, from, to);

public static PresentationEvent Acted(Unit actor, Unit target, bool skill) =>
    new PresentationEvent(skill ? EventKind.Skill : EventKind.Attack, actor,
        actor.transform.position, actor.transform.position, target, target.transform.position);

Chapter 05

FIFO 보관과 단일 소비자

Enqueue는 뒤에 더하고 Dequeue는 앞에서 꺼낸다. 하지만 꺼낸 순간에 그 항목의 처리가 완료되는 것은 아니다. 저장소의 길이와 소비자의 활동 상태를 구분해야 마지막 항목을 기다리는 동안의 상태를 설명할 수 있다.

Enqueue는 뒤에, Dequeue는 앞에서

private readonly Queue<PresentationEvent> _events = new Queue<PresentationEvent>();

이미 IsBusy라면 새 이벤트를 넣어도 다른 소비자를 만들지 않는다. 한 소비자가 앞선 항목의 재생과 대기를 마친 뒤 다음 항목으로 간다. 이때 IsBusy는 큐 Count와 다른 상태다.

ResetUnits();
_cancellation.Dispose();
_cancellation = null;
IsBusy = false;

Chapter 06

저장된 값으로 표현하기

소비자는 기록된 Kind로 표현을 고르고, 저장된 좌표와 HP를 사용한다. 이때 피해나 회복 규칙을 다시 실행하지 않는다. 모든 표현 객체가 동일한 수명을 갖는 것은 아니므로 대기 규칙은 별도로 읽어야 한다.

저장된 종류와 위치로 표현을 고른다

switch (item.Kind)
{
    case PresentationEvent.EventKind.Move: animator.PlayMove(item.From, item.To); break;
    case PresentationEvent.EventKind.Attack: animator.PlayAttack(item.From, item.TargetPosition); break;
    case PresentationEvent.EventKind.Skill: animator.PlaySkill(item.From, item.TargetPosition); break;
    default: await PlayHealthAsync(item, animator, token); return;

HP 바는 item.AfterHp / item.MaxHp를 사용한다. 변화량이 음수면 피격 표현, 양수면 회복 숫자다. 입력 인수가 아닌 실제 차이의 절댓값을 표시한다. 생산자에서 변화 없는 회복은 생략한다.

Chapter 07

두 변화와 실제 변화량의 추적

다음 수치 예는 특정 장면의 공략이나 구현 문제가 아니다. 연속 생산이 끝난 순간의 모델과, 그 뒤 소비자가 보여 주는 중간 값을 구분하기 위한 추적이다. 표의 큐 항목 이름은 설명용이며 공개 디버그 API가 아니다.

A 재생이미 8바 7 / 숫자 −3
B 재생8바 8 / 숫자 +1

설명용 수치 추적이다. 소비자는 Unit.CurrentHp를 읽어 두 번 모두 8을 보여 주지 않는다. A와 B가 보관한 값으로 중간 상태를 재생한다.

상한에 걸린 회복은 요청량과 다르다

출발 조건

최대 HP 10, 현재 HP 9에서 회복량 4를 요청한다. 실제 모델은 10으로 제한된다.

답과 계산

BeforeHp 9, AfterHp 10이므로 변화량은 +1이다. 이미 10이면 생산자가 기록을 만들지 않아 +0도 생략한다.

Queue가 모든 0 변화 항목을 필터링하는 것은 아니다. Heal의 동등값 반환과 TakeDamage의 유효 입력 조건처럼 생산자 경계가 함께 계약을 만든다.

대기 0개여도 마지막 항목은 재생 중일 수 있다

상태내부 CountIsBusy
한 항목을 받아 소비자 시작1true
마지막 항목을 꺼내 재생·대기 중0true
반복 종료와 표현 정리 완료0false

질문 → 답: Count == 0이면 바로 다음 외부 행동을 허용할까? 아니다. 현재 항목의 대기까지 포함하는 IsBusy가 필요하다. Count는 공개 Queue API가 아닌 내부 저장소 상태다.

Chapter 08

모델·대기·효과 수명

규칙 실행과 표현에는 서로 다른 시계가 있다. 모델 값과 결과는 즉시 바뀌어도 화면은 정해진 대기를 따라간다. 또한 다음 항목으로 넘어가는 시간과 개별 숫자가 사라지는 시간이 다르므로 이전 숫자가 잠시 남는 현상은 FIFO 위반이 아니다.

모델의 결과와 표현이 끝나는 시점

모델 시간

HP·논리 위치·승패 값은 규칙 실행 중 바뀐다. 이벤트 소비자가 같은 피해나 회복을 다시 적용하지 않는다.

표현 시간

화면은 기록 순서대로 갱신된다. 결과 표시도 모델 결과와 큐의 바쁨을 함께 보아 기다릴 수 있다.

모델에서 이미 끝난 결과를 화면에 늦게 드러내는 것이다. enqueue 자체가 규칙 실행을 비동기로 만들거나 트랜잭션·되돌리기를 제공하지는 않는다.

FIFO의 대기 종료와 모든 숫자의 소멸은 다르다

현재 시간값의미
Health의 Seconds = 0.35초다음 항목으로 넘어가기 위한 기본 대기
DamageNumber의 독립 수명 = 0.7초자기 Update로 떠오르고 사라짐
AfterHp가 0 이하인 Health추가로 DeathSeconds만큼 사망 프레임 대기

따라서 이전 숫자와 다음 숫자가 겹칠 수 있고, IsBusy가 false여도 마지막 숫자가 남을 수 있다. FIFO는 규정된 재생·대기의 순서이며 모든 효과 객체의 소멸을 기다린다는 약속은 아니다.

Chapter 09

취소와 필수 협력자의 수명

지연 처리는 대상이 계속 유효하다는 가정만으로 끝낼 수 없다. 현재 큐는 비활성화 때 취소하며, 취소가 정리를 소유한다. 예전 대기가 취소된 뒤 새 소비자가 시작되더라도 예전 소비자는 새 상태를 완료 처리하지 않아야 한다.

취소는 대기·큐·임시 표현을 정리한다

_cancellation?.Cancel();
_cancellation?.Dispose();
_cancellation = null;
_events.Clear();
ResetUnits();

Cancel은 토큰을 취소하고 대기 항목을 비운 뒤 자동 표현을 복구한다. 남은 효과도 소유 루트에서 제거하고 IsBusy를 false로 만든다. 이미 바뀐 모델 HP나 위치를 과거로 되돌리는 작업은 아니다.

이전 소비자가 새 소비자를 완료시키면 안 된다

Chapter 10

이득·비용·적용 판단

판단의 출발점은 중간 상태와 표현 순서를 따로 관리할 필요가 있는가다. 그 필요가 없다면 더 간단한 호출 구조도 합리적이다. 큐를 넣는 것은 할당 제거, 속도 향상, 영구 기록이나 분산 전달을 자동으로 해결하는 선택이 아니다.

시간을 분리할 이유와 그 비용

유용할 때

연속 상태 변화의 중간 과정을 읽어야 하거나, 여러 생산자의 표현 순서를 한곳에서 제어해야 한다.

유지할 비용

기록 데이터, 대기 지연, 큐 적체, 대상 수명, 취소와 단일 소비자 소유권을 관리한다. 단순한 즉시 갱신은 직접 호출로 충분할 수 있다.

현재 구현은 숫자를 생성하고 토큰·저장 공간도 사용한다. 무할당이나 FPS 향상은 보장하지 않는다. 네트워크 전달·영구 이벤트 저장·전체 상태 재구성도 이 큐의 기능이 아니다.
