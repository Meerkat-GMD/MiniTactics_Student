CHAPTER 01

즉시 처리에서 시간 분리로

학습 목표: 직접 호출·즉시 알림이 충분한 경우와 큐가 필요한 경우를 구분한다.

직접 호출은 지금 일을 끝내는 약속이다

한 객체가 다른 객체의 메서드를 호출하면 보통 그 메서드가 끝난 다음 자기 일을 계속한다. 호출한 쪽은 상대가 지금 처리할 수 있다고 기대한다. 간단한 작업에서는 이해하기 쉽고, 결과를 즉시 받아야 할 때 특히 자연스럽다.

Observer의 즉시 통지도 비슷한 시간 관계를 가진다. 발행자가 구독자를 직접 알지 않아도 이벤트를 발생시킨 호출 흐름 안에서 구독자의 코드가 실행될 수 있다. 누구에게 전달하는가를 느슨하게 만드는 것과 언제 처리하는가를 나누는 것은 서로 다른 결정이다.

보낸 시간과 처리한 시간

Event Queue는 전송과 처리 사이에 보관 장소를 둔다. 생산자는 발생한 사실을 데이터로 만들어 큐에 넣는다. 소비자는 자신이 정한 시점에 큐에서 데이터를 꺼내 처리한다. 생산자가 전송을 마쳤다는 사실은 소비자의 처리까지 끝났다는 뜻이 아니다.

시간을 나누는 경계생산자는 무엇이 발생했는지 기록한다. 큐는 아직 처리하지 않은 항목을 순서대로 보관한다. 소비자는 언제 꺼내서 어떻게 처리할지 정한다.

큐가 기억하는 순서

Queue는 줄을 선 순서대로 꺼내는 자료구조다. A, B, C 순서로 넣었다면 앞에서 꺼내는 순서도 A, B, C다. 이를 FIFO, 즉 먼저 들어간 것이 먼저 나온다고 부른다. 마지막 입력부터 되돌릴 때 사용하는 Stack의 LIFO와 구분한다.

FIFO는 순서만 정한다. 한 번에 하나를 처리할지, 쌓인 항목을 모두 처리할지, 일정 개수까지만 처리할지는 소비자의 규칙이다. 큐를 사용했다고 자동으로 한 프레임에 하나씩 처리되거나 별도 스레드가 실행되지는 않는다. 실제 처리 시점은 소비 코드를 읽어 확인한다.

void Report(string message)
{
    display.Show(message);
    history.Add(message);
}

설계 비교용 가상 코드 · 호출한 순간 두 작업을 직접 처리한다고 가정한 첫 시도다.

이 비교의 핵심은 표시 기능의 구체적인 내용이 아니다. 생산자가 Report를 호출한 흐름 안에서 모든 수신 작업을 끝내는 구조인지, 기록을 보관하고 다른 시점에 소비하는 구조인지다.

CHAPTER 02

네 역할과 FIFO

학습 목표: 생산자·기록·큐·소비자의 책임을 실제 타입에 대응한다.

발생을 기록하는 쪽과 처리하는 쪽

생산자는 이벤트를 만들고 보낸다. 이 구현에서는 Unit 등 실제 상태를 바꾸는 코드가 필요한 순간의 값을 기록한다. PresentationEvent는 그 기록의 형식이다. Queue<PresentationEvent>는 아직 처리하지 않은 항목을 보관한다. PresentationQueue는 보관한 항목을 꺼내 소비하는 역할도 맡는다.

네 역할이 항상 네 class인 것은 아니다. 설계에서 역할을 구분하는 이유는 파일 수를 늘리기 위해서가 아니라, 변경이 생겼을 때 어디를 읽고 고칠지 알기 위해서다. 여기서는 큐의 보관과 소비를 한 컴포넌트가 관리한다.

private readonly Queue<PresentationEvent> _events = new Queue<PresentationEvent>();

FIFO의 의미

먼저 들어간 항목을 먼저 꺼내는 것을 FIFO라고 한다. Enqueue는 뒤에 추가하고 Dequeue는 앞에서 꺼낸다. A 뒤에 B를 넣었다면 A를 먼저 꺼낸다. Undo에서 최근 행동부터 되돌릴 때 사용했던 Stack의 순서와 반대다.

순서작업큐의 앞에서 뒤처리한 항목
0빈 큐로 시작없음없음
1A 전송A없음
2B 전송A, B없음
3한 항목 처리BA
4C 전송B, CA
5한 항목 처리CA, B

표는 한 번의 소비가 끝날 때마다 상태를 적은 예다. 실제 소비자는 앞 항목의 처리가 끝나면 남은 항목을 계속 처리한다. FIFO가 정하는 것은 꺼내는 순서이고, 하나의 처리가 얼마나 오래 걸리는지는 소비 작업이 정한다.

CHAPTER 03

발생 당시 값의 스냅샷

학습 목표: 나중에 현재 값을 다시 읽는 것과 발생 시점의 값을 복사하는 차이를 설명한다.

값을 지금 보존해야 하는 이유

전송과 처리 사이에 시간이 생기면 원래 객체의 값은 이미 달라질 수 있다. 같은 객체가 여러 번 변경된 뒤 첫 기록을 처리한다면 현재 값 하나로는 각 변경의 결과를 구분할 수 없다. 발생 당시 값의 복사본을 스냅샷이라고 부른다.

public Unit Actor { get; }
public Unit Target { get; }
public Vector3 From { get; }
public Vector3 To { get; }
public Vector3 TargetPosition { get; }
public int BeforeHp { get; }
public int AfterHp { get; }
public int MaxHp { get; }

Kind는 어떤 종류인지, Actor는 표시할 주체를 찾는 참조다. From·To·TargetPosition은 위치 값이다. BeforeHp·AfterHp·MaxHp는 이번 변경을 표현하기 위한 값이다. Target도 객체를 찾는 참조이지만 표시 방향을 위해 과거 위치가 필요하므로 TargetPosition을 별도로 복사한다.

CHAPTER 04

전송과 한 소비자의 처리

학습 목표: 등록·소비·완료의 경계를 실제 코드로 읽는다.

규칙 상태는 즉시 바뀐다

int before = CurrentHp;
CurrentHp = Mathf.Max(0, CurrentHp - damage);
bool queued = before != CurrentHp && TryPresent(PresentationEvent.HealthChanged(this, before, CurrentHp));
HpChanged?.Invoke(this);

실제 코드 · Unit.cs 28–31행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

이 코드에서 CurrentHp 대입은 큐의 소비를 기다리지 않는다. before에 이전 값을 보관하고 새 값을 기록한 뒤 전후 값을 가진 이벤트를 보낸다. 효과가 이미 규칙 상태에 반영되었고, 표시가 이를 뒤따르는 구조다.

첫 전송만 소비를 시작한다

_events.Enqueue(item);
if (!IsBusy)
{
    IsBusy = true;
    _cancellation = CancellationTokenSource.CreateLinkedTokenSource(destroyCancellationToken);
    ConsumeAsync(_cancellation.Token).Forget();
}
return true;

실제 코드 · PresentationQueue.cs 23–30행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

항목을 넣은 뒤 IsBusy를 확인한다. 이미 처리 중이면 새 소비자를 만들지 않는다. 처음이면 IsBusy를 먼저 true로 만들고 소비를 시작한다. 같은 순간 다음 생산자가 기록을 추가해도 그 기록은 같은 FIFO의 뒤에 들어간다.

앞 항목의 처리가 끝날 때까지 기다린다

await UniTask.Yield(token);
while (_events.Count > 0)
    await PlayAsync(_events.Dequeue(), token);
ResetUnits();
IsBusy = false;
_cancellation.Dispose();
_cancellation = null;

실제 코드 · PresentationQueue.cs 37–43행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

중요한 순서는 Dequeue로 앞 항목을 꺼내고, PlayAsync의 처리가 끝난 다음 반복문이 다음 항목을 꺼낸다는 점이다. 처리를 기다리는 동안 다른 생산자가 뒤에 새 항목을 넣을 수 있다. 그 항목도 순서가 오면 같은 소비자가 처리한다.

초기 양보 지점은 생산자의 현재 규칙 처리를 마치고 표시를 시작할 수 있게 한다. 여기서 세부 비동기 API를 일반화하기보다는, 한 소비자가 작업 완료를 기다려 순서를 지킨다는 책임을 읽는다. 큐 자료구조 자체가 스레드나 병렬 실행을 만드는 것은 아니다.

대기열이 비었다는 사실과 전체 완료

마지막 항목을 꺼낸 순간 큐의 Count는 0이 될 수 있다. 그러나 마지막 항목은 아직 처리 중이다. 이 구현은 반복문을 빠져나오고 표시를 정리한 뒤 IsBusy를 false로 바꾼다. 외부는 대기 항목 수만 보고 완료를 판단하지 않는다.

CHAPTER 05

중간 값이 보존되는 실행 추적

학습 목표: 현재 값과 각 기록의 결과를 따로 계산해 FIFO를 검산한다.

출발 상태와 연속 변경

최대 HP가 14인 객체의 현재 HP가 12라고 가정한다. 표시가 시작되기 전에 5 감소, 3 감소, 5 증가가 차례로 일어난다. 규칙 상태의 마지막 값은 9다.

발생한 변경기록한 Before / After나중에 표시할 값
12에서 5 감소12 / 7HP 7, 변화 −5
7에서 3 감소7 / 4HP 4, 변화 −3
4에서 5 증가4 / 9HP 9, 변화 +5

첫 번째 기록을 처리하는 동안 실제 CurrentHp는 이미 9일 수 있다. 하지만 첫 기록이 표현해야 하는 값은 7이다. 두 번째 기록은 4, 세 번째는 9다. 스냅샷이 있으면 이 순서를 잃지 않는다.

소비 코드가 읽는 값

item.Actor.GetComponentInChildren<UnitHealthBar>(true).Show(item.AfterHp, item.MaxHp);
int change = item.AfterHp - item.BeforeHp;

실제 코드 · PresentationQueue.cs 75–76행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

표시 값은 AfterHp다. 변화량은 AfterHp − BeforeHp다. 첫 기록은 7 − 12 = −5, 다음은 4 − 7 = −3, 마지막은 9 − 4 = +5다. 소비 코드가 CurrentHp를 다시 읽지 않는 이유를 수치로 설명할 수 있다.

상한으로 잘린 회복

최대 HP 14, 현재 HP 12에서 회복 요청량 5를 적용한다고 하자. 실제 새 HP는 14다. 이벤트의 전후 값은 12와 14이며 실제 변화량은 +2다. 요청한 양 5를 기록해서 표시하는 것과 실제로 적용된 차이 2를 표시하는 것은 다르다. 이 코드의 이벤트는 실제 전후 상태를 담는다.

처리 도중 새 기록이 들어온 경우

첫 감소를 표시하는 동안 또 다른 변경이 일어났다면 그 기록은 기존 세 항목 뒤에 들어간다. 이미 만들어진 세 스냅샷을 고치지 않는다. 발생 순서와 화면에서 표현할 순서가 같은 FIFO라는 약속을 유지한다.

스스로 검산첫 기록이 끝나기 전의 실제 HP가 9이고 큐에 남은 기록이 둘이라면, 화면이 7을 보여 주는 것이 오류인가? 아니다. 화면은 첫 발생을 순서대로 표현하는 중이고 규칙 값은 이미 최종 상태다.

CHAPTER 06

참조의 수명과 취소

학습 목표: 보관한 기록이 언제까지 의미가 있는지와 취소의 효과를 설명한다.

값과 객체의 수명은 다르다

HP와 위치 값을 복사했어도 소비자가 그릴 객체를 찾을 참조는 필요할 수 있다. 대상 객체가 먼저 파괴되면 스냅샷 숫자는 남아 있어도 표시할 대상을 찾지 못한다. 그래서 기록을 보관하는 시간 동안 어떤 객체를 유지하고 언제 정리할지 정해야 한다.

표시를 위해 객체가 남아 있다는 사실과 규칙에서 여전히 유효하다는 사실도 구분한다. 규칙의 생존 여부를 화면 활성 상태로만 판정하면 지연 표시가 규칙을 바꾸게 된다. 현재 규칙의 판정값과 소비 작업의 수명은 서로 다른 책임이다.

큐를 비울 때 버리는 것

_cancellation?.Cancel();
_cancellation?.Dispose();
_cancellation = null;
_events.Clear();
ResetUnits();

실제 코드 · PresentationQueue.cs 89–93행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

취소는 진행 중인 소비를 멈추고 남은 기록을 버린다. 이미 규칙에 적용된 HP나 위치를 과거로 돌려주지는 않는다. ResetUnits는 표시가 현재 규칙 상태를 다시 나타내게 한다. Event Queue 취소를 Command Undo와 혼동하지 않는다.

이전 소비자와 새 소비자의 경계

취소 뒤에 새 작업이 시작될 수 있다. 이전 소비자의 취소 처리가 늦게 돌아와 새 작업의 IsBusy를 꺼 버리면 새 작업이 끝난 것처럼 보일 수 있다. 이 구현은 취소 정리를 Cancel이 맡고, 이전 소비자의 취소 경로가 새 소비 상태를 덮어쓰지 않게 한다.

화면이나 작업 범위가 바뀔 때 이전 기록을 계속 처리해야 하는지도 정해야 한다. 과거 작업의 기록이 새 작업에 섞이면 FIFO 순서를 지켰더라도 의미는 잘못된다. 수명 경계를 넘기 전에 남은 처리를 취소하거나 완료하는 정책이 필요하다.

CHAPTER 07

Observer, Command와의 비교

학습 목표: 수신자·시간·데이터 의미가 서로 다른 설계 축임을 설명한다.

누가 듣는지와 언제 처리하는지

Observer는 구독자를 등록해 발행자와 수신자의 관계를 나눈다. 일반적인 C# 즉시 이벤트는 발행 호출 흐름 안에서 구독자를 실행한다. Event Queue는 항목을 보관하고 소비자가 나중에 꺼내게 한다. 한 구조가 다른 구조를 무조건 대체하는 것이 아니라 나누는 책임이 다르다.

이벤트와 명령은 뜻이 다르다

이벤트는 발생한 사실이나 알림을 표현한다. 명령은 일을 수행하라는 요청을 표현한다. 둘 다 큐라는 자료구조에 넣을 수 있지만, 소비하지 못했을 때의 의미가 다르다. 이미 생긴 상태를 표시하지 못한 것과 실행해야 할 요청을 처리하지 못한 것은 같은 실패가 아니다.

이 수업에서는 규칙 상태를 먼저 바꾸고 그 결과와 동작을 표현하는 기록을 순서대로 소비한다. 큐를 비웠다고 규칙 결과가 취소되지 않는다. 과거 상태를 복원하려면 별도로 필요한 정보를 보존하고 되돌리는 동작을 설계해야 한다.

현재 구현의 한계

이 큐는 한 소비자가 화면 처리를 순서대로 맡는다. 네트워크 메시지 보장, 여러 스레드의 동시 접근, 영구 저장, 실패 항목 재시도까지 제공하지 않는다. Event Queue를 쓴다는 이름만으로 그런 성질이 따라오지는 않는다.

CHAPTER 08

비용과 적용 기준

학습 목표: 지연·적체·수명 관리 비용을 직접 호출의 단순함과 비교한다.

늦게 읽을 데이터의 수명

즉시 처리할 때 존재했던 객체가 나중에는 사라질 수 있다. 객체는 남아 있어도 값이 달라질 수 있다. 예를 들어 이름을 표시해야 하는 기록에 객체 참조만 저장했다면 소비할 때 그 객체의 현재 이름을 읽게 된다. 발생 당시의 이름이 필요하다면 전송 시점에 문자열을 복사하는 방식이 더 적절하다.

모든 데이터를 무조건 복사하는 것도 비용이다. 중요한 것은 소비자가 어떤 시점의 값을 필요로 하는지 먼저 정하는 일이다. 발생 당시 사실을 남길 항목과 처리할 때 현재 상태를 읽을 항목을 구분한다. 이 선택을 명시하지 않으면 같은 큐를 사용해도 실행 시점에 따라 의미가 달라진다.

생산이 소비보다 빠르면 쌓인다

한 번에 두 항목씩 들어오는데 하나씩만 꺼내면 남은 항목 수는 매번 하나씩 늘어난다. 순서가 정확해도 너무 늦게 표시하면 사용할 수 없는 결과가 된다. 큐의 최대 길이, 처리량, 오래된 항목을 버리는 정책은 사용하는 상황에 따라 정해야 한다. Event Queue 자체가 적체 문제를 해결해 주지는 않는다.

화면이나 장면이 바뀔 때의 책임

큐의 항목이 어느 범위의 작업인지 알아야 한다. 이전 작업에 관한 알림이 새 작업으로 넘어가서 처리되면 순서는 맞아도 의미가 틀릴 수 있다. 큐를 계속 유지할지 비울지, 누가 그 시점을 정할지는 수명 관리의 일부다. 큐를 비우는 행위는 아직 처리하지 않은 정보를 버리는 결정이라는 점도 함께 이해한다.

직접 반환이 필요한 경우“지금 이 행동을 해도 되는가?”의 답을 받아 바로 분기해야 한다면 직접 메서드 호출과 반환값이 더 단순하다. 큐에 질문을 넣으면 답이 올 때까지 이어서 진행할 방법까지 설계해야 한다. 시간을 나눌 이유가 없는 호출에는 그 복잡성이 이득이 되지 않는다.

Event와 Command를 구분한다

이벤트는 이미 일어난 사실을 알린다. 명령은 어떤 일을 하라는 요청이다. 둘 다 큐에 넣을 수 있지만 소비하지 못했을 때의 의미는 다르다. 알림을 놓치는 것과 실행해야 할 요청을 놓치는 것은 같은 문제가 아니다. 자료구조가 같다는 이유로 의미까지 같다고 생각하지 않는다.

복습 질문과 용어

학습 목표: 기록의 내용·순서·완료·취소를 자신의 말로 설명한다.

질문과 해설

1. A를 처리하는 동안 B와 C를 보내면 새 소비자가 두 개 생기는가?
아니다. IsBusy가 true인 동안에는 뒤에 넣기만 한다. 현재 소비자가 A를 끝낸 다음 B, C를 처리한다.

2. 마지막 항목을 꺼낸 뒤 큐가 비었다. 모든 처리가 끝났는가?
아직 아닐 수 있다. 마지막 항목의 처리가 끝나기 전까지 IsBusy는 true다.

3. HP 12에서 14로 회복되었다. 요청량이 5였다면 기록에서 표시할 실제 변화량은?
AfterHp − BeforeHp = 14 − 12 = +2다. 요청량과 실제 변화량은 다를 수 있다.

4. readonly 이벤트가 Actor 객체의 상태도 고정하는가?
아니다. Actor는 참조다. 위치와 HP가 필요하면 발생 당시 값을 따로 복사하고 대상 객체의 수명도 관리한다.

5. Cancel이 HP와 위치를 변경 전으로 돌리는가?
아니다. 남은 표시를 버리고 화면을 현재 규칙 상태와 맞춘다. 과거 상태 복원은 별도의 Undo 책임이다.
