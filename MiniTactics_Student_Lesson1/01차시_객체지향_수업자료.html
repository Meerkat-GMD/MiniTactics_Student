Invariant · Hypothetical

불변 조건은 모든 정상 상태에서 지킬 규칙이다

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

public void TakeDamage(int amount)
{
    if (amount <= 0) return;
    Hp = Math.Max(0, Hp - amount);
}

가상 HP 규칙

Hp는 객체 안에서만 바꾸고 시작값은 0 이상이라고 가정한다. 불변 조건은 Hp ≥ 0이다.

계산과 답

Hp 3, 피해 5 → max(0, −2) = 0.
피해 −2 또는 0 → 무시, Hp는 3.
음수 피해가 회복으로 바뀌지 않는다.

Lesson1 Unit에는 HP나 TakeDamage가 없다. 불변 조건을 설명하기 위한 부분 코드이며 Math는 System.Math다.

State and Transition · Hypothetical

상태와 처음 그 상태가 된 순간은 다르다

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

bool wasAlive = Hp > 0;
Hp = Math.Max(0, Hp - amount);
if (wasAlive && Hp == 0) OnDied();
가상 입력 · amount > 0현재 상태이번에 죽음으로 전이했나?
Hp 3 → 피해 5 → Hp 0죽어 있음예 · OnDied 1회
Hp 0 → 피해 2 → Hp 0죽어 있음아니요 · 추가 호출 없음

전이는 이전 상태에서 다른 상태로 바뀌는 사건이다. OnDied는 가상 알림 메서드다. 단순히 Hp == 0만 검사하면 같은 사건을 반복 처리할 수 있다.

Tell, Don’t Ask

규칙은 주인에게 요청하고 필요한 값은 묻는다

피해야 할 가상 비교

외부에서 Hp를 꺼내 피해를 빼고 0 보정까지 대입하면 규칙이 여러 호출자에게 흩어진다.

TakeDamage(amount)처럼 상태의 주인이 규칙을 적용하게 요청한다.

질의도 정당한 협력이다

현재 Controller가 BoardView.CanMoveTo에 가능 여부를 묻는 것은 자연스럽다. 화면 표시를 위해 MoveDistance를 읽는 것도 가능하다.

Tell, Don’t Ask는 “값을 절대 읽지 말라”가 아니다. 읽어 온 값으로 상대의 내부 규칙을 대신 작성하고 있는지 살피라는 기준이다.

Contract

약속에는 입력·결과·한계가 함께 있다

실제 요청/질의기대하는 약속구분할 한계
BoardView.CellToWorld(cell)셀 중심의 월드 위치 반환이동 가능 판정은 별도
Unit.MoveTo(board, cell)그 Unit의 루트 위치 대입스스로 범위·점유를 검사하지 않음
TryMoveSelectedUnit(cell)가능하면 이동하고 true 반환실패하면 먼저 false 반환

계약은 호출자가 기대할 수 있는 조건과 결과다. 필요한 협력 객체는 올바르게 연결되어 있다고 전제한다. 정상적인 “선택 없음”은 실패 결과로 다룬다.

Interface · Hypothetical

서로 다른 구현을 같은 역할로 쓰려면

Polymorphism · Hypothetical

같은 요청이 연결된 객체에 따라 달라진다

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

IResultLog log = new ScreenLog();
log.Write("완료");

log.Write("완료");

ScreenLog와 MemoryLog는 IResultLog를 구현한다고 가정한다. 다형성은 같은 계약을 통해 서로 다른 구현에 요청하는 성질이다. 실제 Lesson1의 사용자 정의 구현이 아니다.

Inheritance and Substitution

상속은 부모 자리에 놓여도 약속을 지켜야 한다

설계 비교용 가상 예시

부모 기록기가 모든 유효 문자열을 받는다고 약속했는데 자식이 한 글자만 받는다면 호출자가 쓰던 입력이 실패한다.

대체 가능성

자식이 더 까다로운 조건을 요구하거나 보장된 결과를 줄이면 부모를 대신하기 어렵다. 코드 재사용만으로 상속을 결정하지 않는다.

실제 Unit : MonoBehaviour는 Unity 동작에 참여하는 타입 관계다. 이것만으로 별도의 게임플레이 상속 계층이나 사용자 정의 다형성을 구현했다고 말할 수 없다.

Composition · Hypothetical

독립적으로 바뀌는 역할은 부품으로 가진다

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

public sealed class ResultWriter
{
    private IResultLog _log;
    public ResultWriter(IResultLog log) { _log = log; }
    public void Write(string text) { _log.Write(text); }
}

ResultWriter는 기록기 “한 종류”가 아니라 기록기 부품을 가진다. 생성할 때 ScreenLog 또는 MemoryLog를 넘기면 같은 규칙을 다른 기록 방법과 조합할 수 있다. 연결·소유의 책임도 생긴다.

직접 의존하는 경우

결과 규칙이 화면 텍스트 도구를 직접 사용하면 화면 없이 규칙을 확인하기 어렵다.

의존성 역전

규칙 쪽이 필요한 IResultLog 계약을 정하고 화면 어댑터가 그 계약을 구현한다. 규칙과 어댑터 모두 계약을 바라본다.

Cohesion and Coupling

함께 바뀌는 것은 모으고 아는 세부는 줄인다

응집도

한 목적의 상태와 행동이 모인 정도다. BoardView에 좌표 변환 지식을 모으면 변환 변경의 주인을 찾기 쉽다.

결합도

다른 객체의 타입과 세부에 의존하는 정도다. Unit은 Tilemap 대신 BoardView의 변환 메서드에 기대지만 의존 자체가 사라진 것은 아니다.

작은 클래스가 많다는 이유만으로 좋은 설계가 되지 않는다. 한 동작을 이해하려고 너무 많은 객체를 오간다면 나눈 경계의 비용을 다시 살핀다.

Judgment

지금의 작은 구체 참조로 충분할 수 있다

분리할 근거

서로 다른 이유로 자주 바뀐다. 같은 종류 판별이 반복된다. 실제로 바꿔 쓸 구현이 둘 이상 필요하다.

늘어나는 비용

인터페이스, 연결 코드, 추적할 객체가 늘어난다. 어떤 변경을 쉽게 했는지 설명할 수 없다면 과한 분리일 수 있다.

현재 Lesson1에는 BoardView 구현이 하나다. Unit과 Controller가 구체 타입을 아는 단순한 경계가 합리적이다. 모든 의존성마다 인터페이스를 만들 필요는 없다.

Prediction and Answer

요청의 결과와 바뀌지 않는 값을 구별한다

질문답과 이유
A와 B의 MoveDistance가 같으면 같은 객체인가?아니다. 값이 같아도 선택 대상과 위치는 각각이다.
A 이동 성공 뒤 CanMove가 false인가?아니다. MoveTo는 _canMove를 바꾸지 않는다.
목적지 실패 뒤 SelectedUnit이 null인가?A가 선택되어 있었다면 그대로 A다. 실패 분기에서 먼저 반환한다.
상태 조회를 모두 없애야 하는가?아니다. 가능 여부 질의와 화면용 조회는 정당하다.

Takeaway

다음 변경을 맡을 주인을 먼저 찾는다

  1. 클래스는 정의이고 객체는 상태·행동·정체성을 가진 실제 인스턴스다.
  2. 상태를 바꾸는 규칙을 주인에게 모으고 공개된 요청과 질의로 협력한다.
  3. 함께 바뀌는 지식은 모으고 독립적으로 바뀌는 책임은 나눈다.
  4. 상속·합성·인터페이스는 실제 변화와 연결 비용을 보고 선택한다.

객체지향의 기준은 패턴 개수가 아니라 변경의 위치와 결과를 이해할 수 있는가다. 마지막으로 Unity가 제공하는 책임 분리인 Component를 살펴본다.

Theory Corner · Component 1/2

GameObject는 여러 컴포넌트를 담는다

Transform위치·회전·크기를 담는 컴포넌트
Unit유닛 상태 조회와 루트 위치 변경 요청
UnitAnimator위치 변화를 관찰하고 Visual의 표현을 조정
SpriteRenderer그림을 화면에 그리는 컴포넌트

Component는 하나의 GameObject에 필요한 책임을 가진 부품을 조합하는 Unity의 구조다. 예를 들어 루트의 Unit·UnitAnimator가 자식 Visual의 Transform·SpriteRenderer와 협력할 수 있다.

유닛 종류마다 거대한 상속 계층을 만들기보다 위치·행동·표현 역할을 나누어 조합할 수 있다.

[SerializeField] private UnitLook _look;

실제 코드 발췌 — UnitAnimator.cs

if (transform.position != _lastPosition)

실제 코드 발췌 — UnitAnimator.cs · LateUpdate 안의 조건 한 줄

관찰하는 표현 책임

루트 위치는 MoveTo에서 이미 바뀌었다. UnitAnimator는 그 변화를 보고 자식 Visual의 localPosition과 그림을 조정한다.

모든 객체가 컴포넌트는 아니다

UnitLook은 그림 배열을 담는 ScriptableObject 데이터 에셋이다. MovementOverlayPool은 일반 C# 표시 도우미다.

참조로 연결했다고 같은 종류의 객체가 되지는 않는다. “어떤 정보를 알고 어떤 일을 맡는가”로 부품을 읽는다.
