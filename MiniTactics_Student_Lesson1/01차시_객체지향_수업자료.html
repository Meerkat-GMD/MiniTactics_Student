Object-oriented Programming

객체지향은 책임을 가진 객체들의 협력이다

관련된 상태와 행동을 객체로 묶고,
객체들이 공개된 요청으로 협력하게 만든다.

객체 안에서는

자기가 가진 상태가 유효하도록 규칙을 지킨다. Character는 피해를 받아도 HP를 0 아래로 내리지 않는다.

객체 사이에서는

상대의 내부 계산을 대신하지 않고 공개된 행동을 요청한다. 공격자는 방어자에게 TakeDamage를 요청한다.

Object

객체에는 상태·행동·정체성이 있다

고블린 A

상태: HP 10, 장착 무기 검
행동: 피해 받기, 무기 교체
정체성: 전장 왼쪽의 그 고블린

고블린 B

상태: HP 10, 장착 무기 검
행동: 피해 받기, 무기 교체
정체성: 전장 오른쪽의 다른 고블린

값이 같아도 A와 B는 별개다. A가 피해를 받았다고 B의 HP가 줄어들어서는 안 된다. 정체성은 상태 값과 별개로 “어느 객체인가”를 구별한다.

Identity and Value

값만 중요한 정보는 값으로 다룰 수 있다

정체성을 구별해야 할 때

고블린 둘의 HP가 같아도 다른 대상이다. 선택, 피해, 사망은 특정 고블린에 적용한다.

값이 같으면 같게 다룰 때

피해량 10이나 좌표 (2,3)은 값 자체가 의미다. 변경할 수 없는 값 객체로 표현하면 함께 읽기도 쉽다.

화면에 보이는 모든 명사를 독립된 객체로 만들 필요는 없다. 어떤 정보에 정체성이 필요한지, 어떤 정보는 값 비교로 충분한지 판단한다.

Encapsulation

캡슐화는 상태를 바꾸는 통로를 관리한다

public int Hp { get; private set; }

public void TakeDamage(int damage)
{
    if (damage <= 0) return;
    Hp = Math.Max(0, Hp - damage);
}

외부는 HP를 읽을 수 있지만 마음대로 대입할 수 없다. TakeDamage라는 통로로 요청하면 객체 안에서 한 가지 규칙으로 변경한다.

Invariant

불변 조건은 모든 정상 상태에서 지켜야 한다

HP가 3인 캐릭터가 피해 8을 받았다.
HP는 −5일까, 0일까?

계산 단계결과
단순 뺄셈3 − 8 = −5
HP의 유효 범위를 적용최소 0으로 제한
호출이 끝난 상태HP = 0, 생존하지 않음

불변 조건은 “정상적인 객체라면 항상 성립해야 하는 규칙”이다. 이 예시에서는 0 ≤ HP ≤ 최대 HP를 각 변경 메서드가 지킨다.

State Transition

처음 죽을 때와 이미 죽어 있을 때를 구분한다

살아 있음 → 죽음

이전 HP가 양수이고 새 HP가 0이면 사망 전이가 일어났다. 사망 처리와 보상은 이 변화에 맞춰 수행한다.

죽음 → 죽음

이미 HP가 0인데 다시 피해를 받았다고 사망 보상을 또 주면 안 된다. 현재 값뿐 아니라 이전 상태도 판단에 필요하다.

상태는 지금의 값이고, 전이는 이전 상태에서 새 상태로 바뀌는 과정이다. 같은 HP 0이라도 어떻게 도달했는지에 따라 처리할 일이 다르다.

Tell, Don’t Ask

정보를 꺼내 대신 판단하기보다 행동을 요청한다

호출자가 대신 결정

HP를 읽고 피해를 빼고 0으로 보정한 뒤 사망을 처리한다. 호출자마다 방어자의 규칙을 알아야 한다.

상태의 주인에게 요청

defender.TakeDamage(8)를 부른다. 방어자가 유효 범위와 사망 전이를 관리한다.

값 조회를 모두 금지하자는 뜻은 아니다. UI처럼 현재 HP를 표시하는 일은 조회가 자연스럽다. 상태를 바꾸는 판단이 여러 곳에 퍼지는지 살핀다.

Abstraction

무기 종류가 달라도 필요한 요청은 같다

Battle이 필요한 것

선택한 무기의 사거리를 확인하고 공격 효과를 얻고 싶다. 검인지 활인지에 따른 세부 구현은 무기가 맡으면 된다.

Weapon이 공개할 약속

사거리와 공격 효과를 제공한다. 칼날 효과, 화살 생성, 지팡이의 원소 처리처럼 다른 부분은 각 구현 안에 둔다.

추상화는 사용하는 쪽에 필요한 공통 역할을 드러내는 것이다. 중요하지 않은 세부 차이를 경계 안에 두어 변경이 퍼지는 범위를 줄인다.

Interface Contract

인터페이스는 사용할 수 있는 약속을 적는다

public interface IWeapon
{
    int Range { get; }
    AttackEffect CreateEffect();
}

AttackEffect는 여기서 무기가 만들어 전달하는 공격 효과를 뜻하는 설계 예시 타입이다.

다형성은 같은 요청에 구현별로 응답하는 것이다

모델의 한계

장착 무기는 전투 중 바뀔 수 있다. 직업과 무기를 같은 상속 계층으로 묶으면 전사+검, 전사+활처럼 조합마다 타입이 늘어난다.

상속은 안정적인 “한 종류다” 관계를 표현할 때 적합하다. 교체할 수 있는 능력까지 타입으로 고정하는지 확인한다.

Substitution

상속한 타입은 부모의 약속을 지켜야 한다

상속으로 표현하는 관계

하위 타입을 상위 타입 자리에 넣어도 기존 호출자가 사용하는 규칙이 성립해야 한다.

약속이 깨지는 예

부모는 모든 유효 대상에 공격할 수 있다고 약속했는데 자식은 특정 대상만 받아들이면 기존 호출이 실패한다.

부모의 코드를 재사용할 수 있다는 이유만으로 상속하지 않는다. 하위 타입이 더 까다로운 입력을 요구하거나 보장된 결과를 줄이는지 확인한다.

Dependency Problem

화면 로그가 없어도 전투 규칙을 실행하려면?

구체적인 UI에 직접 의존

Battle이 화면 텍스트와 애니메이션 도구를 직접 다루면, 피해 계산을 확인할 때도 그 화면 구성이 필요해진다.

전투 쪽에서 필요한 역할

Battle은 “이 결과를 기록한다”는 작은 약속만 필요하다. 화면에 그릴지 메모리에 모을지는 별도 구현이 맡을 수 있다.

의존성이란 한 코드가 다른 코드의 타입이나 동작을 알아야 하는 관계다. 어떤 세부 기술을 알고 있는지 보면 변경이 퍼지는 방향을 알 수 있다.

Dependency Inversion

의존성 역전은 규칙 쪽에서 약속을 정한다

public interface IBattleLog
{
    void Write(string message);
}

IBattleLog게임: 화면 로그 / 검증: 메모리 기록기
난수 제공 역할게임: 실제 난수 / 검증: 고정된 값

핵심 규칙을 UI 도구에 맞추는 대신, UI 도구가 핵심 규칙에 필요한 약속을 구현한다. 작은 인터페이스만 추가하는 것으로 끝내지 않고 실제 연결도 바꾸어야 한다.

독 시간 관리

무기가 효과를 만들고, 피해 정책이 공격·방어 조건을 계산한다. 방어자는 HP 규칙을 지킨다. 이후 턴의 독 피해와 남은 시간은 독 효과가 맡는다.

Battle은 이 협력의 순서를 조정하고 결과를 로그 역할에 전달한다. 원래 한 전투 함수가 알던 세부 규칙을 각 담당자가 소유하게 된다.

Cohesion and Coupling

한 목적의 규칙은 모으고 공개 약속은 작게 한다

응집도

한 목적을 위해 함께 바뀌는 상태와 규칙이 한 객체에 모인 정도다. HP와 피해·회복 규칙이 함께 있으면 변경 위치가 분명하다.

결합도

객체가 다른 객체의 세부 사항에 얼마나 의존하는지다. 필요한 작은 약속만 알면 상대 구현을 바꾸기 쉬워진다.

작은 클래스가 많다고 좋은 설계가 되는 것은 아니다. 한 행동을 이해하려고 지나치게 많은 객체를 오간다면 경계를 다시 묶는 편이 낫다.

Judgment

모든 기능을 미리 추상화할 필요는 없다

분리할 근거가 있는 경우

같은 종류 판별이 반복된다. 한 객체가 서로 다른 이유로 자주 바뀐다. 실제로 교체할 구현이 둘 이상 필요하다.

비용이 더 큰 경우

변화가 거의 없는데 인터페이스와 중간 객체만 늘어난다. 어떤 변경을 쉽게 만들었는지 설명할 수 없다.

처음의 짧은 피해 함수도 합리적인 출발점이었다. 반복되는 변경을 관찰하면서 책임을 옮기고 필요한 경계를 만든다.

Mini Tactics Connection

1차시 게임에서도 선택·판정·이동의 주인을 찾는다

입력어느 유닛과 셀을 눌렀는지 전달한다.
BattleController선택한 유닛과 이동 요청을 조정한다.
BoardView좌표 변환과 이동 가능 여부를 제공한다.
UnitMoveTo로 실제 위치를 바꾼다.

앞의 RPG 무기·전투 예시는 책임을 나누는 원리를 설명했다. 실제 1차시에서는 작은 이동 기능에서 같은 질문을 적용하고, 2차시에서 Undo라는 새 요구를 만난다.

Takeaway

새 기능을 더할 때 먼저 책임을 묻는다

  1. 객체는 관련된 상태와 행동을 가지며 자기 규칙을 지킨다.
  2. 객체끼리는 공개된 행동을 요청하며 협력한다.
  3. 함께 바뀌는 규칙은 모으고 독립적으로 바뀌는 부분은 나눈다.
  4. 상속·합성·추상화는 실제 변화와 비용을 보고 선택한다.

체력 바의 색을 바꾸는데 피해 함수를 고쳐야 한다면?
표시와 피해 처리의 책임이 섞였는지 살핀다.

좋은 설계의 기준은 사용한 패턴의 수가 아니라, 다음 변경을 이해할 수 있는 범위에서 수행할 수 있는가이다.
