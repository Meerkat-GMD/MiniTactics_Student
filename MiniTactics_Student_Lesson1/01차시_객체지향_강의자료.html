객체의 책임과 협력

실제 Unit·BoardView·Controller의 짧은 코드로 상태, 요청, 경계를 읽고 설계 판단으로 연결한다.

Chapter 01

두 객체에서 시작하기

이동 거리 2, 이동 허용 true인 Unit A와 B가 있다. 상태 값은 같지만 A는 왼쪽 유닛이고 B는 오른쪽 유닛이다. A에게만 위치 변경을 요청하면 B의 위치는 그대로여야 한다. “값이 무엇인가”와 “어느 대상인가”는 다른 질문이다.

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

a.MoveTo(board, targetCell);
예상 질문의 답: a가 A를 가리킬 때 A만 바뀐다. 참조는 객체 전체를 복사한 것이 아니라 특정 객체를 가리키는 값이다. 같은 객체를 두 참조가 가리킬 수도 있고, 같은 값을 가진 두 객체를 각각 가리킬 수도 있다.

처음에는 좌표 변환, 위치 대입, 그림 교체를 한 함수에 써도 충분하다. 그러나 변환 방식과 그림 표현을 따로 고치기 시작하면 서로 다른 변경이 같은 함수에 모인다. 이때 필요한 지식과 행동의 주인을 나누어 본다.

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

Vector3 center = tilemap.GetCellCenterWorld(cell);
unit.transform.position = center;
body.sprite = picture;

위 코드는 책임이 섞이는 상황을 비교하는 가상 첫 시도다. 현재 Teacher의 코드가 아니며 구현 절차가 아니다. 객체지향은 이런 변경을 관찰하면서 관련된 상태와 행동을 묶고 공개된 요청으로 협력하도록 설계하는 관점이다.

Chapter 02

객체·클래스·상태·값

public sealed class Unit : MonoBehaviour

실제 코드 발췌 — Unit.cs · 타입 선언 한 줄

클래스는 공통 상태와 행동의 정의다. 인스턴스는 그 정의에 따라 실행 중 존재하는 실제 객체다. Unit A와 B는 같은 Unit 클래스의 서로 다른 인스턴스다. Unit은 MonoBehaviour이므로 Unity가 GameObject에 붙인 인스턴스를 사용한다. 일반 C# 객체처럼 new Unit()으로 생성하지 않는다.

[SerializeField, Min(0)] private int _moveDistance = 2;
[SerializeField] private bool _canMove = true;

public int MoveDistance => _moveDistance;
public bool CanMove => _canMove;

실제 코드 발췌 — Unit.cs

필드는 값을 저장하는 멤버이고, 속성은 정해진 접근 방법을 제공한다. _moveDistance와 _canMove는 private 필드이고 두 공개 속성은 값을 반환한다. 상태는 현재 기억하는 정보이며, 행동은 요청에 따라 수행하는 일이다. MoveTo는 위치를 바꾸는 행동이다. 현재 코드에는 이동 뒤 _canMove를 바꾸는 문장이 없다.

Min(0)은 Inspector 입력을 돕는 메타데이터다. 모든 실행 경로에서 음수가 불가능함을 보장하는 런타임 검증과 같지 않다. 읽기 전용 속성이 있다고 객체 전체가 불변인 것도 아니다.
public MovementCell(Vector2Int cell, bool isOccupied)
{
    Cell = cell;
    IsOccupied = isOccupied;
}

public Vector2Int Cell { get; }
public bool IsOccupied { get; }

실제 코드 발췌 — MovementCell.cs · public readonly struct MovementCell 내부

MovementCell은 좌표와 점유 여부를 함께 전달하는 읽기 전용 값 묶음이다. Unit에서는 “누구인가”가 중요하지만 이 정보에서는 좌표와 점유 값이 중요하다. Cell과 IsOccupied는 생성자에서 정해지고 이후 이 멤버를 대입해 바꾸지 않는다. 여기서는 메모리 할당이나 기본 동등성 구현을 추론할 필요가 없다.

public void MoveTo(BoardView board, Vector2Int targetCell)
{
    transform.position = board.CellToWorld(targetCell);
}

실제 코드 발췌 — Unit.cs

이 호출의 수신자는 특정 Unit이다. board는 협력 객체의 참조이고 targetCell은 셀 좌표 값이다. 먼저 board.CellToWorld(targetCell)의 결과를 구하고 그 Unit의 transform.position에 대입한다. Unit은 Tilemap의 구체적인 변환 방법을 직접 작성하지 않는다.

public Vector3 CellToWorld(Vector2Int cell)
{
    return _tilemap.GetCellCenterWorld(new Vector3Int(cell.x, cell.y, 0));
}

실제 코드 발췌 — BoardView.cs

BoardView가 변환 지식을 가진다. 셀 중심의 실제 숫자는 Grid와 Tilemap 설정에 따라 달라진다. 따라서 셀 좌표만 보고 월드 위치가 같은 숫자라고 가정하면 안 된다. 추상화는 호출자에게 필요한 의미를 공개하고 세부 방법을 경계 안에 두는 것이다. 이 경계는 interface 키워드 없이도 생긴다.

책임을 나눈다는 말은 모든 검사를 모든 메서드에 반복한다는 뜻이 아니다. 이 협력에서는 Controller가 BoardView에 가능 여부를 묻고 Unit에 위치 변경을 요청한다. Unit.MoveTo 자체는 범위나 점유를 검사하지 않는다.

캡슐화와 불변 조건

public Unit SelectedUnit { get; private set; }

실제 코드 발췌 — BattleController.cs

다른 객체는 SelectedUnit을 읽을 수 있지만 private set 때문에 이 속성에 대입하는 책임은 BattleController 내부에 있다. 캡슐화는 정보와 변경 통로를 관리해 규칙이 흩어지지 않게 하는 것이다. 다만 이 속성이 Unit의 위치까지 보호하지는 않는다. Unity의 transform은 다른 코드에서도 접근할 수 있다.

현재 코드에 없는 HP로 규칙 비교하기

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

public void TakeDamage(int amount)
{
    if (amount <= 0) return;
    Hp = Math.Max(0, Hp - amount);
}

이 부분 코드는 Hp의 시작값이 0 이상이고 외부에서 직접 대입하지 않는 객체를 가정한다. Math는 System.Math다. 불변 조건은 모든 정상 상태에서 지켜야 하는 규칙이며 여기서는 Hp ≥ 0이다. 필드를 숨기기만 해서는 충분하지 않고 상태를 바꾸는 모든 통로가 규칙을 지켜야 한다.

Chapter 06

상태·전이와 Tell, Don’t Ask

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

bool wasAlive = Hp > 0;
Hp = Math.Max(0, Hp - amount);
if (wasAlive && Hp == 0) OnDied();

위 부분 코드는 양수 피해를 검사한 뒤의 가상 처리다. 상태는 지금 죽어 있는가이고, 전이는 살아 있던 상태에서 처음 죽음으로 바뀌었는가이다. Hp 3에서 피해 5를 받으면 Hp 0, wasAlive true이므로 OnDied를 한 번 부른다. 이미 Hp 0에서 다시 피해 2를 받으면 wasAlive false이므로 부르지 않는다. OnDied는 설명용 알림 메서드다.

상태의 주인이 규칙을 수행하게 한다

외부에서 Hp를 읽어 피해를 빼고 보정한 값을 다시 넣으면 피해 규칙이 호출자마다 반복된다. TakeDamage(amount)를 요청하면 규칙을 주인에게 모을 수 있다. 이것이 Tell, Don’t Ask의 취지다.

예상 질문의 답: 모든 조회를 금지해야 하는가? 아니다. 화면에 값을 표시하거나 다른 책임의 판단 결과를 물을 수 있다. 실제 Controller가 BoardView.CanMoveTo에 가능 여부를 묻는 것도 정당한 협력이다. 읽어 온 값으로 상대의 내부 규칙을 대신 작성하는지 살핀다.

Chapter 07

추상화·계약·인터페이스·다형성

계약은 사용할 수 있는 요청과 그 입력 조건, 기대 결과를 정한다. CellToWorld는 셀 중심을 반환하고 MoveTo는 Unit의 루트 위치를 대입한다. CellToWorld가 이동 가능 여부까지 보장하는 것은 아니다. 계약을 읽을 때 무엇을 보장하지 않는지도 확인한다.

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

public interface IResultLog
{
    void Write(string message);
}

이 가상 계약은 결과 문자열을 기록하는 역할이다. 호출자는 저장 방법을 몰라도 요청할 수 있다. ScreenLog는 화면 표시, MemoryLog는 메모리 보관으로 이 계약을 구현한다고 가정한다.

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

IResultLog log = new ScreenLog();
log.Write("완료");
log = new MemoryLog();
log.Write("완료");

다형성은 같은 계약의 같은 요청에 실제 연결된 객체가 자기 구현으로 응답하는 성질이다. 첫 호출은 화면에 표시하고 두 번째 호출은 메모리에 보관한다. 호출은 같지만 수신 객체의 구현은 다르다. interface는 추상화의 한 수단이며 모든 추상화에 필요한 키워드는 아니다.

IResultLog, ScreenLog, MemoryLog는 현재 Lesson1에 없는 설계 비교용 가상 타입이다. 실제 Unit의 MonoBehaviour 상속만으로 이 사용자 정의 다형성이 구현되었다고 말하지 않는다.

가상 부모 기록기가 모든 유효 문자열을 받는다고 약속했는데 자식이 한 글자만 받는다면 기존 입력이 실패한다. 부모 대신 자식을 넣어도 호출자의 기대가 유지되는 대체 가능성을 해친 것이다. 부모 코드 재사용만으로 상속을 정하지 않는다.

설계 비교용 가상 코드 — 현재 Lesson1에 없는 예시

public sealed class ResultWriter
{
    private IResultLog _log;
    public ResultWriter(IResultLog log) { _log = log; }
    public void Write(string text) { _log.Write(text); }
}

가상 ResultWriter는 기록기의 한 종류가 아니라 기록기 부품을 가진다. 생성할 때 ScreenLog나 MemoryLog를 받으면 결과를 만드는 객체의 종류를 바꾸지 않고 기록 방식을 조합한다.

질문과 답: 화면 기록을 메모리 기록으로 바꾸려면 상속 계층을 늘려야 하는가? 이 요구에서는 독립된 기록 역할을 연결하는 합성이 자연스럽다. 안정적인 타입 관계와 교체할 역할 중 무엇을 표현하는지 먼저 묻는다.

Chapter 09

의존성·응집도·결합도와 설계 판단

의존성은 코드가 다른 타입이나 동작을 알아야 하는 관계다. 현재 Unit은 BoardView.CellToWorld를 사용하므로 BoardView에 의존한다. BoardView 뒤에 Tilemap의 변환 세부를 두면 Unit이 아는 세부는 줄지만 의존 자체가 사라지는 것은 아니다.

응집도는 한 목적을 위해 함께 바뀌는 상태와 행동이 모인 정도다. 좌표 변환 지식을 BoardView에 모으면 그 변경의 주인을 찾기 쉽다. 결합도는 다른 객체의 타입과 세부에 의존하는 정도다. 연결이 많고 내부 규칙까지 알아야 하면 변경이 쉽게 퍼진다.

의존성 역전의 가상 비교

결과 규칙이 화면 텍스트 도구를 직접 사용하면 화면 없는 환경에서도 그 도구가 필요하다. 규칙 쪽이 IResultLog라는 필요한 계약을 정하고 화면 어댑터가 구현하게 하면 규칙과 어댑터 모두 그 계약을 바라본다. 앞의 ResultWriter처럼 실제 연결도 바꾸어야 한다. 인터페이스 선언 하나로 모든 결합이 해결되지는 않는다.

분리할 근거경계를 늘리는 비용
다른 이유로 자주 바뀌는 지식탐색해야 할 객체와 파일이 늘어난다.
같은 종류 판별이 반복됨생성·연결·소유를 정해야 한다.
실제로 교체할 구현이 둘 이상 필요계약을 이해하고 유지해야 한다.
현재 판단: Lesson1에는 BoardView 구현이 하나다. Unit과 Controller가 구체 타입을 아는 단순한 경계로 충분할 수 있다. 모든 의존성을 미리 인터페이스로 감싸는 것이 목표는 아니다.

한 동작을 이해하려고 지나치게 많은 객체를 오간다면 경계를 다시 묶는다. 다음 변경을 어디서 수행할 수 있고 어떤 영향이 생기는지 설명할 수 있어야 한다.

이론 코너: Unity의 Component

GameObject는 컴포넌트를 담는 객체다. Transform은 위치·회전·크기를, SpriteRenderer는 그림 출력을 맡는다. Unit과 UnitAnimator는 MonoBehaviour를 상속한 행동 컴포넌트다. 필요한 부품을 조합하면 서로 다른 책임을 나눌 수 있다.

[SerializeField] private Transform _visual;
[SerializeField] private SpriteRenderer _body;
[SerializeField] private UnitLook _look;

실제 코드 발췌 — UnitAnimator.cs

if (transform.position != _lastPosition)

실제 코드 발췌 — UnitAnimator.cs · LateUpdate 안의 조건 한 줄

UnitAnimator는 _visual로 자식 Transform, _body로 SpriteRenderer, _look으로 UnitLook 데이터를 참조한다. Unit.MoveTo가 루트 위치를 이미 목적지로 옮기고, UnitAnimator는 그 변화를 관찰해 Visual의 localPosition과 그림을 조정한다. 논리 위치의 변경과 화면 표현의 보간을 구별한다.

참조되는 객체가 모두 컴포넌트인 것은 아니다. UnitLook은 그림 배열을 담는 ScriptableObject 데이터 에셋이다. MovementOverlayPool은 MonoBehaviour가 아닌 일반 C# 표시 도우미다. 이름에 Pool이 있다고 이 차시의 주제가 Object Pool 패턴이 되는 것은 아니다.
