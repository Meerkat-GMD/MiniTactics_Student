RPG 전투 시스템으로 이해하는
객체지향 프로그래밍

Definition

객체지향 프로그래밍이란 무엇인가

객체지향 프로그래밍은 프로그램을 상태와 행동을 가진 객체들의 협력으로 구성하고, 각 객체에 적절한 책임을 배치하는 프로그래밍 방식이다.

객체와 책임

  • 객체는 서로 관련된 상태와 행동을 하나의 단위로 묶는다.
  • 각 객체는 자신이 소유한 상태와 그 상태를 다루는 규칙에 책임을 진다.

메시지와 협력

  • 객체들은 공개된 메시지를 주고받으며 혼자서는 완성할 수 없는 기능을 함께 수행한다.
  • RPG에서는 캐릭터, 무기와 스킬 객체가 각자의 규칙을 담당하고 협력하여 하나의 전투를 완성한다.

핵심은 현실의 사물을 그대로 복제하는 것이 아니라, 프로그램의 책임과 변경 경계를 객체라는 단위로 설계하는 데 있다.

Change Pressure

RPG 전투 시스템은 계속 변한다

  • 초기 전투는 공격력에서 방어력을 빼는 계산 하나만으로 구현할 수 있다.
  • 게임이 발전하면 직업 공식, 사거리, 치명타, 원소 상성과 상태 효과가 추가된다.
  • 무기 밸런스, 피해 공식과 UI 로그는 서로 다른 주기로 변경된다.
  • 하나의 코드가 모든 변경을 담당하면 충돌과 회귀 오류가 증가한다.
  • 객체지향 설계는 변경의 영향을 관련 객체 내부로 제한하여 다른 기능으로의 전파를 줄인다.

좋은 경계: 빙결 효과 추가는 빙결 코드에서, 로그 출력 변경은 로그 구현에서 끝나야 한다.

First Implementation

첫 구현: 하나의 전투 함수에 모든 절차를 적는다

  • 작은 프로토타입에서는 하나의 전투 함수가 단순하고 빠른 선택이다.
  • 전투 함수는 공격자와 방어자의 수치로 최종 피해를 계산한다.
  • 기능이 늘어나면 전투 함수가 모든 종류와 세부 규칙을 알게 된다.
전투(공격자, 방어자)

 ├ 무기 종류 확인
 ├ 스킬 종류 확인
 ├ 치명타 판정

 ├ 상태 효과 적용

  • 객체지향적 분리가 필요한 순간은 서로 다른 변화가 한 함수에 축적될 때다.

Coupling

거대한 조건문의 문제는 지식의 집중이다

중앙 코드가 아는 것

  • 중앙 코드는 모든 직업과 무기의 구체적인 종류를 안다.
  • 중앙 코드는 스킬별 비용과 효과 계산법을 안다.
  • 중앙 코드는 방어자의 상태부터 UI와 로그의 출력 방법까지 안다.

변경이 만드는 결과

  • 새로운 종류가 추가될 때마다 기존 분기를 수정해야 한다.
  • 동일한 종류 판별 코드가 여러 장소에서 반복된다.
  • 한 규칙의 변경이 다른 규칙을 깨뜨리고 테스트 범위까지 넓힐 수 있다.

객체지향적 개편은 함수를 잘게 자르는 일이 아니라, “누가 이 판단을 맡아야 하는가?”를 다시 정하는 일이다.

Object

객체는 상태·행동·정체성을 가진 협력 주체다

  • 상태는 현재 체력, 마나와 장착 무기처럼 시간에 따라 변하는 정보다.
  • 행동은 피해 받기, 스킬 사용과 장비 교체처럼 상태를 사용하는 규칙이다.
  • 정체성이 있으므로 체력이 같은 고블린 두 마리도 서로 다른 생명 주기와 상태 효과를 가진다.

Character 객체

  • 상태는 hp, mana, weapon과 effects로 표현할 수 있다.
  • 행동은 takeDamage(), useSkill()과 equip()으로 표현할 수 있다.
  • 정체성은 전장에 존재하는 특정 캐릭터를 구분한다.

외부에서 데이터를 마음대로 꺼내 쓰는 상자가 아니라, 자신의 규칙을 지키면서 다른 객체의 요청에 응답하는 주체로 본다.

Class & Instance

클래스는 정의, 인스턴스는 실행 중인 실체다

클래스

  • 클래스는 객체의 상태, 행동과 외부 약속을 정의한다.
  • Character 클래스는 책임과 캡슐화의 경계 안에서 체력 처리와 생존 판단의 규칙을 정의한다.

인스턴스

  • 인스턴스는 클래스 정의를 바탕으로 실행 중에 생성된 구체적 객체다.
  • 기사 아린과 마법사 루나처럼 같은 클래스의 인스턴스도 상태와 생명 주기는 서로 독립적이다.
  • 플레이어는 정체성이 중요한 엔티티로 표현한다.
  • ‘불 속성’과 ‘피해량 10’은 값이 같으면 동일하게 취급하는 불변 값 객체로 표현할 수 있다.

Responsibility

책임: 누가 무엇을 알고 결정해야 하는가

  • 책임은 객체가 무엇을 알고 무엇을 수행해야 하는지를 의미한다.
  • 필요한 정보를 가진 객체가 그 정보를 사용하는 판단도 맡아야 한다.
  • 체력의 유효 범위는 캐릭터가 관리한다.
  • 독의 지속 시간과 기본 공격 방식은 각각 상태 효과와 무기 객체가 관리한다.
Character 체력·자원·생존 상태 Weapon 기본 공격 방식 Skill 조건·비용·효과 생성 Effect 적용 시점·지속 시간 Battle 턴 순서·협력 조정
  • 한 객체가 여러 이유로 자주 변경된다면 책임이 과도할 수 있다.
  • 행동 하나를 이해하기 위해 너무 많은 객체를 거쳐야 한다면 책임을 지나치게 분리했을 수 있다.

Message & Collaboration

메시지와 협력: 전투 한 번은 여러 객체가 완성한다

  • 메시지는 상대 객체에게 특정 행동을 수행해 달라고 요청하는 것이다.
  • 요청을 구체적으로 수행하는 방법은 메시지를 받은 객체가 결정한다.
  • 호출자는 상대의 내부 필드가 아니라 공개된 행동에 의존한다.

Battle이 방어자의 체력을 직접 덮어쓰지 않고 “이 피해를 받아 달라”고 요청하면, 방어자는 보호막·무적·최소 체력 같은 자신의 규칙을 지킬 수 있다.

Encapsulation

캡슐화는 값을 숨기는 것보다 변화를 가두는 일이다

약한 캡슐화

  • 필드를 비공개로 만들더라도 모든 값에 읽기와 쓰기를 제공하면 내부 구조가 노출된다.
  • 외부에서 체력을 계산하고 저장하면 체력 규칙이 호출자에게 퍼진다.

의도 중심 캡슐화

  • takeDamage(), heal()과 spendMana()처럼 의미 있는 행동만 공개한다.
  • 내부 자료 구조와 검증 순서는 객체가 책임진다.
  • 외부 객체는 대상이 피해를 받을 수 있다는 공개 약속만 알면 되고, 체력 필드나 보호막 적용 순서는 알 필요가 없다.
  • 공개된 행동이 유지되면 내부 구현의 변경은 객체 안에서 끝난다.

정보 은닉은 보안 장치가 아니라 변경 전파를 막는 설계의 방화벽이다.

Invariant & State Transition

불변 조건과 상태 전이로 객체를 항상 유효하게 유지한다

  • 불변 조건은 객체가 존재하는 동안 항상 참이어야 하는 규칙이다.
  • 캐릭터의 체력은 유효 범위를 벗어날 수 없고, 사망한 캐릭터는 일반 행동을 수행할 수 없다.
  • 상태 전이는 공격 시작 같은 허용된 사건을 통해서만 상태를 변경하는 과정이다.
  • 사망 상태의 캐릭터에 대한 공격 시작 요청은 거부된다.
행동 가능 │ 공격 시작 ▼ 행동 중 ── 완료 ─▶ 대기 │ 치명적 피해 ▼ 사망 사망 + 공격 요청 = 거부
  • 외부가 상태를 직접 바꾸면 사망했지만 공격 가능한 캐릭터 같은 불가능한 조합이 생긴다.
  • 상태를 소유한 객체가 모든 상태 전이의 유효성을 검사해야 한다.

Tell, Don't Ask

데이터를 캐묻고 대신 판단하면 책임이 누수된다

Ask 중심

hp = target.getHp()
shield = target.getShield()
effects = target.getEffects()
계산 후 target.setHp(...)
  • 호출자가 대상의 내부 구조와 규칙을 모두 알아야 한다.

Tell 중심

result = target
  .receive(damage)
  • 호출자는 대상에게 의도를 전달하고 대상은 자신의 규칙으로 결과를 만든다.
  • Tell, Don't Ask는 모든 조회 기능을 금지하는 절대 규칙이 아니다.
  • 다른 객체의 데이터를 연속해서 읽고 대신 판단하는 코드는 책임 누수의 신호다.
  • 책임 누수가 발견되면 해당 판단을 정보를 소유한 객체로 이동할지 검토한다.

Abstraction & Interface

추상화는 중요한 차이를 남기고 불필요한 차이를 감춘다

  • 전투 진행자에게 검의 재료나 활의 애니메이션 파일은 중요하지 않다.
  • 전투 진행자에게는 모든 무기가 공격 효과를 제공한다는 공통 역할이 중요하다.
  • 인터페이스는 객체를 사용하는 쪽에 필요한 공통 약속을 표현한다.

Useful Abstraction

좋은 추상화는 사용자의 필요와 실제 변화에서 출발한다

실제 변화에 근거한 추상화와 과잉 추상화의 차이

사용자가 필요한 작은 약속만 공개한다.구현 클래스의 모든 기능을 거대한 인터페이스에 복사한다.

  • 인터페이스의 수가 많다고 확장성이 자동으로 높아지는 것은 아니다.
  • 추상화에는 새로운 개념을 배우고 객체의 연결과 실행 흐름을 추적하는 비용이 따른다.
  • 반복되는 변화나 교체 가능성이 확인될 때 추상화의 비용을 정당화할 수 있다.
  • 이 추상화를 제거했을 때 어려워지는 변경이 없다면 아직 추상화가 필요하지 않을 수 있다.

Inheritance

상속은 코드 복사 방지보다 타입 관계를 표현한다

  • 상속은 공통 행동을 재사용하면서 안정적인 “A는 B의 한 종류다”라는 타입 관계를 표현한다.
  • 상속 계층이 깊어지면 부모의 상태와 호출 순서에 대한 결합이 커져 작은 변경도 여러 자식에게 전파될 수 있다.

대체 가능성 점검

  • 하위 타입은 상위 타입의 자리에 놓였을 때 기존 프로그램의 약속을 깨뜨리지 않아야 한다.
  • 하위 타입은 더 까다로운 입력 조건을 요구하거나 상위 타입이 보장한 결과를 약화해서는 안 된다.
  • “전사는 검 사용자다”를 상속으로 표현하면 전사가 활을 장착하는 순간 모델이 깨진다.
  • 무기 사용은 캐릭터의 본질적 타입보다 교체 가능한 능력에 가깝다.

Composition

합성은 독립적으로 변하는 행동을 부품처럼 조립한다

  • 캐릭터는 Sword를 상속하는 대신 Weapon 역할의 객체를 보유하고 공격 행동을 위임한다.
  • 합성을 사용하면 실행 중에 검을 활로 교체할 수 있다.
  • 직업, 무기, AI, 원소와 상태 효과를 상속하면 조합 수만큼 클래스가 증가한다.
  • 합성은 독립적으로 변하는 행동을 각각의 구성요소로 분리한다.

Polymorphism

다형성은 같은 메시지에 각 객체가 다르게 응답하게 한다

종류 판별 중심

  • Battle은 검, 활과 지팡이의 종류를 직접 판별한다.
  • 새 무기를 추가할 때마다 중앙 전투 코드를 수정해야 한다.

다형성 중심

  • Battle은 Weapon에게 공격 효과를 요청하고 각 무기는 자신의 규칙으로 응답한다.
  • 새로운 Weapon 구현을 추가해도 Battle의 요청 방식은 유지된다.
  • 다형성은 모든 조건문을 없애는 기법이 아니라 구체적인 종류에 관한 지식을 해당 객체로 이동시켜 수정 범위를 줄이는 방법이다.
  • 단순한 조건문은 유지하되 종류가 계속 증가하고 동일한 판별이 반복될 때 다형성을 검토한다.

Dependency Inversion

의존성 역전은 핵심 전투 규칙을 세부 기술에서 보호한다

  • Battle이 특정 화면 로그를 직접 사용하면 UI 없이 전투 규칙을 테스트하기 어렵다.
  • Battle이 실제 난수 생성기를 직접 사용하면 테스트 결과를 일정하게 재현하기 어렵다.
  • 핵심 정책이 구체적인 기술을 직접 사용하면 세부 구현의 형태에 끌려간다.
  • BattleLog와 RandomSource의 역할은 핵심 전투 규칙 쪽에서 정의한다.
  • 게임에서는 화면 로그와 실제 난수를 연결한다.
  • 테스트에서는 메모리 기록기와 고정 난수를 연결한다.
BattleRules ─▶ BattleLog ◀─ UI Log ◀─ Test Log BattleRules ─▶ RandomSource ◀─ Real Random ◀─ Fixed Test

의존 방향의 역전: 상위 정책이 하위 도구에 맞추는 대신, 하위 구현이 상위 정책이 정한 안정적인 약속에 맞춘다.

Final Architecture

완성된 전투 시스템: 책임은 나뉘고 협력은 명확해진다

Input ▼ Battle ── 턴과 협력 조정 ├▶ Character ─ 상태·불변 조건 ├▶ Weapon/Skill ─ 효과 생성 ├▶ DamagePolicy ─ 피해 계산 ├▶ StatusEffect ─ 지속 효과 └▶ BattleLog ─ 결과 전달
  • 독 묻은 검은 물리 피해와 독 상태 효과를 생성한다.
  • 피해 정책은 공격자, 방어자와 치명타 조건을 조합한다.
  • 방어자는 자신의 불변 조건을 지키면서 피해를 받는다.
  • 독 객체는 다음 턴부터 피해량과 지속 시간을 관리한다.
  • 얼음 지팡이는 새 Weapon과 빙결 효과를 연결하여 추가한다.
  • 응집도가 높은 객체는 한 목적의 규칙을 모으고, 결합도가 낮은 객체는 협력자의 작은 공개 약속만 안다.

Conclusion

좋은 객체지향 설계는 좋은 질문에서 시작한다

설계할 때 반복할 질문

  • 이 규칙을 가장 잘 아는 객체는 누구인가?
  • 이 객체가 변경되는 이유는 몇 개인가?
  • 다른 객체의 내부 상태를 대신 판단하고 있지 않은가?
  • 새로운 종류를 추가할 때 중앙 분기를 수정해야 하는가?
  • 이 추상화가 해결하는 실제 변화가 존재하는가?

객체지향은 변화하는 규칙을 적절한 객체에 배치하고 안정적인 메시지를 통한 협력으로 시스템을 구성하는 방법이다.

  • 처음부터 완벽한 설계를 기대하기보다 반복되는 변경을 관찰하고 책임을 다시 배치하면서 모델을 발전시켜야 한다.

좋은 설계의 기준은 패턴의 수가 아니라, 다음 변경을 예측 가능한 범위에서 수행할 수 있는가이다.
