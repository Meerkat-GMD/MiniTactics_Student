CHAPTER 01

직접 호출에서 명령 데이터로

학습 목표: 직접 호출이 충분한 경우와 명령 목록이 유용해지는 경우를 구분한다.

직접 호출은 순서가 코드에 보인다

프로그램의 동작이 늘 같은 순서로 실행된다면 메서드를 차례로 호출하는 방식은 읽기 쉽다. 실행할 동작의 이름을 위에서 아래로 읽으면 흐름을 알 수 있고, 잘못된 매개변수 형식은 C# 컴파일러가 확인한다. 동작이 두세 가지이고 자주 바뀌지 않는다면 이 장점만으로 충분할 수 있다.

어려움은 같은 작은 동작을 다른 순서와 값으로 자주 조합할 때 생긴다. A 다음 B를 실행하는 경우, B 다음 A를 실행하는 경우, A를 두 번 실행하는 경우마다 메서드를 하나씩 만들 수 있다. 그러나 조합에서 달라진 것은 작은 동작 자체가 아니라 순서와 값이다. 조합 수만큼 C# 파일이나 분기가 늘어나면 무엇이 공통이고 무엇이 다른지 읽기가 어려워진다.

동작의 뜻과 동작의 나열

두 책임을 나누어 본다. 첫째는 “이 명령은 무엇을 하는가”다. 둘째는 “이번에는 어떤 명령들을 어떤 순서로 사용하는가”다. 첫째는 실행기가 C# 코드로 정하고, 둘째는 데이터가 정하게 만들 수 있다. 데이터 한 줄이 작은 명령 하나를 표현하고 여러 줄의 순서가 프로그램을 표현한다.

책임의 경계명령의 뜻은 실행기에 둔다. 명령의 종류·값·순서는 데이터에 둔다. 같은 실행기가 서로 다른 명령 목록을 읽으면 실행 코드 자체를 복사하지 않고 여러 흐름을 표현할 수 있다.

Bytecode라는 이름의 범위

일반적인 Bytecode는 가상 머신이 읽을 수 있도록 인코딩한 명령의 나열이다. 가상 머신은 실제 CPU와 다른, 프로그램 안에서 구현한 실행기다. CPU가 C# 코드를 직접 읽듯이 데이터를 읽는다는 뜻은 아니다. C#으로 작성한 실행기가 명령의 종류를 해석하고 해당 작업을 호출한다.

이 수업은 네 가지 명령 종류를 가진 단순한 데이터 인터프리터로 이 경계를 배운다. 인터프리터는 명령을 읽고 그 뜻에 따라 실행하는 코드다. 압축된 바이트 스트림, 컴파일러, 범용 스택 가상 머신은 다루지 않는다. 명령이 데이터이고 실행기가 그 뜻을 정한다는 원리는 같지만 표현 범위와 구현 규모는 훨씬 작다.

void FirstSequence()
{
    ShowText("시작");
    Wait(1);
    ShowText("끝");
}

설계 비교용 가상 코드 · 호출 순서가 코드에 고정된 첫 시도다. ShowText와 Wait는 비교를 위한 가상 메서드다.

예의 ShowText와 Wait는 구조를 비교하기 위한 가상 메서드다. 실제 프로젝트의 네 명령에는 기다리기 명령이 없다. 직접 호출과 데이터 해석의 책임 차이만 읽는다.

명령의 종류, 값, 프로그램

명령의 종류는 enum으로 제한한다

enum은 이름을 붙인 선택지의 집합이다. 실행기가 이해하는 종류를 네 가지로 고정한다. 문자열이 아무 이름이나 들어올 수 있다고 해서 실행기가 모든 이름을 처리할 수 있는 것은 아니다.

한 명령에 필요한 값을 묶는다

Instruction은 종류와 정수를 한 값으로 묶는다. Code는 어떤 동작인지, Value는 그 동작의 재료다. 같은 정수라도 명령 종류에 따라 의미가 다르다. AREA의 1은 반경이고 HEAL의 1은 회복량이다.

public readonly struct Instruction
{
    public Instruction(OpCode code, int value)
    {
        Code = code;
        Value = value;
    }

    public OpCode Code { get; }
    public int Value { get; }
}

readonly struct는 만들어진 작은 데이터의 내용을 바꾸지 않도록 표현한 값 형식이다. 생성자에서 Code와 Value를 정한 뒤 get만 있는 속성으로 읽는다. 실행 도중 바뀌는 반경은 명령에 다시 쓰지 않고 실행기의 지역 변수에 보관한다.

CHAPTER 03

한 줄을 읽는 파서

학습 목표: 문자열의 문법과 값의 허용 범위를 각각 검사하는 이유를 설명한다.

문법 검사와 의미 검사

파싱은 글을 정해진 구조로 바꾸는 과정이다. 이 파서는 공백으로 분리한 이름 하나와 정수 하나를 기대한다. 구조가 맞는지 확인한 뒤 이름과 값이 허용 범위 안인지 검사한다.

string[] parts = line.Split((char[])null, StringSplitOptions.RemoveEmptyEntries);
if (parts.Length != 2) return false;
if (!Enum.TryParse(parts[0], out OpCode code)) return false;
if (!Enum.IsDefined(typeof(OpCode), code) || code.ToString() != parts[0]) return false;
if (!int.TryParse(parts[1], out int value)) return false;

실제 코드 · SkillProgram.cs 57–61행 · 일부 발췌다. 바깥 선언과 다른 메서드는 생략했다.

Split은 공백을 기준으로 문자열을 나눈다. RemoveEmptyEntries는 연속한 공백 사이의 빈 조각을 제외한다. parts.Length가 2인지 먼저 확인하므로 뒤의 parts[0]과 parts[1]을 읽을 수 있다.

Enum.TryParse는 글을 enum 값으로 읽으려고 시도한다. 성공했다는 사실만으로 허용하는 명령 이름이 되지는 않는다. 이어지는 IsDefined와 이름 비교는 숫자로 쓴 enum 표기나 정확하지 않은 이름을 거부한다. int.TryParse는 두 번째 조각이 정수인지 확인한다.

out은 성공 여부와 별도로 결과를 받는다

TryParse 계열 메서드는 bool로 성공 여부를 돌려주고, out 매개변수로 읽은 값을 전달한다. 실패했을 때는 그 값을 유효한 명령으로 사용하지 않는다. 이 코드의 if와 return이 그 흐름을 눈에 보이게 만든다.

int maximum = code == OpCode.AREA ? 3 : 99;
if (value < 0 || value > maximum) return false;
if (code == OpCode.PUSH && value != 1) return false;
instruction = new Instruction(code, value);
error = string.Empty;
return true;

AREA는 최대 3, DAMAGE와 HEAL은 최대 99다. PUSH는 앞의 일반 범위 검사를 지난 뒤 1인지 다시 확인한다. 검사를 모두 통과한 마지막에 Instruction을 만든다.

처음에는 결과가 없는 상태다

program = null;
error = "Program is empty.";

program은 아직 없고 기본 오류는 빈 프로그램이라는 내용이다. 글이 없거나 공백뿐이면 바로 실패한다. 한 줄이라도 읽을 글이 있으면 줄바꿈으로 나누어 순회한다. 문자열을 읽는 과정에서는 아직 효과를 적용하지 않는다.

실패한 줄 번호를 보존한다

for (int index = 0; index < lines.Length; index++)
{
    if (string.IsNullOrWhiteSpace(lines[index])) continue;
    if (!TryInstruction(lines[index], out Instruction instruction, out error))
    {
        error = $"Line {index + 1}: {error}";
        return false;
    }

    instructions.Add(instruction);
}

CHAPTER 05

실행기가 목록을 읽는 방법

학습 목표: 명령 데이터와 실행 중 상태를 구분하고 분기문의 역할을 설명한다.

반경은 이번 실행의 상태다

protected override void Activate(Unit target)
{
    if (!ReadProgram(out SkillProgram program)) return;
    int radius = 0;
    foreach (SkillProgram.Instruction instruction in program.Instructions)
    {
        if (instruction.Code == SkillProgram.OpCode.AREA)
        {
            radius = instruction.Value;
        }
        else
        {
            Execute(instruction, target, radius);
        }
    }
}

실제 코드 · ScriptedSkill.cs 18–33행 · 해당 메서드 전체다.

실행을 시작할 때 radius는 0이다. foreach는 Instructions에 들어 있는 순서대로 명령을 꺼낸다. AREA이면 반경 값만 바꾼다. 다른 명령이면 현재 반경을 Execute에 전달한다. AREA의 영향은 다음 AREA를 만날 때까지 이어지고, 다음번 Activate 호출은 다시 0에서 시작한다.

선택한 중심과 효과 대상은 구분한다

bool heal = instruction.Code == SkillProgram.OpCode.HEAL;
Team team = heal ? User.Team : (User.Team == Team.Player ? Team.Enemy : Team.Player);
foreach (Unit target in Turns.GetUnitsInRange(center, radius, team))

실제 코드 · ScriptedSkill.cs 37–39행 · 일부 발췌다. 바깥 선언과 다른 메서드는 생략했다.

center는 이번 실행의 중심이다. radius는 중심에서 얼마나 떨어진 대상을 포함할지 정한다. HEAL은 사용자 진영을, DAMAGE와 PUSH는 반대 진영을 찾는다. 각각의 효과 명령을 실행할 때 대상 목록을 다시 읽으므로 앞 명령에서 사라지거나 이동한 대상의 상태가 다음 명령에 영향을 줄 수 있다.

opcode가 실제 작업과 연결되는 위치

switch (instruction.Code)
{
    case SkillProgram.OpCode.DAMAGE:
        Strike(target, instruction.Value);
        break;
    case SkillProgram.OpCode.HEAL:
        Restore(target, instruction.Value);
        break;
    case SkillProgram.OpCode.PUSH:
        Turns.PushAway(User, target);
        break;
}

실제 코드 · ScriptedSkill.cs 41–52행 · 일부 발췌다. 바깥 선언과 다른 메서드는 생략했다.

switch의 각 case가 명령의 뜻이다. DAMAGE n은 n을 추가 피해로 기존 Strike에 전달한다. 그러므로 DAMAGE 0은 아무 일도 안 하는 명령이 아니다. HEAL n은 Restore에 회복량을 전달한다. PUSH는 파서가 1만 허용하므로 실행기는 한 칸 밀기를 요청한다.

실제 이동·피해·회복의 세부 방법은 여기서 다시 만들지 않는다. 실행기는 명령의 종류를 기존 작업에 연결한다. 이런 경계를 두어야 같은 명령의 뜻이 데이터마다 달라지지 않는다.

AREA는 HP를 바꾸지 않는다. 다음 효과가 사용하는 반경만 바꾼다. 반경 0의 HEAL은 중심 A만 회복하고, 반경 1의 HEAL은 A와 B를 함께 회복한다. 사용자의 위치에서 반경을 재는 것으로 읽으면 이 표를 설명할 수 없다. 중심은 선택한 대상이다.

순서를 바꾸면 무엇이 달라지는가

AREA 1
HEAL 2
HEAL 5
AREA 0
HEAL 1

실행 추적용 입력이다. C# 코드가 아니라 이 실행기가 읽는 명령 문자열이다.

AREA 1을 맨 앞에 옮기면 첫 HEAL 2도 B에게 적용된다. A는 9로 같고 B는 8이 된다. HEAL의 구현이나 정수 값은 바꾸지 않았다. 순서가 실행 상태를 바꾸었기 때문에 결과가 달라졌다.

값 하나를 바꾸면 무엇이 달라지는가

첫 번째 목록의 마지막 HEAL 1을 HEAL 3으로 바꾸면 A는 11, B는 6이다. 마지막 명령의 반경은 0이므로 B는 영향을 받지 않는다. 단, 회복 후 HP는 대상의 최대 HP를 넘지 않는 기존 Restore의 규칙을 따른다.

추적 순서출발 상태를 적고, 읽을 명령을 고른 뒤, 그 명령이 상태를 바꾸는지 효과를 실행하는지 구분한다. 현재 반경으로 대상과 결과를 계산하고 다음 명령으로 넘어간다.

CHAPTER 07

표현 범위와 다른 패턴의 관계

학습 목표: 데이터 변경과 실행기 변경을 구분하고 기존 패턴과의 연결 범위를 설명한다.

실행기가 알고 있는 조합

AREA·DAMAGE·HEAL·PUSH의 순서와 값을 바꾸면 많은 조합을 표현할 수 있다. 그러나 조건 분기, 반복 점프, 기다리기, 변수 계산을 문자열에 적는 문법은 없다. 이 명령 언어가 제공하지 않는 동작은 이름만 적어도 사용할 수 없다.

요구현재 데이터만 변경이유
회복량 5를 3으로가능기존 HEAL의 값 변경
범위를 바꾼 뒤 두 효과 실행가능기존 명령을 순서대로 나열
HP가 절반 이하이면 실행불가능조건 명령이 없음
새 TELEPORT 동작불가능명령과 실행기의 연결을 추가해야 함

Command와 비교

Command도 실행할 요청을 데이터처럼 다룬다. 일반적인 명령 객체는 자신의 Execute 안에 실행 방법을 가진다. 이 수업의 Instruction은 종류와 정수만 가진다. 실제 실행 방법은 ScriptedSkill의 분기문에 있다. 요청을 보관한다는 공통점과 실행 방법이 놓이는 위치의 차이를 함께 본다.

Subclass Sandbox와의 연결

ScriptedSkill은 기존 Skill의 자식이다. 바깥은 이전과 같은 GetTargets와 Use 입구를 사용한다. 이 자식 안에 명령 목록을 읽는 실행기가 들어간다. 기존 입구를 유지하면서 자식의 동작을 데이터로 조합하는 구조다.

새 실행기는 User와 Turns 문맥에도 접근하므로 부모 도구만 사용하던 이전 자식보다 바깥 시스템을 더 많이 안다. 이는 범위 대상을 다시 찾고 밀기를 요청하기 위한 실제 의존이다. Bytecode를 도입했다고 모든 결합이 사라졌다고 설명하지 않는다.

CHAPTER 08

비용과 적용 기준

학습 목표: 동작 조합의 유연성과 해석·검증의 비용을 함께 비교한다.

새 조합과 새 동작은 수정할 곳이 다르다

실행기가 이미 아는 명령을 재배열하거나 값을 바꾸는 작업은 데이터로 표현할 수 있다. 반대로 실행기가 한 번도 배운 적 없는 동작은 명령 목록에 이름만 적어도 실행되지 않는다. 그 동작을 나타내는 명령 종류와 실행기의 해석 코드를 함께 추가해야 한다. 데이터로 표현한다는 말은 모든 새 동작을 코드 수정 없이 만들 수 있다는 뜻이 아니다.

실행 과정이 한 단계 더 생긴다

직접 메서드를 호출하면 호출 위치에서 실행할 코드를 따라갈 수 있다. 인터프리터에서는 먼저 현재 명령을 확인하고, 명령 종류로 분기한 뒤, 실제 작업을 따라가야 한다. 잘못된 결과를 조사할 때 데이터의 순서와 값, 실행기의 분기, 작업을 수행하는 대상까지 확인해야 한다. 저장 방식이 유연해진 만큼 추적할 지점도 늘어난다.

검증할 책임이 데이터 쪽으로 이동한다

C# 코드로만 표현한 동작은 컴파일러가 검사하는 부분이 많다. 데이터로 옮긴 값의 범위나 명령 순서의 의미까지 C# 컴파일러가 알지는 못한다. 제작 도구와 실행기가 어떤 입력을 허용할지 정해야 한다. 이 수업의 데이터 형식이 허용하는 명령과 값을 이해하고 사용해야 하는 이유다.

성능에 대한 판단간접 해석이 추가되므로 Bytecode를 사용했다는 이유만으로 실행이 빨라지지는 않는다. 이 수업의 목적은 동작 조합을 데이터로 표현하고 책임을 분리하는 것이다. 실제 성능은 작업의 종류와 데이터 양, 실행 횟수를 정해 측정해야 한다.

적용을 판단하는 질문

같은 작은 동작의 순서와 값만 다른 경우가 반복되는가? 그 조합을 코드 파일을 열지 않고 수정할 가치가 있는가? 표현 가능한 동작을 제한해도 괜찮은가? 이 질문에 긍정적으로 답할 수 있을 때 명령 데이터와 실행기를 나누는 비용을 검토할 만하다. 실행 흐름이 고정되어 있고 새 동작마다 C# 코드가 필요한 작은 프로그램은 직접 호출로도 충분하다.

더 읽기: Game Programming Patterns의 Bytecode. 이 교재는 해당 패턴의 책임 경계를 프로젝트의 작은 실행기로 설명한다.

CHAPTER 09

복습 질문과 용어

학습 목표: 정답의 근거를 실제 코드와 연결해 말한다.

질문과 해설

1. AREA 1 뒤에 HEAL 5가 두 번 있으면 반경은 언제 0으로 돌아가는가?
그 목록 안에 AREA 0이 없다면 이번 실행 동안은 1을 유지한다. 다음 Activate 호출이 지역 변수 radius를 0으로 초기화한다.

2. DAMAGE 0은 피해를 주지 않는 명령인가?
아니다. 0은 추가 피해이고 Strike의 기존 공격 처리 자체는 실행된다. 값의 의미는 명령의 종류와 연결된 실행 코드를 읽어야 알 수 있다.

3. 유효한 첫 줄 다음에 잘못된 줄이 있으면 첫 줄만 실행되는가?
아니다. 파서가 전체 목록을 성공으로 만들기 전에는 Activate의 효과 순회를 시작하지 않는다. 다만 실행 중 상태 변화를 모두 취소하는 기능과는 구분한다.

4. AREA 1은 사용자의 선택 사거리를 늘리는가?
아니다. 선택한 중심에서 이후 효과의 반경을 정한다. 중심을 선택할 수 있는 범위는 별도의 기존 대상 선택 규칙이다.

5. 새로운 동작 이름을 문자열에 추가하면 실행되는가?
파서가 아는 네 이름 중 하나가 아니면 실패한다. 새 동작은 종류, 값의 규칙, 실행기 분기까지 추가해야 한다.
