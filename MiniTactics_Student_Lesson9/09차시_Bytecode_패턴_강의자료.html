Chapter 01

직접 호출과 조합 복사의 한계

직접 호출은 잘못된 설계가 아니다. 작은 고정 조합에는 가장 읽기 쉬운 선택일 수 있다. 같은 연산의 순서와 값만 바뀌는 요구가 반복될 때, 복사된 메서드와 이름별 분기가 유지 비용이 되는지 관찰한다.

작은 연산 도구가 이미 있다

고정된 작업

기존 Skill은 Strike와 Restore 같은 제한된 작업 통로를 제공한다. 호출할 수 있는 연산의 뜻은 C# 코드에 있다.

새로 달라지는 조합

반경을 바꾸고, 어떤 효과를 먼저 호출할지 달리하고 싶다. 연산 자체와 연산의 조합은 다른 변경 이유다.

앞선 구조는 작업의 세부를 감추는 데 유용하다. 여기서는 그 도구의 순서와 매개변수를 표현하는 문제만 본다.

조합마다 메서드를 복사하면?

설계 비교용 가상 코드 · 현재 소스에 없는 비교 예

void VariantA()
{
    SetArea(1);
    DealDamage(4);
    PushOnce();
}

충분한 경우

조합이 한두 개로 고정되고 드물게 바뀌면 직접 호출이 간단하다.

복사가 늘면

값과 순서만 다른 메서드에도 비슷한 흐름이 반복된다. 바꿀 때마다 C# 코드를 손본다.

이름별 switch도 조합을 코드에 묶는다

설계 비교용 가상 코드 · 현재 소스에 없는 비교 예

switch (variantName)
{
    case "A": SetArea(1); DealDamage(4); break;
    case "B": SetArea(2); DealDamage(4); break;
}

이름이 적으면 합리적인 첫 시도다. 하지만 새 순서를 추가할 때마다 분기가 늘어난다. 공통 해석 흐름을 유지하며 명령 목록만 바꾸는 경계가 필요하다.

Chapter 02

작은 언어와 책임의 경계

프로그램 데이터는 무엇을 어떤 순서로 요청할지 표현한다. 파서는 원문의 형태를 검사하고, 해석기는 고정된 어휘를 기존 작업 통로에 연결한다. 이 구분은 임의의 C# 코드를 실행하도록 허용한다는 뜻이 아니다.

연산의 뜻과 조합 데이터를 나눈다

→

→

→
해석기 · 실행

코드로 고정

허용할 명령 이름, 인수 범위, 각 연산의 실행 방법.

데이터로 변경

명령의 순서, 반경과 효과의 정수 인수.

파서(parser)는 텍스트를 읽고 구조를 검사한다. 해석기(interpreter)는 검사된 명령 목록을 차례로 읽어 작업을 요청한다.

이 수업의 Bytecode는 메모리 속 명령 목록

명령의 표현

문자열을 OpCode와 정수 인수의 쌍으로 바꾸어 메모리에 보관한다. 매번 텍스트의 뜻을 추측하며 실행하지 않는다.

현재 언어의 범위

앞에서 뒤로 읽는 작은 언어다. 스택, 점프, 반복문, 임의의 C# 실행은 없다.

여기서 SkillProgram은 일반 sealed C# 클래스다. Unity 에셋이나 C# 컴파일 결과, 기계어 바이너리가 아니다. Bytecode라는 패턴의 명령 데이터와 해석 흐름 분리를 작게 구현한다.

Chapter 03

명령 값과 프로그램 목록

명령어(opcode)는 허용한 연산의 이름이며 인수(operand)는 그 연산에 전달할 값이다. 현재 표현은 둘을 가진 readonly Instruction이다. 읽기 전용 목록의 소유 경로와 참조한 객체 전체의 불변성은 구분해서 읽는다.

OpCode는 실행 가능한 말의 목록

Chapter 04

한 줄의 이름과 인수 검사

한 줄의 문법은 두 토큰이다. 앞은 정의된 대문자 이름, 뒤는 int.TryParse가 해석한 정수이며 명령별 범위를 통과해야 한다. 예를 들어 +2 같은 표기를 단지 부호가 있다는 이유만으로 거절하는 숫자 전용 정규식을 가정하면 현재 소스와 다르다.

한 줄은 명령 이름과 정수 인수 두 토큰

입력 예문법 결과이유
AREA 2 / PUSH 1허용이름과 인수가 정해진 범위
area 2 / 0 2거절대문자 명령 이름만 허용
AREA 4 / PUSH 2거절반경 상한 / PUSH의 고정 인수 위반
HEAL / HEAL 3 extra거절정확히 두 토큰 필요

토큰은 공백으로 나뉜 문자열 조각이다. 빈 줄은 무시한다. 정수 해석은 int.TryParse를 사용하므로 “숫자 문자만”이라는 별도 정규식을 가정하지 않는다.

숫자 enum 값까지 이름으로 받아들이지 않는다

string[] parts = line.Split((char[])null, StringSplitOptions.RemoveEmptyEntries);
if (parts.Length != 2) return false;
if (!Enum.TryParse(parts[0], out OpCode code)) return false;
if (!Enum.IsDefined(typeof(OpCode), code) || code.ToString() != parts[0]) return false;
if (!int.TryParse(parts[1], out int value)) return false;

    break;
case SkillProgram.OpCode.HEAL:
    Restore(target, instruction.Value);

DAMAGE는 Strike, HEAL은 Restore에 Value를 전달한다. 해석기는 제한된 연산만 요청한다. 데이터에 없는 C# 코드를 실행하는 통로는 없다.

    Turns.PushAway(User, target);

Chapter 08

반경과 원문 순서를 추적하기

아래는 개념을 설명하는 프로그램 추적이다. 특정 장면이나 배치의 공략이 아니다. 같은 명령 집합이라도 순서를 바꾸면 조회 시점의 위치와 생존 상태가 달라질 수 있다. 실제 호출 순서와 조회 시점을 함께 읽어야 한다.

AREA 변경은 이후 효과의 반경을 바꾼다

원문 순서실행 전 → 후 radius요청
시작0없음

설명용 프로그램 추적이다. DAMAGE는 상대 팀, HEAL은 사용자 팀을 각각 고르므로 같은 대상 목록이라는 가정은 없다. AREA의 위치를 옮기면 그 효과가 받는 반경도 달라진다.

PUSH 다음 DAMAGE와 그 반대는 같을까?

AREA 1 → PUSH 1 → DAMAGE 4

PUSH가 대상을 옮겼다면 DAMAGE는 옮겨진 상태로 새로 조회한다. 중심 대상도 이동했다면 중심의 현재 위치를 사용한다.

AREA 1 → DAMAGE 4 → PUSH 1

DAMAGE 뒤에 살아 있는 대상만 PUSH 조회에 남는다. 앞선 명령의 결과가 뒤의 조회에 영향을 줄 수 있다.

답: 같다고 보장할 수 없다. 각 Execute 안의 목록은 그 호출에서 순회하지만, 다음 명령은 새로운 목록을 받는다. 원문 순서는 의미의 일부다.

Chapter 09

문법 실패와 막힌 작업의 차이

파서가 모든 문법 오류를 앞에서 거절하는 것과 유효한 프로그램 전체가 원하는 결과를 반드시 내는 것은 다른 보장이다. 실행 단계의 작업 규칙은 각 연산에 적용된다. 현재 구조에는 실행한 효과를 일괄 취소하는 기록이 없다.

Chapter 10

이득과 비용으로 적용 판단하기

Bytecode 패턴의 이득은 안정된 어휘 위에서 데이터로 조합을 바꾸는 데 있다. 속도 향상은 별도 측정 문제다. 제한된 언어가 요구를 충분히 담는지, 오류를 설명하고 유지할 비용을 감당할 수 있는지 먼저 판단한다.

조합 변경의 편의에는 언어를 유지하는 비용이 따른다

이득

같은 해석기를 쓰며 명령 순서와 값을 데이터로 바꾼다. 허용된 어휘로 조합의 범위를 제한한다.

비용

문법 검사, 오류 위치, 디버깅이 필요하다. 조회·사용 때 재파싱과 할당이 반복된다. 명령 추가는 파서와 해석기 변경을 요구한다.

이 패턴을 썼다고 실행 속도나 FPS가 높아지는 것은 아니다. 현재 자료는 성능 향상을 측정하거나 보장하지 않는다.

조합이 자주 달라지는 제한된 언어가 필요한가?

상황판단
몇 개의 고정 호출만 있음직접 호출이나 작은 분기로 충분할 수 있음
같은 연산을 여러 순서·값으로 자주 조합명령 데이터와 해석기를 나눌 근거가 생김
복잡한 분기·반복이 필요현재 네 명령 언어가 충분한지 다시 판단
새 기본 연산을 자주 추가데이터 변경만으로 끝나지 않는 비용을 고려

먼저 바뀌는 것이 조합인지 연산의 뜻인지 구분한다. 언어를 작게 유지하는 것도 설계 결정이다.
