Mini Tactics · Lesson 09

미니 택틱스로 이해하는
Bytecode 패턴

작은 동작의 뜻은 코드에 두고,
동작의 순서와 값은 데이터로 표현한다.

Starting point

직접 호출은 고정된 순서를 읽기 쉽다

void FirstSequence()
{
    ShowText("시작");
    Wait(1);
    ShowText("끝");
}

설계 비교용 가상 코드 · 호출 순서가 코드에 고정된 첫 시도다. ShowText와 Wait는 비교를 위한 가상 메서드다.

동작이 적고 순서가 잘 바뀌지 않으면 이 방식으로 충분하다. 위에서 아래로 읽으면 실행 순서를 알 수 있다.

New requirement

같은 동작을 다른 순서로 조합한다

작은 동작은 같은데
값과 순서만 다른 조합이 계속 늘어난다.
조합마다 C# 메서드를 만들어야 할까?

같은 부분

각 동작이 실제로 일하는 방법이다.

달라지는 부분

무슨 동작을 어떤 값으로, 어떤 순서에 실행하는가다.

First attempt

첫 시도는 조합마다 메서드를 만든다

void SequenceA() { Damage(2); Heal(3); }
void SequenceB() { Heal(3); Damage(2); }
void SequenceC() { Damage(5); Heal(3); }

설계 비교용 가상 코드 · 조합을 별도 메서드로 적은 비교 예다. Damage와 Heal은 가상 메서드다.

각 줄은 이해하기 쉽다. 하지만 순서나 값이 바뀔 때마다 코드에서 조합을 수정한다. 동작의 구현과 조합의 수정 주기가 달라질수록 분리할 이유가 생긴다.

Observe the limit

조합의 차이를 코드로 반복해서 적는다

변경첫 시도에서 수정할 것
같은 동작, 다른 값메서드 본문의 인수
같은 값, 다른 순서메서드 안의 호출 순서
새로운 조합새 메서드 또는 분기
새로운 작은 동작그 동작의 실제 구현

앞의 세 변경은 동작의 뜻을 바꾸지 않는다. 이 차이를 데이터로 적을 수 있는지 살펴본다.

Find the boundary

동작의 뜻과 명령 목록을 나눈다

실행기가 정하는 것

각 명령이 어떤 작업을 하는지 정한다. 명령을 읽고 해당 작업을 호출한다.

데이터가 정하는 것

실행할 명령의 종류, 그 명령에 줄 값, 명령의 나열 순서를 정한다.

같은 실행기에 다른 명령 목록을 주면 다른 조합을 실행한다.

Bytecode pattern

명령을 데이터로 적고 실행기가 해석한다

원본 문자열사람이 적은 명령과 값이다.
파서 · SkillProgram문자열을 검사하고 명령 목록을 만든다.
명령 · Instruction명령의 종류와 정수 값을 보관한다.
실행기 · ScriptedSkill목록을 순서대로 읽고 동작을 고른다.

파서는 글을 정해진 구조로 읽는 코드다. 인터프리터는 그 구조의 뜻을 해석해 실행하는 코드다.

Model boundary

이 수업은 단순한 데이터 인터프리터를 사용한다

일반적인 Bytecode

가상 머신이 읽는 명령을 인코딩한 나열이다. 가상 머신은 프로그램 안에서 구현한 실행기다.

수업의 축소 모델

문자열을 네 종류의 명령과 정수 값으로 바꾼다. C# 실행기가 명령 목록을 해석한다.

압축 바이트 스트림이나 범용 스택 VM을 구현하는 것은 아니다. 데이터와 실행기를 나누는 책임 경계에 집중한다.

Actual code · Instruction

생성한 명령의 값은 읽기만 한다

public Instruction(OpCode code, int value)
{
    Code = code;
    Value = value;
}

public OpCode Code { get; }
public int Value { get; }

생성자가 Code와 Value를 기록한다. get만 있는 속성은 만들어진 명령의 값을 읽는 입구다. 해석 도중 명령 자체를 고치는 대신 실행기가 별도 상태를 가진다.

Actual code · Parser

한 줄은 이름 하나와 정수 하나다

string[] parts = line.Split((char[])null, StringSplitOptions.RemoveEmptyEntries);
if (parts.Length != 2) return false;
if (!Enum.TryParse(parts[0], out OpCode code)) return false;
if (!Enum.IsDefined(typeof(OpCode), code) || code.ToString() != parts[0]) return false;
if (!int.TryParse(parts[1], out int value)) return false;

공백으로 나눈 조각이 정확히 둘이어야 한다. 명령 이름은 AREA·DAMAGE·HEAL·PUSH 중 하나를 대문자로 적는다. 숫자로 된 enum 표기와 소문자 이름도 거부한다.

값의 허용 범위도 파서가 확인한다

int maximum = code == OpCode.AREA ? 3 : 99;
if (value < 0 || value > maximum) return false;
if (code == OpCode.PUSH && value != 1) return false;
instruction = new Instruction(code, value);
error = string.Empty;

Validation before execution

틀린 마지막 줄 앞의 명령도 실행하지 않는다

HEAL 5
PUSH 2

실행 추적용 입력이다. C# 코드가 아니라 이 실행기가 읽는 명령 문자열이다.

예측과 답

첫 줄의 효과가 먼저 실행될까?

아니다. PUSH는 1만 허용하므로 파싱이 실패한다. 프로그램 전체를 읽기 전에 효과를 실행하지 않는다.

if (!ReadProgram(out SkillProgram program)) return;

Change locations

새 조합과 새 동작은 수정 위치가 다르다

바꾸려는 것어디를 바꾸는가이유
HEAL 5를 HEAL 3으로명령 데이터실행기가 HEAL을 이미 안다.
AREA 뒤에 HEAL 추가명령 데이터기존 명령을 다른 순서로 조합한다.
새로운 TELEPORT 동작명령 종류·검증·실행기현재 네 opcode로 표현할 수 없다.

데이터가 표현할 수 있는 범위는 실행기가 제공하는 명령의 범위다.

Costs

유연한 조합에는 해석과 검증 비용이 따른다

이득함께 생기는 비용
같은 실행기로 조합을 바꾼다.데이터와 실행기를 함께 추적해야 한다.
동작 순서를 데이터로 적는다.허용 이름·값·순서의 규칙을 정해야 한다.
표현 가능한 동작을 제한한다.새 종류의 동작은 실행기를 고쳐야 한다.

이 구조가 자동으로 실행 속도를 높여 주지는 않는다. 간접 해석의 비용과 제작·변경의 이득은 따로 판단한다.

Judgment

반복되는 차이가 순서와 값인지 살핀다

도입을 검토할 상황

같은 작은 동작의 조합이 많다. 순서와 값을 자주 바꾼다. 정해진 명령만 사용하도록 제한할 이유가 있다.

직접 코드가 충분한 상황

흐름이 고정되어 있다. 조합이 적다. 매번 새로운 종류의 동작을 구현해야 해서 명령 목록의 이득이 작다.

코드 파일의 수만 세지 말고, 실제로 바뀌는 부분이 동작의 뜻인지 조합 데이터인지 확인한다.

Check yourself

명령의 값과 실행기의 책임을 구분한다

질문 1

AREA 1을 읽은 다음 AREA가 없으면 반경이 자동으로 0이 되는가?

답: 아니다. 이번 실행에서 이후 명령은 계속 반경 1을 사용한다. 다음 실행은 다시 0으로 시작한다.

질문 2

DAMAGE 0 다음 알 수 없는 이름이 있다. 첫 피해는 실행되는가?

답: 아니다. 전체 파싱이 먼저 실패한다. 유효한 DAMAGE 0 하나만 있다면 기본 공격 피해는 발생한다.

Takeaway

데이터는 조합을 적고 실행기는 뜻을 정한다

  1. 명령은 종류와 값을 가진 데이터다.
  2. 파서는 모든 줄을 검사한 뒤 프로그램을 만든다.
  3. 실행기는 순서대로 읽으며 필요한 실행 상태를 관리한다.
  4. 새 조합은 데이터로, 새 동작은 실행기 확장으로 만든다.

유연하게 바꿀 부분과 코드가 책임질 부분을 함께 정한다.
