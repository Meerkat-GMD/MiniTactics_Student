미니 택틱스로 이해하는
Observer 패턴

유닛 하나의 체력이 바뀌면 여러 곳이 함께 달라져야 한다.
이때 누가 누구를 알아야 할까?

Starting Point

지금까지는 필요한 객체를 직접 호출했다

GameManager.Instance.Finish(result);

5차시부터 사용하고 있는 실제 호출이다. 전투 결과를 확정할 때 사용한다.

직접 호출의 장점

호출하는 줄을 읽으면 다음에 어떤 메서드가 실행되는지 바로 알 수 있다.

직접 호출의 전제

부르는 쪽이 받는 쪽의 class와 메서드 이름을 알고 있다. 받는 쪽은 하나로 정해져 있다.

오늘은 이 전제가 맞지 않는 상황을 다룬다. 받는 쪽이 여럿이고 앞으로 더 늘어날 수 있는 경우다.

New Requirement

체력이 바뀌면 여러 곳이 함께 달라져야 한다

“유닛의 체력이 줄었을 때
달라져야 하는 것은
무엇인가?”

반응하는 곳해야 하는 일
체력바체력이 바뀔 때마다 남은 체력의 비율만큼 길이를 줄인다.
전멸 판정유닛이 쓰러졌을 때 같은 진영에 살아 있는 유닛이 남았는지 확인한다.
피해 숫자, 효과음, 전투 기록아직 없지만 앞으로 추가될 수 있다.

일어난 사실은 “체력이 바뀌었다” 하나다. 그 사실에 반응하는 곳은 여럿이고 앞으로 늘어난다.

First Attempt

첫 시도: Unit이 필요한 곳을 모두 직접 호출한다

public void TakeDamage(int damage)
{
    CurrentHp = Mathf.Max(0, CurrentHp - damage);
    _healthBar.Refresh(CurrentHp, _maxHp);
    if (CurrentHp == 0)
    {
        GameManager.Instance.OnUnitDied(this);
    }
}

이 코드는 동작한다. 반응하는 곳이 둘뿐이고 앞으로도 늘어나지 않는다면 이 방식으로 충분하다.

설계 비교용 가상 코드다. 5차시에는 사망 기능이 없었다. 오늘 사망을 추가하면서 떠올릴 수 있는 첫 시도를 적은 것이며, 프로젝트에 있었던 코드가 아니다.

Observe the Limit

첫 시도에서는 기능을 추가할 때마다 Unit을 고쳐야 한다

Unit이 알고 있어야 하는 것

UnitHealthBar의 Refresh와 그 인수 두 개, 그리고 GameManager의 OnUnitDied다. 발행하는 쪽인 Unit이 반응하는 class 두 개의 이름과 메서드를 모두 알고 있다.

새 요구첫 시도에서 고쳐야 하는 곳
효과음을 추가한다.새 class를 만들고, Unit.cs에 필드와 호출 한 줄을 추가한다.
피해 숫자를 추가한다.새 class를 만들고, Unit.cs에 필드와 호출 한 줄을 추가한다.
체력바가 없는 유닛을 만든다._healthBar가 비어 있으면 NullReferenceException이 발생한다. Unit.cs에 null 검사를 추가한다.

체력을 깎는 규칙은 한 번도 바뀌지 않았다. 그런데도 Unit.cs는 요구가 생길 때마다 수정된다.

Flip the Direction

방향을 뒤집는다: 듣는 쪽이 스스로 등록한다

첫 시도의 방향

Unit → UnitHealthBar
Unit → GameManager

알리는 쪽이 듣는 쪽을 모두 알고 있다. 듣는 쪽이 늘어나면 알리는 쪽을 고쳐야 한다.

뒤집은 방향

UnitHealthBar → Unit
GameManager → Unit

듣는 쪽이 알리는 쪽을 알고 있다. 듣는 쪽이 늘어나도 알리는 쪽은 그대로다.

Unit은 “체력이 바뀌었다”고 알리기만 한다. 그 사실에 관심이 있는 쪽이 자신의 메서드를 Unit에 등록한다. 의존이 없어지는 것은 아니다. 의존의 방향이 바뀌는 것이다.

Observer Pattern

이 구조의 이름이 Observer 패턴이다

상태를 가진 객체가 변화를 알리면, 미리 등록한 객체들이 각자 자신의 일을 한다.

발행자(Subject) · Unit체력을 소유한다. 체력이 바뀌거나 쓰러졌을 때 알린다. 누가 듣는지는 알지 못한다.
알림 · HpChanged, Died발행자가 공개하는 알림의 통로다. C#에서는 event로 선언한다.
구독자 1 · UnitHealthBarHpChanged를 구독한다. 자기 유닛의 체력바 길이를 바꾼다.
구독자 2 · GameManagerDied를 구독한다. 한 진영이 전멸했는지 판정한다.

발행은 알림을 보내는 일이고, 구독은 알림을 받을 메서드를 등록하는 일이다. 구독자를 영어로 Observer라고 부르며 패턴의 이름은 여기에서 왔다.

C# event

C# event는 선언, 발행, 구독, 해제의 네 동작으로 쓴다

public event Action<Unit> HpChanged;   // 선언: 알림의 통로
HpChanged?.Invoke(this);               // 발행: 듣는 쪽이 없어도 된다
_unit.HpChanged += Refresh;            // 구독: 듣는 쪽이 등록한다
_unit.HpChanged -= Refresh;            // 해제: 등록한 쪽이 책임진다
동작코드를 쓰는 곳뜻
선언발행자(Unit)알림의 통로를 만든다.
발행발행자(Unit)등록된 메서드를 모두 호출한다.
구독 +=구독자자신의 메서드를 등록한다.
해제 -=구독자등록했던 메서드를 목록에서 뺀다.

서로 다른 파일에 있는 네 줄을 한곳에 모은 것이다. 선언과 발행은 Unit.cs에, 구독과 해제는 UnitHealthBar.cs에 있다.

Declaration

선언: Action<Unit>은 구독할 메서드의 모양을 정한다

// Unit.cs
public event Action<Unit> HpChanged;
public event Action<Unit> Died;

// 구독할 수 있는 메서드의 모양
private void Refresh(Unit unit)          // UnitHealthBar.cs
private void OnUnitDied(Unit deadUnit)   // GameManager.cs

Action<Unit>의 뜻

Unit 하나를 받고 반환값이 없는 메서드를 뜻한다. 구독하는 메서드는 이 모양과 같아야 한다. 모양이 다르면 +=에서 컴파일 오류가 발생한다.

전달되는 Unit은 변화가 일어난 바로 그 유닛이다. 구독자는 이 유닛에서 CurrentHp, MaxHp, Team, IsAlive를 읽는다. 알림에 피해량이나 새 체력을 따로 담지 않아도 된다.

선언 두 줄은 Unit.cs의 실제 코드다. 아래 두 줄은 각 파일에 있는 메서드의 첫 줄만 옮긴 것이다.

event Keyword

event 키워드는 바깥의 대입과 발행을 막는다

// Unit이 아닌 class에서 작성한 코드
unit.HpChanged += Refresh;       // 허용: 구독
unit.HpChanged -= Refresh;       // 허용: 해제
unit.HpChanged = null;           // 컴파일 오류: 대입
unit.HpChanged.Invoke(unit);     // 컴파일 오류: 발행

대입을 막는 이유

=로 대입하면 이미 등록된 메서드가 모두 지워진다. 구독자 하나가 실수로 대입하면 같은 알림을 듣던 다른 구독자의 등록까지 사라진다.

발행을 막는 이유

바깥에서 Invoke를 호출하면 체력이 바뀌지 않았는데도 바뀌었다는 알림이 나간다. 발행은 값을 소유한 Unit만 할 수 있어야 한다.

event를 빼고 public Action<Unit> HpChanged;로 선언하면 위의 네 줄이 모두 컴파일된다.

허용되는 코드와 오류가 나는 코드를 비교하기 위한 설명용 코드다.

Actual Code · Unit.cs

발행: 값을 먼저 바꾸고, 그다음에 알린다

public void TakeDamage(int damage)
{
    CurrentHp = Mathf.Max(0, CurrentHp - damage);
    HpChanged?.Invoke(this);

    if (!IsAlive)
    {
        Died?.Invoke(this);
        gameObject.SetActive(false);
    }
}

실행 순서

  1. CurrentHp를 새 값으로 바꾼다.
  2. HpChanged를 발행한다.
  3. 쓰러졌다면 Died를 발행한다.
  4. 마지막에 유닛을 비활성화한다.

이 메서드에는 체력바도 GameManager도 등장하지 않는다. 첫 시도의 직접 호출 두 줄이 발행 두 줄로 바뀌었다. IsAlive는 CurrentHp > 0을 계산하는 속성이다.

Unit.cs의 TakeDamage 전체다.

Null-conditional Invoke

?.Invoke는 구독자가 없는 정상 상황을 위한 것이다

HpChanged.Invoke(this);    // 구독자가 없으면 NullReferenceException이 발생한다
HpChanged?.Invoke(this);   // 구독자가 없으면 아무 일도 하지 않는다

구독자가 없을 때의 event

아무도 구독하지 않은 event의 값은 null이다. ?.는 왼쪽이 null이면 호출을 건너뛰고, null이 아니면 호출한다.

오류가 아니라 정상이다

구독자가 0개인 것은 잘못된 상태가 아니다. 체력바가 없는 유닛도 만들 수 있다. 첫 시도에서는 같은 경우에 예외가 발생했다.

첫 줄은 비교를 위한 설명용 코드다. 실제 코드는 둘째 줄의 형태만 사용한다.

Think · Order

발행 순서를 바꾸면 구독자는 무엇을 읽게 되는가?

바꾼 순서일어나는 일
HpChanged를 먼저 발행하고 값을 나중에 바꾼다.HP 10인 유닛이 피해 5를 받는다. 체력바는 알림을 받은 즉시 CurrentHp를 읽는데 아직 10이다. 10 / 10 = 1.0이므로 체력바는 100%로 남는다. 화면이 항상 한 번씩 늦다.
Died를 먼저 발행하고 값을 나중에 바꾼다.전멸 판정이 쓰러진 유닛의 IsAlive를 읽으면 아직 true다. 마지막 유닛이 쓰러졌는데도 전멸로 판정하지 않는다.
비활성화를 먼저 하고 Died를 나중에 발행한다.유닛의 자식 오브젝트에 있으면서 OnDisable에서 해제하는 구독자는 비활성화되는 순간 구독이 풀린다. 그런 구독자는 Died를 받지 못한다.

답: 구독자는 알림을 받은 순간에 발행자의 현재 값을 읽는다. 그래서 값을 먼저 바꾼 뒤에 알리고, Died를 발행한 뒤에 비활성화한다.

세 경우 모두 순서를 바꾸었다고 가정한 것이다. 현재 코드는 올바른 순서로 작성되어 있다.

Subscriber 1 · UnitHealthBar.cs

첫 번째 구독자: 체력바는 켜질 때 구독하고 꺼질 때 해제한다

private void OnEnable()
{
    _unit.HpChanged += Refresh;
}

private void OnDisable()
{
    _unit.HpChanged -= Refresh;
}
private void Refresh(Unit unit)
{
    Vector3 scale = _fill.localScale;
    scale.x = (float)unit.CurrentHp / unit.MaxHp;
    _fill.localScale = scale;
}

구독은 듣는 쪽이 한다. Unit.cs는 체력바가 생겼다는 사실을 알지 못한다. Refresh는 전달받은 unit에서 체력을 읽으며, 체력바는 체력을 따로 저장하지 않는다. (float)는 정수 나눗셈 때문에 5 / 10이 0이 되는 것을 막는다.

UnitHealthBar.cs의 실제 코드다. _unit과 _fill은 Inspector에서 연결하는 필드다.

Subscription Lifetime

+=와 -=는 짝이다. 해제하지 않으면 어떤 문제가 생기는가?

상황해제를 빠뜨렸을 때 일어나는 일
체력바를 껐다가 다시 켠다.OnEnable이 다시 실행되어 같은 메서드가 두 번 등록된다. 발행 한 번에 Refresh가 두 번 실행된다.
체력바만 파괴되고 유닛은 남는다.Unit의 등록 목록에 파괴된 체력바의 메서드가 남는다. 다음 발행에서 Refresh가 호출되고, 파괴된 _fill에 접근하여 예외가 발생한다.
구독자가 더 이상 필요하지 않다.발행자가 구독자를 계속 참조한다. 구독자가 메모리에서 정리되지 않는다.

발행자는 누가 구독했는지 알지 못하므로 대신 정리해 줄 수 없다. 구독한 쪽이 자신의 수명에 맞춰 해제한다. OnEnable에서 구독했으면 OnDisable에서, Start에서 구독했으면 OnDestroy에서 해제한다.

표는 해제를 빠뜨렸다고 가정한 것이다. 현재 코드는 OnDisable에서 해제하므로 이 문제가 없다.

Subscriber 2 · GameManager.cs

두 번째 구독자: GameManager는 Start에서 구독하고 OnDestroy에서 해제한다

private void Start()
{
    foreach (Unit unit in _spawner.Units)
    {
        unit.Died += OnUnitDied;
    }
}
private void OnDestroy()
{
    if (Instance != this) return;
    foreach (Unit unit in _spawner.Units)
    {
        unit.Died -= OnUnitDied;
    }
    Instance = null;
}

같은 Unit에 구독자가 둘이 되었다. 그동안 Unit.cs는 한 줄도 바뀌지 않았다. 이것이 첫 시도와의 차이다. 구독은 발행자가 만들어진 뒤에 할 수 있다. 유닛은 UnitSpawner의 Awake에서 만들어지므로 그 뒤에 실행되는 Start에서 구독한다.

Start는 실제 코드다. OnDestroy는 첫 검사를 한 줄로 줄인 축약이다. Instance 검사와 Instance = null은 5차시 Singleton에서 이어진 코드이고, 오늘 추가한 부분은 -= 반복문이다.

Subscriber 2 · Reaction

OnUnitDied는 같은 진영에 살아 있는 유닛이 있는지 확인한다

private void OnUnitDied(Unit deadUnit)
{
    foreach (Unit unit in _spawner.Units)
    {
        if (unit.Team == deadUnit.Team && unit.IsAlive)
        {
            return;
        }
    }

    Finish(deadUnit.Team == Team.Enemy
        ? BattleResult.PlayerWon : BattleResult.PlayerLost);
}

읽는 순서

  1. 쓰러진 유닛과 같은 진영의 유닛을 차례로 확인한다.
  2. 살아 있는 유닛을 하나라도 찾으면 돌아간다. 전투는 계속된다.
  3. 하나도 없으면 전멸이다. 적 진영이면 PlayerWon, 아군 진영이면 PlayerLost로 확정한다.

알림을 받은 시점에 deadUnit.IsAlive는 이미 false다. Unit이 값을 먼저 바꾸고 발행하기 때문이다. 그래서 unit != deadUnit 조건을 추가할 필요가 없다.

GameManager.cs의 실제 코드다. 마지막 문장은 화면 폭에 맞춰 두 줄로 나누었다.

호출하는 쪽이 아는 것

실행되는 시점

구독자의 메서드는 Invoke 안에서 바로 실행된다. 다음 프레임으로 미루어지지 않는다. 등록된 메서드가 모두 끝난 뒤에 TakeDamage의 다음 줄이 실행된다.

TurnManager.Attack의 마지막 줄이다. 피해량을 구하는 앞부분은 이 자료에서 다루지 않는다.

Trace the Numbers

Think · Trace

이어서 B도 피해 5를 두 번 받으면 결과는 무엇인가?

B의 두 번째 피해에서
OnUnitDied는 무엇을 하는가?

답을 순서대로 확인한다

  1. B의 CurrentHp는 10 → 5 → 0이 된다. 체력바는 50%, 0%가 된다.
  2. 두 번째 피해에서 IsAlive가 false가 되어 Died가 발행된다.
  3. OnUnitDied(B)가 적 진영을 확인한다. A는 false이고 B도 false다.
  4. 살아 있는 유닛을 찾지 못하고 반복문이 끝난다. B는 적 진영이므로 Finish(PlayerWon)이 호출된다.

피해가 5가 아니라 7이었다면 CurrentHp는 10 → 3 → max(0, 3 − 7) = 0이 된다. 체력바는 30%, 0%가 되고 이후의 과정은 같다. Mathf.Max가 있으므로 체력은 0 아래로 내려가지 않는다.

Extension

DeathLogger를 추가할 때 고쳐야 할 기존 파일은 0개다

// 새 파일 DeathLogger.cs의 class 안
[SerializeField] private UnitSpawner _spawner;

private void Start()
{
    foreach (Unit unit in _spawner.Units) unit.Died += Log;
}
private void OnDestroy()
{
    foreach (Unit unit in _spawner.Units) unit.Died -= Log;
}
private void Log(Unit unit) => Debug.Log($"{unit.name} 쓰러짐");
방식고치는 기존 파일
첫 시도Unit.cs 1개. 필드와 호출을 추가한다.
event0개. 새 파일만 추가한다.

새 class가 스스로 구독하면 된다. Unit.cs, UnitHealthBar.cs, GameManager.cs는 열어 볼 필요가 없다. 이것이 Observer의 이득이다.

확장 예시용 가상 코드다. 프로젝트에 포함된 파일이 아니다. 쓰러질 때 Console에 기록을 남기는 구독자를 가정했다.

Check Yourself

이해 확인: 답을 먼저 예측한 뒤에 확인한다

질문 1

Unit.cs에서 “UnitHealthBar”와 “GameManager”를 검색하면 몇 번 나오는가?

답: 0번이다. 발행자가 구독자를 알지 못한다는 뜻이다. 구독자를 추가하거나 없애도 Unit.cs는 바뀌지 않는다.

질문 2

OnDisable의 해제를 빠뜨린 체력바를 두 번 껐다가 켰다. 발행 한 번에 Refresh는 몇 번 실행되는가?

답: 3번이다. 처음 켜질 때 1번 등록되고, 다시 켜질 때마다 1번씩 더 등록된다. 1 + 2 = 3이므로 같은 메서드가 3번 등록되어 있다.

질문 2의 상황에서 -=를 제대로 작성했다면 꺼질 때마다 등록이 0번으로 돌아간다. 다시 켜져도 등록은 항상 1번이다.

Cost

Observer에는 대가가 있다

대가구체적인 모습대응
호출 흐름을 한곳에서 읽을 수 없다.TakeDamage를 읽어도 그 뒤에 체력바와 전멸 판정이 실행된다는 사실이 보이지 않는다.이벤트 이름으로 +=의 위치를 검색하여 구독자를 찾는다.
구독 해제는 구독자의 책임이다.해제를 빠뜨리면 중복 실행, 파괴된 객체의 호출, 정리되지 않는 메모리가 생긴다.구독과 해제를 수명 메서드의 짝으로 작성한다.
실행 순서를 가정하면 안 된다.구독자 사이의 호출 순서는 등록된 순서에 따라 달라진다. 순서에 기대는 규칙은 구독자가 추가되거나 등록 시점이 바뀌면 깨진다.각 구독자는 이미 저장된 값을 읽어 독립적으로 판단한다.

체력바와 GameManager는 서로의 존재를 모른다. 둘 중 어느 쪽이 먼저 실행되어도 결과가 같도록 작성되어 있다.

Judgment

적용 기준: 알려야 할 곳이 여럿이고 늘어날 수 있는가?

event가 이득인 경우

하나의 변화를 알려야 할 곳이 여럿이다. 알려야 할 곳이 앞으로 늘어날 수 있다. 발행자가 구독자를 몰라도 되는 편이 낫다.

예: 체력의 변화와 사망.

직접 호출이 나은 경우

받는 쪽이 하나로 정해져 있다. 호출 흐름을 한곳에서 읽을 수 있는 것이 더 중요하다.

예: 결과를 확정하는 GameManager.Instance.Finish(result).

5차시의 Finish 직접 호출은 오늘도 그대로 둔다. OnUnitDied 안에서도 Finish를 직접 호출한다. 패턴은 실제로 나눌 책임이 있을 때에만 도입한다.

Singleton vs Observer

Singleton과 Observer는 서로 다른 질문에 답한다

Singleton · “어떻게 닿는가”

하나뿐인 객체에 어디에서나 접근하는 방법을 정한다.

GameManager.Instance

Observer · “누가 누구를 알아야 하는가”

변화를 알리는 쪽과 반응하는 쪽 사이에서 의존의 방향을 정한다.

unit.Died += OnUnitDied;

첫 시도의 GameManager.Instance.OnUnitDied(this)에서 Singleton은 GameManager에 닿는 방법을 해결해 주었다. 그러나 Unit이 GameManager를 알아야 한다는 문제는 그대로였다. 닿을 수 있다는 것과 알아야 한다는 것은 다른 문제다.

GameManager는 두 패턴에 함께 참여한다. Singleton으로 접근되는 객체이면서 Died를 듣는 구독자다.

Takeaway

발행자는 알리고, 구독자는 스스로 듣는다

  1. 발행자는 event를 선언하고, 값을 먼저 바꾼 뒤에 ?.Invoke(this)로 알린다.
  2. 구독자는 +=로 등록하고, 자신의 수명이 끝날 때 -=로 해제한다.
  3. 발행자는 구독자를 알지 못한다. 구독자가 늘어나도 발행자의 코드는 바뀌지 않는다.
  4. 대가는 흩어진 호출 흐름, 해제 책임, 가정할 수 없는 실행 순서다.
  5. 받는 쪽이 하나로 정해져 있으면 직접 호출이 더 읽기 쉽다.
