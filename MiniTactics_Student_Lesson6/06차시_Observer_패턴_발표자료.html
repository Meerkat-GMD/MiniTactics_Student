Responsibility Boundary

HP를 바꾸는 책임과 반응하는 책임을 나눈다

Unit이 맡을 것

현재 HP를 보관하고 피해를 적용한다. 실제로 HP가 바뀌거나 사망했을 때 그 사실을 알린다.

관찰자가 맡을 것

체력 바는 길이를 갱신한다. GameManager는 사망을 듣고 남은 전투원을 센다.

Unit은 누가 체력 바인지 몰라도 된다. 관찰자는 필요한 알림에 자신이 실행할 함수를 등록한다.

Event Contract

Action은 등록할 함수의 모양을 정한다

public event Action<Unit> HpChanged;
public event Action<Unit> Died;
public event Action<Unit, Vector2Int, Vector2Int> Moved;
선언등록할 함수가 받는 값
Action<Unit>변화가 일어난 Unit 하나. 반환값은 없다.
Moved움직인 Unit, 출발 셀, 도착 셀. 반환값은 없다.

event로 공개하면 외부는 등록과 해제만 할 수 있다. 이 이벤트를 직접 발행하는 일은 선언한 Unit 내부에서 맡는다.

실제 선언: Unit.cs

Read the Syntax

등록·해제·발행은 서로 다른 동작이다

unit.HpChanged += HandleHpChanged; // 관찰자 등록
unit.HpChanged -= HandleHpChanged; // 같은 함수 해제

HpChanged?.Invoke(this);          // Unit 내부에서 발행

+= 와 -=

같은 대상에 같은 함수를 등록하고 해제한다. 반복 등록하면 한 번의 변화에 같은 함수가 여러 번 실행될 수 있다.

?.Invoke(this)

듣는 함수가 있으면 호출하고, 없으면 건너뛴다. this는 변화를 일으킨 현재 Unit이다.

Actual Code · Unit

HP를 먼저 저장하고 그다음 알린다

int previousHp = _currentHp;
_currentHp = Mathf.Max(0, previousHp - damage);
bool didDie = previousHp > 0 && _currentHp == 0;
HpChanged?.Invoke(this);

관찰자는 알림을 받자마자 CurrentHp를 읽는다. HP를 바꾸기 전에 알리면 관찰자가 이전 값을 읽어 화면이 한 단계 늦어진다.

Unit.TakeDamage 일부. 피해가 0 이하이거나 이미 죽은 유닛이면 앞에서 반환한다.

Call Order

현재 구현의 실행 순서

왜 알아야 할까?

사망 콜백 안에서 승리가 확정될 수 있다. 호출한 쪽은 TakeDamage가 끝난 뒤 전투가 계속 중인지 다시 확인해야 한다.

C# 이벤트는 자동으로 다음 프레임이나 별도 스레드로 넘어가지 않는다. 등록된 함수가 예외를 던지면 뒤의 처리도 중단될 수 있다.

Observer · Health Bar

체력 바는 HP를 소유하지 않고 읽는다

scale.x = _unit.MaxHp > 0
    ? Mathf.Clamp01(_unit.CurrentHp / (float)_unit.MaxHp)
    : 0f;
_fill.localScale = scale;

수치의 의미

현재 HP 6 / 최대 HP 10 = 0.6이므로 채움 부분의 가로 길이를 60%로 표시한다.

float로 바꾸는 이유

정수끼리 6 / 10을 계산하면 0이다. (float)로 소수 계산을 해야 0.6을 얻는다.

UnitHealthBar.Refresh 일부. scale은 기존 localScale을 읽어 둔 값이다.

Subscription Lifetime

구독은 관찰자의 수명에 맞춰 정리한다

체력 바가 켜질 때

OnEnable에서 등록하고 현재 HP를 표시한다. _isSubscribed와 활성 상태 검사가 중복 등록을 막는다.

체력 바가 꺼질 때

OnDisable에서 HpChanged와 Died에 등록한 함수를 모두 해제한다. 사망 알림을 받은 바도 비활성화되며 해제된다.

발행자는 등록된 함수의 대상을 참조한다. 해제를 빠뜨리면 더 이상 표시하지 않는 바가 계속 알림을 받거나 참조가 남을 수 있다.

Rebind

표시할 유닛을 바꾸면 이전 연결부터 끊는다

public void Bind(Unit unit)
{
    Unsubscribe();
    _unit = unit;
    Subscribe();
    Refresh();
}

A를 표시하던 바가 B를 표시하게 되었다면, 먼저 A의 이벤트에서 해제한다. 그다음 B에 등록하고 B의 현재 HP를 읽어야 A가 맞을 때 B의 바가 반응하는 오류를 피한다.

Attack Rule

인접 공격은 상하좌우 한 칸이다

거리 = |공격자.x - 대상.x|
     + |공격자.y - 대상.y|

(3,2) → (4,2): 1  공격 가능
(3,2) → (4,3): 2  대각선, 불가

대상 조건

거리가 1이고 상대 팀인 활성·생존 전투원이어야 한다. 같은 팀이나 쓰러진 유닛은 공격 대상에서 제외한다.

맨해튼 거리는 x 차이와 y 차이의 절댓값을 더한 수다. 대각선 한 칸도 이 기준에서는 거리가 2다.

행동의 마무리

실제 HP가 줄면 이동 이력을 지운다. 공격이 끝나면 행동을 완료하고 다음 입력 상태로 돌아간다.

한 공격을 설명할 때 “누가 계산했는가, 누가 저장했는가, 누가 반응했는가”를 구분하면 흐름이 보인다.

Undo Boundary

공격 전에는 방금 이동을 되돌릴 수 있다

피해 적용 전

공격 대상 선택 중이고 보류 중인 이동 명령이 있으면 Undo로 출발 위치를 복원한다. PlayerMoveCommand가 HasMoved도 false로 되돌린다.

피해 적용 후

현재 명령은 이동만 복원한다. HP·죽음·승패까지 복구할 정보가 없으므로 피해가 확정된 공격의 이동 이력을 지운다.

이동 Undo가 곧 전투 전체 Undo가 되는 것은 아니다. 되돌리려는 변화마다 저장하고 복구할 상태가 필요하다.

Command and Notification

이동 명령과 이동 알림은 역할이 다르다

Command · 실행 요청

MoveUnitCommand는 Unit.MoveTo를 호출해 위치를 바꾼다. Undo는 같은 메서드에 원래 출발 셀을 전달한다.

Moved · 결과 알림

Unit은 위치를 바꾼 뒤, 출발 셀과 도착 셀이 다를 때만 Moved를 알린다. 알림을 듣는 관찰자가 실제 이동을 실행하는 것은 아니다.

Vector2Int sourceCell = board.WorldToCell(transform.position);
transform.position = board.CellToWorld(targetCell);
if (sourceCell != targetCell)
    Moved?.Invoke(this, sourceCell, targetCell);

A에서 B로 이동하면 Moved(Unit, A, B), 그 이동을 Undo하면 Moved(Unit, B, A)가 발생한다. 위치 변화마다 알리므로 Undo도 관찰자에게 새로운 이동 사실로 전달된다.

Unit.MoveTo 핵심 발췌. Board가 없는 경우의 앞쪽 반환문과 중괄호 일부를 생략했다.

Re-entry Guard

알림이 처리되는 동안 중복 행동을 막는다

_isResolvingAttack = true;
try { defender.TakeDamage(damage); }
finally
{
    _attackApplied = defender.CurrentHp < previousHp;
    if (_attackApplied) { _history.Clear(); _pendingMove = null; }
    _isResolvingAttack = false;
}

TakeDamage 도중 관찰자가 다른 행동을 요청할 수 있다. 처리 중에는 입력과 행동 완료를 막고, HP 감소 여부를 확인해 이력을 정리한 다음 잠금을 푼다.

BattleController.TryAttack 순서를 보존한 축약. 실제 코드는 성공 여부도 반환한다.

Action and Phase

공격 한 번이 끝나도 플레이어 턴은 계속될 수 있다

행동을 완료한 뒤다음 흐름
아직 행동할 수 있는 아군이 있음Player 단계에서 다른 아군 선택
모든 활성 아군이 행동 완료Enemy 단계 요청, 이동 이력 정리
이번 공격으로 승패 확정Finished로 전환, 추가 입력 차단

HasMoved는 해당 유닛의 행동 여부이고 Phase는 전체 차례다. 공격을 건너뛰어도 그 유닛의 행동은 끝나지만, 다른 아군의 행동까지 끝나는 것은 아니다.

5차시의 목표 방향 이동에 공격 선택을 더한다. 이동 후에는 현재 위치에서 대상을 다시 검사하므로, 멀리 있던 아군을 사거리 밖에서 공격하지 않는다.

공격은 플레이어와 같은 인접·생존·팀 규칙과 같은 피해 계산기를 사용한다.

Think · AI Target

인접한 적의 공격 대상은 누가 될까?

적 (3,3) 옆의 아군HP판정
A (2,3)6HP가 더 많아 뒤로
B (3,2)4선택: HP 동점에서 y가 더 작음
C (4,3)4HP 동점, y가 더 큼

우선순위는 현재 HP, y 좌표, x 좌표의 오름차순이다. 동점 규칙이 있으므로 같은 상황을 다시 실행해도 대상을 일관되게 선택한다.

이 예시는 세 아군이 모두 활성·생존 상태이며 공격 가능한 전투원이라고 가정한다.

가장 가까운 아군을 목표로 삼고, 도착 후보를 목표 거리 → 이동 비용 → y → x 순으로 고른다. 현재보다 가까워지는 칸이 없으면 기다린다.

이는 매 차례 가까워지는 선택이다. 잠시 멀어져야 하는 우회 경로까지 계획하지는 않는다.

Sequential Turns

적 하나의 비동기 행동이 끝나야 다음 적으로 간다

EnemyTurnStarted?.Invoke(unit);
await enemyAi.TakeCombatTurnAsync(
    unit, _units, cancellationToken);

await의 역할

이 적의 행동과 짧은 대기가 완료될 때까지 다음 적의 실행을 미룬다. Unity의 화면 처리는 계속 진행된다.

알림 뒤 재확인

이동·사망 관찰자가 전투를 끝내거나 취소를 요청할 수 있다. AI는 후속 공격 전에 진행 가능 여부를 다시 확인한다.

TurnManager.RunEnemyPhaseAsync 일부 / EnemyAI.TakeCombatTurnAsync

Cancellation

취소는 남은 행동을 중단하라는 요청이다

취소 토큰

장면의 수명이 끝났을 때 비동기 대기와 다음 행동을 중단하도록 전달한다. 이미 실행한 이동이나 피해를 자동으로 복원하지 않는다.

전투가 끝난 경우

AI의 대기는 결과 확정도 감지한다. TurnManager는 결과를 다시 읽고 Finished로 끝내므로 남은 적과 새 Player 턴을 진행하지 않는다.

비동기 작업의 완료, 취소, 전투 결과는 다른 사실이다. 기다림이 끝났다는 이유만으로 무조건 다음 행동을 시작하면 안 된다.

Result는 누가 이겼는지, Phase는 누가 행동할 차례인지를 나타낸다. 두 값이 연결되어야 승리한 뒤 적 턴이 새로 시작되는 일을 막는다.

Limits

이벤트 하나로 모든 변화가 자동 전달되지는 않는다

이 구조가 제공하는 것

변화가 일어나는 순간 등록된 함수들을 호출한다. 반응 종류를 추가해도 HP 변경 코드와 분리할 수 있다.

따로 정해야 하는 것

과거 사건 저장, 예외 격리, 등록·해제 시점, 알림을 발생시키는 경로를 정해야 한다.

예를 들어 ConfigureCombat은 값을 설정하지만 HpChanged를 발행하지 않는다. 초기 Refresh처럼 현재 값을 읽는 절차가 여전히 필요하다.

Judgment

Observer가 필요한 변화인지 판단한다

도입 가치가 큰 경우

한 상태 변화에 UI·로그·승패 등 독립적인 기능 여러 개가 반응한다. 반응하는 대상이 켜지거나 교체될 수 있다.

감수할 비용

실행 흐름을 찾으려면 등록 위치까지 따라가야 한다. 해제 누락과 중복 등록, 콜백 도중 상태 변화를 관리해야 한다.

반응이 하나뿐이고 연결이 고정되어 있다면 직접 메서드 호출도 단순한 선택이다. 패턴의 가치는 실제로 분리할 책임이 있을 때 커진다.

Connect the Course

한 번의 공격에서 각 패턴의 역할이 드러난다

State클릭이 선택·이동·공격 중 무엇인지 정한다.
Command이동 한 건을 실행하고 가능한 범위에서 취소한다.
Flyweight같은 지형 에셋의 규칙을 여러 셀이 공유한다.
ObserverUnit의 변화에 표시와 승패 판정이 반응한다.

GameManager는 결과를 보관하고 TurnManager는 차례를 진행한다. 패턴 이름마다 하나의 질문과 담당 책임을 연결해 설명할 수 있어야 한다.

Takeaway

상태의 주인은 바꾸고, 관찰자는 반응한다

  1. Unit은 HP를 먼저 변경한 뒤 HpChanged를 발행한다.
  2. 관찰자는 등록된 함수로 알림을 받고 현재 상태를 읽는다.
  3. 구독을 시작할 때 현재 값을 표시하고, 수명이 끝나면 해제한다.
  4. 사망 알림으로 승패가 바뀔 수 있으므로 후속 행동 전에 결과를 확인한다.

HP 6인 유닛의 체력 바가 새로 켜졌다.
필요한 동작은 등록 + 현재 값 읽기다.

이벤트에는 과거 기록이 없기 때문이다. 이것을 설명할 수 있다면 알림과 상태의 차이를 이해한 것이다.
