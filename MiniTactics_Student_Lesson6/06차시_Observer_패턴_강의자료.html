Chapter 01

직접 호출의 성과와 결합의 한계

반응 하나에는 직접 호출도 충분하다

상태를 가진 객체

체력 값을 가진 객체가 있다. 값이 바뀌면 표시도 최신 값으로 바꾸어야 한다.

반응하는 객체

표시 하나만 고정되어 있다면 직접 호출로 연결할 수 있다. 요구가 작을 때는 명확한 방법이다.

값을 바꾼 쪽이 표시를 직접 부른다

설계 비교용 가상 코드 — 현재 Teacher 구현이 아닌 첫 시도

currentHp = newHp;
healthBar.Show(currentHp, maxHp);

값 변경과 화면 표시가 한곳에서 이어진다. 두 객체가 늘 함께 존재하고 반응이 하나라면 충분할 수 있다.

반응이 늘면 발행자도 계속 고쳐야 한다

설계 비교용 가상 코드 — 현재 Teacher 구현이 아닌 확장 비교

healthBar.Show(currentHp, maxHp);
statusLabel.Refresh(currentHp);
changeLog.Record(currentHp);

이름을 직접 아는 연결을 결합이라고 한다. 표시·기록이 바뀔 때 상태를 가진 쪽도 수정한다. 상태의 책임과 각 반응의 책임을 나눌 경계가 필요하다.

Chapter 02

Observer의 역할과 알림 계약

상태의 변화와 반응의 선택을 나눈다

발행자 · Publisher

상태를 소유하고 “바뀌었다”는 사실을 알린다. 어떤 화면과 기록이 반응할지 일일이 호출하지 않는다.

구독자 · Subscriber

필요한 알림에 자신의 처리 함수를 등록한다. 알림을 받으면 각자 맡은 반응을 수행한다.

Observer는 한 객체의 변화를 여러 관찰자에게 전달하는 패턴이다. 이 구현은 C# event로 연결한다.

이 코드의 역할과 연결

역할실제 대응알아야 할 것
발행자Unit자신의 상태와 알림 시점
알림HpChanged / Died어떤 사실이 발생했는가
구독자UnitHealthBar / GameManager관찰할 Unit과 자신의 반응
처리 함수Refresh / OnUnitDied전달받은 Unit의 의미

구독자는 발행자의 이벤트를 안다. 발행자는 각 구독자의 구체 클래스를 몰라도 된다. 의존성의 방향과 범위를 줄인 것이다.

알림은 Unit 참조를 함께 전달한다

public event Action<Unit> HpChanged;
public event Action<Unit> Died;

event Action<Unit>

Unit 하나를 받고 값을 반환하지 않는 처리 함수를 등록한다. 외부 객체는 += / -=로 구독을 바꾼다.

발행 권한

외부 구독자가 이 event를 직접 발행할 수는 없다. Unit 내부가 자신의 사실을 알린다.

Chapter 03

사실을 발행하는 시점과 순서

초기 상태를 정한 뒤에도 알린다

CurrentHp = _maxHp;
HpChanged?.Invoke(this);

이 두 줄은 초기 값 대입 뒤 알림이라는 순서를 보여 준다. this는 알림을 보낸 바로 그 Unit이다. 구독이 아직 없으면 ?.Invoke는 아무 처리 함수도 호출하지 않는다.

값 변경 알림 뒤에 사망 알림을 보낸다

HpChanged?.Invoke(this);
if (IsAlive) return;
Died?.Invoke(this);

Teacher6 a0921ab 실제 코드 · Unit.cs:42–44 · TakeDamage의 앞선 검사·값 변경과 뒤의 비활성화 생략; 들여쓰기만 공통 제거

HpChanged 시점에는 값 변경이 이미 끝났다. 살아 있으면 반환한다. 살아 있지 않으면 Died를 호출한다. 이 발췌는 알림 순서만 다룬다.

Chapter 04

구독·초기 갱신·해제

활성화할 때 반응을 등록한다

[SerializeField] private Unit _unit;
[SerializeField] private HealthBarView _view;
private void OnEnable() => _unit.HpChanged += Refresh;

Teacher6 a0921ab 실제 코드 · UnitHealthBar.cs:6–8 · 클래스의 나머지 멤버 생략; 들여쓰기만 공통 제거

누구를 관찰하는가?

_unit이 관찰 대상이고 Refresh가 처리 함수다. +=는 Refresh를 이벤트의 호출 목록에 더한다.

무엇을 분리했는가?

Unit은 UnitHealthBar.Refresh를 직접 호출하지 않는다. 구독자가 자신의 화면 갱신을 선택한다.

받은 Unit에서 현재 상태를 읽는다

private void Start() => Refresh(_unit);
private void Refresh(Unit unit) => _view.Show(unit.CurrentHp, unit.MaxHp);

Teacher6 a0921ab 실제 코드 · UnitHealthBar.cs:10–11 · 클래스의 나머지 멤버 생략; 들여쓰기만 공통 제거

Start의 직접 Refresh는 처음 화면을 맞춘다. 이벤트는 과거 알림을 저장해 다시 보내는 장치가 아니기 때문이다. 이후에는 알림마다 전달받은 Unit의 현재 값으로 표시한다.

비활성화할 때 같은 연결을 해제한다

private void OnEnable() => _unit.HpChanged += Refresh;
private void OnDisable() => _unit.HpChanged -= Refresh;

Teacher6 a0921ab 실제 코드 · UnitHealthBar.cs:8–9 · 클래스의 나머지 멤버 생략; 들여쓰기만 공통 제거

같은 발행자와 같은 처리 함수로 -=한다. OnEnable / OnDisable을 짝지으면 비활성 구독자의 불필요한 반응과 활성화 반복에 따른 중복 등록을 막는 데 도움이 된다.

이 C# 이벤트 호출은 동기적이다. 별도 대기열이나 비동기 전달을 만들지 않는다. 처리 함수가 오래 걸리면 발행자의 다음 문장도 그만큼 늦어진다.

Chapter 06

상태와 알림 순서 추적

같은 알림을 서로 다른 구독자가 받는다

시점Unit 상태 · 설명용 입력구독자 반응
시작CurrentHp 10 / MaxHp 10Start에서 Refresh → 10 / 10
값 변경 완료CurrentHp 7 / MaxHp 10HpChanged → Refresh → 7 / 10
독립 관찰자도 구독한 경우같은 Unit 참조 전달각 처리 함수가 자신의 책임 수행

숫자는 알림 결과를 읽기 위한 설명용 상태다. 값 변경 계산은 다루지 않는다. 한 구독자의 결과를 다른 구독자의 선행 조건으로 삼지 않는 편이 안전하다.

마지막 알림과 해제의 순서

Unit 내부의 순서관찰할 결과
① HpChanged 발행현재 값 0을 읽는 Refresh 실행
② 살아 있지 않음을 확인Died 발행 → 등록된 OnUnitDied 실행
③ Unit 비활성화이 대상과 함께 비활성화되는 UnitHealthBar는 OnDisable에서 해제

설명용 상태는 CurrentHp 0이다. Died가 HpChanged보다 먼저 호출되는 구현이 아니다. 비활성화는 두 알림의 동기 호출이 반환한 뒤에 있다.

Chapter 07

수명과 호출 비용

구독을 분리해도 수명 책임은 남는다

놓치기 쉬운 연결

등록만 하고 해제하지 않으면 필요 없는 반응이나 오래 남는 참조가 생길 수 있다. 발행자와 구독자의 수명이 다를수록 주의한다.

정할 책임

언제 등록·해제할지, 처음 상태는 누가 읽을지, 관찰 대상을 바꿀 때 이전 연결을 누가 끊을지 정한다.

현재 UnitHealthBar는 고정된 _unit을 전제로 한다. 런타임에 관찰 대상을 바꾸는 기능을 자동 제공하지 않는다.

알림도 호출 비용과 실패를 가진다

실행 비용

발행할 때마다 구독자들의 처리 시간이 합쳐진다. 빈번한 알림에 무거운 작업이 연결되면 비용이 커진다.

실패 전파

일반 C# 이벤트에서 처리 함수가 예외를 던지면 호출 흐름이 중단될 수 있다. 이 코드에는 구독자별 예외 격리나 재시도 장치가 없다.

Observer는 자동 비동기 처리, 오류 격리, 과거 알림 재생을 보장하지 않는다. 알림 간 간접 의존성도 추적해야 한다.

Chapter 08

질문과 적용 판단

연결이 없거나 늦으면 어떻게 될까?

질문답과 이유
구독자가 없는데 Invoke하면??.Invoke이므로 처리 함수 호출 없이 진행한다.
구독 전에 일어난 알림도 받나?아니다. 초기 Refresh처럼 현재 값을 직접 읽어 맞춘다.
같은 함수를 두 번 +=하면?중복 등록될 수 있다. 등록·해제를 짝지어 관리한다.
event만 쓰면 결합이 사라지나?아니다. 구독 대상·인수·수명에 대한 계약이 남는다.

독립적인 반응이 늘어나는가?

Observer가 유용할 때

하나의 사실에 여러 독립 반응이 연결되고, 반응을 추가할 때 상태 소유자를 계속 수정하고 싶지 않다.

직접 호출로 충분할 때

협력자가 고정된 하나이고 순서·성공 결과를 명시적으로 제어해야 한다. 간접 연결을 늘릴 이유가 작다.

발생 사실을 알리는가, 특정 작업의 수행을 요청하는가를 먼저 구분한다. Observer 알림 자체가 취소·이력·처리 성공을 보장하지는 않는다.
