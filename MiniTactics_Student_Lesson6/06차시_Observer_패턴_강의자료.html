CHAPTER 01 · 문제

하나의 변화와 여러 반응

학습 목표: 직접 호출이 잘 맞는 조건을 설명한다. 하나의 변화에 반응하는 곳이 여럿일 때 직접 호출이 어떤 한계를 갖는지 코드로 확인한다.

1.1 지금까지의 방법은 직접 호출이다

이전 차시까지는 한 객체가 다른 객체의 메서드를 직접 호출했다. 전투 결과를 확정하는 다음 호출이 그 예다.

실제 코드 · 5차시부터 사용하고 있는 호출

GameManager.Instance.Finish(result);

직접 호출에는 분명한 장점이 있다. 호출하는 줄을 읽으면 다음에 어떤 메서드가 실행되는지 바로 알 수 있다. 이 방법에는 두 가지 전제가 있다. 부르는 쪽이 받는 쪽의 class와 메서드 이름을 알고 있다. 그리고 받는 쪽이 하나로 정해져 있다. 이 장에서는 이 전제가 맞지 않는 상황을 살펴본다.

1.2 새 요구: 체력이 바뀌면 여러 곳이 함께 달라져야 한다

유닛의 체력이 줄었을 때 달라져야 하는 것을 적어 본다. 먼저 체력바의 길이가 줄어야 한다. 유닛이 쓰러졌다면 같은 진영에 살아 있는 유닛이 남았는지 확인하는 전멸 판정도 필요하다. 앞으로 피해 숫자, 효과음, 전투 기록이 추가될 수도 있다.

가장 먼저 떠올릴 수 있는 방법은 체력을 깎는 메서드 안에서 필요한 곳을 모두 호출하는 것이다.

CHAPTER 02 · 구조

방향을 뒤집는 구조

학습 목표: 의존의 방향을 뒤집는다는 말의 뜻을 설명한다. 발행자, 알림, 구독자의 역할을 실제 class와 대응시킨다.

2.1 알리는 쪽은 모르고, 듣는 쪽이 등록한다

첫 시도에서는 Unit이 UnitHealthBar와 GameManager를 알았다. 이 방향을 뒤집는다. Unit은 “체력이 바뀌었다”고 알리기만 한다. 그 사실에 관심이 있는 쪽이 자신의 메서드를 Unit에 등록한다.

첫 시도의 방향

Unit → UnitHealthBar, Unit → GameManager. 알리는 쪽이 듣는 쪽을 모두 알고 있다. 듣는 쪽이 늘어나면 알리는 쪽을 고쳐야 한다.

뒤집은 방향

UnitHealthBar → Unit, GameManager → Unit. 듣는 쪽이 알리는 쪽을 알고 있다. 듣는 쪽이 늘어나도 알리는 쪽은 그대로다.

의존이 없어지는 것은 아니다. 구독자는 어느 Unit의 알림을 들을지 알아야 하고, 알림이 전달하는 값의 뜻도 알아야 한다. 달라지는 것은 의존의 방향이다. 발행자는 구독자의 class 이름과 메서드를 알 필요가 없게 된다.

2.2 Observer 패턴의 역할

이 구조의 이름이 Observer 패턴이다. 상태를 가진 객체가 변화를 알리면, 미리 등록한 객체들이 각자 자신의 일을 한다. 발행은 알림을 보내는 일이고, 구독은 알림을 받을 메서드를 등록하는 일이다. 구독자를 영어로 Observer라고 부르며 패턴의 이름은 여기에서 왔다.

주의Observer를 “GameManager에게 알리는 기능”으로 이해하면 핵심을 놓친다. 발행자는 누가 듣는지 알지 못한다. 듣는 쪽이 0개여도, 1개여도, 10개여도 발행자의 코드는 같다.

옮겨진 것이다. 체력바가 Unit을 아는 것은 자연스럽다. 체력바는 원래 특정 유닛의 체력을 보여 주는 객체이기 때문이다. 반대로 Unit이 체력바를 알아야 할 이유는 없다. 의존이 자연스러운 쪽으로 옮겨졌다.

CHAPTER 03 · 문법

C# event의 네 동작

학습 목표: 선언, 발행, 구독, 해제의 네 동작을 구분한다. event 키워드가 막아 주는 것과 ?.Invoke의 뜻을 설명한다.

3.1 네 동작을 한곳에서 본다

Observer는 구조의 이름이고, C#의 event는 그 구조를 작성하는 문법이다. event는 네 동작으로 쓴다.

서로 다른 파일의 네 줄을 한곳에 모은 것 · 선언과 발행은 Unit.cs, 구독과 해제는 UnitHealthBar.cs

public event Action<Unit> HpChanged;   // 선언: 알림의 통로
HpChanged?.Invoke(this);               // 발행: 듣는 쪽이 없어도 된다
_unit.HpChanged += Refresh;            // 구독: 듣는 쪽이 등록한다
_unit.HpChanged -= Refresh;            // 해제: 등록한 쪽이 책임진다
네 동작과 코드를 쓰는 곳
동작코드를 쓰는 곳뜻
선언발행자알림의 통로를 만든다.
발행발행자등록된 메서드를 모두 호출한다.
구독 +=구독자자신의 메서드를 등록한다.
해제 -=구독자등록했던 메서드를 목록에서 뺀다.

3.2 선언: Action<Unit>은 구독할 메서드의 모양을 정한다

실제 코드 · Unit.cs

public event Action<Unit> HpChanged;
public event Action<Unit> Died;

Action<Unit>은 Unit 하나를 받고 반환값이 없는 메서드를 뜻한다. 구독하는 메서드는 이 모양과 같아야 한다. UnitHealthBar의 void Refresh(Unit unit)과 GameManager의 void OnUnitDied(Unit deadUnit)이 이 모양이다. 모양이 다르면 +=에서 컴파일 오류가 발생한다.

전달되는 Unit은 변화가 일어난 바로 그 유닛이다. 구독자는 이 유닛에서 CurrentHp, MaxHp, Team, IsAlive를 읽는다. 그래서 알림에 피해량이나 새 체력을 따로 담지 않아도 된다. 대신 발행자는 알리기 전에 값을 먼저 바꾸어 두어야 한다. 이 순서는 4장에서 다룬다.

3.3 event 키워드는 바깥의 대입과 발행을 막는다

설명용 코드 · Unit이 아닌 class에서 작성했을 때

unit.HpChanged += Refresh;       // 허용: 구독
unit.HpChanged -= Refresh;       // 허용: 해제
unit.HpChanged = null;           // 컴파일 오류: 대입
unit.HpChanged.Invoke(unit);     // 컴파일 오류: 발행

=로 대입하면 이미 등록된 메서드가 모두 지워진다. 구독자 하나가 실수로 대입하면 같은 알림을 듣던 다른 구독자의 등록까지 사라진다. 바깥에서 Invoke를 호출하면 체력이 바뀌지 않았는데도 바뀌었다는 알림이 나간다. 발행은 값을 소유한 Unit만 할 수 있어야 한다.

흔한 실수event를 빼고 public Action<Unit> HpChanged;로 선언하면 위의 네 줄이 모두 컴파일된다. 바깥에서 다른 구독자를 모두 지우거나 직접 발행할 수 있게 된다.

3.4 ?.Invoke는 구독자가 없는 정상 상황을 위한 것이다

첫 줄은 비교를 위한 설명용 코드 · 실제 코드는 둘째 줄의 형태만 사용한다

HpChanged.Invoke(this);    // 구독자가 없으면 NullReferenceException이 발생한다
HpChanged?.Invoke(this);   // 구독자가 없으면 아무 일도 하지 않는다

아무도 구독하지 않은 event의 값은 null이다. ?.는 왼쪽이 null이면 호출을 건너뛰고, null이 아니면 호출한다. 구독자가 0개인 것은 잘못된 상태가 아니다. 체력바가 없는 유닛도 만들 수 있다. 첫 시도에서는 같은 경우에 예외가 발생했다.

3.5 구독과 해제에는 같은 메서드 이름을 쓴다

-=는 +=로 등록한 것과 같은 메서드를 지정해야 동작한다. 그래서 구독하는 메서드는 이름이 있는 메서드로 작성한다. 등록할 때와 해제할 때 각각 새 람다식을 쓰면 두 람다식은 서로 다른 것으로 취급되어 해제되지 않는다.

연습event 키워드를 빼고 선언했을 때 바깥의 코드가 할 수 있게 되는 일 두 가지는 무엇인가? 각각 어떤 문제가 생기는가?
해설 보기

첫째는 = 대입이다. 다른 구독자의 등록이 모두 지워진다. 둘째는 바깥에서의 발행이다. 일어나지 않은 변화를 알리게 된다.

CHAPTER 04 · 발행자

발행자 Unit과 발행 순서

학습 목표: TakeDamage의 네 단계를 순서대로 설명한다. 값을 먼저 바꾸고 알리는 이유와 Died를 발행한 뒤에 비활성화하는 이유를 설명한다.

4.1 TakeDamage에는 구독자가 등장하지 않는다

실제 코드 · Unit.cs의 TakeDamage 전체

public void TakeDamage(int damage)
{
    CurrentHp = Mathf.Max(0, CurrentHp - damage);
    HpChanged?.Invoke(this);

    if (!IsAlive)
    {
        Died?.Invoke(this);
        gameObject.SetActive(false);
    }
}

IsAlive는 CurrentHp > 0을 계산하는 속성이다. 따로 저장하는 값이 아니므로 체력이 0인데 살아 있다고 표시되는 불일치가 생기지 않는다.

이 메서드에는 체력바도 GameManager도 등장하지 않는다. 첫 시도의 직접 호출 두 줄이 발행 두 줄로 바뀌었다. 실행 순서는 다음과 같다.

CurrentHp 변경→HpChanged 발행→쓰러졌다면 Died 발행→비활성화

4.2 값을 먼저 바꾸고, 그다음에 알린다

구독자는 알림을 받은 순간에 발행자의 현재 값을 읽는다. 그래서 알림보다 값의 변경이 먼저여야 한다. 체력바가 알림을 받고 CurrentHp를 읽을 때 이미 새 값이어야 한다.

4.3 Died를 발행한 뒤에 비활성화한다

Died를 먼저 발행하고 그다음에 SetActive(false)를 호출한다. 구독자가 알림을 받는 동안 유닛은 아직 활성 상태다. 이 시점에 IsAlive는 이미 false다. 값이 먼저 바뀌었기 때문이다.

순서를 바꾸었다고 가정했을 때 일어나는 일
바꾼 순서일어나는 일
HpChanged를 먼저 발행하고 값을 나중에 바꾼다.HP 10인 유닛이 피해 5를 받는다. 체력바는 아직 10인 CurrentHp를 읽는다. 10 / 10 = 1.0이므로 체력바는 100%로 남는다. 화면이 항상 한 번씩 늦다.
Died를 먼저 발행하고 값을 나중에 바꾼다.전멸 판정이 쓰러진 유닛의 IsAlive를 읽으면 아직 true다. 마지막 유닛이 쓰러졌는데도 전멸로 판정하지 않는다.
비활성화를 먼저 하고 Died를 나중에 발행한다.유닛의 자식 오브젝트에 있으면서 OnDisable에서 해제하는 구독자는 비활성화되는 순간 구독이 풀린다. 그런 구독자는 Died를 받지 못한다.

4.4 알림은 발행하는 즉시 실행된다

구독자의 메서드는 Invoke 안에서 바로 실행된다. 다음 프레임으로 미루어지지 않고, 별도의 스레드에서 실행되지도 않는다. 등록된 메서드가 모두 끝난 뒤에 TakeDamage의 다음 줄이 실행된다. 그러므로 HpChanged의 구독자가 모두 실행된 뒤에 Died가 발행된다.

연습Died의 구독자가 실행되는 동안 쓰러진 유닛의 gameObject.activeSelf는 true인데 IsAlive는 false다. 오류인가?
해설 보기

오류가 아니라 정해진 순서다. 체력이 먼저 0으로 바뀌어 IsAlive가 false가 되고, Died의 구독자가 모두 끝난 다음에 유닛이 비활성화된다. 그래서 전멸 판정은 활성 여부가 아니라 IsAlive를 읽는다.

CHAPTER 05 · 구독자 1

첫 번째 구독자와 구독 수명

학습 목표: UnitHealthBar가 구독하고 해제하는 위치를 설명한다. 구독을 해제하지 않았을 때 생기는 문제 세 가지를 설명한다.

5.1 체력바는 켜질 때 구독하고 꺼질 때 해제한다

실제 코드 · UnitHealthBar.cs

[SerializeField] private Unit _unit;
[SerializeField] private Transform _fill;

private void OnEnable()
{
    _unit.HpChanged += Refresh;
}

private void OnDisable()
{
    _unit.HpChanged -= Refresh;
}

구독은 듣는 쪽이 한다. Unit.cs는 체력바가 생겼다는 사실을 알지 못한다. OnEnable과 OnDisable은 Unity가 컴포넌트를 켜고 끌 때 호출하는 메서드다. 두 메서드는 항상 짝으로 호출되므로 +=와 -=를 짝지어 두기에 알맞다.

5.2 반응: 전달받은 유닛에서 값을 읽는다

실제 코드 · UnitHealthBar.cs

private void Refresh(Unit unit)
{
    Vector3 scale = _fill.localScale;
    scale.x = (float)unit.CurrentHp / unit.MaxHp;
    _fill.localScale = scale;
}

Refresh의 모양은 Action<Unit>과 같다. 체력바는 체력을 따로 저장하지 않고, 알림을 받을 때마다 전달받은 unit에서 현재 값을 읽는다. (float)는 정수 나눗셈 때문에 5 / 10이 0이 되는 것을 막는다. 변환한 뒤에는 5 / 10 = 0.5가 된다.

5.3 구독을 해제하지 않으면 생기는 문제

OnDisable의 해제를 빠뜨렸다고 가정했을 때
상황일어나는 일
체력바를 껐다가 다시 켠다.OnEnable이 다시 실행되어 같은 메서드가 두 번 등록된다. 발행 한 번에 Refresh가 두 번 실행된다.
체력바만 파괴되고 유닛은 남는다.Unit의 등록 목록에 파괴된 체력바의 메서드가 남는다. 다음 발행에서 Refresh가 호출되고, 파괴된 _fill에 접근하여 예외가 발생한다.
구독자가 더 이상 필요하지 않다.발행자가 구독자를 계속 참조한다. 구독자가 메모리에서 정리되지 않는다.
구독 수명의 규칙발행자는 누가 구독했는지 알지 못하므로 대신 정리해 줄 수 없다. 구독한 쪽이 자신의 수명에 맞춰 해제한다. OnEnable에서 구독했으면 OnDisable에서, Start에서 구독했으면 OnDestroy에서 해제한다.

현재 코드는 OnDisable에서 해제하므로 위의 문제가 없다. 유닛이 쓰러져 비활성화되면 자식인 체력바의 OnDisable도 실행되어 구독이 함께 해제된다.

연습OnDisable의 해제를 빠뜨린 체력바를 두 번 껐다가 켰다. 발행 한 번에 Refresh는 몇 번 실행되는가?
해설 보기

3번이다. 처음 켜질 때 1번 등록되고, 다시 켜질 때마다 1번씩 더 등록된다. 1 + 2 = 3이므로 같은 메서드가 3번 등록되어 있다. 해제를 제대로 작성했다면 꺼질 때마다 등록이 0번으로 돌아가므로 항상 1번만 실행된다.

CHAPTER 06 · 구독자 2

두 번째 구독자와 전멸 판정

학습 목표: GameManager가 구독하고 해제하는 위치를 설명한다. OnUnitDied가 전멸을 판정하는 과정을 읽는다. 구독자가 늘어나는 동안 발행자가 바뀌지 않았음을 확인한다.

6.1 Start에서 모든 유닛의 Died를 구독한다

실제 코드 · GameManager.cs

private void Start()
{
    foreach (Unit unit in _spawner.Units)
    {
        unit.Died += OnUnitDied;
    }
}

구독은 발행자가 만들어진 뒤에 할 수 있다. 유닛은 UnitSpawner의 Awake에서 만들어진다. Start는 모든 Awake가 끝난 뒤에 실행되므로 이 시점에는 _spawner.Units가 채워져 있다. Awake에서 구독하면 실행 순서에 따라 목록이 비어 있어서 아무것도 구독하지 못할 수 있다.

6.2 OnDestroy에서 같은 메서드를 해제한다

실제 코드 · GameManager.cs

private void OnDestroy()
{
    if (Instance != this)
    {
        return;
    }

    foreach (Unit unit in _spawner.Units)
    {
        unit.Died -= OnUnitDied;
    }

    Instance = null;
}

Instance 검사와 Instance = null은 5차시 Singleton에서 이어진 코드다. 이번 차시에 추가한 부분은 가운데의 -= 반복문이다. Start의 +=와 짝을 이룬다.

6.3 OnUnitDied는 같은 진영에 살아 있는 유닛이 있는지 확인한다

실제 코드 · GameManager.cs

private void OnUnitDied(Unit deadUnit)
{
    foreach (Unit unit in _spawner.Units)
    {
        if (unit.Team == deadUnit.Team && unit.IsAlive)
        {
            return;
        }
    }

    Finish(deadUnit.Team == Team.Enemy ? BattleResult.PlayerWon : BattleResult.PlayerLost);
}

쓰러진 유닛과 같은 진영의 유닛을 차례로 확인한다. 살아 있는 유닛을 하나라도 찾으면 돌아가고 전투는 계속된다. 하나도 없으면 전멸이다. 쓰러진 유닛이 적 진영이면 PlayerWon, 아군 진영이면 PlayerLost로 결과를 확정한다.

알림을 받은 시점에 deadUnit.IsAlive는 이미 false다. Unit이 값을 먼저 바꾸고 발행하기 때문이다. 그래서 unit != deadUnit 조건을 추가할 필요가 없다. 4장의 발행 순서가 구독자의 코드를 단순하게 만든다.

6.4 구독자가 둘이 되는 동안 Unit.cs는 바뀌지 않았다

같은 Unit에 구독자가 둘이 되었다. 그동안 Unit.cs는 한 줄도 바뀌지 않았다. 이것이 첫 시도와의 차이다. 두 구독자는 서로의 존재도 알지 못한다.

두 구독자의 구독 수명
구독자구독하는 알림구독해제
UnitHealthBar자기 유닛의 HpChangedOnEnableOnDisable
GameManager모든 유닛의 DiedStartOnDestroy

두 구독자가 같은 수명 메서드를 쓰지는 않는다. 구독자마다 자신의 수명에 맞는 짝을 고른다. 체력바는 켜지고 꺼지는 객체이므로 OnEnable과 OnDisable을 쓴다. GameManager는 장면이 유지되는 동안 계속 듣는 객체이므로 Start와 OnDestroy를 쓴다.

연습적 진영에 유닛이 둘 있다. 그중 하나가 쓰러졌다. OnUnitDied는 어디에서 돌아가는가? 결과는 무엇인가?
해설 보기

반복문이 살아 있는 나머지 적을 찾은 순간 return으로 돌아간다. Finish는 호출되지 않고 결과는 Playing으로 남는다. 나머지 적까지 쓰러지면 살아 있는 적을 찾지 못하고 반복문이 끝나서 Finish(PlayerWon)이 호출된다.

CHAPTER 07 · 실행 흐름

발행 한 번의 단계별 추적

학습 목표: TakeDamage 한 번이 두 구독자에게 전달되는 과정을 값과 함께 따라간다. 각 단계의 CurrentHp, 체력바 비율, IsAlive, 전멸 판정 결과를 직접 계산한다.

7.1 출발 상태와 호출

적 진영에 A와 B가 있고 둘 다 HP 10 / 10이다. 각 유닛의 체력바가 HpChanged를, GameManager가 모든 유닛의 Died를 구독하고 있다. 호출하는 쪽은 다음 한 줄만 쓴다.

실제 코드 · TurnManager.Attack의 마지막 줄

defender.TakeDamage(damage);

피해량을 구하는 앞부분은 이 교재에서 다루지 않는다. 아래의 추적에서는 피해량을 5로 둔다.

체력바와 전멸 판정은 호출하는 쪽의 코드에도, Unit의 코드에도 나타나지 않는다. 그 연결은 구독자가 등록한 +=에 있다.

7.2 A가 피해 5를 두 번 받는다

A.TakeDamage(5)를 두 번 호출했을 때
단계첫 번째 호출두 번째 호출
CurrentHpmax(0, 10 − 5) = 5max(0, 5 − 5) = 0
HpChanged → 체력바5 / 10 = 0.5, 길이 50%0 / 10 = 0.0, 길이 0%
IsAlive5 > 0 이므로 true0 > 0 이 아니므로 false
Died발행하지 않는다.발행한다.
전멸 판정실행되지 않는다.A는 false, B는 true다. B를 찾고 돌아간다. 결과는 Playing이다.
비활성화하지 않는다.A를 비활성화한다. 자식인 체력바의 OnDisable이 실행되어 구독이 해제된다.

7.3 이어서 B도 피해 5를 두 번 받는다

  1. B의 CurrentHp는 10 → 5 → 0이 된다. 체력바는 50%, 0%가 된다.
  2. 두 번째 피해에서 IsAlive가 false가 되어 Died가 발행된다.
  3. OnUnitDied(B)가 적 진영을 확인한다. A는 false이고 B도 false다.
  4. 살아 있는 유닛을 찾지 못하고 반복문이 끝난다. B는 적 진영이므로 Finish(PlayerWon)이 호출된다.
추적에서 확인할 점발행자는 두 번의 발행만 했다. 체력바의 길이와 승패는 구독자가 각자 읽고 판단한 결과다. 같은 TakeDamage 호출이라도 구독자의 구성이 달라지면 이어지는 반응이 달라진다.
손으로 계산하기HP 10인 유닛이 피해 7을 두 번 받는다. 각 호출 뒤의 CurrentHp와 체력바 비율은 얼마인가? Died는 몇 번 발행되는가?
해설 보기

첫 번째 호출 뒤에는 max(0, 10 − 7) = 3이고 체력바는 3 / 10 = 0.3, 30%다. 두 번째 호출 뒤에는 max(0, 3 − 7) = 0이고 체력바는 0%다. Mathf.Max가 있으므로 체력은 0 아래로 내려가지 않는다. Died는 두 번째 호출에서 1번 발행된다.

CHAPTER 08 · 판단

확장, 대가, 적용 기준

학습 목표: 새 구독자를 추가할 때 기존 파일이 바뀌지 않음을 확인한다. Observer의 대가 세 가지와 적용 기준을 설명한다. Singleton과 Observer가 다루는 문제를 구분한다.

8.1 DeathLogger를 추가할 때 고쳐야 할 기존 파일은 0개다

유닛이 쓰러질 때 Console에 기록을 남기는 구독자를 추가한다고 하자.

확장 예시용 가상 코드 · 프로젝트에 포함된 파일이 아니다

public sealed class DeathLogger : MonoBehaviour
{
    [SerializeField] private UnitSpawner _spawner;

    private void Start()
    {
        foreach (Unit unit in _spawner.Units) unit.Died += Log;
    }

    private void OnDestroy()
    {
        foreach (Unit unit in _spawner.Units) unit.Died -= Log;
    }

    private void Log(Unit unit) => Debug.Log($"{unit.name} 쓰러짐");
}
같은 기능을 추가할 때 고치는 기존 파일
방식고치는 기존 파일
첫 시도(직접 호출)Unit.cs 1개. 필드와 호출을 추가한다.
event0개. 새 파일만 추가한다.

새 class가 스스로 구독하면 된다. Unit.cs, UnitHealthBar.cs, GameManager.cs는 열어 볼 필요가 없다. 이것이 Observer의 이득이다.

8.2 Observer의 대가

대가와 대응
대가구체적인 모습대응
호출 흐름을 한곳에서 읽을 수 없다.TakeDamage를 읽어도 그 뒤에 체력바와 전멸 판정이 실행된다는 사실이 보이지 않는다.이벤트 이름으로 +=의 위치를 검색하여 구독자를 찾는다.
구독 해제는 구독자의 책임이다.해제를 빠뜨리면 중복 실행, 파괴된 객체의 호출, 정리되지 않는 메모리가 생긴다.구독과 해제를 수명 메서드의 짝으로 작성한다.
실행 순서를 가정하면 안 된다.구독자 사이의 호출 순서는 등록된 순서에 따라 달라진다. 순서에 기대는 규칙은 구독자가 추가되거나 등록 시점이 바뀌면 깨진다.각 구독자는 이미 저장된 값을 읽어 독립적으로 판단한다.

8.3 적용 기준

event가 이득인 경우

하나의 변화를 알려야 할 곳이 여럿이다. 알려야 할 곳이 앞으로 늘어날 수 있다. 예: 체력의 변화와 사망.

직접 호출이 나은 경우

받는 쪽이 하나로 정해져 있다. 호출 흐름을 한곳에서 읽을 수 있는 것이 더 중요하다. 예: 결과를 확정하는 Finish 호출.

5차시의 GameManager.Instance.Finish(result) 직접 호출은 이번 차시에도 그대로 둔다. OnUnitDied 안에서도 Finish를 직접 호출한다. 받는 쪽이 GameManager 하나로 정해져 있기 때문이다. 패턴은 실제로 나눌 책임이 있을 때에만 도입한다.

8.4 Singleton과 Observer의 구분

두 패턴이 답하는 질문
패턴답하는 질문코드
Singleton(5차시)“어떻게 닿는가” · 하나뿐인 객체에 어디에서나 접근하는 방법을 정한다.GameManager.Instance
Observer(6차시)“누가 누구를 알아야 하는가” · 알리는 쪽과 반응하는 쪽 사이에서 의존의 방향을 정한다.unit.Died += OnUnitDied;

첫 시도의 GameManager.Instance.OnUnitDied(this)에서 Singleton은 GameManager에 닿는 방법을 해결해 주었다. 그러나 Unit이 GameManager를 알아야 한다는 문제는 그대로였다. 닿을 수 있다는 것과 알아야 한다는 것은 다른 문제다. GameManager는 두 패턴에 함께 참여한다. Singleton으로 접근되는 객체이면서 Died를 듣는 구독자다.

생각할 문제결과를 확정하는 GameManager.Instance.Finish(...) 직접 호출도 event로 바꾸어야 하는가?
해설 보기

바꾸지 않아도 된다. 받는 쪽이 GameManager 하나로 정해져 있고 늘어날 계획이 없다. 이 경우에는 직접 호출이 더 읽기 쉽다. event로 바꾸면 호출 흐름이 흩어지는 대가만 치르게 된다.

CHAPTER 09 · 복습

복습 질문과 용어

학습 목표: 다섯 질문에 자신의 말로 답한다. 이번 차시의 용어를 정확한 뜻으로 사용한다.

9.1 스스로 설명하는 다섯 질문

  1. Unit.cs에서 “UnitHealthBar”와 “GameManager”를 검색하면 몇 번 나오는가? 그것은 무엇을 뜻하는가?
  2. 쓰러질 때 Console에 기록을 남기는 DeathLogger를 추가한다면 고쳐야 할 기존 파일은 몇 개인가?
  3. OnDisable에서 구독을 해제하지 않으면 어떤 문제가 생기는가?
  4. event로 연결하면 “TakeDamage를 호출하면 무슨 일이 일어나는가”를 코드 한 곳에서 읽을 수 없게 된다. 이 대가는 언제 감수할 만한가?
  5. 값을 바꾸기 전에 HpChanged를 발행하면 체력바는 어떤 값을 읽는가?
답 확인

1. 0번이다. 발행자가 구독자를 알지 못한다는 뜻이다. 2. 0개다. 새 class가 스스로 구독하면 된다. 3. 다시 켜질 때마다 같은 메서드가 중복으로 등록된다. 파괴된 객체의 메서드가 호출될 수 있고, 발행자가 구독자를 계속 참조하여 메모리에서 정리되지 않는다. 4. 알려야 할 곳이 여럿이고 늘어날 수 있을 때다. 받는 쪽이 하나로 정해져 있으면 직접 호출이 더 읽기 쉽다. 5. 바뀌기 전의 값을 읽는다. HP 10에서 피해 5를 받았다면 10을 읽어 100%로 표시한다.

9.2 용어 사전

용어이번 차시에서의 뜻
Observer 패턴상태를 가진 객체가 변화를 알리면, 미리 등록한 객체들이 각자 반응하는 구조.
발행자(Subject)값을 소유하고 변화를 알리는 객체. 이번 차시에서는 Unit.
구독자(Observer)알림을 받을 메서드를 등록한 객체. 이번 차시에서는 UnitHealthBar와 GameManager.
발행등록된 메서드를 모두 호출하는 일. ?.Invoke(this)로 작성한다.
구독 / 해제메서드를 등록하는 일 / 등록했던 메서드를 빼는 일. +=와 -=로 작성한다.
event바깥에서는 구독과 해제만 할 수 있도록 제한하는 C# 키워드.
Action<Unit>Unit 하나를 받고 반환값이 없는 메서드의 모양.
구독 수명언제 구독을 시작하고 언제 해제하는지의 범위.
HpChanged / Died체력이 바뀌었다는 알림 / 유닛이 쓰러졌다는 알림.

9.3 요약

이번 차시의 기준발행자는 값을 먼저 바꾼 뒤에 알리고, 구독자는 스스로 등록하고 스스로 해제한다. 발행자는 구독자를 알지 못하므로 구독자가 늘어나도 발행자의 코드는 바뀌지 않는다. 대가는 흩어진 호출 흐름, 해제 책임, 가정할 수 없는 실행 순서다. 받는 쪽이 하나로 정해져 있으면 직접 호출을 그대로 쓴다.
