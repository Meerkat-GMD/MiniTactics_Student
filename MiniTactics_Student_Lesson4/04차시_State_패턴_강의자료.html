입력 모드를
상태 객체로 나눈다

이 자료는 발표 요약이 아니라 수업 뒤에도 다시 읽을 수 있는 교과서형 강의 자료다. 대기와 선택 상태를 구현하며 State 패턴의 구조, 전환 생명주기, 다른 패턴과의 협력을 배운다.

1. 같은 클릭, 다른 의미

마우스 왼쪽 클릭이라는 물리 입력은 하나지만 게임의 반응은 현재 모드에 따라 달라진다. 아무 유닛도 선택하지 않은 대기 모드에서 유닛을 클릭하면 선택이 시작된다. 이미 유닛을 선택한 모드에서 빈 셀을 클릭하면 이동을 시도한다.

Idle

유닛 클릭은 선택 시작. 빈 셀은 무시.

UnitSelected

유닛 클릭은 선택 교체. 빈 셀은 이동 시도.

공격과 스킬 모드가 추가될 때 하나의 Update 안에서 모든 조합을 검사하면 변경 이유가 섞인다. State 패턴은 모드별 규칙을 별도 객체로 옮긴다.

2. State 패턴의 역할

State 패턴은 객체의 내부 상태가 바뀌면 행동도 바뀌는 문제를 다룬다. 이번 수업에서는 네 역할을 구분한다.

  • Context: Board와 Command를 사용하는 BattleController
  • State: 모든 입력 상태의 공통 계약 InputState
  • Concrete State: IdleState와 UnitSelectedState
  • State Machine: Current를 보관하고 전환을 실행
입력 → State Machine → Current State → Context 기능 호출

State는 게임 전체 데이터를 소유하지 않는다. 무엇을 할지 결정하고 실제 기능은 Context에 요청한다.

3. InputState: 같은 입력 표면

public abstract class InputState
{
    public virtual void Enter() { }
    public virtual void Exit() { }
    public abstract void HandleBoardClick(Unit unit, Vector2Int cell);
    public abstract void HandleUndo();
}

추상 클래스 덕분에 State Machine은 현재 객체가 Idle인지 Selected인지 묻지 않고 같은 메서드를 호출한다. Enter와 Exit는 모든 상태에 필수 행동이 아니므로 기본 구현이 있는 가상 메서드다. 클릭과 Undo는 모든 구체 상태가 의미를 정해야 하므로 추상 메서드다.

4. InputStateMachine: 전환의 단일 관문

public void ChangeState(InputState next)
{
    if (next == null) throw new ArgumentNullException(nameof(next));
    if (ReferenceEquals(Current, next)) return;
    Current?.Exit();
    Current = next;
    Current.Enter();
}

순서는 반드시 이전 Exit, Current 교체, 새 Enter다. 새 상태의 Enter가 실행될 때 Current가 이미 자신을 가리키므로, Enter 안에서 현재 상태를 조회해도 일관된다.

각 상태가 Current를 직접 대입하게 만들면 Exit나 Enter를 빠뜨릴 수 있다. 모든 전환은 ChangeState를 통과시킨다.

public void HandleBoardClick(Unit unit, Vector2Int cell)
    => Current?.HandleBoardClick(unit, cell);

State Machine은 입력의 의미를 판단하지 않고 현재 상태에 전달만 한다.

5. IdleState: 선택을 시작하는 상태

public override void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    if (clickedUnit != null && clickedUnit.CanMove)
        _machine.ChangeState(
            new UnitSelectedState(_machine, _controller, clickedUnit));
}

Idle은 빈 셀이나 고정 유닛을 무시한다. 이동 계산이나 오버레이 코드는 없다. Undo 입력은 Controller의 UndoLast를 호출한다. 이렇게 한 상태의 규칙을 한 파일에서 읽을 수 있다.

6. UnitSelectedState: 선택 문맥을 가진 상태

선택 상태는 생성자에서 선택된 Unit을 기억한다. 이것이 이 상태만의 문맥이다.

public override void Enter()
    => _controller.ShowSelection(_unit);

public override void Exit()
    => _controller.ClearSelection();

다른 이동 유닛을 클릭하면 새 UnitSelectedState로 전환한다. 빈 셀을 클릭하면 Controller에 이동을 요청하고 성공 여부와 관계없이 Idle로 돌아간다. Exit가 항상 호출되므로 오버레이 정리가 흩어지지 않는다.

_controller.ExecuteMove(_unit, cell);
_machine.ChangeState(new IdleState(_machine, _controller));

7. BattleController는 Context다

Controller는 입력 좌표를 변환하고, Physics2D로 클릭한 Unit을 찾은 뒤 상태 머신에 전달한다.

StateMachine.HandleBoardClick(
    clickedUnit,
    _board.WorldToCell(worldPosition));

상태가 사용할 기능은 작게 나눈다.

  • ShowSelection: 이동 범위 계산과 표시
  • ClearSelection: 선택과 오버레이 정리
  • ExecuteMove: Board 검증 후 MoveUnitCommand 실행
  • UndoLast: CommandHistory의 최근 행동 복원

Controller가 방법을 알고 State가 시점을 결정한다.

8. Undo와 기존 패턴의 협력

State 패턴을 추가했다고 Command나 Flyweight를 버리지 않는다. 세 패턴은 다른 문제를 푼다.

Flyweight

반복되는 지형 규칙 공유

Command

실행한 이동 기억과 Undo

State

현재 모드에서 입력 해석

Controller

세 구조를 연결

Idle의 Undo는 단순 복원이다. Selected의 Undo는 복원 후 ShowSelection을 다시 호출해 현재 위치 기준 범위를 갱신한다.

9. UnitSpawner와 3유닛 씬

선택 전환을 명확히 관찰하려고 세 유닛을 서로 떨어진 셀에 둔다. UnitSpawner는 설정된 셀마다 Prefab을 생성한다. 이미 자식 Unit이 존재하면 기존 배열을 반환한다.

Unit[] existing = GetComponentsInChildren<Unit>(true);
if (existing.Length > 0 || _unitPrefab == null)
    return existing;

이 성질을 멱등성이라고 부른다. 같은 명령을 반복해도 결과가 더 늘어나지 않는다. Play Mode 재진입이나 씬 빌더 재실행 때 중복 생성을 막는다.

10. 언제 State를 쓸까?

다음 질문 중 두 개 이상이 참이면 State가 유용하다.

  • 같은 입력이 현재 모드에 따라 다르게 동작하는가?
  • 모드별로 Enter/Exit 정리가 필요한가?
  • 새 모드가 계속 추가될 예정인가?
  • 하나의 조건문이 서로 다른 변경 이유를 품고 있는가?

반대로 상태가 두 개뿐이고 규칙이 한두 줄이며 확장 가능성이 낮다면 단순 조건문이 더 읽기 쉬울 수 있다. 패턴은 목표가 아니라 복잡성을 다루는 도구다.
