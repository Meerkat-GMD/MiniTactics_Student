입력의 뜻을
상태 객체에 맡긴다

이 자료는 발표 요약이 아니라 수업 뒤에도 다시 읽을 수 있는 교과서형 강의 자료다. State 패턴 하나만 다룬다. State 패턴이 해결하는 문제, 구조와 역할, 코드, 실행 흐름, 대가와 적용 기준을 순서대로 설명한다.

1. 같은 입력이 상황에 따라 다른 뜻을 가진다

State 패턴을 적용하기 전의 BattleController에는 입력을 받는 메서드가 두 개 있었다. 클릭을 처리하는 Update와 Undo 버튼을 처리하는 OnUndoClicked다. 아래는 이전 차시(3차시) BattleController의 실제 발췌다. 첫 번째 코드는 Update의 끝부분이고, 두 번째 코드는 OnUndoClicked다. Select는 유닛을 선택하는 메서드이고, TryMoveSelectedUnit은 선택된 유닛의 이동을 시도하는 메서드다.

if (clickedUnit != null && clickedUnit.CanMove)
{
    Select(clickedUnit);
    return;
}

if (SelectedUnit != null)
{
    TryMoveSelectedUnit(_board.WorldToCell(worldPosition));
}
public void OnUndoClicked()
{
    _history.UndoLast();
}

두 메서드는 짧고 올바르게 동작한다. 살펴볼 대상은 기능이 아니라 입력의 뜻을 정하는 판단이 놓인 위치다. 같은 클릭이 유닛을 선택하기 전과 선택한 중에 서로 다른 뜻을 가진다.

입력유닛을 선택하기 전유닛을 선택한 중
아군 유닛 클릭그 유닛을 선택한다.선택을 그 유닛으로 바꾼다.
빈 셀 클릭아무 일도 하지 않는다.선택한 유닛을 그 셀로 이동시킨다.
Undo최근 이동을 취소한다.최근 이동을 취소한다. 위 코드는 선택하기 전과 똑같이 처리한다.

입력의 뜻은 “무엇을 눌렀는가”와 “지금 어떤 상황인가”가 함께 정한다. 그런데 위 코드는 지금의 상황을 따로 기억하지 않는다. 클릭이 올 때마다 SelectedUnit != null 같은 조건으로 상황을 매번 다시 알아낸다.

여기에 요구 두 가지가 더해진다고 하자. 첫째, 선택 중에 Undo를 누르면 선택을 유지한 채 선택한 유닛의 범위를 새로 표시한다. 둘째, 나중에 “공격 대상 선택”이라는 세 번째 상황이 추가된다. 첫째 요구는 OnUndoClicked에 선택 여부를 묻는 조건을 더 넣어야 하고, 둘째 요구는 두 입력 메서드 모두에 조건을 더 넣어야 한다. 공격 대상 선택은 상황이 늘어나는 경우를 설명하기 위한 예시이며 현재 구현에는 없다.

2. 첫 해결 시도: enum과 switch, 그리고 그 한계

처음 떠올릴 수 있는 방법은 지금의 상황을 enum 필드에 기억하고, 입력 메서드 안에서 switch로 나누는 것이다. enum은 정해진 이름 몇 개 중 하나만 값으로 가질 수 있는 형식이다. 아래 코드는 설계 비교용 가상 코드이며 현재 Teacher 구현이 아니다.

enum InputMode { Idle, UnitSelected }
InputMode _mode = InputMode.Idle;

void HandleClick(Unit clickedUnit, Vector2Int cell)
{
    switch (_mode)
    {
        case InputMode.Idle:         /* 선택 */ break;
        case InputMode.UnitSelected: /* 선택 변경 또는 이동 */ break;
    }
}

상황을 _mode에 한 번 기억하므로 다른 필드의 값으로 상황을 다시 알아낼 필요가 없다. 상황이 두 개이고 앞으로 늘지 않는다면 이 코드나 if 문이 가장 읽기 쉽다. 한계는 상황이 늘어날 때 드러난다.

한계 1. 상황이 늘 때마다 모든 입력 메서드에 분기가 추가된다

void HandleUndo()
{
    switch (_mode)
    {
        case InputMode.Idle:         /* 취소 */ break;
        case InputMode.UnitSelected: /* 취소 후 범위 갱신 */ break;
        case InputMode.AttackTarget: /* 새로 추가 */ break;
    }
}

상황 하나를 추가하면 HandleClick의 switch에도 같은 case를 추가해야 한다. 상황이 3개이고 입력 메서드가 2개이면 관리할 case는 6개이고, 입력 메서드가 3개가 되면 9개다. 한 상황의 규칙이 입력 메서드의 수만큼 여러 곳에 나뉘어 있고, 한 곳을 빠뜨려도 컴파일러가 알려 주지 않는다. enum과 switch는 조건문의 위치만 옮긴다.

한계 2. 상황에 들어가고 나올 때 할 일이 여러 곳에 흩어진다

// 선택 중에 다른 아군을 클릭했을 때
HideRange();                 // 이전 유닛의 범위 표시를 끈다.
ShowRange(clickedUnit);

// 선택 중에 셀을 클릭했을 때
TryMove(_selected, cell);
HideRange();                 // 여기에서도 끈다.
_mode = InputMode.Idle;

선택 상황에서 나오는 경로는 선택 변경, 이동, 거부된 클릭으로 여러 개다. 경로마다 범위 표시를 끄는 줄을 직접 적어야 하고, 새 경로를 추가하면서 그 줄을 빠뜨리면 이전 유닛의 범위 표시가 화면에 남는다. _mode를 바꾸는 줄과 뒷정리를 하는 줄이 서로 묶여 있지 않기 때문이다. HideRange, ShowRange, TryMove는 설명을 위해 붙인 이름이다.

3. 상태 전이표로 규칙 전체를 적는다

코드를 고치기 전에 규칙 전체를 표로 적는다. 상태는 다음 입력을 어떻게 해석할지를 정하는 상황이고, 전이는 한 상태에서 다른 상태로 바뀌는 일이다. 표의 한 행은 “현재 상태에서 이 입력을 받으면 무엇을 하고 어느 상태가 되는가”를 뜻한다.

현재 상태입력하는 일다음 상태
대기아군 클릭없음선택
대기빈 셀 클릭없음대기
대기Undo최근 이동 취소대기
선택다른 아군 클릭없음선택(새 유닛)
선택셀 클릭이동 시도대기
선택Undo최근 이동 취소 후 범위 새로 표시선택

표에 적히지 않은 규칙이 하나 더 있다. 이동 범위 표시는 선택 상태에 들어갈 때 켜고 나올 때 끈다.

표의 “현재 상태” 열을 class로 만들면 각 class 안에는 자기 행만 남는다. enum 방식은 코드를 입력별로 묶었기 때문에 한 상태의 규칙이 여러 메서드에 나뉘었다. 상태별 class는 한 상태의 입력 규칙과 진입·이탈 시 할 일을 한 곳에 모은다.

4. State 패턴의 역할 대응

State 패턴은 상태마다 달라지는 행동을 상태별 객체에 맡기고, 상태가 바뀌면 현재 객체를 교체하는 구조다. 입력을 받는 쪽은 현재 상태를 나타내는 객체 하나를 가리키고 있다가, 입력이 오면 그 객체에 넘긴다.

  • Context = BattleController: 입력을 현재 상태에 전달하고, 상태가 요청하는 기능을 제공한다.
  • State = InputState: 상태가 받을 수 있는 입력(클릭, Undo)과 진입·이탈 시점을 선언한다.
  • Concrete State = IdleState, UnitSelectedState: 현재 상태에서 입력이 무엇을 뜻하는지, 다음 상태가 무엇인지 결정한다.
  • 전환 담당 = InputStateMachine: 현재 상태를 보관하고 Exit, 교체, Enter의 순서를 지킨다.
입력 → Context → 상태 기계 → 현재 상태 → Context의 기능 요청 또는 전환

State 패턴의 기본 구조는 Context, State, Concrete State 세 역할이다. 이 구현은 Context가 직접 맡을 수도 있는 “현재 상태의 보관과 전환”을 InputStateMachine이라는 별도의 class로 분리했다. 이 자료에서는 이 class를 상태 기계라고 부른다.

5. InputState: abstract와 virtual의 구분

public abstract class InputState
{
    public virtual void Enter()
    {
    }

    public virtual void Exit()
    {
    }

    public abstract void HandleBoardClick(Unit clickedUnit, Vector2Int cell);
    public abstract void HandleUndo();
}

실제 발췌(InputState.cs, using과 namespace 생략)다. abstract class는 new로 직접 만들 수 없고, 상속한 class의 객체만 만들 수 있다.

abstract: 모든 상태가 답해야 하는 입력

본문이 없는 선언이다. 상속한 class가 override로 구현하지 않으면 컴파일 오류가 발생한다. 클릭과 Undo의 뜻은 상태마다 다르므로 구현을 빠뜨릴 수 없게 한다.

virtual: 필요한 상태만 재정의하는 시점

빈 본문이라는 기본 동작이 있다. 진입하거나 이탈할 때 할 일이 없는 상태는 그대로 두고, 할 일이 있는 상태만 재정의한다.

HandleBoardClick을 virtual로 선언하고 빈 본문을 두면, 새 상태에서 구현을 잊어도 컴파일러가 알려 주지 않는다. 반드시 답해야 하는 입력은 abstract로 선언한다.

6. InputStateMachine: 입력 전달과 전환 순서

public sealed class InputStateMachine
{
    public InputState Current { get; private set; }

    public void ChangeState(InputState next)
    {
        if (next == null)
        {
            throw new ArgumentNullException(nameof(next));
        }

        if (ReferenceEquals(Current, next))
        {
            return;
        }

        Current?.Exit();
        Current = next;
        Current.Enter();
    }

    public void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
    {
        Current?.HandleBoardClick(clickedUnit, cell);
    }

    public void HandleUndo()
    {
        Current?.HandleUndo();
    }
}

실제 발췌(InputStateMachine.cs, using과 namespace 생략)다. Current는 지금 입력을 맡은 상태 객체를 가리키며, private set이므로 이 class 밖에서는 값을 바꿀 수 없다.

입력 전달

두 전달 메서드에는 IdleState라는 이름도 if 문도 없다. 상태 기계는 어떤 상태가 있는지 모른다. Current가 가리키는 실제 객체의 override가 실행된다. 같은 호출이 객체에 따라 다른 동작을 하는 이 성질을 다형성이라고 한다.

전환 순서

ChangeState의 핵심은 마지막 세 줄이다. 전환 순서는 항상 “이전 상태의 Exit → 교체 → 새 상태의 Enter”다. 모든 전환은 ChangeState를 거친다. 이 순서를 한 곳에 두면 상태들은 서로에게 뒷정리를 부탁하지 않아도 된다. 나가는 상태는 자신의 Exit만, 들어오는 상태는 자신의 Enter만 책임진다.

Current = next;를 가장 먼저 쓰면 그다음 줄의 Exit는 새 상태의 Exit가 된다. 이전 상태는 뒷정리를 하지 못한다.

ChangeState 앞부분의 두 검사

  • next == null: null을 현재 상태로 삼으면 다음 입력을 맡을 객체가 없어진다. 전환을 요청한 코드의 오류이므로 ArgumentNullException으로 즉시 알린다.
  • ReferenceEquals(Current, next): 두 변수가 같은 객체를 가리키는지 검사한다. 같은 객체로의 전환은 Exit와 Enter를 실행하지 않고 돌아간다. 선택 변경처럼 new로 새 객체를 만들어 넘기는 전환은 이 검사에 걸리지 않는다.

?.는 첫 상태가 정해지기 전에만 의미가 있다

?.는 왼쪽이 null이면 호출을 건너뛰는 연산자다. BattleController는 시작할 때 첫 상태를 IdleState로 정한다. 그 뒤에는 첫 검사가 null을 거부하므로 Current가 다시 null이 되지 않는다. 따라서 Current가 null인 때는 첫 상태가 정해지기 전뿐이다.

  • Current?.Exit();: 맨 처음 전환에서는 이전 상태가 없으므로 호출을 건너뛴다. ?.가 없다면 이 전환에서 NullReferenceException이 발생한다.
  • Current.Enter();: 바로 앞 줄에서 넣은 next는 첫 검사를 통과했으므로 null이 아니다. 그래서 ?.가 필요 없다. 맨 처음 전환에서는 IdleState가 Enter를 재정의하지 않았으므로 빈 본문이 실행된다.
  • Current?.HandleBoardClick(…);과 Current?.HandleUndo();: 첫 상태를 정하지 않은 상태 기계에 입력이 와도 예외를 내지 않고 아무 일도 하지 않는다. BattleController는 첫 상태를 정한 뒤에 입력을 전달하므로 이 구현의 실행 중에는 호출을 건너뛰는 일이 없다.

7. IdleState: 전이표의 대기 행

public override void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    if (clickedUnit != null && clickedUnit.CanMove)
        _machine.ChangeState(new UnitSelectedState(_machine, _controller, clickedUnit));
}

public override void HandleUndo() => _controller.UndoLast();

실제 발췌(IdleState.cs의 두 메서드)다. _machine과 _controller는 생성자에서 받아 둔 상태 기계와 Context다. CanMove는 이동할 수 있는 아군인지를 알려 주는 값이다. =>는 본문이 식 하나뿐인 메서드를 중괄호 없이 적는 표기다.

  • 대기, 아군 클릭 → 선택: if가 참이다. 클릭한 유닛을 보관하는 선택 상태를 새로 만들어 전환한다.
  • 대기, 빈 셀 클릭 → 대기: if가 거짓이다. 아무 줄도 실행하지 않으므로 상태가 그대로다.
  • 대기, Undo → 대기: Context에 최근 이동의 취소만 요청한다. 전환은 없다.

이 class에는 이동을 요청하는 코드가 없고, Enter와 Exit도 재정의하지 않는다. 대기 상태의 규칙 전체를 이 파일 하나에서 읽을 수 있다.

8. UnitSelectedState: 전이표의 선택 행

입력의 뜻은 SelectedUnit 검사가 아니라 현재 상태의 종류가 정한다

private readonly Unit _unit;

public UnitSelectedState(InputStateMachine machine, BattleController controller, Unit unit)
{
    _machine = machine;
    _controller = controller;
    _unit = unit;
}

실제 발췌(UnitSelectedState.cs의 필드와 생성자, _machine과 _controller의 필드 선언 생략)다. 패턴 적용 전에는 Update가 SelectedUnit != null을 검사하여 클릭이 이동 요청인지를 정했다. 이제 입력의 뜻을 정하는 것은 그 검사가 아니라 현재 상태의 종류다. Current가 UnitSelectedState이면 선택 중이고, 선택된 유닛은 그 상태 객체가 생성자에서 받아 _unit에 보관한다.

선택 상태는 유닛을 받아야만 만들 수 있으므로 “선택 중인데 선택한 유닛이 없는” 경우가 생기지 않는다. 그래서 이 class에는 선택한 유닛이 있는지 묻는 검사가 없다. _unit은 readonly이므로 다른 유닛을 선택할 때에는 값을 바꾸지 않고 새 상태 객체를 만든다.

BattleController의 SelectedUnit 속성은 남아 있다. 이 값은 선택 상태가 진입할 때 ShowSelection이 기록하고 이탈할 때 ClearSelection이 null로 되돌린다. 즉 현재 상태를 따라 바뀌는 값이며, 상태 class는 입력의 뜻을 정할 때 이 값을 읽지 않는다.

Enter와 Exit에 범위 표시의 수명을 맡긴다

public override void Enter() => _controller.ShowSelection(_unit);
public override void Exit() => _controller.ClearSelection();

실제 발췌(UnitSelectedState.Enter와 Exit)다. 두 메서드는 InputState의 빈 virtual 메서드를 재정의한다. 범위는 선택 상태가 현재 상태인 동안에만 표시된다. Enter와 Exit는 상태 기계의 ChangeState가 호출하므로, 상태에 들어오고 나가는 어떤 경로에서도 빠지지 않는다.

클릭: 선택 변경을 먼저 검사한다

public override void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    if (clickedUnit != null && clickedUnit.CanMove)
    {
        _machine.ChangeState(new UnitSelectedState(_machine, _controller, clickedUnit));
        return;
    }

    _controller.ExecuteMove(_unit, cell);
    _machine.ChangeState(new IdleState(_machine, _controller));
}
  • 선택, 다른 아군 클릭 → 선택(새 유닛): 그 유닛을 보관하는 새 선택 상태로 전환한다. return을 빠뜨리면 선택을 바꾼 직후에 이동을 시도하고 대기로 돌아간다.
  • 선택, 셀 클릭 → 대기: 그 밖의 클릭은 이동 시도다. ExecuteMove가 이동을 거부해도 다음 줄은 실행되므로 대기로 돌아간다. 범위 밖을 클릭하는 것이 선택 취소의 역할을 한다.

Undo: 전환 없이 범위만 새로 표시한다

public override void HandleUndo()
{
    _controller.UndoLast();
    _controller.ShowSelection(_unit);
}

ChangeState를 호출하지 않으므로 Exit와 Enter는 실행되지 않고 선택 상태가 유지된다. 취소로 유닛의 위치가 바뀌었을 수 있으므로 같은 유닛의 범위를 다시 표시한다. IdleState의 HandleUndo는 UndoLast 한 줄뿐이었다. 같은 Undo 입력이 현재 상태에 따라 다른 본문을 실행한다.

1절의 첫째 요구(선택 중 Undo는 선택을 유지한 채 범위만 새로 표시한다)가 이 상태의 메서드 하나에서 해결되었다. 다른 상태의 코드와 Context의 입력 메서드는 고치지 않았다.

9. BattleController는 Context다

// Update의 마지막 줄: 클릭한 유닛과 셀을 구한 뒤에 실행한다.
StateMachine.HandleBoardClick(clickedUnit, _board.WorldToCell(worldPosition));

public void OnUndoClicked() => StateMachine.HandleUndo();

실제 발췌(BattleController.Update의 마지막 줄과 OnUndoClicked, 첫 줄의 주석은 설명을 위해 추가)다. StateMachine은 BattleController가 가진 상태 기계를 돌려주는 속성이다. BattleController는 시작할 때 첫 상태를 IdleState로 정한다. Update는 클릭을 “유닛과 셀”이라는 두 값으로 바꾸는 일만 한다. 빈 셀을 클릭하면 clickedUnit은 null이다. 그 클릭이 무슨 뜻인지는 현재 상태가 결정한다.

1절에서 본 두 if 문이 Update에서 사라졌다. 두 입력 메서드에는 SelectedUnit != null처럼 선택 여부를 물어 입력의 뜻을 가르는 조건문이 하나도 없다.

Context는 상태가 요청할 기능을 internal 메서드로 제공한다. internal은 함께 컴파일되는 같은 어셈블리의 코드만 호출할 수 있다는 뜻이다. 그 내부 구현은 State 패턴의 범위가 아니므로 이 자료에서 다루지 않는다.

  • ShowSelection: 선택된 유닛을 기록하고 이동 범위를 표시한다.
  • ClearSelection: 선택된 유닛의 기록을 지우고 범위 표시를 끈다.
  • ExecuteMove: 이동할 수 있는 셀이면 유닛을 이동시킨다.
  • UndoLast: 최근 이동을 취소한다.

상태는 언제 할지를 정하고, Context는 어떻게 할지를 안다.

BattleController에는 다른 코드가 선택과 이동을 직접 요청할 때 사용하는 public 메서드 Select와 TryMoveSelectedUnit도 있다. 두 메서드도 상태를 바꿀 때에는 ChangeState를 호출한다. 모든 전환이 ChangeState를 거친다는 규칙은 Context 자신에게도 적용된다.

10. 클릭 한 번의 흐름을 단계별로 추적한다

Selected(A)는 A를 보관하는 UnitSelectedState 객체를 줄여 쓴 표기다.

추적 1. 대기 상태에서 아군 A를 클릭한다

  1. Context의 Update가 A와 셀을 구하고 StateMachine.HandleBoardClick(A, cell)을 호출한다. Current는 Idle이다.
  2. 상태 기계가 Current?.HandleBoardClick(A, cell)을 호출한다. Current가 null이 아니므로 IdleState의 메서드가 실행된다.
  3. IdleState의 if가 참이므로 ChangeState(new UnitSelectedState(…, A))를 호출한다.
  4. next가 null이 아닌 새 객체이므로 ChangeState 앞부분의 두 검사를 통과한다. 상태 기계가 Current?.Exit()를 실행한다. IdleState의 Exit는 빈 본문이다.
  5. 상태 기계가 Current = next를 실행한다. Current는 Selected(A)가 된다.
  6. 상태 기계가 Current.Enter()를 실행한다. Selected(A)의 Enter가 ShowSelection(A)를 요청하고, A의 범위가 표시된다.

클릭 한 번이 Context, 상태 기계, 현재 상태, 전환의 순서로 흐른다. 범위를 표시하라고 요청한 것은 IdleState가 아니라 새 상태의 Enter다.

추적 2. 선택 상태에서 유닛이 없는 셀을 클릭한다

출발 상태는 Current가 Selected(A)이고 A의 범위가 표시된 상태다.

  1. Context가 HandleBoardClick(null, cell)을 호출하고, 상태 기계가 Current에 넘긴다.
  2. Selected(A)의 첫 if는 clickedUnit이 null이므로 거짓이다.
  3. Selected(A)가 _controller.ExecuteMove(A, cell)을 요청한다. 이동할 수 있는 셀이면 이동하고, 아니면 거부한다.
  4. Selected(A)가 ChangeState(new IdleState(…))를 호출하고, 이 호출은 두 검사를 통과한다. 상태 기계의 Current?.Exit()가 Selected(A)의 Exit를 실행하고, Exit가 ClearSelection()을 요청한다. 범위 표시가 꺼진다.
  5. 상태 기계가 Current = next를 실행한 뒤 Current.Enter()를 실행한다. Current는 Idle이고, IdleState의 Enter는 빈 본문이다.

3단계의 결과가 이동이든 거부이든 4단계와 5단계는 똑같이 실행된다.

범위 표시를 끄는 코드는 Exit 한 곳뿐이다

선택 변경, 이동, 거부된 클릭은 모두 선택 상태에서 나오는 일이고, 상태에서 나오는 길은 ChangeState 하나뿐이다. ChangeState는 항상 이전 상태의 Exit를 먼저 호출한다. 그래서 끄는 코드가 Exit 한 곳뿐인데도 세 경우 모두에서 범위 표시가 꺼진다. 선택 변경의 경우에는 Selected(A)의 Exit가 표시를 끈 뒤에 Selected(B)의 Enter가 B의 범위를 표시한다. 2절의 가상 코드처럼 경로마다 끄는 줄을 적을 필요가 없다.

11. 확장성, 대가, 적용 기준

새 상태를 추가할 때

  • 새로 만든다: 새 상태의 class 파일 하나(예: 공격 대상 선택 상태). 그 상태의 클릭 규칙, Undo 규칙, 진입·이탈 시 할 일을 한 class에 작성한다.
  • 고친다: 그 상태로 전환을 시작하는 기존 상태. 어떤 입력을 받았을 때 새 상태로 ChangeState를 호출하는 줄을 넣는다.
  • 필요할 때만 추가한다: Context의 기능 메서드. 새 상태가 요청할 기능이 Context에 아직 없는 경우에만 추가한다.
  • 고치지 않는다: Context의 Update와 OnUndoClicked, InputStateMachine, InputState. 입력의 종류와 전달하는 방식이 그대로이기 때문이다.

enum 방식에서는 상태 하나를 추가하면 모든 입력 메서드의 switch를 고쳐야 했다. State 패턴에서는 새 규칙이 새 class 안에 모인다. 공격 대상 선택 상태는 확장을 설명하기 위한 예시이며 현재 구현에는 없다.

반대의 경우도 알아 둔다. 새로운 입력의 종류를 추가하면 InputState에 abstract 메서드가 하나 늘고, 모든 상태 class가 그것을 구현해야 한다. State 패턴은 상태의 추가에 유리한 구조다.

대가

  • class의 수가 늘어난다. 이 구현은 상태 두 개를 위해 InputState, InputStateMachine, IdleState, UnitSelectedState 네 개를 만들었다.
  • 한 입력의 처리 전체를 보려면 여러 파일을 열어야 한다.
  • 상태가 두 개이고 늘지 않는다면 if 문이 더 단순하다.

이득이 되는 조건

  • 상태마다 같은 입력의 뜻이 달라진다.
  • 상태에 들어가고 나올 때 해야 할 일이 있다.
  • 상태가 앞으로 늘어날 예정이다.

State 패턴은 실행 속도나 메모리를 개선하는 기법이 아니다. 위의 조건이 성립할 때 “한 상태의 규칙을 한 곳에서 읽고 고칠 수 있다”는 이득이 class 수의 증가라는 대가보다 커진다. 조건이 성립하지 않는다면 1절과 같은 if 문을 그대로 두는 것이 올바른 판단이다.

12. 이해 확인 질문과 답

  1. 선택 상태의 코드는 SelectedUnit != null을 검사하지 않는다. 이동시킬 유닛은 어디에서 얻는가?
    UnitSelectedState 객체가 생성자에서 받아 _unit에 보관한 유닛이다. 선택 중인지는 현재 상태의 종류가 알려 주므로 검사가 필요 없다. BattleController의 SelectedUnit 속성은 ShowSelection과 ClearSelection이 기록하는 값이며, 상태 class는 이 값을 읽지 않는다.
  2. 범위 표시를 끄는 코드는 한 곳뿐이다. 선택 전환, 이동, 거부된 클릭에서 모두 꺼지는 이유는 무엇인가?
    세 경우 모두 ChangeState를 거쳐 선택 상태에서 나오고, ChangeState는 항상 이전 상태의 Exit를 먼저 호출하기 때문이다.
  3. ChangeState에서 Current = next;를 Exit보다 먼저 쓰면 이동 후에 무엇이 달라지는가?
    새 상태인 IdleState의 빈 Exit가 호출되고 선택 상태의 Exit는 호출되지 않는다. 범위 표시가 화면에 남는다.
  4. 선택 상태에서 Undo를 누르면 Exit와 Enter가 호출되는가?
    호출되지 않는다. HandleUndo는 ChangeState를 호출하지 않고 ShowSelection을 직접 다시 요청한다.
  5. “공격 대상 선택” 상태를 추가한다면 새로 만들 파일과 고칠 파일은 각각 무엇인가?
    새 상태의 class 파일을 만들고, 그 상태로 전환을 시작하는 기존 상태를 고친다. Context의 Update와 OnUndoClicked, 상태 기계, InputState는 고치지 않는다.
  6. 상태가 두 개뿐이라면 if 문으로도 충분하다. 어느 시점부터 State 패턴이 이득인가?
    상태마다 입력의 뜻이 달라지고, 상태에 들어가고 나올 때 해야 할 일이 있고, 상태가 늘어날 예정일 때다. 상태가 두 개이고 늘지 않는다면 if 문이 더 단순하다.
