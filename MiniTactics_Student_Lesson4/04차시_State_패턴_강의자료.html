Chapter 01

같은 입력과 달라지는 모드

클릭에 한 가지 뜻만 있다면 한 메서드로도 충분하다. 선택 전후에 클릭의 뜻이 달라지면 현재 모드를 함께 보아야 한다. 여기서 상태는 객체가 가진 모든 값이 아니라 입력을 해석하는 모드다.

좌표보다 먼저 현재 모드를 묻는다

현재 모드입력해석
Idle · 선택 없음선택 가능한 유닛 클릭그 유닛의 선택 상태로 전환
UnitSelected · 선택 중다른 선택 가능 유닛 클릭새 유닛의 선택 상태로 전환
UnitSelected · 선택 중선택 가능 유닛이 아닌 곳 클릭현재 유닛의 이동을 시도

입력의 모양이 같아도 실행할 규칙은 현재 모드가 결정한다. 이동 가능 여부의 세부 계산은 이 패턴의 책임이 아니다.

Chapter 02

두 모드의 조건문도 출발점이 된다

설계 비교용 가상 코드 · 현재 Teacher 구현 아님 · 두 모드만 가정, 입력 감지와 선택 검증 생략

문제는 조건문 수보다 흩어진 규칙이다

한곳에 섞이기 쉬운 것

클릭 해석, 선택 표시, 해제, Undo 뒤 갱신을 각각 수정할 때마다 현재 모드를 다시 검사한다.

원하는 변경 단위

“선택 중 입력”의 행동을 한곳에서 읽고 바꾸고 싶다. 상태별 행동과 전환 경계를 함께 찾는다.

조건문은 틀린 문법이 아니다. 같은 모드의 규칙이 여러 입력 처리에 반복되고 서로 어긋날 때 분리의 가치가 커진다.

질문과 답: 두 모드가 있으면 반드시 클래스를 나누어야 할까? 아니다. 분기가 짧고 바뀌지 않는다면 조건문이 더 간단하다. 여러 입력에 같은 모드 규칙이 흩어져 함께 수정하기 어려워질 때 상태별 경계를 검토한다.

Chapter 07

Enter에서 전환을 반복하지 않는 이유

Enter는 표시를 준비하고 전환을 반복하지 않는다

public override void Enter() => _controller.ShowSelection(_unit);
public override void Exit() => _controller.ClearSelection();

현재 실제 코드 발췌 · Teacher4 2f82ead · UnitSelectedState.cs L16–17 · 진입·이탈 훅 두 줄; 생성자·입력 처리 생략

Enter → ShowSelection

현재 유닛과 범위를 표시한다. 새 상태를 요청하지 않는다.

Exit → ClearSelection

이전 선택과 표시를 지운다. 다음 Enter가 새 표시를 준비한다.

Enter에서 Select를 다시 호출하면 새 객체의 Enter가 또 전환을 요청할 수 있다. 현재 코드는 표시 준비와 전환 요청의 경계를 지킨다.

표시 준비는 공통 작업을 호출한다

internal void ShowSelection(Unit unit)
{
    SelectedUnit = unit;
    _highlighter.Show(_board.CalculateMovementRange(unit), unit);
}

현재 실제 코드 발췌 · Teacher4 2f82ead · BattleController.cs L37–41 · ShowSelection 전체; 다른 서비스 생략

SelectedUnit을 설정하고 현재 범위를 보여 준다. 이 메서드에는 ChangeState나 Select 호출이 없다. 범위 계산 자체의 구현은 State 설명에서 생략한다.

Enter에서 Select를 호출한다는 설명은 현재 코드와 다르다. Select는 새 상태를 만들고 그 상태의 Enter를 실행할 수 있다. 표시를 준비하려고 다시 Select를 호출하면 이 경로가 반복될 위험이 있다. 현재 구현의 Enter는 ShowSelection을 사용한다.

유닛을 고르면 Select로 교체를 요청한다. 이동 성공 때만 Select(null)로 Idle을 요청한다. 실패하면 현재 상태와 표시가 유지된다.

A 선택 중 B를 고르면 어떤 순서일까?

순서실행과 관찰
1 · 입력 해석A의 UnitSelectedState가 B를 보고 Select(B) 요청
2 · 생성Controller가 B의 새 UnitSelectedState 생성
3 · 이탈A 상태의 Exit → ClearSelection
4 · 교체와 진입Current를 B 상태로 교체 → Enter → ShowSelection(B)

답: A 표시 정리 뒤 B 표시 준비다. 새 상태 생성 시점은 Exit보다 앞이며, Enter 실행 시점은 Current 교체 뒤다.

이동 성공은 Idle 요청으로 이어지고, 이동 실패는 전환 요청 없이 반환된다. 따라서 실패 뒤에도 선택 상태와 표시가 유지된다. B로 선택 대상을 바꾸는 경우에는 새 B 상태 객체 생성, A의 표시 해제, Current 교체, B 표시 준비를 구별한다. 이 설명은 입력의 해석과 상태 변화에 한정한다.

Chapter 10

이득과 비용으로 적용을 판단한다

두 상태만으로 패턴이 필수는 아니다

분리가 유용한 때

모드마다 여러 입력의 뜻이 달라지고, 같은 모드의 규칙을 함께 수정·검증해야 한다.

지불하는 비용

클래스와 참조가 늘고 호출 경로를 더 따라간다. Controller 서비스와 전환 권한의 경계를 관리해야 한다.

두 모드의 짧고 안정된 조건문이라면 그대로 두는 편이 더 명확할 수 있다. 현재 Select는 요청마다 새 상태 객체를 만든다. 할당 비용의 크기는 별도 측정 대상이다.
