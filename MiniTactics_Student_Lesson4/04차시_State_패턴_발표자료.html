State 패턴

같은 칸을 눌렀는데, 왜 이번에는 이동할까?
현재 조작 단계에 따라 입력을 해석하는 객체를 만든다.

Yesterday's Success

3차시는 지형에 맞는 이동을 완성했다

  • 여러 셀이 같은 지형 규칙을 공유한다.
  • 지형별 비용을 더해 이동 범위를 구한다.
  • 선택한 유닛을 이동하고 Undo로 되돌린다.

이미 나뉜 책임

Board는 지형을, 이동 범위 계산은 비용을, Command는 이동 기록을 맡는다. 기존 구조는 이 기능들을 충분히 설명한다.

현재 맵의 각 셀은 공통 TileData 에셋을 참조하고, 같은 에셋의 RuntimeTerrain을 공유한다. 이제 살펴볼 대상은 클릭의 뜻을 정하는 코드다.

현재 구조: MapLoader.Load(MapData), TileData.RuntimeTerrain, BattleController

New Requirement

조작 단계마다 다른 규칙이 필요하다

“A 선택 중 B를 누르면 B로 바꾸고,
Undo 후에는 현재 선택한 유닛의 범위를 다시 보여 주세요.”

빈 칸 클릭, 유닛 클릭, Undo를 항상 같은 방식으로 처리할 수는 없다. 요구가 늘어날수록 지금 어떤 조작 단계인가에 따라 규칙을 골라야 한다. 다음 장에서 같은 입력의 결과를 비교한다.

Observation

좌표만 같아도 클릭의 뜻은 달라진다

입력 전 상황같은 입력실행할 일
선택 없음빈 칸 (3,2) 클릭아무 일도 하지 않음
A 선택, 이동 가능빈 칸 (3,2) 클릭A의 이동 요청

입력의 뜻 = 무엇을 눌렀는가 + 지금 어떤 단계인가

A는 (2,2)에 있고 (3,2)는 갈 수 있는 빈 평지라고 가정한다. 좌표는 같지만, 두 번째 입력은 어느 유닛을 움직일지까지 결정된다. 이전 선택을 기억하기 때문이다.

설명용 좌표 예제. 현재 동작 근거: IdleState / UnitSelectedState

First Attempt

첫 생각은 선택 여부를 검사하는 것이다

if (selectedUnit == null)
{
    Select(clickedUnit);
}
else
{
    TryMove(selectedUnit, cell);
}

작은 요구에는 충분하다

선택하지 않았으면 선택하고, 선택했다면 이동한다. 상태가 두 가지이고 처리도 짧다면 한 조건문으로 흐름을 읽을 수 있다.

이 예제는 최초 아이디어를 보여 주는 가상 코드다. 선택 가능한 대상 검사와 재선택 규칙이 추가되기 전에는, 선택 여부 하나로 두 행동을 나누는 방식도 이해하기 쉽다.

설명용 가상 코드: 현재 Teacher 구현이 아님. Select / TryMove의 세부 동작 생략

More Rules

규칙이 늘면 여러 입력에 조건이 퍼진다

void OnClick() {
    if (isSelected) HandleSelectedClick();
    else HandleIdleClick();
}
void OnUndo() {
    if (isSelected) UndoAndRefresh();
    else UndoOnly();
}

추가 요구를 대입하면

선택 중 클릭은 다시 유닛 클릭과 빈 칸 클릭으로 나뉜다. Undo 뒤 범위 갱신도 선택 여부에 달렸다. 이후 공격 대기가 생기면 두 입력의 분기를 함께 수정해야 한다.

문제는 if라는 문법 자체가 아니다. 하나의 모드 규칙이 여러 입력 처리 위치에 흩어지는 것이 변경을 어렵게 한다.

설명용 가상 코드. 공격 대기는 확장 상황이며 현재 구현에는 없음

Conflicting State

여러 값으로 한 모드를 표현하면 어긋날 수 있다

의도한 조합

isSelected = true
selectedUnit = A
선택 중이며, 다음 이동 대상은 A다.

실수로 남긴 조합

isSelected = false
selectedUnit = A
어떤 값에 따라 클릭을 해석해야 할까?

모드와 선택 대상을 별도 필드로 관리하면 모든 전환에서 둘을 맞춰야 한다. 해제할 때 대상만 남기거나 표시만 지우는 실수도 가능하다. 함께 변하는 정보와 행동을 한 단위로 묶을 이유가 생긴다.

설명용 가상 실패 사례. 현재 Teacher 코드에 이 두 필드가 있다는 뜻은 아님

Responsibility Boundary

한 조작 단계에 필요한 것을 묶는다

선택 중이라는 단위

선택 대상 + 클릭 해석 + Undo 후 처리 + 시작과 정리

  • 유닛 클릭이면 새 선택으로 바꾼다.
  • 빈 칸 클릭이면 대상의 이동을 요청한다.
  • 진입할 때 범위를 보여 준다.
  • 나갈 때 선택 표시를 지운다.

이 항목들은 모두 ‘선택 중’이라는 같은 이유로 달라진다. 이 단위에 입력을 맡기면 Controller는 모드별 규칙을 매번 분기할 필요가 없다.

State Pattern

State는 현재 모드의 행동을 객체로 만든다

현재 입력을 처리할 객체를 정하고,
모드가 바뀌면 그 객체를 교체한다.

IdleState

대기 상태. 선택 가능한 유닛을 기다린다. 빈 칸을 눌러도 이동 요청을 만들지 않는다.

UnitSelectedState

선택 상태. 특정 유닛의 참조를 기억하고 재선택·이동 요청·Undo 후 표시를 처리한다.

여기서 상태(State)는 다음 입력을 해석하는 모드다. 체력, 위치, 지형처럼 게임의 모든 데이터를 이 객체에 넣는다는 뜻은 아니다.

Roles

입력 감지와 해석과 실행을 나눈다

Controller클릭한 유닛과 셀을 구한다. 이동 검사와 표시 기능을 연결한다.
상태 기계현재 상태 하나를 보관하고 입력 전달과 교체 순서를 맡는다.
현재 State이번 클릭의 뜻과 다음 모드를 정한다.
명령과 이력실제 이동을 실행하고 되돌릴 기록을 남긴다.

상태 기계(State Machine)는 현재 모드를 보관하고 다른 모드로 바꾸는 관리자다. ‘무엇을 눌렀나’, ‘무슨 뜻인가’, ‘무엇을 바꾸나’를 각 담당자에게 물을 수 있다.

대응: BattleController / InputStateMachine / InputState의 자식 / MoveUnitCommand·CommandHistory

Current Reference

Current는 지금 입력을 맡은 객체다

public InputState Current { get; private set; }

하나의 공통 타입

Current에는 IdleState 또는 UnitSelectedState 객체를 가리키는 참조가 들어간다. 한 시점에 입력을 맡는 객체는 하나다.

교체하는 입구 제한

get은 외부 읽기를 허용한다. private set은 대입을 이 클래스 안으로 제한해, 정해진 교체 절차를 거치게 한다.

Controller는 상태 기계를 처음 사용할 때 Current가 비어 있으면 IdleState를 넣는다. 따라서 처음 입력은 대기 규칙으로 처리한다.

실제 발췌: InputStateMachine.Current. 초기화: BattleController.StateMachine

Abstract Contract

InputState는 모든 상태의 공통 약속이다

public abstract class InputState
{
    public abstract void HandleBoardClick(
        Unit clickedUnit, Vector2Int cell);
    public abstract void HandleUndo();
}

abstract와 override

abstract는 자식이 채워야 할 틀이다. InputState 자체를 new로 만들 수 없으며, 구체적인 자식은 override로 클릭과 Undo의 내용을 작성한다.

상태 기계는 구체적인 클래스 이름을 몰라도 이 두 메서드를 호출할 수 있다. 대기는 클릭을 무시할 수 있고, 선택 상태는 같은 호출로 이동을 요청할 수 있다.

InputState.cs 선언을 설명용으로 축약. Enter / Exit 생략, 긴 선언 줄바꿈 정리

Entry and Exit Contract

virtual은 바꾸어 쓸 수 있는 기본 동작이다

public virtual void Enter()
{
}

public virtual void Exit()
{
}

필요한 상태만 재정의

virtual 메서드에는 기본 본문이 있다. 여기서는 아무 일도 하지 않는다. 대기 상태는 그대로 쓰고, 선택 상태는 시작·정리 동작을 override한다.

Enter는 그 상태가 현재 상태가 될 때, Exit는 그 역할을 끝낼 때 호출한다. 선택 표시를 시작하고 지우는 일을 이 두 시점에 모으면 전환에서 빠뜨리기 어렵다.

실제 발췌: InputState.Enter / Exit

유닛 참조

null은 클릭 위치에서 유닛을 찾지 못했다는 뜻이다. 같은 칸을 누른 사실 자체가 사라지는 것은 아니다.

셀 좌표

Vector2Int는 가로·세로의 정수 좌표 두 개를 담는다. 빈 칸에도 이동 목적지가 될 좌표는 있다.

Controller가 화면 위치를 월드 위치로 바꾸고, 그곳의 유닛과 보드 셀을 구한다. State는 마우스 장치 대신 이 결과를 받는다.

실제 경로: BattleController.Update → StateMachine.HandleBoardClick

State Data

선택 상태는 유닛의 참조를 기억한다

private readonly Unit _unit;

// 생성자 안에서 선택 대상을 받는다.
_unit = unit;

같은 유닛을 계속 가리킨다

객체를 만들 때 호출하는 생성자에서 A를 받으면 _unit은 A 객체를 가리킨다. A가 움직여도 같은 객체이므로, 다시 범위를 구할 때 현재 위치를 읽는다.

readonly의 범위

생성 후 이 필드에 B를 다시 대입할 수 없다. A의 위치 변경까지 막는 것은 아니다. B를 선택할 때는 새 상태 객체를 만든다.

Transition Guard

같은 상태 객체인지 먼저 검사한다

if (ReferenceEquals(Current, next))
{
    return;
}

비교 대상은 객체 자체

ReferenceEquals는 두 참조가 정확히 같은 객체를 가리키는지 확인한다. 같으면 Exit와 Enter를 반복하지 않는다. 클래스 이름이나 선택 유닛만 비교하지 않는다.

A를 기억하는 선택 상태를 new로 다시 만들면 다른 객체다. 따라서 A를 다시 선택해도 전환할 수 있다. 또한 ChangeState에 null을 넘기면 예외를 발생시켜 잘못된 다음 상태를 거절한다.

실제 발췌·검사 순서: InputStateMachine.ChangeState

IdleState

대기는 선택 가능한 유닛만 받는다

if (clickedUnit != null && clickedUnit.CanMove)
    _machine.ChangeState(new UnitSelectedState(
        _machine, _controller, clickedUnit));

조건이 참

유닛이 있고 이동 가능한 대상이면, 그 유닛을 기억하는 선택 상태를 만들어 전환한다. 아직 이동 명령을 만들지는 않는다.

조건이 거짓

빈 칸이나 이동 불가 유닛을 클릭하면 아무 일도 하지 않고 Idle에 머문다. &&는 앞 조건이 거짓이면 뒤 속성을 읽지 않는다.

실제 발췌: IdleState.HandleBoardClick, 긴 호출 줄바꿈만 정리

Trace · Enter

A를 선택하면 진입 동작이 범위를 표시한다

public override void Enter() =>
    _controller.ShowSelection(_unit);
public override void Exit() =>
    _controller.ClearSelection();
A 클릭 후 순서현재 상태선택 화면
Idle.ExitIdle아직 없음
Current 교체Selected(A)아직 없음
Selected(A).EnterSelected(A)A 기준 범위 표시

Selected(A)는 A를 기억하는 UnitSelectedState라는 설명용 표기다. ShowSelection은 Controller의 SelectedUnit에 A를 넣고 현재 위치의 범위를 표시한다. 나갈 때는 Exit가 선택과 표시를 정리한다.

실제 발췌: UnitSelectedState.Enter / Exit, 줄바꿈 정리. 표시: BattleController

Click Priority

선택 중에는 재선택을 먼저 검사한다

if (clickedUnit != null && clickedUnit.CanMove)
{
    _machine.ChangeState(new UnitSelectedState(
        _machine, _controller, clickedUnit));
    return;
}

A 선택 중 이동 가능한 B를 누르면 B를 기억하는 새 상태로 전환한다. return이 이번 클릭 처리를 끝내므로 A를 B의 칸으로 옮기는 요청은 발생하지 않는다. B 선택은 A의 이동 범위와도 별개다.

실제 발췌: UnitSelectedState.HandleBoardClick의 첫 분기, 긴 호출 줄바꿈 정리

Trace · Reselection

재선택은 이전 표시를 지운 뒤 다시 그린다

B를 클릭한 뒤CurrentController의 선택과 표시
기존 ExitSelected(A)선택 해제, A 표시 숨김
참조 교체Selected(B)아직 없음
새 EnterSelected(B)B 선택, B 범위 표시

변하는 것

앞으로 입력을 해석할 상태 객체와 선택 대상이 바뀐다. A와 B의 위치는 그대로이며 이동 이력은 추가되지 않는다.

A를 다시 눌러도

new로 새 선택 상태를 만들기 때문에 같은 전환 순서를 거친다. A를 가리키는 유닛 참조와 상태 객체의 동일성은 별개다.

실제 경로: UnitSelectedState.HandleBoardClick → InputStateMachine.ChangeState

Move Request

재선택이 아니면 기억한 유닛의 이동을 요청한다

_controller.ExecuteMove(_unit, cell);
_machine.ChangeState(new IdleState(_machine, _controller));

클릭에서 얻은 정보

빈 칸 (3,2)를 누르면 clickedUnit은 null이고 cell은 (3,2)다. 새로운 선택 대상은 없다.

상태가 더한 정보

Selected(A)는 _unit으로 A를 기억한다. 따라서 Controller에 ‘A를 (3,2)로 이동해 달라’고 요청할 수 있다.

같은 빈 칸을 대기 중에 누르면 요청이 없다. 선택 중이면 이 두 줄을 실행한다. 두 번째 줄은 이동 결과와 관계없이 Idle로 전환하는 현재 클릭 정책이다.

실제 발췌: UnitSelectedState.HandleBoardClick의 마지막 두 줄

Validate Before Execute

이동 가능성은 기존 담당자에게 묻는다

if (unit == null || _board == null ||
    !_board.CanMoveTo(unit, targetCell)) return false;
_history.Execute(new MoveUnitCommand(unit, _board, targetCell));
return true;

State가 결정

어느 유닛을 어느 셀로 보내고 싶은지 정한다. 이동 예산과 지형 계산을 상태마다 다시 작성하지 않는다.

BoardView가 검사

목적지가 다른 유닛에게 점유됐는지, 제자리인지, 지형 비용에 따른 범위에 포함되는지 확인한다. 통과하면 명령을 실행하고 기록한다.

실제 발췌: BattleController.ExecuteMove 본문, 조건 줄바꿈 정리. 검사: BoardView.CanMoveTo

이동 뒤 대기가 되어도 기록은 남는다

Selected(A)

Trace · Failed Move

갈 수 없는 빈 칸도 선택을 끝낸다

위치, 선택, 이력은 어떻게 될까?

실제 결과

A는 움직이지 않고 이동 이력도 늘지 않는다. ExecuteMove의 검사에서 false를 반환하기 때문이다.

선택은 해제된다

클릭 상태는 반환값을 검사하지 않고 다음 줄에서 Idle로 전환한다. Exit가 선택 표시를 숨기므로 다시 선택해야 한다.

이 구현의 클릭 정책은 재선택이 아닌 클릭 한 번이면 선택을 끝내는 것이다. ‘이동 실패’만 보고 선택이 유지될 것이라고 예상하면 실제 흐름과 달라진다.

답의 근거: UnitSelectedState.HandleBoardClick / BattleController.ExecuteMove

Occupied Cell

유닛 클릭도 선택 가능 여부로 나뉜다

A 선택 중 입력먼저 정하는 뜻그 뒤 결과
이동 가능한 B 클릭B를 새로 선택이동 요청 없이 Selected(B)
이동 불가인 다른 B 클릭A의 이동을 요청점유 검사로 실패, Idle
강 또는 범위 밖 빈 칸A의 이동을 요청범위 검사로 실패, Idle

선택 가능 여부는 클릭한 유닛의 CanMove로 정한다. 목적지 점유 여부는 BoardView가 다른 활성 유닛의 위치로 검사한다. 화면에 유닛이 있다는 사실만으로 재선택을 단정할 수 없다.

UnitSelectedState.HandleBoardClick / BoardView.IsOccupiedByOther·CanMoveTo

Different Entry Point

공개 이동 메서드는 실패 시 선택을 유지한다

if (!ExecuteMove(SelectedUnit, targetCell)) return false;
StateMachine.ChangeState(new IdleState(StateMachine, this));
return true;

실패하면 여기서 끝난다

Controller의 공개 메서드 TryMoveSelectedUnit은 이동 실패 시 즉시 반환한다. ChangeState까지 내려가지 않으므로 기존 선택이 유지된다.

앞의 마우스 예제는 Update → 상태 기계 → 선택 상태 경로다. 이름이 비슷해도 공개 메서드와 실패 후 동작은 다르다. 각 경로에서 ‘전환하는 줄에 도달하는가’를 확인해야 한다.

실제 발췌: BattleController.TryMoveSelectedUnit의 본문

Pattern Boundary

State와 Command는 다른 것을 기억한다

State의 기억

현재 입력 모드와 선택 대상을 기억한다. A에서 B로 재선택할 때 앞으로 클릭을 해석할 대상이 바뀐다.

Command의 기억

이동한 유닛, 보드, 출발 셀과 도착 셀을 기억한다. 상태가 Idle로 바뀌어도 실행한 이동 기록은 남는다.

// MoveUnitCommand의 Execute 본문
_unit.MoveTo(_board, _toCell);
// MoveUnitCommand의 Undo 본문
_unit.MoveTo(_board, _fromCell);

출발 셀은 명령을 만들 때 저장한다. History의 스택은 나중에 넣은 명령을 먼저 꺼내 Undo한다. 선택 시작과 해제는 이 이동 이력에 들어가지 않는다.

실제 본문 발췌: MoveUnitCommand.Execute / Undo. 기록: CommandHistory

실제 발췌: IdleState.HandleUndo. 좌표는 설명용

Undo While Selected

선택 중 Undo는 같은 대상을 다시 표시한다

public override void HandleUndo()
{
    _controller.UndoLast();
    _controller.ShowSelection(_unit);
}

위치 복구

A 이동 후 A를 다시 선택했다고 하자. Undo로 A가 (3,2)에서 (2,2)로 돌아와도 _unit은 같은 A 객체를 가리킨다.

범위 갱신

ShowSelection이 A의 새 현재 위치로 범위를 다시 구한다. ChangeState를 호출하지 않으므로 기존 선택 상태를 유지하고 Exit·Enter도 실행하지 않는다.

실제 발췌: UnitSelectedState.HandleUndo. 표시 갱신: BattleController.ShowSelection

Trace · Global History

B를 선택했어도 마지막 이동은 A의 것일 수 있다

순서A 위치B 위치상태와 이력
A를 (3,2)로 이동(3,2)(5,2)Idle / A 이동 1개
B 선택(3,2)(5,2)Selected(B) / A 이동 1개
Undo(2,2)(5,2)Selected(B) / 이력 없음

답: A가 돌아가고 B의 범위를 다시 표시한다. Controller의 이동 이력은 유닛별로 나뉘지 않는다. 마지막 명령 대상은 A이고, 현재 선택 상태가 기억한 대상은 B이므로 두 유닛의 역할이 다르다.

이력이 비어 있으면 UndoLast는 아무것도 되돌리지 않는다. 그래도 선택 상태의 다음 줄은 실행되므로 B의 범위는 다시 표시된다.

Spawner

유닛 생성은 게임 시작 준비의 책임이다

생성 입력

프리팹은 복제할 유닛 원본이다. UnitSpawner는 이 원본과 생성 셀 목록을 받아 Awake에서 SpawnAll을 호출한다.

생성 결과

셀마다 별도 유닛을 자신의 자식으로 만든다. 이름을 붙이고 BoardView로 셀 중심의 월드 위치를 구해 배치한다.

설명용 생성 셀만드는 객체

(5,2)Squad Unit 2

Spawner는 유닛을 준비하고, State는 준비된 유닛 중 누구의 입력을 처리할지 정한다. 생성 책임을 선택 상태에 넣지 않아도 두 기능은 연결된다.

현재 코드: UnitSpawner.Awake / SpawnAll. BoardView가 없으면 셀 좌표를 월드 좌표로 사용

Idempotence

반복 생성 요청은 기존 유닛을 반환한다

Unit[] existing = GetComponentsInChildren<Unit>(true);

    return existing;

검사 기준

자식에서 유닛을 먼저 찾는다. true는 비활성 객체도 검색한다는 뜻이다. 하나라도 있거나 프리팹이 없으면 새로 만들지 않는다.

Judgment

모드별 규칙이 함께 달라질 때 가치가 커진다

도입 가치

  • 같은 클릭의 뜻이 모드마다 달라진다.
  • Undo 이후 처리도 모드에 따라 다르다.
  • 모드의 시작과 정리를 함께 관리한다.

비용

  • 클래스와 연결할 참조가 늘어난다.
  • 각 상태로 들어가고 나올 조건을 설계한다.
  • 현재 구현은 재선택마다 객체를 새로 만든다.

두 모드의 규칙이 아주 짧고 안정적이면 작은 조건문이 읽기 쉬울 수 있다. State는 속도나 메모리의 자동 개선책이 아니다. 함께 바뀌는 규칙을 한곳에서 읽고 고치는 가치와 연결 비용을 비교한다.

Takeaway

현재 모드를 알면 같은 입력의 결과를 설명할 수 있다

  1. 입력의 뜻은 클릭 정보와 현재 모드가 함께 정한다.
  2. State는 그 모드의 대상과 행동을 묶고, 상태 기계는 현재 객체에 입력을 맡긴다.
  3. 전환은 Exit → Current 교체 → Enter 순서로 정리와 준비를 수행한다.
  4. 이동·Undo의 기록은 Command에 남고, 선택 화면은 현재 상태 규칙으로 처리한다.

확인과 답: A가 이동한 뒤 B를 선택하고 Undo하면? 마지막 이동 명령이 A를 되돌리고, Selected(B)는 B의 범위를 다시 표시한다. 현재 선택과 마지막 이동 기록을 따로 추적하면 예측할 수 있다.

State 패턴의 핵심은 현재 모드의 행동을 객체에 맡기는 것이다.
