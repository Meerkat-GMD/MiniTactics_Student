Mini Tactics · Lesson 04

미니 택틱스로 이해하는
State 패턴

같은 클릭이 어떤 때에는 선택이고 어떤 때에는 이동이다.
입력의 뜻을 정하는 규칙을 상태별 객체에 나누어 맡긴다.

Starting Point

패턴을 적용하기 전에는 입력 메서드가 직접 판단했다

if (clickedUnit != null && clickedUnit.CanMove)
{
    Select(clickedUnit);
    return;
}

if (SelectedUnit != null)
{
    TryMoveSelectedUnit(_board.WorldToCell(worldPosition));
}
public void OnUndoClicked()
{
    _history.UndoLast();
}

입력을 받는 메서드는 클릭을 처리하는 Update와 Undo 버튼을 처리하는 OnUndoClicked 두 개다. 두 메서드는 짧고 올바르게 동작한다. 이 자료가 살펴볼 대상은 기능이 아니라 입력의 뜻을 정하는 판단이 어디에 놓여 있는가이다.

실제 발췌: 이전 차시(3차시) BattleController.Update의 끝부분과 OnUndoClicked. Select는 유닛을 선택하는 메서드이고, TryMoveSelectedUnit은 선택된 유닛의 이동을 시도하는 메서드다.

Observation

같은 입력이 상황에 따라 다른 뜻을 가진다

입력유닛을 선택하기 전유닛을 선택한 중
아군 유닛 클릭그 유닛을 선택한다.선택을 그 유닛으로 바꾼다.
빈 셀 클릭아무 일도 하지 않는다.선택한 유닛을 그 셀로 이동시킨다.
Undo최근 이동을 취소한다.최근 이동을 취소한다. 앞 장의 코드는 선택하기 전과 똑같이 처리한다.

입력의 뜻은 “무엇을 눌렀는가”와 “지금 어떤 상황인가”가 함께 정한다. 앞 장의 코드는 지금의 상황을 따로 기억하지 않는다. 클릭이 올 때마다 SelectedUnit != null 같은 조건으로 상황을 매번 다시 알아낸다.

여기에 요구 두 가지가 더해진다고 하자. 첫째, 선택 중에 Undo를 누르면 선택을 유지한 채 선택한 유닛의 범위를 새로 표시한다. 둘째, 나중에 “공격 대상 선택”이라는 세 번째 상황이 추가된다. 첫째 요구는 OnUndoClicked에 선택 여부를 묻는 조건을 더 넣어야 하고, 둘째 요구는 두 입력 메서드 모두에 조건을 더 넣어야 한다.

공격 대상 선택은 상황이 늘어나는 경우를 설명하기 위한 예시이며 현재 구현에는 없다.

First Attempt

첫 시도는 상황을 enum에 기억하고 switch로 나누는 것이다

enum InputMode { Idle, UnitSelected }
InputMode _mode = InputMode.Idle;

void HandleClick(Unit clickedUnit, Vector2Int cell)
{
    switch (_mode)
    {
        case InputMode.Idle:         /* 선택 */ break;
        case InputMode.UnitSelected: /* 선택 변경 또는 이동 */ break;
    }
}

이 범위에서는 충분하다

지금의 상황을 _mode에 한 번 기억하므로, 다른 필드의 값으로 상황을 다시 알아낼 필요가 없다. 상황이 두 개이고 앞으로 늘지 않는다면 이 코드나 if 문이 가장 읽기 쉽다.

enum은 정해진 이름 몇 개 중 하나만 값으로 가질 수 있는 형식이다. 여기서는 “대기 중인가, 유닛을 선택한 중인가”를 이름으로 기억하는 데 사용한다.

설계 비교용 가상 코드. 현재 Teacher 구현이 아니다.

Limit 1

상황이 늘 때마다 모든 입력 메서드에 분기가 추가된다

{

    {
        case InputMode.Idle:         /* 취소 */ break;
        case InputMode.UnitSelected: /* 취소 후 범위 갱신 */ break;
        case InputMode.AttackTarget: /* 새로 추가 */ break;
    }
}

상황 하나를 추가하면 HandleClick의 switch에도 같은 case를 추가해야 한다. 한 상황의 규칙이 입력 메서드의 수만큼 여러 곳에 나뉘어 있고, 한 곳을 빠뜨려도 컴파일러가 알려 주지 않는다. enum과 switch는 조건문의 위치만 옮긴다.

설계 비교용 가상 코드. AttackTarget은 상황이 늘어나는 경우의 예시이며 현재 구현에는 없다.

Limit 2

상황에 들어가고 나올 때 할 일이 여러 곳에 흩어진다

// 선택 중에 다른 아군을 클릭했을 때
HideRange();                 // 이전 유닛의 범위 표시를 끈다.
ShowRange(clickedUnit);

// 선택 중에 셀을 클릭했을 때
TryMove(_selected, cell);
HideRange();                 // 여기에서도 끈다.
_mode = InputMode.Idle;

나오는 경로마다 같은 뒷정리를 적는다

선택 상황에서 나오는 경로는 선택 변경, 이동, 거부된 클릭으로 여러 개다. 경로마다 범위 표시를 끄는 줄을 직접 적어야 한다.

한 줄을 빠뜨리면 화면에 남는다

새 경로를 추가하면서 끄는 줄을 빠뜨리면 이전 유닛의 범위 표시가 화면에 남는다. _mode를 바꾸는 줄과 뒷정리를 하는 줄이 서로 묶여 있지 않기 때문이다.

설계 비교용 가상 코드. HideRange, ShowRange, TryMove는 설명을 위해 붙인 이름이다.

Transition Table

먼저 상태 전이표로 규칙 전체를 적는다

현재 상태입력하는 일다음 상태
대기아군 클릭없음선택
대기빈 셀 클릭없음대기
대기Undo최근 이동 취소대기
선택다른 아군 클릭없음선택(새 유닛)
선택셀 클릭이동 시도대기
선택Undo최근 이동 취소 후 범위 새로 표시선택

상태는 다음 입력을 어떻게 해석할지를 정하는 상황이고, 전이는 한 상태에서 다른 상태로 바뀌는 일이다. 표의 한 행은 “현재 상태에서 이 입력을 받으면 무엇을 하고 어느 상태가 되는가”를 뜻한다. 표에 적히지 않은 규칙이 하나 더 있다. 이동 범위 표시는 선택 상태에 들어갈 때 켜고 나올 때 끈다.

Responsibility Boundary

표의 현재 상태 열을 class로 만든다

대기 상태의 class

전이표에서 현재 상태가 대기인 세 행만 구현한다. 이동을 요청하는 코드는 들어 있지 않다.

선택 상태의 class

현재 상태가 선택인 세 행만 구현한다. 선택한 유닛을 직접 보관하고, 들어올 때 범위 표시를 켜고 나갈 때 끈다.

한 상태의 입력 규칙과 진입·이탈 시 할 일을
한 class에 모은다.

enum 방식은 코드를 입력별로 묶었기 때문에 한 상태의 규칙이 여러 메서드에 나뉘었다. 이 방식은 코드를 상태별로 묶는다. 입력을 받는 쪽은 현재 상태를 나타내는 객체 하나를 가리키고 있다가, 입력이 오면 그 객체에 넘기기만 한다. 상태가 바뀌면 가리키는 객체를 교체한다.

State Pattern

이 해법의 이름이 State 패턴이다

상태마다 달라지는 행동을 상태별 객체에 맡기고,
상태가 바뀌면 현재 객체를 교체한다.

Context
BattleController입력을 현재 상태에 전달하고, 상태가 요청하는 기능을 제공한다.
State
InputState상태가 받을 수 있는 입력과 진입·이탈 시점을 선언한다.
Concrete State
IdleState, UnitSelectedState현재 상태에서 입력이 무엇을 뜻하는지, 다음 상태가 무엇인지 결정한다.
전환 담당
InputStateMachine현재 상태를 보관하고 Exit, 교체, Enter의 순서를 지킨다.

State 패턴의 기본 구조는 Context, State, Concrete State 세 역할이다. 이 구현은 Context가 직접 맡을 수도 있는 “현재 상태의 보관과 전환”을 InputStateMachine이라는 별도의 class로 분리했다. 이 자료에서는 이 class를 상태 기계라고 부른다.

State · InputState

입력은 abstract로, 진입과 이탈은 virtual로 선언한다

public abstract class InputState
{
    public virtual void Enter()
    {
    }

    public virtual void Exit()
    {
    }

    public abstract void HandleBoardClick(Unit clickedUnit, Vector2Int cell);
    public abstract void HandleUndo();
}

abstract: 모든 상태가 답해야 하는 입력

본문이 없는 선언이다. 상속한 class가 override로 구현하지 않으면 컴파일 오류가 발생한다. 클릭과 Undo의 뜻은 상태마다 다르므로 구현을 빠뜨릴 수 없게 한다.

virtual: 필요한 상태만 재정의하는 시점

빈 본문이라는 기본 동작이 있다. 진입하거나 이탈할 때 할 일이 없는 상태는 그대로 두고, 할 일이 있는 상태만 재정의한다.

실제 발췌: InputState.cs (using과 namespace 생략)

Machine · Dispatch

상태 기계는 현재 상태에 입력을 그대로 넘긴다

public InputState Current { get; private set; }

public void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    Current?.HandleBoardClick(clickedUnit, cell);
}

public void HandleUndo()
{
    Current?.HandleUndo();
}

현재 상태는 하나다

Current는 지금 입력을 맡은 상태 객체를 가리킨다. private set이므로 이 class 밖에서는 값을 바꿀 수 없다.

어떤 상태가 있는지 모른다

이 코드에는 IdleState라는 이름도 if 문도 없다. Current가 가리키는 실제 객체의 override가 실행된다. 같은 호출이 객체에 따라 다른 동작을 하는 이 성질을 다형성이라고 한다.

실제 발췌: InputStateMachine.cs의 속성과 두 전달 메서드. ?.는 13장에서, ChangeState는 다음 장에서 다룬다.

Machine · Transition

전환은 Exit, 교체, Enter의 순서로 한 곳에서 실행한다

public void ChangeState(InputState next)
{
    // (next를 확인하는 검사 두 개 생략. 다음 장에서 다룬다.)
    Current?.Exit();
    Current = next;
    Current.Enter();
}

순서를 바꾸면

Current = next;를 가장 먼저 쓰면 그다음 줄의 Exit는 새 상태의 Exit가 된다. 이전 상태는 뒷정리를 하지 못한다.

Exit
→

next로 교체
→
새 상태의
Enter
→
다음 입력부터
새 상태가 처리

모든 전환은 이 메서드를 거친다. 전환 순서를 한 곳에 두면 상태들은 서로에게 뒷정리를 부탁하지 않아도 된다. 나가는 상태는 자신의 Exit만, 들어오는 상태는 자신의 Enter만 책임진다.

축약: InputStateMachine.ChangeState. 핵심인 마지막 세 줄은 실제 코드와 같고, 그 앞에 있는 검사 두 개는 주석으로 바꾸었다.

Machine · Guards

상태 기계는 잘못된 전환과 비어 있는 Current를 방어한다

if (next == null)
{
    throw new ArgumentNullException(nameof(next));
}

if (ReferenceEquals(Current, next))
{
    return;
}

ChangeState 앞부분의 두 검사

null을 현재 상태로 삼으면 입력을 맡을 객체가 없어지므로 예외로 즉시 알린다. ReferenceEquals는 두 변수가 같은 객체를 가리키는지 검사한다. 같은 객체로의 전환은 Exit와 Enter를 실행하지 않고 돌아간다.

?.가 호출을 건너뛰는 경우

?.는 왼쪽이 null이면 호출을 건너뛰는 연산자다. Current?.Exit()는 이전 상태가 없는 맨 처음 전환에서만 건너뛴다. 11장의 두 전달 줄은 첫 상태를 정하기 전에 입력이 온 경우에만 건너뛴다.

BattleController는 시작할 때 첫 상태를 IdleState로 정하고, 그 뒤에는 첫 검사가 null을 거부하므로 Current는 다시 null이 되지 않는다. ?.는 첫 상태가 정해지기 전에만 의미가 있다.

실제 발췌: InputStateMachine.ChangeState의 앞부분. ?.가 있는 줄은 같은 파일의 ChangeState와 두 전달 메서드에 있다.

Concrete State · IdleState

IdleState는 전이표의 대기 행만 구현한다

public override void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    if (clickedUnit != null && clickedUnit.CanMove)
        _machine.ChangeState(new UnitSelectedState(_machine, _controller, clickedUnit));
}

public override void HandleUndo() => _controller.UndoLast();
전이표의 행코드에서 일어나는 일
대기, 아군 클릭 → 선택if가 참이다. 클릭한 유닛을 보관하는 선택 상태를 새로 만들어 전환한다. CanMove는 이동할 수 있는 아군인지를 알려 주는 값이다.
대기, 빈 셀 클릭 → 대기if가 거짓이다. 아무 줄도 실행하지 않으므로 상태가 그대로다.
대기, Undo → 대기Context에 최근 이동의 취소만 요청한다. 전환은 없다.

실제 발췌: IdleState.cs의 두 메서드. _machine과 _controller는 생성자에서 받아 둔 상태 기계와 Context다. =>는 본문이 식 하나뿐인 메서드를 중괄호 없이 적는 표기다.

Concrete State · UnitSelectedState

입력의 뜻은 현재 상태의 종류가 정한다

private readonly Unit _unit;

public UnitSelectedState(InputStateMachine machine, BattleController controller, Unit unit)
{
    _machine = machine;
    _controller = controller;
    _unit = unit;
}

패턴 적용 전

Update가 SelectedUnit != null을 검사하여 클릭이 이동 요청인지를 정했다.

패턴 적용 후

Current가 UnitSelectedState이면 선택 중이다. 선택된 유닛은 그 상태 객체가 생성자에서 받아 _unit에 보관한다.

선택 상태는 유닛을 받아야만 만들 수 있으므로 이 class에는 선택한 유닛이 있는지 묻는 검사가 없다. 다른 유닛을 선택할 때에는 readonly인 _unit을 바꾸지 않고 새 상태 객체를 만든다. BattleController에 남아 있는 SelectedUnit 속성은 상태가 진입하고 이탈할 때 기록되는 값이며, 상태 class는 이 값을 읽지 않는다.

실제 발췌: UnitSelectedState.cs의 필드와 생성자 (_machine, _controller의 필드 선언 생략)

Enter and Exit

범위 표시의 수명을 Enter와 Exit에 맡긴다

public override void Enter() => _controller.ShowSelection(_unit);
public override void Exit() => _controller.ClearSelection();

두 메서드는 InputState의 빈 virtual 메서드를 재정의한다. =>는 본문이 식 하나뿐인 메서드를 중괄호 없이 적는 표기다.

Context가 제공하는 기능하는 일
ShowSelection선택된 유닛을 기록하고 이동 범위를 표시한다.
ClearSelection선택된 유닛의 기록을 지우고 범위 표시를 끈다.
ExecuteMove이동할 수 있는 셀이면 유닛을 이동시킨다.
UndoLast최근 이동을 취소한다.

상태는 언제 할지를 정하고, Context는 어떻게 할지를 안다. 범위는 선택 상태가 현재 상태인 동안에만 표시된다. Enter와 Exit는 상태 기계의 ChangeState가 호출하므로, 상태에 들어오고 나가는 어떤 경로에서도 빠지지 않는다.

실제 발췌: UnitSelectedState.Enter / Exit. 네 기능은 BattleController의 internal 메서드다. internal은 함께 컴파일되는 같은 어셈블리의 코드만 호출할 수 있다는 뜻이다. 그 내부 구현은 State 패턴의 범위가 아니므로 다루지 않는다.

Concrete State · UnitSelectedState

선택 상태의 클릭은 선택 변경을 먼저 검사한다

if (clickedUnit != null && clickedUnit.CanMove)
{
    _machine.ChangeState(new UnitSelectedState(_machine, _controller, clickedUnit));
    return;
}

_controller.ExecuteMove(_unit, cell);
_machine.ChangeState(new IdleState(_machine, _controller));

선택 → 선택(새 유닛)

이동할 수 있는 다른 아군을 클릭하면 그 유닛을 보관하는 새 선택 상태로 전환한다. return을 빠뜨리면 선택을 바꾼 직후에 이동을 시도하고 대기로 돌아간다.

선택 → 대기

그 밖의 클릭은 이동 시도다. ExecuteMove가 이동을 거부해도 다음 줄은 실행되므로 대기로 돌아간다. 범위 밖을 클릭하는 것이 선택 취소의 역할을 한다.

실제 발췌: UnitSelectedState.HandleBoardClick의 본문 전체

Concrete State · UnitSelectedState

선택 상태의 Undo는 전환 없이 범위만 새로 표시한다

public override void HandleUndo()
{
    _controller.UndoLast();
    _controller.ShowSelection(_unit);
}

대기 상태의 Undo와 비교

IdleState의 HandleUndo는 UndoLast 한 줄뿐이다. 같은 Undo 입력이 현재 상태에 따라 다른 본문을 실행한다.

ChangeState를 호출하지 않으므로 Exit와 Enter는 실행되지 않고 선택 상태가 유지된다. 취소로 유닛의 위치가 바뀌었을 수 있으므로 같은 유닛의 범위를 다시 표시한다.

3장의 첫째 요구가 이 상태의 메서드 하나에서 해결되었다. 다른 상태의 코드와 Context의 입력 메서드는 고치지 않았다.

실제 발췌: UnitSelectedState.HandleUndo

Context · BattleController

Context의 입력 메서드에는 분기가 남지 않는다

// Update의 마지막 줄: 클릭한 유닛과 셀을 구한 뒤에 실행한다.
StateMachine.HandleBoardClick(clickedUnit, _board.WorldToCell(worldPosition));

public void OnUndoClicked() => StateMachine.HandleUndo();

남은 일

Update는 클릭을 “유닛과 셀”이라는 두 값으로 바꾸는 일만 한다. 빈 셀을 클릭하면 clickedUnit은 null이다. 그 클릭이 무슨 뜻인지는 현재 상태가 결정한다.

사라진 것

2장에서 본 두 if 문이 Update에서 사라졌다. 두 입력 메서드에는 SelectedUnit != null처럼 선택 여부를 물어 입력의 뜻을 가르는 조건문이 하나도 없다.

실제 발췌: BattleController.Update의 마지막 줄과 OnUndoClicked. 첫 줄의 주석은 설명을 위해 추가했다. StateMachine은 BattleController가 가진 상태 기계를 돌려주는 속성이다.

Question

범위 표시를 끄는 코드는 Exit 한 곳뿐이다

선택 변경, 이동, 거부된 클릭에서
범위 표시가 모두 꺼지는 이유는 무엇인가?

경우선택 상태가 실행하는 줄그 뒤에 상태 기계가 하는 일
다른 아군 B 클릭ChangeState(new UnitSelectedState(…, B))Selected(A)의 Exit가 표시를 끄고, Selected(B)의 Enter가 B의 범위를 표시한다.
이동 성공ExecuteMove 후 ChangeState(new IdleState(…))Selected(A)의 Exit가 표시를 끈다.
거부된 클릭위와 같은 두 줄Selected(A)의 Exit가 표시를 끈다.

답: 세 경우 모두 선택 상태에서 나오는 일이고, 상태에서 나오는 길은 ChangeState 하나뿐이다. ChangeState는 항상 이전 상태의 Exit를 먼저 호출한다. 6장의 가상 코드처럼 경로마다 끄는 줄을 적을 필요가 없다.

Extension

새 상태를 추가할 때 Context의 입력 메서드는 고치지 않는다

구분대상이유
새로 만든다새 상태의 class 파일 하나 (예: 공격 대상 선택 상태)그 상태의 클릭 규칙, Undo 규칙, 진입·이탈 시 할 일을 한 class에 작성한다.
고친다그 상태로 전환을 시작하는 기존 상태어떤 입력을 받았을 때 새 상태로 ChangeState를 호출하는 줄을 넣는다.
필요할 때만 추가한다Context의 기능 메서드새 상태가 요청할 기능이 Context에 아직 없는 경우에만 추가한다.
고치지 않는다Update, OnUndoClicked, InputStateMachine, InputState입력의 종류와 전달하는 방식이 그대로이기 때문이다.

5장의 enum 방식에서는 상태 하나를 추가하면 모든 입력 메서드의 switch를 고쳐야 했다. State 패턴에서는 새 규칙이 새 class 안에 모인다.

반대의 경우도 알아 둔다. 새로운 입력의 종류를 추가하면 InputState에 abstract 메서드가 하나 늘고, 모든 상태 class가 그것을 구현해야 한다. State 패턴은 상태의 추가에 유리한 구조다.

공격 대상 선택 상태는 확장을 설명하기 위한 예시이며 현재 구현에는 없다.

Cost and Criteria

State에는 대가가 있고, 이득이 되는 조건이 있다

대가

  • class의 수가 늘어난다. 이 구현은 상태 두 개를 위해 InputState, InputStateMachine, IdleState, UnitSelectedState 네 개를 만들었다.
  • 한 입력의 처리 전체를 보려면 여러 파일을 열어야 한다.
  • 상태가 두 개이고 늘지 않는다면 if 문이 더 단순하다.

이득이 되는 조건

  • 상태마다 같은 입력의 뜻이 달라진다.
  • 상태에 들어가고 나올 때 해야 할 일이 있다.
  • 상태가 앞으로 늘어날 예정이다.

State 패턴은 실행 속도나 메모리를 개선하는 기법이 아니다. 오른쪽의 조건이 성립할 때 “한 상태의 규칙을 한 곳에서 읽고 고칠 수 있다”는 이득이 class 수의 증가라는 대가보다 커진다. 조건이 성립하지 않는다면 2장과 같은 if 문을 그대로 두는 것이 올바른 판단이다.

Check and Takeaway

이해 확인 질문과 답

질문답
1. 선택 상태의 코드는 SelectedUnit != null을 검사하지 않는다. 이동시킬 유닛은 어디에서 얻는가?UnitSelectedState 객체가 생성자에서 받아 _unit에 보관한 유닛이다. 선택 중인지는 현재 상태의 종류가 알려 주므로 검사가 필요 없다.
2. ChangeState에서 Current = next;를 Exit보다 먼저 쓰면 이동 후에 무엇이 달라지는가?새 상태인 IdleState의 빈 Exit가 호출되고 선택 상태의 Exit는 호출되지 않는다. 범위 표시가 화면에 남는다.
3. 선택 상태에서 Undo를 누르면 Exit와 Enter가 호출되는가?호출되지 않는다. HandleUndo는 ChangeState를 호출하지 않고 ShowSelection을 직접 다시 요청한다.
4. 상태를 하나 추가할 때 고치지 않는 곳은 어디인가?Context의 Update와 OnUndoClicked, 상태 기계, InputState다.

State 패턴의 핵심은 현재 상태의 행동을
그 상태의 객체에 맡기는 것이다.
