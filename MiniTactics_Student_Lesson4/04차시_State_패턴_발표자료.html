미니 택틱스로 이해하는
State 패턴

같은 클릭도 현재 모드에 따라 뜻이 달라진다면
그 판단과 행동은 어디에 모아 둘까?

현재 상태에게 입력의 해석을 맡긴다.

A Small Start

입력 하나에 뜻이 하나라면 단순하다

작은 출발

클릭한 대상을 확인하고 한 가지 행동을 호출한다. 규칙이 짧고 일정하면 한 메서드로도 충분하다.

달라지는 맥락

선택 전에는 유닛을 고르는 클릭이다. 선택 중에는 다른 유닛을 고르거나 이동을 시도하는 클릭이다.

여기서 상태는 객체가 가진 모든 값의 목록이 아니라, 입력을 해석하는 현재 모드를 뜻한다.

Same Input, Different Meaning

좌표보다 먼저 현재 모드를 묻는다

현재 모드입력해석
Idle · 선택 없음선택 가능한 유닛 클릭그 유닛의 선택 상태로 전환
UnitSelected · 선택 중다른 선택 가능 유닛 클릭새 유닛의 선택 상태로 전환
UnitSelected · 선택 중선택 가능 유닛이 아닌 곳 클릭현재 유닛의 이동을 시도

입력의 모양이 같아도 실행할 규칙은 현재 모드가 결정한다. 이동 가능 여부의 세부 계산은 이 패턴의 책임이 아니다.

A Limited Attempt

두 모드의 조건문도 출발점이 된다

설계 비교용 가상 코드 · 현재 Teacher 구현 아님 · 두 모드만 가정, 입력 감지와 선택 검증 생략

if (selected == null)
{
    if (clicked != null) selected = clicked;
}
else
{
    if (clicked != null) selected = clicked;
    else TryMove(selected, cell);
}

짧고 안정된 두 갈래라면 읽기 쉽다. 이 비교 예시는 실제 이동·표시·검증의 구현을 제시하는 코드가 아니다.

Scaling Limit

문제는 조건문 수보다 흩어진 규칙이다

한곳에 섞이기 쉬운 것

클릭 해석, 선택 표시, 해제, Undo 뒤 갱신을 각각 수정할 때마다 현재 모드를 다시 검사한다.

원하는 변경 단위

“선택 중 입력”의 행동을 한곳에서 읽고 바꾸고 싶다. 상태별 행동과 전환 경계를 함께 찾는다.

조건문은 틀린 문법이 아니다. 같은 모드의 규칙이 여러 입력 처리에 반복되고 서로 어긋날 때 분리의 가치가 커진다.

모드별 행동과 공통 서비스를 나눈다

각 모드의 입력 해석

맥락은 상태가 쓰는 공통 기능을 제공한다. 전환기는 현재 상태를 보관한다. 이 구현에서는 둘을 별도 클래스로 나누었다.

State Pattern

객체를 바꾸어 입력의 해석을 바꾼다

상태마다 같은 계약으로 행동을 구현하고,
현재 상태에 처리를 위임한다.

호출하는 쪽

클릭과 Undo를 같은 입구로 전달한다. 모든 모드의 분기를 직접 늘어놓지 않는다.

현재 상태

그 입력의 의미를 정한다. 필요하면 맥락에 전환을 요청한다.

State는 입력 해석을 나누는 설계다. 이동 계산이나 이력 저장 알고리즘까지 대신하지 않는다.

Input Contract

모든 구체 상태는 입력을 해석한다

public abstract void HandleBoardClick(Unit clickedUnit, Vector2Int cell);
public abstract void HandleUndo();

abstract인 두 메서드는 각 구체 상태가 구현한다. 이 상태에서 입력을 처리하지 않기로 결정하는 것도 상태의 정책이다.

Optional Lifecycle Hooks

아무 준비가 없으면 훅을 생략할 수 있다

public virtual void Enter()
{
}

public virtual void Exit()
{
}

Enter · 진입 준비

상태가 활성화될 때 필요한 표시나 준비를 한다.

Exit · 이탈 정리

다음 상태로 넘기기 전에 이전 표시나 자원을 정리한다.

virtual의 빈 기본 구현은 의도된 선택적 훅이다. IdleState에 빈 override를 반드시 채워야 하는 미완성 지점이 아니다.

Lifecycle Order

이전 상태를 정리한 뒤 새 상태를 시작한다

Current = next;
Current.Enter();

Transition Guards

같은 참조와 새 인스턴스는 다르다

if (ReferenceEquals(Current, next))
{
    return;
}

현재 실제 코드 발췌 · Teacher4 2f82ead · InputStateMachine.cs L17–20 · ChangeState의 참조 동일성 검사; 앞의 null 검사·뒤의 전환 생략

전달한 next결과
현재 객체와 같은 참조그대로 반환 · Exit/Enter 없음
같은 타입의 새 객체서로 다른 참조 · 정상 전환
null앞의 검사에서 ArgumentNullException

타입 이름이 같다는 이유로 전환을 생략하지 않는다. 이 방어 조건은 같은 객체를 다시 전달할 때만 적용된다.

Delegation

전환기는 현재 객체에 입력을 전달한다

public void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    Current?.HandleBoardClick(clickedUnit, cell);
}

public void HandleUndo()
{
    Current?.HandleUndo();
}

현재 실제 코드 발췌 · Teacher4 2f82ead · InputStateMachine.cs L27–35 · 두 입력 전달 메서드 전체; Current·ChangeState 생략

?.는 아직 Current가 없으면 호출하지 않는다는 뜻이다. 전환기는 유닛 선택이나 이동의 성공 조건을 직접 해석하지 않는다.

Controller Owns Construction

상태를 만드는 곳은 Controller다

public void Select(Unit unit)
{
    _stateMachine.ChangeState(CanSelect(unit)
        ? new UnitSelectedState(this, unit)
        : new IdleState(this));
}

현재 실제 코드 발췌 · Teacher4 2f82ead · BattleController.cs L28–33 · Select 메서드 전체; CanSelect 등 다른 멤버 생략

CanSelect가 참이면 선택 상태, 거짓이면 Idle을 만든다. 상태 객체는 이 Select를 호출해 전환을 요청하며 다른 구체 상태를 직접 만들지 않는다.

First State

초기 상태도 같은 전환 경로를 쓴다

_stateMachine = new InputStateMachine();
_stateMachine.ChangeState(new IdleState(this));

Controller의 선택

전환기를 만들고 최초 Idle 객체를 전달한다.

Machine의 실행

이전 Current는 null이므로 Exit 없음 → 참조 교체 → Idle.Enter 기본 구현.

구체 상태의 생성 책임과 Exit→교체→Enter 순서를 수행하는 책임을 구별한다.

Idle Interprets Input

Idle은 선택 가능한 유닛만 고른다

public override void HandleBoardClick(Unit clickedUnit, Vector2Int cell)
{
    if (_controller.CanSelect(clickedUnit))
    {
        _controller.Select(clickedUnit);
    }
}

Idle에서 선택 불가능한 클릭은 아무 전환도 요청하지 않는다. 같은 클릭 입구라도 선택 중 상태에서는 다른 해석을 할 수 있다.

Display Setup Is Not a Transition

Enter는 표시를 준비하고 전환을 반복하지 않는다

public override void Enter() => _controller.ShowSelection(_unit);
public override void Exit() => _controller.ClearSelection();

현재 실제 코드 발췌 · Teacher4 2f82ead · UnitSelectedState.cs L16–17 · 진입·이탈 훅 두 줄; 생성자·입력 처리 생략

Enter → ShowSelection

현재 유닛과 범위를 표시한다. 새 상태를 요청하지 않는다.

Exit → ClearSelection

이전 선택과 표시를 지운다. 다음 Enter가 새 표시를 준비한다.

Enter에서 Select를 다시 호출하면 새 객체의 Enter가 또 전환을 요청할 수 있다. 현재 코드는 표시 준비와 전환 요청의 경계를 지킨다.

Context Service

표시 준비는 공통 작업을 호출한다

internal void ShowSelection(Unit unit)
{
    SelectedUnit = unit;
    _highlighter.Show(_board.CalculateMovementRange(unit), unit);
}

SelectedUnit을 설정하고 현재 범위를 보여 준다. 이 메서드에는 ChangeState나 Select 호출이 없다. 범위 계산 자체의 구현은 State 설명에서 생략한다.

선택 상태는 대상 교체와 이동을 구분한다

유닛을 고르면 Select로 교체를 요청한다. 이동 성공 때만 Select(null)로 Idle을 요청한다. 실패하면 현재 상태와 표시가 유지된다.

Trace the Transition

A 선택 중 B를 고르면 어떤 순서일까?

순서실행과 관찰
1 · 입력 해석A의 UnitSelectedState가 B를 보고 Select(B) 요청
2 · 생성Controller가 B의 새 UnitSelectedState 생성
3 · 이탈A 상태의 Exit → ClearSelection
4 · 교체와 진입Current를 B 상태로 교체 → Enter → ShowSelection(B)

답: A 표시 정리 뒤 B 표시 준비다. 새 상태 생성 시점은 Exit보다 앞이며, Enter 실행 시점은 Current 교체 뒤다.

Undo in a Mode

같은 Undo도 현재 모드가 후처리를 정한다

public override void HandleUndo()
{
    if (_controller.UndoLast())
    {
        _controller.ShowSelection(_unit);
    }
}

선택 중

이력 되돌리기가 성공한 경우에만 현재 선택의 범위를 다시 표시한다. 상태 객체는 바꾸지 않는다.

Idle

UndoLast를 호출한다. 선택 표시를 갱신하는 정책은 없다.

Undo 저장·실행의 구현은 공통 이력에 남는다. State는 이 모드에서 필요한 후처리만 묶는다.

Trade-offs

두 상태만으로 패턴이 필수는 아니다

분리가 유용한 때

모드마다 여러 입력의 뜻이 달라지고, 같은 모드의 규칙을 함께 수정·검증해야 한다.

지불하는 비용

클래스와 참조가 늘고 호출 경로를 더 따라간다. Controller 서비스와 전환 권한의 경계를 관리해야 한다.

두 모드의 짧고 안정된 조건문이라면 그대로 두는 편이 더 명확할 수 있다. 현재 Select는 요청마다 새 상태 객체를 만든다. 할당 비용의 크기는 별도 측정 대상이다.

Visible Review Answers

상태의 경계로 결과를 설명한다

질문답과 이유
상태가 다른 상태를 new 하는가?아니다. Select에 요청하고 Controller가 생성한다
Enter가 Select를 호출하는가?아니다. ShowSelection으로 표시만 준비한다
같은 타입이면 전환이 생략되는가?아니다. 같은 참조일 때만 생략한다
이동 실패 뒤 Current는?선택 상태 유지 · 전환 요청이 없다
훅은 모두 override해야 하는가?아니다. Enter/Exit는 선택적 기본 구현이 있다
