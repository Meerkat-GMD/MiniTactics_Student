CHAPTER 01

객체의 생존과 한 번의 사용

학습 목표: 생성·파괴의 장점과 반복 사용에서 생기는 비용을 구분한다.

객체가 존재하는 시간과 사용하는 시간

객체를 만들고 잠시 사용한 뒤 파괴하는 방식은 소유 관계가 간단하다. 사용이 끝나면 객체도 사라지므로 다음 사용에 이전 값이 남아 있지 않는다. 드물게 쓰는 객체라면 이 방식이 가장 이해하기 쉬울 수 있다.

같은 종류의 객체를 짧은 시간 동안 반복해서 사용한다면 매번 만들고 버리는 비용을 검토할 수 있다. Object Pool은 사용을 끝낸 객체를 파괴하지 않고 보관한다. 다음 요청이 오면 보관한 객체를 다시 준다. 객체가 존재하는 시간 안에 여러 번의 사용 기간이 들어가는 구조다.

대여와 반납

대여는 풀에서 객체를 꺼내 사용 권한을 얻는 일이다. 반납은 사용을 끝내고 풀에 돌려주는 일이다. 반납한 객체는 다른 요청이 다시 빌릴 수 있으므로 이전 사용자는 그 객체를 계속 조작하지 않아야 한다. 참조 변수가 남아 있다는 사실과 계속 사용할 권한이 있다는 사실을 구분한다.

풀의 핵심 책임풀은 사용하지 않는 객체를 보관하고 요청에 맞게 내준다. 사용자는 대여한 객체를 사용한 뒤 정해진 경로로 반납한다. 반복 사용에 필요한 초기화와 사용 종료의 책임을 함께 정한다.

한 객체를 다시 사용하는 과정

풀이 비어 있을 때 A를 요청하면 새 객체가 필요할 수 있다. A를 반납한 다음 B를 요청하면 같은 객체를 다시 줄 수 있다. A와 B는 사용 기간의 이름이지 서로 다른 객체라는 뜻이 아니다. 같은 객체라는 사실 때문에 생성 횟수는 줄지만 이전 사용의 상태가 남을 수 있다.

풀을 처음부터 여러 객체로 채우는 방법도 있고 요청이 들어올 때 필요한 만큼 늘리는 방법도 있다. 어느 방식이든 핵심은 사용을 끝낸 객체를 보관해 다시 쓰는 것이다. 시작할 때 모든 객체를 만드는 것만이 풀링은 아니다.

GameObject marker = Instantiate(markerPrefab);
marker.transform.position = position;

// 사용이 끝난다.
Destroy(marker);

설계 비교용 가상 코드 · 필요할 때 만들고 사용이 끝나면 파괴하는 첫 시도다.

이 비교에서 Use가 세 번 호출되는 것은 두 방식 모두 같다. Object Pool이 바꾸는 부분은 사용을 위한 객체 준비와 사용 후 정리다. 생성 횟수를 줄였다는 사실은 그 자체로 전체 작업이 빨라졌다는 증거가 아니다. 그대로 남은 처리 비용도 함께 확인한다.

CHAPTER 02

보관, 대여, 소유의 역할

학습 목표: 풀의 자료구조와 사용자의 진행 목록이 맡은 책임을 구분한다.

풀은 같은 종류의 객체를 관리한다

TransientPool<T>의 T는 빌려 줄 컴포넌트 형식이다. 숫자 컴포넌트의 풀과 프레임 효과 컴포넌트의 풀은 같은 일반 코드를 사용하지만 서로 다른 객체 집합을 관리한다. 표시 내용이 다른 객체를 하나의 이름 사전으로 뒤섞지 않는다.

private readonly Stack<T> _available = new Stack<T>();
private readonly Dictionary<T, long> _active = new Dictionary<T, long>();
private readonly List<T> _owned = new List<T>();
private long _sequence;
private bool _disposed;

세 집합을 구분한다

_available은 지금 빌려 줄 수 있는 객체를 보관하는 Stack이다. _active는 사용 중인 객체와 그 대여 번호를 연결한다. _owned는 이 풀이 실제로 만든 객체의 목록으로, 풀을 폐기할 때 모두 정리하는 근거다. 같은 정보를 무조건 세 번 복사한 것이 아니라 질문이 다르다.

물어보는 질문조회할 상태
다음에 빌려 줄 객체가 있는가?_available
이 반납이 지금 유효한 대여인가?_active와 대여 번호
풀을 없앨 때 무엇을 파괴할 것인가?_owned

사용자는 빌린 객체의 작업을 진행한다

TransientPresenter는 현재 표시 중인 대여의 목록을 보관한다. 이 목록으로 시간을 진행시키고 사용이 끝난 항목을 반납한다. 표시 목록은 반납의 권한을 판정하지 않는다. 대여가 유효한지 확인하는 권한은 풀에 있다.

풀은 개별 객체의 글자나 그림을 어떻게 지울지 직접 알지 않는다. 생성자로 전달받은 reset 동작을 호출한다. 재사용하는 일반 규칙과 표시 종류별 초기화를 나누는 경계다.

CHAPTER 03

대여와 반납의 실제 코드

학습 목표: 객체 재사용, 새 대여 발급, 유효 반납을 순서대로 읽는다.

Rent는 보관 객체부터 찾는다

public PoolLease<T> Rent()
{
    ThrowIfDisposed();
    T value = null;
    while (_available.Count > 0 && value == null) value = _available.Pop();
    if (value == null) value = Create();
    Reset(value);
    long sequence = ++_sequence;
    _active.Add(value, sequence);
    value.gameObject.SetActive(true);
    return new PoolLease<T>(value, this, sequence);
}

실제 코드 · TransientPool.cs 43–54행 · 해당 메서드 전체다.

먼저 이미 폐기한 풀인지 확인한다. 보관 목록에 객체가 있으면 꺼내고, Unity에서 이미 파괴되어 사용할 수 없는 객체는 건너뛴다. 살아 있는 객체를 얻지 못했을 때만 Create를 호출한다.

Reset은 다음 사용을 시작할 상태를 준비한다. 이어 _sequence를 증가시켜 이번 대여 번호를 만들고 _active에 기록한다. 객체를 활성화한 뒤 Value·Owner·Sequence를 묶은 PoolLease를 반환한다. 같은 객체를 다시 사용해도 번호는 새로 발급된다.

Return은 유효한 대여만 끝낸다

public bool Return(PoolLease<T> lease)
{
    if (_disposed || lease.Owner != this || ReferenceEquals(lease.Value, null)) return false;
    if (!_active.TryGetValue(lease.Value, out long sequence) || sequence != lease.Sequence) return false;
    _active.Remove(lease.Value);
    if (lease.Value == null) return false;
    Reset(lease.Value);
    lease.Value.gameObject.SetActive(false);
    _available.Push(lease.Value);
    return true;
}

실제 코드 · TransientPool.cs 56–66행 · 해당 메서드 전체다.

풀의 폐기 여부, 소유자, 기본 참조 여부를 먼저 본다. 이어 _active에 등록한 번호와 반납할 대여 번호가 같아야 한다. 조건에 맞지 않으면 어떤 객체도 초기화하거나 다시 보관하지 않고 false를 반환한다.

정상 대여라면 현재 등록을 지운다. 객체가 외부에서 이미 파괴되었다면 보관 목록에 다시 넣지 않는다. 살아 있는 객체는 Reset으로 상태를 지우고 비활성화한 뒤 _available에 한 번만 넣는다. 반납 결과가 true라는 것은 그 대여의 사용을 정상적으로 끝냈다는 뜻이다.

반납 이후의 책임참조 변수가 남았어도 반납한 객체를 계속 조작하면 안 된다. 다른 요청이 그 객체를 다시 빌렸을 수 있다. 대여 번호 검사는 잘못된 반납을 막지만, 남은 Value 참조로 직접 필드를 바꾸는 일까지 자동으로 막지는 못한다.

CHAPTER 04

두 객체를 세 번 사용하는 추적

학습 목표: 객체 수와 대여 횟수를 따로 세고 오래된 기록의 결과를 예측한다.

빈 풀에서 시작한다

보관 객체가 없고 아무 객체도 파괴되지 않는다고 가정한다. 첫 대여와 두 번째 대여는 반납 없이 연속해서 요청한다. 세 번째 대여 앞에는 첫 객체를 반납한다.

작업사용 중 객체풀에 남은 객체누적 생성 수
빈 풀로 시작없음없음0
첫 번째 대여객체 1없음1
두 번째 대여객체 1, 객체 2없음2
객체 1 반납객체 2객체 12
세 번째 대여객체 2, 객체 1없음2

총 대여는 세 번이지만 만든 객체는 두 개다. 세 번째 요청은 객체 1을 다시 사용한다. 새 대여를 받는 쪽은 Reset 뒤의 상태를 받고 자신의 표시 값을 설정한다.

같은 객체여도 대여 기록은 바뀐다

작업실제 객체현재 유효한 대여결과
A를 빌림객체 1소유자 P / 번호 1A 사용 시작
A를 반납객체 1없음비활성 보관

여기서는 다른 대여가 끼어들지 않는 한 풀 P의 순서를 1, 2로 단순화했다. 실제 _sequence는 풀 전체의 Rent마다 증가한다. 객체별로 매번 1부터 시작하지 않는다. 중요한 것은 이전 대여와 새 대여의 번호가 같지 않다는 사실이다.

손으로 검산하는 질문

두 객체를 사용 중인데 객체 1을 두 번 반납하면 보관 목록에 두 번 들어가는가? 아니다. 첫 정상 반납에서 _active 기록이 사라진다. 두 번째 요청에는 일치하는 현재 대여가 없으므로 false를 반환한다. 따라서 다음 두 요청이 같은 객체를 동시에 받는 중복 보관을 막는다.

다른 풀 Q가 P의 대여를 반납하려 해도 Owner가 다르므로 거절한다. 값이 비슷하거나 같은 형식이라는 사실은 반납 권한이 아니다.

CHAPTER 05

이전 사용의 상태를 초기화하는 책임

학습 목표: 비활성화와 초기화를 구별하고 일반 상태와 표시 상태를 나눈다.

SetActive(false)는 필드 값을 지우지 않는다

숫자를 반쯤 투명하게 표시하다 반납했다면 색의 alpha나 경과 시간이 남을 수 있다. 다음 사용에서 이를 지우지 않으면 새 표시가 처음부터 희미하거나 바로 끝난다. 위치·크기·회전처럼 외부 코드가 바꾼 상태도 함께 점검한다.

풀의 공통 초기화

private void Reset(T value)
{
    value.transform.SetParent(_root, false);
    value.transform.localPosition = Vector3.zero;
    value.transform.localRotation = Quaternion.identity;
    value.transform.localScale = Vector3.one;

제공 helper는 글자를 비우고 경과 시간·색을 새 사용의 출발 상태로 만든다. FrameEffect 쪽은 프레임 목록·시간·현재 그림·색·뒤집기·정렬값을 정리한다. 이전 대상 참조를 계속 보관하면 불필요한 객체 수명이 늘거나 새 사용자가 예전 데이터를 읽을 수 있다.

작업의 진행 주체도 한 곳이어야 한다

풀에서 빌린 객체는 스스로 파괴하는 자동 수명 처리를 끄고 사용자가 시간을 진행시킨다. 같은 객체를 자동 Update와 사용자의 목록에서 동시에 진행시키면 두 배로 빨리 끝날 수 있다. 초기화는 자동 수명을 임의로 다시 켜지 않고, 사용자가 대여한 뒤 수명 모드를 명시한다.

초기화 목록의 기준모든 필드를 무조건 0으로 만드는 것이 목표는 아니다. 다음 사용에서 무엇을 보장할지 정하고 공통 Reset, 종류별 ResetVisual, 새 사용의 Show가 각각 책임지는 값을 확인한다.

CHAPTER 06

잘못된 반납과 소유자의 수명

학습 목표: 중복·오래된·다른 소유자의 반납을 구별하고 전체 정리 경계를 읽는다.

잘못된 반납은 새 사용에 영향을 주지 않는다

중복 반납은 이미 끝난 같은 대여를 다시 반납하는 요청이다. 오래된 반납은 그 객체가 새로운 번호로 다시 대여된 뒤 예전 기록으로 반납하는 요청이다. 다른 소유자의 반납은 이 풀에서 발급하지 않은 기록으로 요청하는 경우다. 세 경우 모두 현재 사용 권한을 확인해야 한다.

이 구현은 Owner와 현재 _active 번호를 검사한다. 기본값 대여에는 소유자가 없으므로 정상 반납으로 처리하지 않는다. Unity 객체가 외부에서 파괴된 경우에는 현재 대여 기록을 정리하되 파괴된 참조를 보관 목록에 다시 넣지 않는다. 이 정책은 재사용 가능한 살아 있는 객체만 꺼내기 위한 것이다.

사용자의 진행 목록을 먼저 비운다

숫자와 효과의 진행 목록을 지운 뒤 풀의 모든 대여를 반납한다. 목록만 남으면 다음 Update가 이미 반납했거나 다시 빌린 객체의 시간을 잘못 진행시킬 수 있다. 이전 사용의 예약된 작업과 반납 상태를 함께 끝내는 이유다.

풀 자체를 끝낼 때

public void Dispose()
{
    if (_disposed) return;
    ReturnAll();
    _disposed = true;
    foreach (T value in _owned)
        if (value != null) UnityEngine.Object.Destroy(value.gameObject);
    _owned.Clear();
    _available.Clear();
}

씬마다 소유자가 다르면 다음 씬은 새 풀과 새 객체 집합을 만든다. 이전 풀의 대여를 새 풀에서 사용할 권한은 없다. 사용 중 잠시 모두 반납하는 것과 씬 소유자가 사라지며 객체를 파괴하는 것을 구분한다. 이 범위를 전역 객체로 늘리려면 수명과 참조 정책부터 다시 설계해야 한다.

미리 준비할 크기와 기존 재사용

학습 목표: 전체 요청 수보다 최대 동시 사용량을 보고 보관 비용을 계산한다.

Prewarm은 생성 시점을 앞당긴다

public void Prewarm(int count)
{
    ThrowIfDisposed();
    T[] available = _available.ToArray();
    _available.Clear();
    for (int index = available.Length - 1; index >= 0; index--)
        if (available[index] != null) _available.Push(available[index]);
    while (_available.Count < count)
    {
        T value = Create();
        Reset(value);
        value.gameObject.SetActive(false);
        _available.Push(value);
    }
}

현재 보관 객체 수가 목표 count보다 적으면 필요한 만큼 미리 만든다. 각 객체는 초기화·비활성화된 상태로 쌓인다. 생성 비용이 사라진 것이 아니라 준비 구간으로 옮겨 간 것이다. 만들어 놓은 객체는 사용하지 않는 동안에도 메모리를 차지한다.

모든 풀에 같은 자료구조가 필요한 것은 아니다. 한 사용자에게 전체 표시 목록을 다시 주는 구조와 여러 개별 사용이 서로 다른 시간에 끝나는 구조는 추적할 상태가 다르다. 실제 사용 방식에 맞춰 가장 작은 계약을 정한다.

CHAPTER 08

공정한 측정과 적용 판단

학습 목표: 같은 작업의 관측값을 비교하고 생성 감소를 성능 전체로 과장하지 않는다.

재사용하기 전에 지워야 하는 것

객체를 비활성화해도 필드 값이 자동으로 모두 초기화되지는 않는다. 이전 위치, 색, 재생 시간, 연결한 대상 같은 값은 남을 수 있다. 다음 사용이 올바르게 시작하려면 어떤 값을 매번 다시 설정할지 정해야 한다. 처음 한 번 실행하는 초기화와 대여할 때마다 실행하는 초기화를 구분한다.

남아 있는 참조도 확인한다. 사용이 끝난 대상의 참조를 풀이 계속 보관하면 필요 없어진 대상까지 메모리에 남을 수 있다. 다음 사용자가 이전 대상을 잘못 사용하는 문제도 생길 수 있다. 반납할 때 참조를 정리할지 다음 대여 시에 반드시 덮어쓸지, 실제 사용 방식에 맞게 책임을 정한다.

같은 객체를 두 번 반납하는 문제

이미 반납한 객체를 다시 반납하면 보관 목록에 같은 객체가 두 번 들어갈 수 있다. 그 뒤 두 사용자가 대여하면 둘이 같은 객체를 동시에 조작할 수 있다. 풀을 만든 목적과 반대로 서로의 상태를 덮어쓰게 되는 것이다. 생성과 파괴가 줄어든 대신 대여·반납 규칙을 지킬 책임이 생긴다.

필요한 크기는 동시 사용량과 관련된다

한 객체씩 빌려 쓰고 돌려주는 작업을 백 번 한다면 백 객체가 동시에 필요하지는 않다. 반납하기 전에 열 객체를 한꺼번에 사용한다면 적어도 그 순간의 열 객체가 필요하다. 전체 사용 횟수와 최대 동시 사용량을 구분해야 보관할 크기를 판단할 수 있다.

한 번 크게 늘어난 풀을 계속 유지하면 이후에 사용하지 않는 객체도 메모리를 차지한다. 크기를 제한하면 빈 풀이 되었을 때 새로 만들지, 요청을 거절할지, 다른 정책을 쓸지 정해야 한다. 풀은 무조건 큰 쪽이 좋은 구조가 아니다.

성능을 확인하는 방법같은 종류와 개수의 작업을 비교하고 새 객체 생성 횟수, 메모리, 실제 실행 비용을 관찰한다. 단순히 화면이 부드럽게 보인다는 이유만으로 속도가 몇 배 빨라졌다고 결론 내리지 않는다. 풀의 관리와 재설정 자체에도 비용이 있다.

일반 생성이 더 단순한 경우

사용 횟수가 적거나 객체가 오랫동안 한 번만 사용된다면 보관과 반납의 복잡성이 이득보다 클 수 있다. 반복 생성이 실제 문제인지 먼저 확인하고, 재사용할 때 초기화할 상태를 설명할 수 있는지 살핀다. 생성 비용을 줄인 이득과 보관 메모리·수명 관리 비용을 함께 비교한다.

비교할 일을 같게 맞춘다

풀 경로와 일반 생성 경로가 같은 종류·개수·위치·표시 값·수명·갱신 순서를 사용해야 한다. 한쪽은 가벼운 프리팹을, 다른 쪽은 더 많은 컴포넌트를 쓰면 생성 방식만의 차이를 판단하기 어렵다. 동일 작업을 전제로 준비 구간과 측정 구간을 나눈다.

준비와 워밍업은 따로 기록한다

풀을 미리 만드는 시간과 메모리는 비용이다. 실제 사용 중 수치를 비교하려고 이를 측정 구간 밖으로 옮겼다면 준비 비용도 별도로 기록한다. 첫 글자·재질·코드 경로가 준비되는 차이를 줄이기 위해 두 방식 모두 같은 워밍업을 하고, 측정 순서를 번갈아 여러 번 실행한다.

지표읽는 의미주의할 한계
생성 호출 수실제로 새 객체를 만든 횟수속도 배율을 뜻하지 않음
관리 메모리 할당량관측 프레임에서 새로 할당한 바이트GC 수집 발생이나 전체 메모리 크기와 다름

보관 객체 수다음 요청을 위해 유지한 객체반복 생성 감소의 반대편 메모리 비용

Editor에서 관측한 값은 Editor 실행 조건의 값이다. 실제 배포 게임의 성능이라고 바꾸어 말하지 않는다. 지원되지 않는 카운터는 0으로 적는 대신 이용할 수 없다고 표시한다. 생성 수가 줄어도 문자열 처리와 애니메이션·렌더링의 일은 계속 남을 수 있다.

CHAPTER 09

복습 질문과 용어

학습 목표: 객체 재사용·대여 유효성·초기화·측정의 뜻을 자신의 말로 설명한다.

질문과 해설

1. 하나를 빌리고 반납하는 일을 100번 하면 객체 100개가 필요한가?
빈 풀에서 정상 반납하며 동시에 하나만 사용한다면 하나를 계속 재사용할 수 있다. 사용 횟수와 동시 사용량을 구분한다.

2. 같은 객체를 두 번 반납하면 왜 문제가 되는가?
보관 목록에 중복으로 들어가면 다음 두 사용자가 같은 객체를 동시에 받을 수 있다. 현재 구현은 첫 반납에서 대여 기록을 지워 두 번째 반납을 거절한다.

3. 이미 반납한 A와 현재 B가 같은 Value를 갖는다. A의 반납은 유효한가?
아니다. 새 사용에는 새 번호가 발급되므로 현재 번호와 같지 않다. 객체의 동일성과 대여의 동일성은 다르다.

4. 비활성화한 객체의 시간·색·참조도 지워지는가?
아니다. 다음 사용을 위해 Reset과 종류별 초기화가 필요하다. 초기화하지 않은 상태는 새 사용자에게 남을 수 있다.

5. ReturnAll과 Dispose는 무엇이 다른가?
ReturnAll은 사용을 끝내고 객체를 다음 대여에 남긴다. Dispose는 소유 객체를 파괴하고 풀이 더 이상 새 대여를 받지 않게 한다.

6. 생성 횟수가 100에서 1로 줄었다면 게임이 100배 빨라졌는가?
아니다. 생성 횟수의 변화만 계산한 것이다. 남아 있는 작업, 준비·보관 비용과 실제 프레임 시간 분포를 함께 관측해야 한다.
