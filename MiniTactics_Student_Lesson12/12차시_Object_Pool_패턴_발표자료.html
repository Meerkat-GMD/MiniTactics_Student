Object Pool 패턴

Object Pool
버리지 않고, 돌려받기

짧게 나타났다 사라지는 표시를
객체와 대여의 수명으로 나누어 읽는다.

같은 객체를 다시 쓰더라도, 이번 대여와 이전 대여는 구별해야 한다.

A Small Success

짧게 쓰고 없애면 단순하다

표시 한 번

숫자나 먼지를 만들고, 잠깐 보여 준 뒤 없앤다. 드문 표시라면 생성과 파괴가 단순하고 충분할 수 있다.

반복되는 표시

짧은 표시가 겹쳐서 계속 생기면 비슷한 객체를 만들고 버리는 일이 반복된다.

Object Pool은 반복되는 객체 수명 관리의 선택지다. 모든 객체를 미리 보관하라는 규칙은 아니다.

A Concrete Problem

끝난 표시를 다음 요청에 다시 쓸 수 있을까?

한 번에 3개가 나타나고 사라지는 표시를
10번 반복하면 매번 새 객체가 필요할까?

표시할 값과 위치는 바뀌어도 구조는 같다. 끝난 객체를 보관했다가 다시 빌려주면 생성을 줄일 여지가 있다.

여기서 3개·10번은 설명용 가정이다. 실제 성능 측정 결과가 아니다.

Limited First Attempt

객체 하나를 숨겼다가 다시 보여 준다

설계 비교용 가상 코드 · 현재 Teacher 구현이 아니다.

cached.gameObject.SetActive(true);
// 재생이 끝나면
cached.gameObject.SetActive(false);

성공 범위

동시에 하나만 쓰고 상태를 매번 준비하면, 객체 하나를 재사용할 수 있다.

남은 한계

새 표시가 겹치면 같은 객체를 덮는다. 오래된 종료 요청이 새 표시를 숨길 수도 있다.

Observe the Boundary

객체가 같은 것과 대여가 같은 것은 다르다

시점객체 A 하나만 기억한다면
첫 표시가 A를 사용오래된 종료 요청이 A를 기억
첫 표시 종료 뒤 A 재사용두 번째 표시도 A를 사용
늦게 도착한 첫 종료 요청두 번째 표시까지 숨길 위험

A라는 객체 참조만으로는 이번 사용을 구별할 수 없다. 어느 풀에서 몇 번째로 빌렸는지도 함께 기억한다.

Responsibility Boundary

대기·대여·소유를 나누어 관리한다

대기 available지금 빌려줄 수 있는 객체
대여 active현재 사용 중인 객체와 세대 번호
소유 owned풀이 생성해 마지막에 정리할 객체
재생 일정표시가 끝났는지 확인하는 쪽의 기록

재생 일정이 두 번째 소유 목록은 아니다. 인스턴스와 대여 상태는 풀이 관리한다.

Name the Pattern

Object Pool은 재사용 가능한 객체의 대여소다

필요할 때 빌려주고,
끝나면 초기화해 돌려받는다.

대기 객체
→
Rent · 대여
→
사용과 완료
→
Return · 반환

반환은 파괴가 아니다. 객체와 보유 메모리는 다음 대여를 위해 남는다.

Actual Roles

T는 Component 타입이다. 같은 방식의 대여 규칙을 서로 다른 짧은 표시에 적용한다.

Pool State

풀은 세 종류의 기록을 따로 둔다

private readonly Stack<T> _available = new Stack<T>();
private readonly Dictionary<T, long> _active = new Dictionary<T, long>();
private readonly List<T> _owned = new List<T>();
private long _sequence;

_available은 꺼낼 대기 객체의 Stack, _active는 현재 대여와 세대 번호의 Dictionary, _owned는 생성한 객체의 List다.

이 내부 자료구조 이름은 공개 개수 조회 API가 아니다. 대기 수와 대여 수는 뒤의 추적 표에서 설명용으로 센다.

Lease Identity

대여증은 객체·소유 풀·세대를 묶는다

public readonly struct PoolLease<T> where T : Component
{
    public T Value { get; }
    internal TransientPool<T> Owner { get; }
    internal long Sequence { get; }

실제 코드 발췌 · PoolLease.cs 5–9행 · 주변 코드 생략 · SHA-256 015275b8aaa3

Value는 사용하는 객체다. Owner는 빌려준 풀이고 Sequence는 대여할 때 발급한 번호다. Owner와 Sequence는 internal 멤버다.

readonly struct인 대여증을 복사해도 새 대여가 되지 않는다. 같은 대여증의 복사본도 한 번만 유효하게 반환할 수 있다.

Rent and Exhaustion

Rent는 남은 객체를 찾고 없으면 만든다

T value = null;
while (_available.Count > 0 && value == null) value = _available.Pop();
if (value == null) value = Create();
Reset(value);

실제 코드 발췌 · TransientPool.cs 46–49행 · 주변 코드 생략 · SHA-256 72ce310404af

파괴되어 사용할 수 없는 대기 참조는 건너뛴다. 유효한 대기 객체가 없으면 Create로 늘린다.

이 풀은 고정 상한이나 대기 정책이 없다. 소진되면 생성하므로, 미리 준비한 수보다 동시 사용이 많으면 추가 생성된다.

New Rental Generation

같은 객체에도 매번 새 대여 번호를 준다

long sequence = ++_sequence;
_active.Add(value, sequence);
value.gameObject.SetActive(true);
return new PoolLease<T>(value, this, sequence);

실제 코드 발췌 · TransientPool.cs 50–53행 · 주변 코드 생략 · SHA-256 72ce310404af

_sequence를 증가시키고 현재 대여를 기록한 뒤 객체를 활성화한다. 새 대여증은 이 풀과 새 번호를 함께 갖는다.

A를 반환한 뒤 다시 빌리면 Value는 A여도 Sequence는 달라진다. 재사용하는 것은 객체이고 새로 발급하는 것은 대여의 정체성이다.

Reject Invalid Returns

Return은 현재 대여인지 먼저 검사한다

if (_disposed || lease.Owner != this || ReferenceEquals(lease.Value, null)) return false;
if (!_active.TryGetValue(lease.Value, out long sequence) || sequence != lease.Sequence) return false;
_active.Remove(lease.Value);
if (lease.Value == null) return false;

실제 코드 발췌 · TransientPool.cs 58–61행 · 주변 코드 생략 · SHA-256 72ce310404af

폐기된 풀, 다른 풀의 대여증, 기본 대여증은 거절한다. 현재 대여 기록이 없거나 세대 번호가 다르면 false다.

현재 대여와 일치하면 먼저 기록에서 제거한다. 외부에서 이미 파괴한 Unity 객체라면 false이고 대기 목록으로 보내지 않는다.

Successful Return

정상 반환은 초기화하고 비활성화한다

Reset(lease.Value);
lease.Value.gameObject.SetActive(false);
_available.Push(lease.Value);
return true;

실제 코드 발췌 · TransientPool.cs 62–65행 · 주변 코드 생략 · SHA-256 72ce310404af

유효한 현재 대여만 초기화한 뒤 숨기고 대기 Stack에 넣는다. 성공하면 true다.

같은 대여증을 또 반환하면 _active에 해당 대여가 없어 false다. 중복 반환으로 같은 객체가 대기에 두 번 들어가지 않는다.

L1·L2·A는 설명용 이름이다. 다른 풀에 L2를 반환하거나 기본 대여증을 반환해도 false다.

Prewarm Is Available Capacity

Prewarm은 빌려줄 대기 수를 준비한다

while (_available.Count < count)
{
    T value = Create();
    Reset(value);
    value.gameObject.SetActive(false);
    _available.Push(value);

실제 코드 발췌 · TransientPool.cs 34–39행 · 주변 코드 생략 · SHA-256 72ce310404af

이 반복 앞에서 파괴된 대기 참조를 걸러낸다. count는 총 생성 상한이 아니라 유효한 대기 수의 목표다.

대기 1개·대여 2개일 때 Prewarm(3)은 대기 2개를 더 만든다. 대여 2개는 그대로이므로 총 소유 객체는 5개가 된다.

Short Consumer

소비자는 빌린 뒤 표시하고 대여증을 기록한다

lease.Value.SetAutomaticLifetime(false);
lease.Value.Show(amount, healing, position);
_numberSchedule.Add(lease);

Backward Schedule Iteration

완료 일정을 뒤에서부터 제거한다

for (int index = _numberSchedule.Count - 1; index >= 0; index--)
{
    PoolLease<DamageNumber> lease = _numberSchedule[index];
    if (!lease.Value.Advance(Time.deltaTime)) continue;
    _numbers.Return(lease);
    _numberSchedule.RemoveAt(index);
}

Advance가 완료를 알리면 풀에 반환하고 일정에서 제거한다. 뒤에서 앞으로 돌면 RemoveAt 뒤에 앞쪽 인덱스는 바뀌지 않는다.

일정을 먼저 비운 뒤 모두 반환한다

{

}

완료 대기 기록을 남긴 채 풀의 객체만 반환하면, 다음 대여 뒤 오래된 일정이 새 재생을 진행시킬 수 있다.

세대 검사로 낡은 반환은 거절해도, 오래된 코드가 Value.Advance를 먼저 호출하는 것까지 막지는 못한다. 따라서 일정부터 지운다.

Release Versus Destruction

ReturnAll은 재사용, Dispose는 수명 종료다

ReturnAll

현재 대여 중 살아 있는 객체를 초기화·비활성화하여 대기로 보낸다. _active를 비운다. 객체와 누적 대여 번호는 유지한다.

Dispose

ReturnAll 뒤 폐기 상태를 기록하고 소유 객체를 Destroy한다. 소유·대기 목록을 비운다. 이후 Rent와 Prewarm은 예외다.

ReturnAll 뒤 새로 빌려도 번호가 되돌아가지 않는다. Dispose는 번호나 CreatedCount를 0으로 만들지 않는다. 파괴와 세대 보존은 다른 문제다.

Measurement Boundary

생성 감소와 성능 보장은 구별한다

확인할 수 있는 것

같은 출력·수명·관찰 구간에서 생성 횟수를 비교한다. Prewarm 비용과 준비 뒤 추가 생성을 나누어 센다.

여전히 측정할 것

보유 메모리, 초기 준비 시간, 전체 할당·컬렉션, 프레임 시간은 별도 관찰이 필요하다. 생성 0번만으로 판단할 수 없다.

제공된 계측 기반 위에서 PoolComparisonDriver가 대여·반환 작업을 수행한다. 여기에는 기본 설정의 실측 성능 결과가 없으며 전체 게임 zero GC나 FPS 향상을 보장하지 않는다.

Costs and Application

짧고 반복되는 객체에 먼저 검토한다

유용한 조건대가와 판단
숫자·먼지처럼 구조가 같고 반복됨동시 사용량을 추정하고 준비 수를 정한다.
수명이 짧고 종료 경계가 명확함반환 누락·중복·오래된 요청을 관리한다.
초기화할 상태가 명확함재사용 때마다 초기화 비용과 복잡성이 든다.
드물고 오래 사는 객체보유 메모리와 관리 비용이 이득보다 클 수 있다.

기존 MovementOverlayPool은 이전 차시부터 이어진 별도 작업이다. 새 Object Pool 성과로 합산하지 않는다.
