Mini Tactics · Lesson 12

미니 택틱스로 이해하는
Object Pool 패턴

사용이 끝난 객체를 보관하고 다시 빌린다.
재사용에는 초기화와 반납의 책임이 따른다.

Starting point

필요할 때 만들고 끝나면 파괴한다

GameObject marker = Instantiate(markerPrefab);
marker.transform.position = position;

// 사용이 끝난다.
Destroy(marker);

설계 비교용 가상 코드 · 필요할 때 만들고 사용이 끝나면 파괴하는 첫 시도다.

사용이 끝나면 객체도 사라진다. 드물게 쓰는 객체라면 소유와 정리가 분명하고 이해하기 쉽다.

New requirement

짧은 사용이 여러 번 반복된다

같은 종류의 객체를 잠깐 쓰고 버리는 일이
계속 반복된다면,
다 쓴 객체를 다음 요청에 다시 줄 수 있을까?

먼저 반복 생성이 실제 비용인지 확인한다. 재사용은 보관 메모리와 상태 초기화라는 새 책임을 만든다.

First attempt

각 사용마다 새 객체를 만든다

for (int i = 0; i < 3; i++)
{
    Marker value = CreateMarker();
    Use(value);
    DestroyMarker(value);
}

설계 비교용 가상 코드 · 각 Use가 끝난 뒤 파괴까지 완료된다고 가정한 순차 사용 예다.

읽기 쉬운 점

매번 새로운 객체이므로 앞선 사용자의 상태를 이어받지 않는다.

반복될 때 볼 점

동시에 하나만 필요해도 세 번 생성한다. 생성 횟수와 동시 사용량이 다르다.

Observe the limit

전체 사용 횟수와 생성 횟수를 나눈다

순차로 3번 사용새 객체 생성사용이 끝난 객체
매번 생성·파괴3번파괴
빈 풀에서 빌려 쓰고 반납처음 1번보관 뒤 재사용

두 방식 모두 사용은 세 번이다. 바뀌는 것은 객체를 준비하고 사용 뒤 처리하는 방법이다. 이 표는 생성 수의 계산이며 속도 측정값이 아니다.

Find the boundary

객체의 생존과 한 번의 사용을 분리한다

생성·파괴 방식
생성 → 사용 → 파괴
→
재사용 방식
생성 → 사용 → 보관
→ 다시 사용 → 보관

반납은 이번 사용의 끝이다. 객체의 생존 자체가 끝나는 것은 아니므로 필드 값도 남을 수 있다.

Object Pool

보관과 사용 권한을 풀에서 관리한다

풀 · TransientPool만든 객체와 현재 대여를 관리한다.
보관 중 객체비활성 상태로 다음 요청을 기다린다.
대여 · PoolLease어느 풀의 몇 번째 사용인지 기억한다.
사용자빌린 객체를 사용하고 같은 대여를 반납한다.

이 예제의 사용자는 TransientPresenter다. 풀은 객체의 종류별 표시 방법을 알지 않고 전달받은 reset 작업을 사용한다.

Actual code · Ownership

보관 목록과 대여 기록은 책임이 다르다

private readonly Stack<T> _available = new Stack<T>();
private readonly Dictionary<T, long> _active = new Dictionary<T, long>();
private readonly List<T> _owned = new List<T>();

자료구조기억하는 것
_available다음 요청에 줄 수 있는 보관 객체
_active현재 사용 중 객체와 유효한 대여 번호

T는 이 풀에서 빌려 줄 컴포넌트의 형식이다. 한 풀에 서로 다른 종류를 섞어 넣지 않는다.

Actual code · Rent

살아 있는 보관 객체를 꺼내고 없으면 만든다

T value = null;
while (_available.Count > 0 && value == null) value = _available.Pop();
if (value == null) value = Create();
Reset(value);
long sequence = ++_sequence;
_active.Add(value, sequence);
value.gameObject.SetActive(true);
return new PoolLease<T>(value, this, sequence);

보관한 객체를 꺼내고, 사용할 객체가 없을 때만 Create한다. 초기화한 뒤 새 번호를 발급하고 활성화한다. 파괴된 Unity 객체는 건너뛴다.

Actual code · Return

유효한 반납은 한 번만 보관 목록에 넣는다

_active.Remove(lease.Value);
if (lease.Value == null) return false;
Reset(lease.Value);
lease.Value.gameObject.SetActive(false);
_available.Push(lease.Value);
return true;

이 부분에 오기 전에 소유자와 대여 번호를 검사한다. 현재 대여 기록을 없애고, 살아 있는 객체를 초기화·비활성화한 뒤 보관한다. 다시 반납하면 더 이상 유효한 대여 기록이 없다.

Trace · Two objects

두 객체를 세 번 빌리는 과정을 센다

작업사용 중 객체풀에 남은 객체누적 생성 수
빈 풀로 시작없음없음0
첫 번째 대여객체 1없음1
두 번째 대여객체 1, 객체 2없음2
객체 1 반납객체 2객체 12
세 번째 대여객체 2, 객체 1없음2

빈 풀에서 시작하고 도중에 객체가 파괴되지 않았다고 가정한다. 세 번째 대여는 새 객체를 만드는 대신 반납했던 객체 1을 다시 받는다.

Identity

새 사용이 시작되어도 객체는 같을 수 있다

첫 대여 A
객체 1
반납 후 보관
→
다음 대여 B
같은 객체 1
새 사용 시작

A와 B는 사용 기간의 이름이다. 다른 사용이라고 객체도 새로 만들어진 것은 아니다. 이 때문에 이전 상태를 정리할 책임이 생긴다.

Actual code · Reset

비활성화만으로 이전 값이 사라지지는 않는다

public void ResetVisual()
{
    _age = 0f;
    _color = Color.white;
    _text.text = string.Empty;
    _text.color = Color.white;
}

실제 코드 · DamageNumber.cs 14–20행 · 해당 메서드 전체다.

이 제공 helper는 지난 사용의 시간, 색, 글자를 초기화한다. 풀은 별도로 부모·위치·회전·크기를 초기화한다. 새 사용에서 필요한 상태를 누가 다시 정하는지 구분한다.

Actual code · Lease

객체 참조에 소유자와 대여 번호를 더한다

public T Value { get; }
internal TransientPool<T> Owner { get; }
internal long Sequence { get; }

실제 코드 · PoolLease.cs 7–9행 · 일부 발췌다. 바깥 선언과 다른 코드는 생략했다.

Value만 같아도 같은 대여가 아니다. Owner는 어느 풀인지, Sequence는 어느 사용인지 구분한다. readonly는 이 기록의 값을 바꾸지 못하게 하며 Value 객체 자체를 불변으로 만들지는 않는다.

Trace · Stale return

오래된 대여가 새 사용을 끝내면 안 된다

작업실제 객체현재 유효한 대여결과
A를 빌림객체 1소유자 P / 번호 1A 사용 시작
A를 반납객체 1없음비활성 보관
B를 빌림같은 객체 1소유자 P / 번호 2B 사용 시작
오래된 A를 다시 반납같은 객체 1여전히 번호 2거절, B는 계속 사용

번호 1의 반납이 번호 2를 끝내지 못하게 한다. 소유자가 다른 풀의 반납도 거절한다. 반납한 뒤 남은 참조를 계속 사용해도 된다는 뜻은 아니다.

Lifetime

모두 반납하는 일과 풀을 폐기하는 일을 나눈다

ReturnAll

현재 대여를 끝내고 객체를 초기화·비활성화한다.

보관 객체는 남아 다음 요청에 다시 쓸 수 있다.

Dispose

모든 대여를 끝내고 소유 객체를 파괴한다.

폐기한 풀에서는 새 대여를 시작할 수 없다.

public void ReleaseAll()
{
    _numberSchedule.Clear();
    _effectSchedule.Clear();
    _numbers.ReturnAll();
    _effects.ReturnAll();
}

사용자의 진행 목록도 함께 비운다. 이전 사용을 진행시키는 목록이 남으면 다시 빌린 객체를 잘못 조작할 수 있다.

Capacity policy

미리 만들기와 부족할 때의 정책을 정한다

선택현재 구현따르는 비용
미리 준비Prewarm으로 보관 객체를 채움시작 시간과 보관 메모리
보관 객체 부족필요한 새 객체를 생성사용 중 추가 생성 가능
큰 사용량이 지나감보관 객체를 유지쓰지 않는 객체도 메모리 차지

현재 구현에는 최대 용량이나 자동 축소가 없다. 풀이라는 이름만으로 이후 생성 횟수가 언제나 0이 되는 것은 아니다.

Peak demand

필요한 크기는 겹치는 사용량과 관련된다

사용 방법전체 대여 횟수최대 동시 사용새로 필요한 객체
하나씩 빌리고 반납, 100회 반복10011
10개 대여 후 모두 반납, 10회 반복1001010
100개 대여한 뒤 한 번에 반납100100100

빈 풀에서 시작해 정상 반납하며 파괴되지 않는다고 가정한 계산이다. 실제 필요한 크기는 수명과 발생 간격이 겹치는 순간을 기준으로 판단한다.

이전 범위 표시도 객체를 다시 사용했다

MovementOverlayPool은 이미 만든 표시 객체가 있으면 그 참조를 돌려준다. 재사용의 핵심은 같다. 지금 읽은 풀은 개별 대여의 소유자와 번호, 초기화·정리 정책까지 명시한다.

Measurement

같은 일을 비교하고 관측값의 뜻을 구분한다

관측뜻이 값만으로 말할 수 없는 것
실제 생성 횟수새 객체를 몇 번 만들었는가게임이 몇 배 빨라졌는가
프레임별 관리 메모리 할당관측 구간에 할당한 바이트게임 전체 GC가 0인가
프레임 시간 분포관측된 간격의 중앙값·상위 지연다른 기기의 성능도 같은가

같은 프리팹·개수·위치·수명·갱신 순서로 비교한다. 준비와 워밍업을 별도로 기록하고 여러 번 순서를 바꿔 측정한다.

Costs

보관 메모리와 상태 관리가 대가다

비용확인할 책임
유휴 객체 보관필요한 최대 동시 사용량과 보관 범위
이전 상태 잔존매번 다시 정할 값과 참조
중복·오래된 반납대여 소유자와 유효성
수명 복잡성사용 종료, 전체 반납, 소유자 폐기

생성 횟수가 줄어도 렌더링·표시 갱신·문자열 처리까지 자동으로 사라지는 것은 아니다.

Judgment

반복 생성의 비용이 관리 비용보다 큰가

풀을 검토할 때

같은 종류를 짧게 반복해 쓰고, 동시 사용량을 예상할 수 있다. 생성 비용을 줄일 근거가 있다.

일반 생성이 단순할 때

드물게 쓰거나 오래 유지한다. 재사용 상태를 정리하는 비용이 크고 측정에서도 이득이 작다.

성능 목표와 실제 측정, 읽고 유지할 코드의 비용을 함께 본다. 모든 GameObject에 풀을 적용할 필요는 없다.

Check

같은 객체와 같은 대여를 구분한다

질문

A를 반납하고 같은 객체를 B로 다시 빌렸다. A의 오래된 기록으로 반납하면 B도 끝나는가?

답: 아니다. 현재 대여 번호와 달라 거절한다.

한 가지 더

SetActive(false)를 호출하면 필드 값도 새 객체처럼 초기화되는가?

답: 아니다. 초기화 코드가 따로 필요하다.

Takeaway

반복 생성 비용과 재사용 책임을 함께 판단한다

  1. 사용이 끝난 객체를 보관해 다시 빌린다.
  2. 새 사용 전에 이전 값과 참조를 초기화한다.
  3. 반납 권한과 소유자의 수명을 분명히 한다.
  4. 같은 작업에서 관측한 이득과 관리 비용을 비교한다.

객체를 다시 쓸 때는
이전 사용이 끝났다는 약속도 지켜야 한다.
