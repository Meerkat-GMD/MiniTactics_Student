Chapter 01

학습 목표

이번 차시는 두 가지 생각을 연결한다. 첫째, 수많은 셀이 반복해서 갖는 지형 규칙을 하나의 객체로 공유한다. 둘째, 그 공유 규칙을 사용하여 유닛의 이동 예산 안에서 갈 수 있는 셀과 가장 싼 경로를 구한다.

설계 목표

  • 공유 데이터와 셀별 문맥을 구분한다.
  • Flyweight가 메모리뿐 아니라 규칙의 일관성을 어떻게 돕는지 설명한다.
  • 모델, 알고리즘, 화면 표시의 책임을 나눈다.

구현 목표

  • 평지 1, 숲 2, 산 3, 강 통행 불가를 표현한다.
  • 누적 비용으로 이동 범위를 계산한다.
  • 이전 셀 기록으로 최저 비용 경로를 복원한다.
  • Lesson2의 Command와 Undo를 유지한다.
완성 장면: 유닛을 선택하면 지형 비용을 반영한 범위가 나타나고, 강은 범위에서 제외된다. 이동 후 Undo도 이전처럼 동작한다.

Chapter 02

문제: 지형 규칙을 셀마다 복제한다면

12×10 보드에는 120개의 셀이 있다. 각 셀에 이름, 이동 비용, 통행 여부와 그림을 모두 저장하면 숲이라는 사실을 숲 셀 수만큼 반복하게 된다.

Cell (2, 7): name="숲", movementCost=2, isWalkable=true
Cell (3, 7): name="숲", movementCost=2, isWalkable=true
Cell (4, 7): name="숲", movementCost=2, isWalkable=true

세 셀의 좌표는 서로 다르다. 그러나 “숲은 비용 2이며 걸을 수 있다”는 규칙은 완전히 같다. 여기서 좌표는 셀별 정보이고 지형 규칙은 공유 가능한 정보다.

셀마다 달라지는 정보같은 지형끼리 공유할 정보
좌표, 현재 유닛, 선택/강조 상태이름, 이동 비용, 통행 가능 여부
게임 진행 중 자주 변할 수 있음한 스테이지 안에서는 거의 변하지 않음
셀 문맥에 남김TerrainType으로 분리
중요: Lesson1의 단순 Tilemap이 잘못된 것은 아니다. 모든 칸의 이동 비용이 같았던 이전 요구에는 충분했다. 지형 종류와 비용이라는 새 요구가 생기면서 새로운 경계가 필요해졌다.

Chapter 03

Flyweight 패턴

정의: Flyweight는 많은 객체가 반복해서 가지는 변하지 않는 데이터를 별도의 작은 객체로 분리하고, 여러 문맥이 그 객체를 공유하게 하는 패턴이다.

Intrinsic state와 extrinsic state

패턴을 설명할 때 공유 객체 안에 들어가는 데이터를 intrinsic state, 공유 객체 밖의 문맥이 제공하는 데이터를 extrinsic state라고 부른다.

Intrinsic

TerrainType 안에 있다.

  • Name
  • MovementCost
  • IsWalkable

Extrinsic

Board와 플레이 상태에 있다.

  • Vector2Int 좌표
  • 점유 유닛
  • 오버레이 표시

왜 불변이어야 하는가

하나의 Forest 객체를 여러 셀이 참조한다. 어느 셀이 실수로 Forest의 비용을 바꾸면 모든 숲 셀의 규칙이 동시에 바뀐다. 생성 시 값을 검사하고 getter-only 속성으로 노출하면 공유의 위험을 줄일 수 있다.

public sealed class TerrainType
{
    public string Name { get; }
    public int MovementCost { get; }
    public bool IsWalkable { get; }
}

이 프로젝트는 TerrainTypes에 네 canonical object를 만든다. “canonical”은 같은 의미를 대표하는 표준 객체라는 뜻이다.

public static readonly TerrainType Plain =
    new TerrainType("평지", 1, true);
public static readonly TerrainType Forest =
    new TerrainType("숲", 2, true);
public static readonly TerrainType Mountain =
    new TerrainType("산", 3, true);
public static readonly TerrainType River =
    new TerrainType("강", 1, false);

Chapter 04

Board: 좌표와 공유 객체의 관계

Board는 화면에 타일을 그리지 않는다. 셀 좌표가 어떤 지형을 참조하는지 대답하는 순수한 게임 모델이다.

Vector2Int→Dictionary→TerrainType 참조
private readonly Dictionary<Vector2Int, TerrainType> _cells;

public bool Contains(Vector2Int cell)
{
    return _cells.ContainsKey(cell);
}

public TerrainType GetTerrain(Vector2Int cell)
{
    return _cells[cell];
}

사전을 생성자에서 복사하는 이유는 Board를 만든 외부 코드가 나중에 원본 사전을 변경하여 Board의 규칙을 몰래 바꾸지 못하게 하기 위해서다. 존재하지 않는 좌표를 자동으로 평지로 만들지 않는 것도 중요하다. 잘못된 좌표는 조기에 드러나야 한다.

객체 수로 다시 보기

구조셀 관계지형 규칙 객체
복제형120최대 120
Flyweight1204

Flyweight가 모든 메모리를 없애는 것은 아니다. 좌표와 참조 관계는 여전히 120개다. 없애는 것은 “같은 규칙 데이터의 반복”이다.

Chapter 05

MapLoader: 문자를 공유 참조로 바꾸기

텍스트 맵은 사람이 읽고 수정하기 쉽다. 각 문자는 새 객체를 만들라는 명령이 아니라 이미 존재하는 공유 객체를 선택하라는 표지다.

PPPPPPPPPPPP
PPFFFFPPPPPP
PPFMMFPPPPRP
PPFPPFPPPPRP
문자반환 객체규칙
PTerrainTypes.Plain비용 1
FTerrainTypes.Forest비용 2
MTerrainTypes.Mountain비용 3
RTerrainTypes.River통행 불가

좌표 방향

텍스트의 첫 행은 눈으로 보았을 때 맵의 위쪽이다. Unity 격자에서는 높은 y가 위쪽이므로 첫 행을 y = height - 1에 놓고 다음 행마다 y를 줄인다.

입력을 엄격하게 검사하는 이유

  • 행 길이가 다르면 직사각형 보드의 좌표 규칙이 깨진다.
  • 알 수 없는 문자를 평지로 바꾸면 오타가 게임 규칙으로 숨어든다.
  • 빈 중간 행은 보드를 둘로 나누는 의도인지 파일 실수인지 구분할 수 없다.
잘못된 데이터는 “가능한 값”으로 추측하지 않는다. 행 번호나 좌표가 들어간 오류가 제작자의 수정 시간을 줄인다.

Chapter 06

비용 기반 이동 범위

BFS가 정확했던 조건

Lesson1의 BFS는 간선 하나의 비용이 언제나 1이라는 조건에서 최단 칸 수를 구했다. 모든 이동의 비용이 같으면 먼저 방문한 경로가 최저 비용 경로다. 숲과 산이 생기면 같은 칸 수의 경로도 비용이 달라진다.

위 → 오른쪽

숲 2 + 평지 1 = 3

오른쪽 → 위

평지 1 + 평지 1 = 2

축소형 다익스트라의 세 기록

frontier
발견했지만 아직 이웃을 조사하지 않은 셀.
costs
시작에서 각 셀까지 현재 알려진 최저 누적 비용.
previous
그 최저 비용 경로에서 바로 전에 방문한 셀.

반복 규칙

  1. 시작 셀 비용을 0으로 기록한다.
  2. frontier에서 누적 비용이 가장 작은 셀을 꺼낸다.
  3. 상하좌우 이웃이 Board 안에 있는지 확인한다.
  4. 통행 불가 지형은 건너뛴다.
  5. 현재 누적 비용 + 다음 지형 비용을 계산한다.
  6. 예산을 넘으면 건너뛴다.
  7. 처음 찾았거나 기존보다 싸면 costs와 previous를 갱신한다.
int candidateCost = costs[current] + terrain.MovementCost;

if (candidateCost > budget)
    continue;

if (costs.TryGetValue(next, out int knownCost)
    && knownCost <= candidateCost)
    continue;

costs[next] = candidateCost;
previous[next] = current;
frontier.Add(next);

왜 방문 집합 하나로 부족한가

비용이 다른 그래프에서는 어떤 셀을 비싼 길로 먼저 발견한 뒤 더 싼 길로 다시 발견할 수 있다. “한 번 발견했음”만 저장하면 갱신 기회를 잃는다. 따라서 셀마다 현재 최저 비용을 저장하고 비교해야 한다.

이번 수업은 작은 12×10 보드에서 알고리즘을 눈으로 읽기 위해 frontier 전체를 훑어 최저 비용 셀을 찾는다. 큰 맵에서는 우선순위 큐로 교체할 수 있지만 핵심 규칙은 같다.

Chapter 07

previous로 경로 복원하기

costs는 “얼마나 드는가?”에 답하지만 “어느 길로 왔는가?”에는 답하지 못한다. 더 싼 경로를 채택할 때 previous[next] = current도 함께 저장해야 한다.

목표←이전 셀←이전 셀←시작

목표부터 이전 셀을 따라가면 역순이므로 마지막에 한 번 뒤집는다.

List<Vector2Int> path = new() { destination };
Vector2Int current = destination;

while (current != start)
{
    current = previous[current];
    path.Add(current);
}

path.Reverse();

경계 사례

  • 도달하지 못한 목적지: 빈 경로
  • 목적지가 시작점: 시작점 하나
  • previous가 끊어진 비정상 결과: 빈 경로로 안전하게 종료

경로는 10차시 이동 연출에서도 다시 사용된다. 지금 “도달 가능 여부”와 함께 이전 셀을 기록해 두면 미래 기능이 알고리즘을 다시 실행할 필요가 없다.

Chapter 08

게임에 연결되는 데이터 흐름

map01.txt→MapLoader→Board→MovementRange→RangeHighlighter

BoardView

BoardView는 모델을 Tilemap과 Unity 좌표에 연결한다. 선택 유닛의 월드 위치를 셀로 바꾸고, 이동 예산을 MovementRange에 넘긴다. 결과 셀은 RangeHighlighter에 전달한다.

점유 규칙은 어디에 있는가

지형 탐색은 다른 유닛이 있는 셀도 계산할 수 있다. 이 차시에서는 기존 동작처럼 그 셀을 지나갈 수 있지만 최종 목적지로는 선택할 수 없다. 지형의 통행 가능 여부와 유닛 점유는 서로 다른 이유로 바뀌므로 같은 데이터에 섞지 않는다.

Command와의 협력

MovementRange

목적지가 규칙상 가능한지 판단한다.

MoveUnitCommand

검증을 통과한 이동을 실행하고 Undo에 필요한 출발점을 기억한다.

if (!_board.CanMoveTo(SelectedUnit, targetCell))
    return false;

var command = new MoveUnitCommand(SelectedUnit, _board, targetCell);
_history.Execute(command);

Lesson3는 Lesson2 코드를 버리지 않는다. 탐색 책임만 발전시키고 실행·기록 책임은 재사용한다. 이것이 책임 분리의 실제 이점이다.

Chapter 09

언제 Flyweight를 적용할까

적합한 신호주의할 신호
동일 데이터가 수십·수백 번 반복된다.객체 수가 적어 단순한 복제가 더 읽기 쉽다.
공유 데이터가 거의 변하지 않는다.인스턴스마다 자주 독립적으로 바뀐다.
공유 정보와 문맥을 명확히 나눌 수 있다.문맥을 매 호출마다 전달해 코드가 더 복잡해진다.
표준 객체를 참조로 비교할 수 있다.값 동등성이 더 자연스럽고 객체 정체성이 필요 없다.

메모리 절약만이 목적은 아니다

작은 보드에서는 절약되는 바이트가 중요하지 않을 수 있다. 하지만 “숲의 규칙은 한곳에 있다”는 사실은 밸런스 변경과 오류 수정의 경계를 선명하게 만든다. 패턴의 이득은 메모리와 일관성 두 가지다.

공유의 대가

공유 객체를 변경하면 모든 사용처가 영향을 받는다. 그래서 불변 데이터로 만들고, 런타임에 셀 하나만 불타서 잿더미가 되는 변화는 Board가 그 셀의 참조를 다른 TerrainType으로 교체하는 방식으로 표현한다.

스스로 답하기

1. 숲 셀 40개가 Forest 객체 하나를 공유해도 되는 이유는?

숲의 이름, 이동 비용과 통행 규칙은 셀 좌표와 무관하게 동일하며 수업 중에는 변하지 않는 데이터이기 때문이다. 좌표와 점유 정보는 Board와 게임 상태에 남긴다.

2. BFS의 방문 집합만으로 비용 최저 경로를 구하기 어려운 이유는?

비싼 경로로 먼저 발견한 셀을 더 싼 경로로 다시 발견할 수 있기 때문이다. 발견 여부뿐 아니라 현재 알려진 최저 비용을 저장하고 비교해야 한다.

3. 강에 비용 999를 주는 대신 IsWalkable을 두는 이유는?

통행 불가는 비용이 큰 이동과 다른 규칙이다. 예산이 커져도 건널 수 없어야 하므로 먼저 명시적으로 제외한다.

4. previous는 언제 갱신해야 하는가?

새 셀을 처음 발견했거나 기존보다 더 싼 누적 비용을 발견해 costs를 바꿀 때 같은 순간에 갱신한다.

5. Lesson2의 Command가 바뀌지 않은 이유는?

MovementRange는 이동 가능 여부, Command는 검증된 이동의 실행과 취소를 담당한다. 서로 다른 책임이므로 지형 규칙의 변화가 Command 구현을 요구하지 않는다.

한 문장 정리: 같은 지형 규칙은 공유하고, 누적 비용을 비교하며 가장 싼 이동 가능 영역과 경로를 찾는다.
