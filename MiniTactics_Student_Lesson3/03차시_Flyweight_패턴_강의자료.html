Flyweight 패턴으로 120개의 셀이 네 개의 지형 규칙 객체를 함께 참조하게 만들고, 공유되는 상태와 공유되지 않는 상태를 구분한다.

Chapter 01

학습 목표

이번 차시의 주제는 Flyweight 패턴 하나다. 많은 셀이 똑같이 갖는 지형 규칙을 하나의 객체로 분리하고, 셀은 그 객체를 가리키는 참조만 갖게 하는 구조를 배운다.

설명할 수 있어야 하는 것

  • 셀마다 규칙을 복사하면 어떤 문제가 생기는지 설명한다.
  • 공유되는 상태와 공유되지 않는 상태를 구분한다.
  • Flyweight의 이득이 메모리 절약과 규칙의 일관성 두 가지임을 설명한다.
  • 공유 객체를 읽기 전용으로 두는 이유를 설명한다.

코드에서 확인할 것

  • TileData 에셋이 공유 객체 역할을 한다.
  • MapData의 셀 배열은 참조만 보관한다.
  • Board와 MapLoader는 객체를 새로 만들지 않고 참조를 전달한다.
  • Board에는 항목이 120개 있고 객체는 4개 있다.
이 자료의 범위: 이 자료는 Flyweight 패턴만 다룬다. 공유된 이동 비용을 사용하는 이동 범위 계산의 절차는 다루지 않으며, 공유 객체를 읽는 코드 한 줄만 확인한다.

Chapter 02

문제: 지형 규칙을 셀마다 복제한다면

전장은 가로 12칸, 세로 10칸의 격자이므로 셀은 120개다. 지형은 평지, 숲, 산, 강의 네 종류이며 지형마다 이동 비용과 통행 여부가 다르다. 처음 떠올리기 쉬운 방법은 셀마다 규칙 필드를 두는 것이다.

// 설계 비교용 가상 코드
public sealed class Cell
{
    public string TerrainName;
    public int MovementCost;
    public bool IsWalkable;
    public TileBase Tile;
}

이 구조는 읽기 쉽다. 셀 하나를 보면 그 셀의 규칙을 바로 알 수 있다. 셀이 몇 개뿐이거나 셀마다 값이 실제로 다르다면 이 구조로 충분하다. 그러나 120개의 셀을 만들면 다음과 같은 데이터가 생긴다.

Cell (5, 4): name="숲", movementCost=2, isWalkable=true
Cell (5, 5): name="숲", movementCost=2, isWalkable=true
Cell (5, 6): name="숲", movementCost=2, isWalkable=true

세 셀의 좌표는 서로 다르다. 그러나 “숲은 비용이 2이고 지나갈 수 있다”는 규칙은 완전히 같다. 실제 지도에서 숲은 15칸이므로 같은 숲 규칙이 15벌 저장되고, 지도 전체에는 규칙 120벌이 저장된다. 실제로 서로 다른 규칙은 네 종류뿐이다.

규칙을 바꿀 때 드러나는 한계

숲의 비용을 2에서 4로 바꾸려면 숲 셀 15개를 모두 고쳐야 한다. 네 지형의 규칙을 모두 조정한다면 고칠 곳은 120곳이다. 한 곳을 빠뜨리면 같은 숲인데 어떤 셀은 비용이 4이고 어떤 셀은 비용이 2가 된다. 오류 메시지가 나오지 않으므로 어긋난 규칙을 찾기 어렵다.

중요: 위 코드는 설계를 비교하기 위한 가상 코드이며 현재 프로젝트에는 Cell class가 없다. 셀마다 필드를 두는 구조가 항상 잘못된 것도 아니다. 같은 값이 많이 반복되고 그 값이 한곳에서 관리되어야 할 때 한계가 드러난다.

Chapter 03

Flyweight 패턴

정의: Flyweight는 많은 객체가 똑같이 갖는 변하지 않는 데이터를 별도의 객체로 분리하고, 여러 곳에서 그 객체를 함께 참조하게 하는 패턴이다. 함께 참조되는 객체를 Flyweight 또는 공유 객체라고 부른다.

참조는 객체의 내용을 복사한 값이 아니라 그 객체를 가리키는 값이다. 숲 셀 15개가 같은 객체를 참조하면 숲 규칙은 메모리에 하나만 존재한다.

공유되는 상태와 공유되지 않는 상태

패턴을 적용하려면 먼저 데이터를 두 종류로 나눈다. 공유 객체 안에 들어가는 데이터를 내재 상태(intrinsic state)라고 부르고, 공유 객체 밖에서 관리하는 데이터를 외재 상태(extrinsic state)라고 부른다.

공유되는 상태 · 내재 상태

같은 지형이면 어느 셀에서나 값이 같다.

  • 지형 이름이 여기에 속한다.
  • 이동 비용이 여기에 속한다.
  • 통행 여부가 여기에 속한다.
  • 타일 그림이 여기에 속한다.

공유되지 않는 상태 · 외재 상태

셀마다 값이 다르다.

  • 어느 셀이 어느 지형인가 하는 정보가 여기에 속한다.
  • 예를 들어 셀 (5,4)는 숲이고 셀 (4,4)는 평지다.
두 상태를 구분하는 질문은 하나다. “이 값은 같은 지형의 모든 셀에서 항상 같은가?” 그렇다면 한 번만 저장하고, 그렇지 않다면 셀 쪽에 남긴다.

Unity에서는 ScriptableObject 에셋이 공유 객체가 된다

ScriptableObject는 Unity에서 데이터를 담아 .asset 파일로 저장하는 객체다. GameObject에 붙지 않으며 Project 창에 파일로 존재한다. Forest.asset을 여러 곳에 연결해도 Unity는 그 에셋을 한 번만 불러오고, 연결한 곳은 모두 같은 객체를 참조한다.

일반적인 Flyweight 구현에는 공유 객체를 만들어 보관하고 돌려주는 Factory가 있다. 이 프로젝트에서는 Unity의 에셋 시스템이 그 일을 맡는다. 지형마다 에셋을 하나씩 만들면 공유 객체 네 개가 준비된다.

역할 대응

Flyweight의 역할미니 택틱스의 코드책임
Flyweight(공유 객체)TileData 에셋지형 이름, 이동 비용, 통행 여부, 타일 그림을 한 번만 보관한다.
고유 상태(외재 상태)MapData의 셀 배열각 셀이 어느 TileData를 참조하는지만 보관한다.
ClientBoard, MapLoader셀 좌표를 받아 그 셀의 공유 객체를 찾아 준다.
소비자이동 범위 계산의 한 줄찾은 공유 객체에서 이동 비용을 읽는다.

이 표에서 고유 상태는 셀마다 고유한 값, 곧 공유되지 않는 상태를 뜻한다.

Chapter 04

공유 객체: TileData 에셋

TileData는 지형 하나의 규칙을 담는 ScriptableObject다. 네 개의 필드가 내재 상태이며, 좌표를 나타내는 필드는 없다. 공유 객체는 자신이 어느 셀에서 쓰이는지 알지 못하므로 여러 셀이 함께 쓸 수 있다.

public sealed class TileData : ScriptableObject
{
    [SerializeField] private string _displayName = "평지";
    [SerializeField, Min(1)] private int _movementCost = 1;
    [SerializeField] private bool _isWalkable = true;
    [SerializeField] private TileBase _tile;

    public string DisplayName => _displayName;
    public int MovementCost => _movementCost;
    public bool IsWalkable => _isWalkable;
    public TileBase Tile => _tile;
}

[SerializeField]는 private 필드의 값을 에셋 파일에 저장하고 Inspector에 표시한다. Min(1)은 Inspector에서 비용을 1보다 작게 입력하지 못하게 막는다. 위 코드는 TileData.cs의 실제 코드이며 class 위의 CreateAssetMenu 특성만 생략했다.

네 개의 에셋

에셋이름이동 비용통행 여부
Plain.asset평지1가능
Forest.asset숲2가능
Mountain.asset산3가능
River.asset강1불가능

강에는 들어갈 수 없으므로 강의 비용 값은 사용되지 않는다.

왜 읽기 전용이어야 하는가

네 속성은 =>로 작성되어 값을 돌려주기만 한다. 공개 setter가 없으므로 다른 class는 비용을 읽을 수 있지만 대입할 수는 없다.

// 설계 비교용 가상 코드: 컴파일 오류가 난다.
board.GetTile(cell).MovementCost = 4;

이 대입을 허용하면 셀 하나를 고치려던 코드가 같은 에셋을 참조하는 숲 15칸의 비용을 모두 바꾼다. 공유 객체의 값은 에셋을 편집하는 한 곳에서만 바꾼다.

Chapter 05

공유되지 않는 상태: MapData의 셀 배열

MapData는 “어느 셀이 어느 지형인가”라는 외재 상태를 보관하는 ScriptableObject다. 이름, 비용, 통행 여부는 갖지 않는다.

[SerializeField] private TileData[] _cells = new TileData[120];

public TileData GetTile(Vector2Int cell)
{
    return _cells[(_height - 1 - cell.y) * _width + cell.x];
}

배열의 원소 120개는 값의 복사본이 아니라 네 TileData 에셋 중 하나를 가리키는 참조다. new TileData[120]은 참조를 담을 자리 120개를 만들 뿐이며 TileData 객체를 만들지 않는다. GetTile은 셀 좌표를 받아 그 셀이 참조하는 공유 객체를 돌려준다.

대괄호 안의 식은 좌표를 배열의 위치로 바꾸는 계산이다. Flyweight와 관계가 없으므로 이 자료에서는 다루지 않는다. 위 코드는 MapData.cs의 실제 발췌이며 Tooltip 특성과 Width, Height는 생략했다.
구분보관하는 곳개수
지형 규칙(내재 상태)TileData 에셋4개
배치(외재 상태)MapData의 셀 배열참조 120개

Chapter 06

Client: MapLoader와 Board

Client는 셀 좌표를 받아 그 셀의 공유 객체를 찾아 주는 역할이다. MapLoader는 MapData의 참조를 Dictionary로 옮기고, Board는 그 Dictionary로 질문에 답한다.

MapData의 참조 120개→MapLoader.Load→Board의 항목 120개→TileData 객체 4개

MapLoader: 참조를 그대로 옮긴다

public static Board Load(MapData mapData)
{
    Dictionary<Vector2Int, TileData> cells = new Dictionary<Vector2Int, TileData>();
    for (int y = 0; y < mapData.Height; y++)
    {
        for (int x = 0; x < mapData.Width; x++)
        {
            Vector2Int cell = new Vector2Int(x, y);
            cells.Add(cell, mapData.GetTile(cell));
        }
    }

    return new Board(cells);
}

이 코드의 new는 Dictionary, 좌표 값, Board를 만든다. TileData는 만들지 않는다. mapData.GetTile(cell)이 돌려준 참조를 그대로 Dictionary에 넣는다. 안쪽 문장은 12×10=120번 실행되므로 항목 120개가 들어간다.

Board: 셀 좌표로 공유 객체를 찾는다

private readonly Dictionary<Vector2Int, TileData> _cells;

public bool Contains(Vector2Int cell)
{
    return _cells.ContainsKey(cell);
}

public TileData GetTile(Vector2Int cell)
{
    return _cells[cell];
}

Dictionary는 키로 값을 찾는 자료구조다. 여기에서 키는 셀 좌표인 Vector2Int이고 값은 TileData 참조다. GetTile(new Vector2Int(5, 4))와 GetTile(new Vector2Int(5, 5))는 같은 Forest 객체를 돌려준다. 두 항목의 키는 다르지만 값이 가리키는 객체는 하나다. 위 코드는 Board.cs의 실제 발췌이며 생성자는 생략했다.

객체 수로 다시 보기

TileData 에셋이 객체를 참조하는 항목객체
Plain(평지)92개1개
Forest(숲)15개1개
Mountain(산)5개1개
River(강)8개1개
합계92+15+5+8 = 120개4개

“Board에 TileData 객체가 몇 개 들어 있는가?”라는 질문의 답은 “항목은 120개이고 객체는 4개다.”이다. Flyweight가 모든 메모리를 없애는 것은 아니다. 좌표와 참조는 여전히 120개다. 없어지는 것은 같은 규칙 값의 반복이다.

반례: 셀마다 new로 객체를 만드는 경우

// 설계 비교용 가상 코드: 잘못 작성한 MapLoader
Vector2Int cell = new Vector2Int(x, y);
TileData tile = new TileData();
cells.Add(cell, tile);
이 문장은 120번 실행되므로 TileData 객체가 120개 생기고 공유가 사라진다. 새 객체는 에셋에 저장된 값을 갖지 않고 필드의 기본값인 평지, 비용 1을 가진다. 이 객체들은 Forest.asset과 연결되어 있지 않으므로 에셋을 고쳐도 값이 바뀌지 않는다. 또한 Unity는 ScriptableObject를 new로 만들면 경고를 출력한다. 이 코드는 현재 MapLoader의 구현이 아니다.

Chapter 07

공유 규칙을 읽는 쪽

공유된 비용을 읽는 쪽은 이동 범위를 계산하는 코드다. 이 자료에서는 그 코드 가운데 공유 객체를 읽는 한 줄만 확인한다.

int nextCost = costs[current] + board.GetTile(next).MovementCost;

costs[current]는 지금 셀까지 쓴 비용이고, 여기에 다음 셀의 이동 비용을 더한다. 읽는 쪽은 셀 좌표 next를 넘기고 비용을 받는다. 그 객체를 몇 개의 셀이 함께 쓰는지는 알 필요가 없다. 위 코드는 MovementRange.cs의 실제 한 줄이다.

셀 좌표 next→Board.GetTile→공유 객체 TileData→MovementCost 값

추적: 숲 에셋의 비용을 2에서 4로 바꾼다

세 경우 모두 지금 셀까지 쓴 비용 costs[current]가 1이라고 가정한다. Forest.asset의 이동 비용만 2에서 4로 바꾼다.

다음 셀 next참조하는 에셋변경 전 nextCost변경 후 nextCost
(5,4) 숲Forest1+2 = 31+4 = 5
(5,5) 숲Forest1+2 = 31+4 = 5
(4,4) 평지Plain1+1 = 21+1 = 2

고친 곳은 에셋 한 곳이다. 코드와 MapData는 바꾸지 않았다. 숲 15칸이 모두 같은 객체를 읽으므로 결과가 함께 바뀐다. Plain을 참조하는 92칸은 영향을 받지 않는다.

숲 한 칸만 바꾸고 싶다면

셀 (5,4)의 숲만 비용 4로 만들고 싶다면 에셋의 값을 바꾸면 안 된다. Forest의 값을 바꾸면 숲 15칸이 모두 바뀐다. 대신 비용 4인 TileData 에셋을 하나 더 만들고 MapData에서 (5,4)의 항목이 그 에셋을 가리키게 한다. 항목은 120개 그대로이고 객체는 5개가 되며, Forest를 참조하는 항목은 14개가 된다.

“모든 숲의 규칙”은 공유되는 상태이고 “이 셀이 어느 지형인가”는 공유되지 않는 상태다. 바꾸려는 것이 어느 쪽인지 먼저 판단한다.

Chapter 08

언제 Flyweight를 적용할까

적합한 신호주의할 신호
같은 데이터가 수십 번 이상 반복된다.객체 수가 적어서 단순한 복제가 더 읽기 쉽다.
공유할 데이터가 실행 중에 바뀌지 않는다.값이 객체마다 자주, 서로 다르게 바뀐다.
공유되는 값과 셀마다 다른 값을 분명하게 나눌 수 있다.두 종류의 값을 나누기 어려워 코드가 더 복잡해진다.

메모리 절약만이 목적은 아니다

작은 보드에서는 절약되는 메모리가 중요하지 않을 수 있다. 그러나 “숲의 규칙은 한곳에 있다”는 사실 덕분에 한 번의 수정이 그 지형의 모든 셀에 똑같이 적용된다. 패턴의 이득은 메모리와 일관성 두 가지다.

공유의 대가

  • 값을 읽을 때 참조를 한 번 거쳐야 한다.
  • 공유 객체의 값을 바꾸면 모든 사용처가 영향을 받으므로 읽기 전용으로 관리해야 한다.
  • 셀마다 다른 값은 공유 객체가 아닌 다른 곳에 보관해야 한다.
  • 참조 120개는 여전히 필요하므로 메모리가 30분의 1로 줄지는 않는다.

셀마다 달라지는 값은 공유 객체에 넣을 수 없다

예를 들어 TileData에 “불타는 중인지 여부”를 넣고 셀 (5,4)에 불을 붙이면, 같은 객체를 참조하는 숲 15칸이 모두 불타는 중이 된다. 이 값은 셀마다 다르므로 외재 상태이며, 셀 좌표를 기준으로 따로 보관해야 한다.

// 설계 비교용 가상 코드
HashSet<Vector2Int> burningCells;

현재 프로젝트에는 이 기능이 없으며 기준을 설명하기 위한 예시다.

용어와 복습

Flyweight
많은 객체가 똑같이 갖는 변하지 않는 데이터를 공유 객체로 분리하는 패턴이다.
내재 상태(intrinsic state)
공유 객체 안에 있으며 어느 셀에서나 값이 같은 데이터다.
외재 상태(extrinsic state)
공유 객체 밖에서 관리하며 셀마다 값이 다른 데이터다.
참조
객체의 내용을 복사한 값이 아니라 그 객체를 가리키는 값이다.
ScriptableObject
Unity에서 데이터를 에셋 파일로 저장하는 객체이며, 이 프로젝트에서 공유 객체 역할을 한다.
Client
공유 객체를 찾아서 사용하는 쪽에 전달하는 코드다.

스스로 답하기

1. 셀 120개가 TileData 네 개를 공유해서 얻는 것 두 가지는 무엇인가?

같은 규칙 값을 120번 저장하지 않는다. 그리고 규칙을 한 곳에서 고치면 그 지형의 모든 셀에 똑같이 적용된다.

2. Mountain 에셋의 비용을 3에서 5로 바꾸면 셀 몇 개가 영향을 받고, 고친 곳은 몇 곳인가?

산을 참조하는 셀 5개가 영향을 받는다. 고친 곳은 Mountain.asset 한 곳이다.

3. 숲 한 칸만 비용을 바꾸고 싶다면 에셋의 값을 바꿔야 하는가, 셀의 참조를 바꿔야 하는가?

셀의 참조를 바꿔야 한다. 에셋의 값은 공유되는 상태이므로 바꾸면 숲 15칸이 모두 바뀐다. 새 TileData 에셋을 만들고 MapData에서 그 셀의 항목이 새 에셋을 가리키게 한다.

4. TileData에 공개 setter가 없는 이유는 무엇인가?

한 곳에서 값을 대입하면 같은 에셋을 참조하는 모든 셀의 규칙이 함께 바뀌기 때문이다.

5. MapLoader에서 셀마다 new TileData()를 호출하면 무엇이 달라지는가?

객체가 120개 생기고 공유가 사라진다. 새 객체는 에셋의 값을 갖지 않으며, 에셋을 고쳐도 영향을 받지 않는다.

6. 비용 3인 늪 지형을 추가하려면 어느 코드를 고쳐야 하는가?

코드는 고치지 않는다. TileData 에셋을 하나 만들고 MapData에서 늪으로 만들 셀의 참조를 바꾼다. 객체는 5개가 된다.

한 문장 정리: 같은 지형 규칙은 한 번만 만들어 공유하고, 셀은 어느 규칙을 쓰는지 가리키는 참조만 가진다.
