Mini Tactics · Lesson 03

미니 택틱스로 이해하는
Flyweight 패턴

120개의 셀이 네 종류의 지형 규칙을 사용한다면,
같은 규칙은 몇 번 저장해야 할까?

작은 시작점

규칙이 하나뿐이면 셀은 아무것도 기억하지 않아도 된다

  • 전장은 가로 12칸, 세로 10칸의 격자이며 셀은 모두 120개다.
  • 지금까지는 어느 셀에 들어가든 비용이 1이었고 모든 셀을 지나갈 수 있었다.
  • 규칙이 하나뿐이므로 코드에 숫자 1을 한 번만 적어도 충분했다.

이 구조로 충분했던 범위

셀마다 다른 값이 없으면 셀이 데이터를 보관할 이유가 없다. 셀 좌표만 있으면 필요한 계산을 모두 할 수 있었다.

이제 셀의 종류가 늘어난다. 이 자료는 “종류별 규칙을 어디에, 몇 번 저장할 것인가?”라는 질문 하나를 다룬다.

새 요구

지형이 네 종류가 되면 셀마다 규칙이 달라진다

지형이동 비용통행 여부지도에서 차지하는 셀
평지1가능92개
숲2가능15개
산3가능5개
강1불가능8개
합계규칙은 네 종류다.12×10 = 120개

이동 비용은 그 셀에 들어갈 때 쓰는 값이고, 통행 여부는 그 셀에 들어갈 수 있는지를 나타낸다. 강에는 들어갈 수 없으므로 강의 비용 값은 사용되지 않는다. 셀은 120개이지만 규칙의 종류는 네 개뿐이다.

실제 값: Maps/Plain.asset · Forest.asset · Mountain.asset · River.asset · map01.asset

첫 시도 · 설계 비교용 가상 코드

첫 생각: 셀마다 규칙 필드를 두자

// 설계 비교용 가상 코드
public sealed class Cell
{
    public string TerrainName;
    public int MovementCost;
    public bool IsWalkable;
    public TileBase Tile;
}

읽기 쉬운 구조다

셀 하나를 보면 그 셀의 이름, 비용, 통행 여부, 타일 그림을 바로 알 수 있다. 셀이 몇 개뿐이거나 셀마다 값이 실제로 다르다면 이 구조로 충분하다.

이 구조로 셀 120개를 만들면 네 필드의 값이 셀마다 하나씩 저장된다. 다음 장에서는 숲 셀 두 개를 나란히 놓고 비교한다.

공유가 필요한 이유를 보이기 위한 가상 코드다. 현재 프로젝트에는 Cell class가 없다.

한계의 관찰 1

좌표만 다르고 나머지 값은 모두 같다

셀 (5,4)
이름: 숲
비용: 2 · 통행: 가능
＝
셀 (5,5)
이름: 숲
비용: 2 · 통행: 가능
범위셀마다 복사한 규칙실제로 서로 다른 규칙
숲 셀 15개15벌1종류
전체 셀 120개120벌4종류

필요한 것은 서로 다른 120개의 위치다. 내용이 같은 규칙 120벌은 필요하지 않다.

한계의 관찰 2

규칙 하나를 바꾸려면 여러 곳을 고쳐야 한다

숲의 비용을 2에서 4로 바꾸는 경우

숲 셀 15개의 MovementCost를 모두 고쳐야 한다. 네 지형의 규칙을 모두 조정한다면 고칠 곳은 120곳이 된다.

한 곳을 빠뜨린 경우

셀 (5,5)를 고치지 못하면 같은 숲인데 (5,4)의 비용은 4이고 (5,5)의 비용은 2가 된다. 오류 메시지가 나오지 않으므로 어긋난 규칙을 찾기 어렵다.

같은 값을 여러 곳에 복사해 두면
고칠 때마다 모든 복사본을 찾아야 한다.

첫 시도의 문제는 두 가지다. 같은 값이 반복해서 저장되고, 규칙이 한곳에 모여 있지 않다.

필요한 경계

공유되는 상태와 공유되지 않는 상태를 나눈다

공유되는 상태 · 내재 상태

같은 지형이면 어느 셀에서나 값이 같은 정보다. 지형 이름, 이동 비용, 통행 여부, 타일 그림이 여기에 속한다. 영어로는 intrinsic state라고 부른다.

공유되지 않는 상태 · 외재 상태

셀마다 값이 다른 정보다. 어느 셀이 어느 지형인가가 여기에 속한다. 셀 (5,4)는 숲이고 셀 (4,4)는 평지다. 영어로는 extrinsic state라고 부른다.

두 상태를 구분하는 질문은 하나다. “이 값은 같은 지형의 모든 셀에서 항상 같은가?” 그렇다면 한 번만 저장하고, 그렇지 않다면 셀 쪽에 남긴다.

패턴의 이름

Flyweight는 같은 데이터를 한 번만 만들어 공유한다

여러 셀이 지형 규칙을 복사해서 갖지 않고,
하나의 규칙 객체를 함께 참조한다.

참조란?

참조는 객체의 내용을 복사한 값이 아니라 그 객체를 가리키는 값이다. 숲 셀 15개가 같은 객체를 참조하면 숲 규칙은 메모리에 하나만 존재한다.

Flyweight란?

많은 객체가 똑같이 갖는 변하지 않는 데이터를 별도의 객체로 분리하고 여러 곳에서 함께 사용하는 패턴이다. 함께 사용되는 객체를 Flyweight 또는 공유 객체라고 부른다.

Unity에서의 구현 수단

지형마다 에셋이 하나 있고 에셋마다 공유 객체가 하나 있다

TileData 에셋

ScriptableObject는 Unity에서 데이터를 담아 .asset 파일로 저장하는 객체다. GameObject에 붙지 않으며 Project 창에 파일로 존재한다. TileData가 ScriptableObject이며, 지형의 값을 Inspector에서 입력하는 곳이다.

TerrainType 객체

실행 중에 규칙을 계산하는 코드가 읽는 일반 C# 객체다. 지형 이름, 이동 비용, 통행 여부를 가지며 만든 뒤에는 값을 바꿀 수 없다. 이 객체가 공유 객체다.

일반적인 Flyweight 구현에는 공유 객체를 만들어 보관하고 돌려주는 Factory가 있다. 이 프로젝트에서는 TileData 에셋이 그 일을 맡는다. 에셋은 처음 요청을 받을 때 TerrainType을 하나 만들어 보관하고, 그 뒤에는 같은 객체를 돌려준다. 에셋이 평지, 숲, 산, 강의 네 개이므로 공유 객체도 네 개다.

역할 대응

네 가지 역할이 공유 구조를 이룬다

Flyweight · 공유 객체
TerrainType지형 이름, 이동 비용, 통행 여부를 읽기 전용으로 한 번만 보관한다.
Factory
TileData.RuntimeTerrain에셋 하나당 TerrainType을 하나만 만들고, 요청을 받으면 같은 객체를 돌려준다.
고유 상태 · 외재 상태
MapData의 셀 배열각 셀이 어느 TileData 에셋을 참조하는지만 보관한다.
Client
MapLoader · Board셀 좌표별로 공유 객체의 참조를 보관하고, 좌표를 받으면 그 셀의 공유 객체를 찾아 준다.

여기에서 고유 상태는 셀마다 고유한 값, 곧 공유되지 않는 상태를 뜻한다. 다음 장부터 네 역할의 실제 코드를 이 순서대로 읽고, 마지막에 공유 규칙을 읽는 쪽의 코드를 확인한다.

실제 코드 · TerrainType 1

공유 객체는 지형 하나의 규칙을 속성으로 가진다

public sealed class TerrainType
{
    // 축약: 생성자는 다음 장에서 읽는다.
    public string Name { get; }
    public int MovementCost { get; }
    public bool IsWalkable { get; }
}

세 속성이 내재 상태다

같은 지형이면 어느 셀에서나 값이 같은 정보다. TerrainType은 MonoBehaviour나 ScriptableObject를 상속하지 않는 일반 C# class이며, 지형 한 종류의 규칙을 나타낸다.

이 class에는 좌표 필드가 없다. 공유 객체는 자신이 어느 셀에서 쓰이는지 알지 못한다. 그래서 여러 셀이 같은 객체를 함께 쓸 수 있다.

실제 발췌: TerrainType.cs · class 선언과 속성 (생성자 생략, 주석 추가)

실제 코드 · TerrainType 2

공유 객체의 값은 만들 때 한 번만 정해진다

public TerrainType(string name, int movementCost, bool isWalkable)
{
    // 축약: 이름과 비용을 검사하는 예외 처리는 생략했다.
    Name = name;
    MovementCost = movementCost;
    IsWalkable = isWalkable;
}
// 설계 비교용 가상 코드: 컴파일 오류가 난다.
board.GetTerrain(cell).MovementCost = 4;

setter가 없다

{ get; }만 있는 속성에는 생성자 안에서만 값을 대입할 수 있다. 객체를 만든 뒤에는 어느 코드도 값을 바꿀 수 없고 읽을 수만 있다.

대입을 허용하면 셀 하나를 고치려던 코드가 같은 객체를 참조하는 숲 15칸의 비용을 모두 바꾼다. 공유 객체의 값은 에셋을 편집하는 한 곳에서만 정한다.

위쪽은 실제 발췌: TerrainType.cs · 생성자 (예외 검사 생략) / 아래쪽은 읽기 전용의 효과를 보이는 가상 코드

실제 코드 · TileData 1

TileData 에셋은 값을 입력받고 공유 객체를 보관한다

public sealed class TileData : ScriptableObject
{
    [SerializeField] private string _displayName = "평지";
    [SerializeField, Min(1)] private int _movementCost = 1;
    [SerializeField] private bool _isWalkable = true;
    [SerializeField] private TileBase _tile;
    [NonSerialized] private TerrainType _runtimeTerrain;
    // 축약: 속성과 메서드는 다음 장에서 읽는다.
}

두 종류의 필드

[SerializeField] 필드 네 개는 Inspector에서 입력하고 에셋 파일에 저장하는 값이다. [NonSerialized]가 붙은 _runtimeTerrain은 파일에 저장되지 않으며, 실행 중에 만든 TerrainType의 참조를 보관한다.

이름, 비용, 통행 여부는 TerrainType을 만들 때 넘겨준다. 타일 그림인 _tile은 화면 표시에만 쓰이므로 TerrainType에 넘기지 않고 에셋에 둔다. 에셋도 지형마다 하나뿐이므로 타일 그림 역시 한 번만 저장된다.

실제 발췌: TileData.cs · 필드 (CreateAssetMenu 특성, 빈 줄, 속성과 메서드 생략, 주석 추가)

실제 코드 · TileData 2

RuntimeTerrain은 에셋 하나당 공유 객체를 하나만 만든다

public TerrainType RuntimeTerrain
{
    get
    {
        Validate();
        return _runtimeTerrain ??= new TerrainType(_displayName, _movementCost, _isWalkable);
    }
}

??= 연산자

왼쪽 변수가 null일 때만 오른쪽 값을 대입하고, 그 뒤에 왼쪽 변수의 값을 돌려준다.

실행 결과

첫 요청에서는 new TerrainType이 실행되고 그 참조가 보관된다. 두 번째 요청부터는 new를 실행하지 않고 보관한 객체를 돌려준다.

이 속성이 Factory 역할을 한다. Forest 에셋에 몇 번을 요청해도 같은 TerrainType 하나가 돌아온다. Validate는 에셋의 값을 검사하는 메서드이며 이 자료에서는 다루지 않는다.

실제 발췌: TileData.cs · RuntimeTerrain (속성 위의 영문 주석 생략)

실제 코드 · MapData

셀 배열은 어느 셀이 어느 지형인지만 기억한다

[SerializeField] private TileData[] _cells = new TileData[120];

public TileData GetTile(Vector2Int cell)
{
    // 축약: 좌표 범위를 검사하는 예외 처리는 생략했다.
    return _cells[(_height - 1 - cell.y) * _width + cell.x];
}

원소는 복사본이 아니라 참조다

원소 120개는 각각 네 TileData 에셋 중 하나를 가리킨다. new TileData[120]은 참조를 담을 자리 120개를 만들 뿐이며 TileData 객체를 만들지 않는다.

GetTile

셀 좌표를 받아 그 셀이 참조하는 TileData 에셋을 돌려준다. 대괄호 안의 식은 좌표를 배열의 위치로 바꾸는 계산이며 이 자료에서는 다루지 않는다.

MapData에는 이름, 비용, 통행 여부가 없다. 외재 상태인 배치만 보관한다.

실제 발췌: MapData.cs · _cells, GetTile (Tooltip 특성, Width·Height, Validate, 범위 검사 생략)

실제 코드 · MapLoader

Client는 공유 객체를 새로 만들지 않고 참조를 받아서 넣는다

// 축약: null 검사와 mapData.Validate() 호출은 생략했다.
var cells = new Dictionary<Vector2Int, TerrainType>();
for (int y = 0; y < mapData.Height; y++)
for (int x = 0; x < mapData.Width; x++)
{
    var cell = new Vector2Int(x, y);
    cells.Add(cell, mapData.GetTile(cell).RuntimeTerrain);
}
return new Board(cells);

new가 만드는 것

이 코드의 new는 Dictionary, 좌표 값, Board를 만든다. new TerrainType은 없다. 셀의 에셋을 찾고, 그 에셋의 RuntimeTerrain이 돌려준 참조를 그대로 넣는다.

안쪽 문장은 12×10=120번 실행되므로 항목 120개가 들어간다. RuntimeTerrain은 120번 요청되지만, 지도를 처음 읽을 때 new TerrainType은 에셋마다 한 번씩 모두 4번만 실행된다.

실제 발췌: MapLoader.cs · Load의 본문 (null 검사와 Validate 호출 생략, 주석 추가)

실제 코드 · Board

Board는 셀 좌표로 공유 객체를 찾아 준다

private readonly
    Dictionary<Vector2Int, TerrainType> _cells;

public TerrainType GetTerrain(Vector2Int cell)
{
    return _cells[cell];
}

Dictionary란?

키로 값을 찾는 자료구조다. 여기에서 키는 셀 좌표인 Vector2Int이고 값은 TerrainType 참조다.

GetTerrain(new Vector2Int(5, 4))와 GetTerrain(new Vector2Int(5, 5))는 같은 숲 객체를 돌려준다. 두 항목의 키는 다르지만 값이 가리키는 객체는 하나다.

실제 발췌: Board.cs · _cells, GetTerrain (생성자, Cells, Contains 생략, 필드 선언 줄바꿈 조정)

수치 확인

항목은 120개이고 객체는 4개다

TerrainType 객체를 만든 에셋이 객체를 참조하는 항목객체
Plain · 평지92개1개
Forest · 숲15개1개
Mountain · 산5개1개
River · 강8개1개
합계92+15+5+8 = 120개4개

“Board에 TerrainType 객체가 몇 개 들어 있는가?”라는 질문의 답은 “항목은 120개이고 객체는 4개다.”이다. 첫 시도의 구조에는 규칙 120벌이 필요했다. 지금은 규칙 4벌과 참조 120개가 있다.

실제 값: Maps/map01.asset의 Cells 120개를 에셋별로 센 결과. Board.Cells의 항목 수는 120이고, 값에서 서로 다른 객체를 세면 4다.

// 축약: 통행 여부를 확인하는 문장은 생략했다.

이 두 문장은 이동 범위를 계산하는 코드의 일부다. costs[current]는 지금 셀까지 쓴 비용이고, 여기에 다음 셀의 이동 비용을 더한다. 읽는 쪽은 그 객체를 몇 개의 셀이 함께 쓰는지 알 필요가 없다.

수치 추적

숲 에셋의 비용을 4로 바꾸면 모든 숲이 함께 바뀐다

조건: Play를 멈춘 상태에서 Forest.asset의 이동 비용만 2에서 4로 고치고 다시 실행한다. 세 경우 모두 지금 셀까지 쓴 비용 costs[current]가 1이라고 가정한다.

다음 셀 next참조하는 공유 객체변경 전 candidateCost변경 후 candidateCost
(5,4) 숲Forest 에셋의 TerrainType1+2 = 31+4 = 5
(5,5) 숲Forest 에셋의 TerrainType1+2 = 31+4 = 5
(4,4) 평지Plain 에셋의 TerrainType1+1 = 21+1 = 2

고친 곳은 에셋 한 곳이다. 코드와 MapData는 바꾸지 않았다. 다시 실행하면 Forest 에셋이 비용 4인 TerrainType을 하나 만들고 숲 15칸이 모두 그 객체를 읽는다. 실행 중에는 Board가 이미 만들어진 객체를 참조하고 있으므로, 값을 고친 뒤에는 다시 실행해서 확인한다.

예측과 답

숲 한 칸만 바꾸고 싶다면 무엇을 고쳐야 할까?

셀 (5,4)의 숲만 비용 4로 만들고 싶다.
답: 에셋의 값이 아니라 그 셀의 참조를 바꾼다.

에셋의 값을 바꾸는 경우

Forest의 비용을 4로 바꾸면 숲 15칸이 모두 4가 된다. 공유되는 상태를 고쳤기 때문이다.

셀의 참조를 바꾸는 경우

비용 4인 TileData 에셋을 하나 더 만들고 MapData에서 (5,4)의 항목이 그 에셋을 가리키게 한다. 새 에셋이 TerrainType을 하나 만들므로 항목은 120개 그대로이고 객체는 5개가 되며, 숲 객체를 참조하는 항목은 14개가 된다.

“모든 숲의 규칙”은 공유되는 상태이고 “이 셀이 어느 지형인가”는 공유되지 않는 상태다. 바꾸려는 것이 어느 쪽인지 먼저 판단한다.

반례 · 설계 비교용 가상 코드

셀마다 new로 객체를 만들면 공유가 사라진다

// 설계 비교용 가상 코드: 잘못 작성한 MapLoader
var cell = new Vector2Int(x, y);
TileData tile = mapData.GetTile(cell);
cells.Add(cell, new TerrainType(
    tile.DisplayName, tile.MovementCost, tile.IsWalkable));

무엇이 달라지는가

이 문장은 120번 실행되므로 TerrainType 객체가 120개 생긴다. 숲 15칸은 내용이 같은 객체 15개를 하나씩 따로 참조한다.

이동 비용의 계산 결과는 달라지지 않는다. 그러나 같은 규칙이 다시 120벌 저장되므로 첫 시도의 구조로 돌아간다. 올바른 코드는 RuntimeTerrain이 돌려준 참조를 그대로 넣는다. 이 속성은 에셋마다 객체를 한 번만 만들기 때문이다.

공유가 사라지는 경우를 보이기 위한 가상 코드다. 현재 MapLoader의 구현이 아니며, TileData가 세 값을 속성으로 공개한다고 가정했다.

실제 코드 · TerrainTypes

정적 필드로도 공유 객체를 한 번만 만들 수 있다

public static class TerrainTypes
{
    public static readonly TerrainType Plain = new TerrainType("평지", 1, true);
    public static readonly TerrainType Forest = new TerrainType("숲", 2, true);
    public static readonly TerrainType Mountain = new TerrainType("산", 3, true);
    public static readonly TerrainType River = new TerrainType("강", 1, false);
}

static readonly

정적 필드는 프로그램에 하나만 존재하고 readonly 필드는 다른 객체로 바꿀 수 없다. 따라서 TerrainTypes.Forest는 어디에서 읽어도 같은 객체다.

사용하는 곳

글자로 적은 지도를 읽는 MapLoader.Parse가 기호 P, F, M, R을 이 네 객체에 대응시킨다. 값을 코드에 적으므로 값을 바꾸려면 코드를 고쳐야 한다.

실제 지도인 map01은 에셋의 RuntimeTerrain을 사용한다. TerrainTypes.Forest와 Forest 에셋이 만든 TerrainType은 값이 같아도 서로 다른 객체이므로 같은 참조라고 가정하지 않는다.

공유할 수 없는 값 · 가상 설계

셀마다 달라지는 값은 공유 객체에 넣지 않는다

공유 객체에 넣은 경우

TerrainType에 “불타는 중인지 여부”를 바꿀 수 있는 값으로 넣고 셀 (5,4)에 불을 붙이면, 같은 객체를 참조하는 숲 15칸이 모두 불타는 중이 된다.

셀 쪽에 둔 경우

불타는 중인지 여부는 셀마다 다르므로 외재 상태다. 셀 좌표를 기준으로 따로 보관한다.

// 설계 비교용 가상 코드
HashSet<Vector2Int> burningCells;

기준은 앞에서 정한 질문과 같다. “이 값은 같은 지형의 모든 셀에서 항상 같은가?” 불타는 중인지 여부는 그렇지 않으므로 공유 객체에 넣을 수 없다. 현재 프로젝트에는 이 기능이 없으며 기준을 설명하기 위한 예시다.

대가와 적용 기준

Flyweight에도 대가가 있다

유용한 조건

  • 같은 값을 가진 객체가 수십 개 이상 반복된다.
  • 그 값이 실행 중에 바뀌지 않는다.
  • 공유되는 값과 셀마다 다른 값을 분명하게 나눌 수 있다.

치러야 하는 대가

  • 값을 읽을 때 참조를 한 번 거쳐야 한다.
  • 공유 객체를 읽기 전용으로 관리해야 한다.
  • 셀마다 다른 값은 다른 곳에 보관해야 한다.
  • 참조 120개는 여전히 필요하므로 메모리가 30분의 1로 줄지는 않는다.

이득은 메모리 절약만이 아니다. 규칙이 한곳에 있으므로 한 번의 수정이 그 지형의 모든 셀에 똑같이 적용된다. 셀이 몇 개뿐이라면 첫 시도의 구조가 더 읽기 쉬울 수 있다.

가져갈 핵심

같은 규칙은 한 번만 만들고 셀은 참조만 가진다

  1. Flyweight는 많은 객체가 똑같이 갖는 변하지 않는 데이터를 하나의 공유 객체로 분리한다.
  2. 공유되는 상태는 TerrainType에 두고, 공유되지 않는 상태인 배치는 MapData에 둔다.
  3. TileData.RuntimeTerrain은 에셋 하나당 TerrainType을 하나만 만들고, MapLoader와 Board는 그 참조를 그대로 전달한다.
  4. 공유 객체는 읽기 전용으로 공개하고, 셀마다 달라지는 값은 넣지 않는다.
