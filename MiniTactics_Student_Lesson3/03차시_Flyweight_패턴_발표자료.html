Mini Tactics · Lesson 03

미니 택틱스로 이해하는
Flyweight 패턴

120개의 좌표가 같은 규칙을 쓴다면
규칙도 120번 따로 가져야 할까?

함께 쓰는 규칙과 칸마다 다른 위치를 나눈다.

A Small Success

그림은 달라도 같은 규칙으로 다룰 수 있었다

이전의 작은 출발

2차시의 전장에는 이미 서로 다른 지형 그림이 있다. 이동 판단은 지형별 규칙을 구분하지 않는다.

이제 묻는 설계 문제

숲 여러 칸에 같은 이름·비용·통행 규칙을 연결하려면, 반복되는 정보를 어디에 둘까?

그림이 여러 개라는 사실만으로 Flyweight는 아니다. 여러 위치가 같은 규칙 객체를 함께 참조하는지가 핵심이다.

Repeated Rules

같은 숲 규칙이 여러 좌표에 반복된다

지형 규칙 에셋참조하는 칸비용 / 통행
Plain · 평지921 / 가능
Forest · 숲152 / 가능
Mountain · 산53 / 가능
River · 강81 / 불가

검증된 지도는 12 × 10 = 120칸이다. 92 + 15 + 5 + 8 = 120. 강의 비용 값이 1이어도 IsWalkable이 false이므로 통행 가능한 지형이라는 뜻은 아니다.

First Attempt

규칙을 칸마다 복사하면 단순하다

설계 비교용 가상 코드 — 현재 구현에 없는 복사 방식

class CellRules
{
    public string Name;
    public int Cost;
    public bool Walkable;
}
var a = new CellRules { Name = "숲", Cost = 2, Walkable = true };
var b = new CellRules { Name = "숲", Cost = 2, Walkable = true };

a와 b는 값이 같아도 별도 객체다. 칸마다 규칙이 모두 다르거나 독립적으로 자주 바뀌는 작은 자료라면 이 방식이 충분할 수 있다.

A Limited Solution

복사한 규칙은 따로 바뀔 수 있다

설계 비교용 가상 코드 — 현재 구현에 없는 복사 방식

a.Cost = 3;
// a.Cost는 3, b.Cost는 여전히 2

의도가 독립 변경이라면

올바른 결과다. 두 칸의 상태를 별도로 보관한 것이다.

의도가 모든 숲의 규칙 변경이라면

나머지 복사본도 찾아 고쳐야 한다. 하나를 빠뜨리면 같은 숲의 규칙이 달라진다.

이는 가상 복사 방식의 한계다. 현재 Teacher가 규칙을 칸마다 복제한다는 설명이 아니다.

Responsibility Boundary

같은 규칙과 서로 다른 위치를 분리한다

구분뜻이 사례
내재 상태 · intrinsic여러 사용자가 함께 쓸 정보이름, 진입 비용, 통행 여부, Tile 참조
외재 상태 · extrinsic사용하는 맥락마다 다른 정보각 칸의 좌표, 지도 안 배치

두 숲 칸은 같은 규칙을 쓸 수 있지만 같은 위치가 될 수는 없다. 공유 데이터 안에 특정 칸의 좌표를 넣으면 이 경계가 무너진다.

Flyweight

Flyweight는 반복되는 내재 상태를 공유한다

같은 규칙 객체를 여러 맥락에서 사용하고,
맥락마다 다른 상태는 바깥에 둔다.

공유하는 것

Forest TileData 에셋 하나에 숲의 공통 규칙을 둔다.

각각 남기는 것

(5,4), (5,5)처럼 좌표별 항목과 그 에셋을 가리키는 참조는 계속 필요하다.

Roles

실제 구조의 역할은 네 곳에서 보인다

공유 규칙TileData
내재 상태를 보관
배치 데이터MapData
각 위치의 참조 보관
참조 전달MapLoader
좌표와 참조를 연결
조회 맥락Board
좌표별 규칙 조회

이 구현은 미리 작성된 에셋 참조를 직접 전달한다. 같은 값을 찾아 자동 통합하는 전역 저장소나 별도의 생성 공장을 두지 않는다.

Intrinsic Data

TileData에는 공유할 규칙을 모은다

[SerializeField] private string _displayName = "평지";
[SerializeField, Min(1)] private int _movementCost = 1;
[SerializeField] private bool _isWalkable = true;
[SerializeField] private TileBase _tile;

TileBase는 화면에 쓸 Tile의 참조다. 좌표나 칸마다 다른 방문 여부는 없다. 규칙 객체가 그림의 모든 픽셀을 직접 보관한다는 뜻도 아니다.

Read Access

프로퍼티로 읽는 것과 불변은 다르다

public string DisplayName => _displayName;
public int MovementCost => _movementCost;
public bool IsWalkable => _isWalkable;
public TileBase Tile => _tile;

이 코드가 하는 일

런타임 소비자는 현재 에셋의 필드를 읽는다. 여기에는 값 복사본을 만드는 단계가 없다.

보장하지 않는 것

대입용 프로퍼티가 없다고 에셋 전체가 불변이 되지는 않는다. 제작 데이터가 바뀌면 이후 조회 값도 달라진다.

Placement

MapData의 칸에는 TileData 참조가 들어간다

[SerializeField] private TileData[] _cells = new TileData[120];

현재 실제 코드 발췌 · Teacher3 ba1b9b6 · MapData.cs · 배열 필드 한 줄; 크기·검증·조회 생략

현재 지도는 120개 항목을 가진다. 배열의 칸 하나는 TileData 전체를 복제하지 않고 해당 에셋을 가리킨다. 같은 Forest 참조가 여러 항목에 들어갈 수 있다.

Coordinate Lookup

좌표는 배열에서 참조를 고르는 맥락이다

return _cells[(_height - 1 - cell.y) * _width + cell.x];

현재 실제 코드 발췌 · Teacher3 ba1b9b6 · MapData.cs · GetTile의 반환문; 앞의 범위 검사 생략

좌표 · 너비 12, 높이 10배열 인덱스반환 참조
(5,4)(10 − 1 − 4) × 12 + 5 = 65Forest
(5,5)(10 − 1 − 5) × 12 + 5 = 53같은 Forest

배열은 위쪽 행부터 저장한다. 두 인덱스는 달라도 그 안의 참조 대상은 같다. 좌표와 규칙을 한 객체라고 혼동하지 않는다.

Reference Transfer

MapLoader는 참조를 좌표별 항목에 넣는다

var cells = new Dictionary<Vector2Int, TileData>();
for (int y = 0; y < mapData.Height; y++)
for (int x = 0; x < mapData.Width; x++)
{
    var cell = new Vector2Int(x, y);
    cells.Add(cell, mapData.GetTile(cell));
}
return new Board(cells);

GetTile이 돌려준 TileData를 그대로 Add한다. 새 딕셔너리와 좌표 항목은 만들지만, 이 구간에서 TileData를 생성하거나 복제하지 않는다.

Container Copy

Board는 딕셔너리 항목을 복사한다

public Board(IReadOnlyDictionary<Vector2Int, TileData> cells)
{
    _cells = new Dictionary<Vector2Int, TileData>(cells);
}

새로 생기는 것

Board가 소유하는 별도 딕셔너리 컨테이너와 그 항목이다.

계속 공유되는 것

항목의 TileData 참조 대상이다. 생성자 호출이 각 지형 규칙을 깊은 복사하는 것은 아니다.

Read by Coordinate

다른 키로 조회해도 같은 규칙을 받을 수 있다

public IReadOnlyDictionary<Vector2Int, TileData> Cells => _cells;
public bool Contains(Vector2Int cell) => _cells.ContainsKey(cell);
public TileData GetTile(Vector2Int cell) => _cells[cell];

Board의 키는 Vector2Int 좌표, 값은 TileData 참조다. Contains는 키 존재 여부, GetTile은 해당 키의 참조를 반환한다. 두 숲 칸의 키는 별도로 유지된다.

Identity Check

같은 값이면 같은 객체일까?

상황값 비교참조 대상
두 칸이 같은 Forest를 가리킴이름·비용 같음같은 에셋
Forest와 별도 ForestCopy 에셋이름·비용을 같게 만들 수 있음서로 다른 에셋

답: 같은 값만으로 동일성을 알 수 없다. 현재 로더는 값을 비교해 에셋을 하나로 합치지 않는다. ForestCopy는 이해를 위한 가상 별도 에셋이며 배포 지도에는 없다.

Shared Change

공유 규칙 변경은 모든 참조의 읽기에 영향을 준다

설명용 가정 · 실제 데이터는 변경하지 않음(5,4)의 이후 비용 조회(5,5)의 이후 비용 조회
Forest 비용이 2일 때22
같은 Forest의 제작 값을 3으로 바꾸면33

이 지도에서 Forest를 가리키는 15칸 모두 이후 같은 값을 읽는다. 이미 계산해 둔 결과나 화면이 자동으로 재계산·다시 그려진다는 보장은 아니다. 배포된 Forest 비용은 2다.

One Cell Variation

한 칸만 다르게 만들려면 경계를 다시 고른다

새로운 공통 규칙이라면

별도 규칙 에셋을 만들고 그 칸의 참조만 바꾸는 설계를 선택할 수 있다. 다른 Forest 칸은 원래 참조를 유지한다.

그 칸의 일시 상태라면

불, 점유, 방문 여부처럼 위치에 속하는 정보는 좌표별 외재 상태에 둔다. 이들은 개념 비교이며 현재 추가 API가 아니다.

한 칸만 바꾸려다 공통 Forest 자체를 바꾸면 모든 사용자가 영향을 받는다. 무엇을 공유하는지와 누가 변경할 수 있는지를 함께 정해야 한다.

Ownership

공유 데이터의 변경 주체를 분명히 한다

정보둘 곳과 이유
지형 이름·비용·통행·TileTileData · 같은 규칙을 공유
지도 좌표와 어떤 규칙을 쓰는지MapData / Board의 좌표별 항목
유닛의 이동 예산유닛별 상태 · 서로 다를 수 있음
탐색 비용·이전 칸, 칸별 일시 상태각 계산 / 좌표별 맥락 · 공통 지형 규칙 아님

런타임은 작성된 규칙을 읽는다. 공유 객체를 변경하는 기능을 설계한다면 변경 권한과 재계산 시점을 별도로 정해야 한다.

Count Carefully

120개 항목과 4종 규칙을 구분한다

관찰한 수정확한 의미
120지도 좌표 수, MapData 참조 항목 수, Board 항목 수
4이 지도가 참조하는 서로 다른 TileData 에셋 수
15Forest를 가리키는 칸 수

게임 전체 객체가 4개라는 뜻이 아니다. 배열·딕셔너리·좌표·참조, Unity 객체와 Tile·Sprite 등은 계속 존재한다. 규칙의 반복 보관을 줄이는 구조를 확인한 것이다.

Measured and Unmeasured

구조의 이득과 성능 수치를 구분한다

확인한 사실

120개의 칸 항목이 4개의 TileData 에셋을 참조한다. 숲의 공통 규칙을 한곳에서 관리한다.

아직 측정하지 않은 것

총 메모리 바이트, 할당량과 FPS 차이다. 항목 수를 나눠 전체 메모리가 30배 줄었다고 말할 수 없다.

실제 절약량은 공유하는 데이터 크기와 참조·컨테이너 비용에 달려 있다. 성능 판단에는 같은 조건에서 별도 측정이 필요하다.

Costs and Judgment

반복과 독립 변경의 비중을 보고 선택한다

유용한 조건

많은 사용자가 적은 종류의 큰 공통 데이터를 반복 사용한다. 맥락별 상태를 바깥으로 나눌 수 있다.

늘어나는 비용

참조 연결과 데이터 수명 관리가 필요하다. 공유 값의 변경 범위가 넓어지고, 외재 상태를 별도로 전달·조회해야 한다.

값이 거의 모두 다르거나 각 사용자가 자주 독립 변경한다면 공유 이득이 작다. 단순 복사 구조가 더 읽기 쉬운 경우도 있다.
