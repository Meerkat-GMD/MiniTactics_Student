03차시 · 이동 규칙의 변화

같은 두 칸 이동도 지형에 따라 가격이 달라집니다

MiniTactics의 유닛은 이제 칸 수만 보고 움직일 수 없습니다. 평지 두 칸은 비용 2지만 숲 두 칸은 비용 4입니다. 이동 예산은 한 번의 이동에서 지불할 수 있는 총비용의 상한입니다.

입력: 이동 예산 3진입 비용 합계결과
평지 → 평지1 + 1 = 2이동 가능
숲 → 숲2 + 2 = 4예산 초과

이를 설명하려면 두 문제를 풀어야 합니다. 먼저 여러 칸이 같은 지형 규칙을 어떻게 함께 쓰는지 살펴보고, 그 규칙을 읽어 가장 싼 경로와 이동 범위를 구하는 과정을 따라갑니다.

03차시 · 참조와 Flyweight

두 좌표가 하나의 숲 객체를 가리키게 합니다

참조는 객체를 복사한 내용이 아니라 객체를 가리키는 연결입니다. 아래에서 Board의 두 항목은 각각 남아 있지만 오른쪽의 숲 규칙 객체는 하나입니다. 어느 항목으로 읽어도 같은 비용 2를 얻습니다.

Board: 좌표별 항목                   공유 객체
(0,1)의 지형 참조 ───┐
                    ├──→ Forest 객체 1개
(1,1)의 지형 참조 ───┘     이름=숲 / 비용=2 / 통행=true
(0,0)의 지형 참조 ──────→ Plain 객체 1개
                          이름=평지 / 비용=1 / 통행=true

이처럼 반복되는 공통 데이터를 분리해 공유하는 방식을 Flyweight라고 부릅니다. 여기서 공유되는 것은 지형의 규칙입니다. 서로 다른 좌표나 유닛, 화면의 타일 그림까지 하나로 합쳐지는 것은 아닙니다.

03차시 · 참조를 코드로 읽기

같은 값을 두 번 생성한 것과 같은 참조는 다릅니다

아래는 참조를 보여 주기 위한 축약 예시입니다. a와 b에 기존 Forest를 대입하면 두 변수는 하나의 객체를 가리킵니다. c에서는 new가 별도의 객체를 생성하므로 내용이 같아도 같은 객체가 아닙니다.

var a = TerrainTypes.Forest;
var b = TerrainTypes.Forest;
var c = new TerrainType("숲", 2, true);
ReferenceEquals(a, b); // true
ReferenceEquals(a, c); // false

ReferenceEquals는 두 연결이 동일한 객체에 닿는지 묻습니다. 첫 결과는 true이고 두 번째는 false입니다. Flyweight를 적용하려면 이름과 비용을 같게 만드는 데서 끝내지 않고 이미 만들어 둔 객체를 재사용해야 합니다.

03차시 · 공유와 불변

공유 객체를 바꾸면 읽는 모든 칸이 영향을 받습니다

가령 Forest의 비용을 어디서든 9로 바꿀 수 있다면 한 셀의 처리 코드가 전체 숲의 이동 규칙을 바꾸게 됩니다. 같은 객체를 함께 읽는 장점이 있으므로 그 내용을 누가 바꾸는지도 제한해야 합니다.

// 실제 TerrainType의 속성 선언
public string Name { get; }
public int MovementCost { get; }
public bool IsWalkable { get; }

실제 TerrainType은 생성자에서 값을 정하고 읽기 전용 속성으로 공개합니다. get만 있고 set이 없어서 외부에서 비용을 다시 대입할 수 없습니다. 이름 없는 지형이나 0 이하 비용도 생성자에서 거부합니다.

03차시 · C# 선언의 의미

static은 공유 위치를, readonly는 재대입 제한을 뜻합니다

static 필드는 개별 Board마다 생기는 필드가 아니라 클래스에 속합니다. 그래서 TerrainTypes.Forest처럼 클래스 이름으로 접근합니다. readonly는 초기화한 필드를 다른 객체로 다시 바꾸는 것을 제한합니다.

// 실제 선언: 줄바꿈만 조정
public static readonly TerrainType Forest =
    new TerrainType("숲", 2, true);

readonly만으로 객체 내부까지 불변이 되는 것은 아닙니다. 이 프로젝트는 readonly 필드와 get 전용 속성을 함께 씁니다. 전자는 공유 참조를 고정하고 후자는 지형 규칙의 외부 수정을 막는 역할입니다.

TerrainTypes에는 아래 네 공유 객체가 있습니다. 비용은 다음 셀에 들어갈 때 지불하는 수치이고 IsWalkable은 그 셀을 통과할 수 있는지 나타내는 참·거짓 값입니다. 탐색은 통행 여부를 먼저 확인합니다.

공유 객체이름진입 비용통행
Plain평지1가능
Forest숲2가능

강에 저장된 비용 1은 건널 수 있다는 뜻이 아닙니다. 통행 불가를 비용 999처럼 표현하면 예산이 충분한 유닛이 건널 수 있습니다. 별도 통행 규칙을 두면 예산과 무관하게 강 진입을 거부할 수 있습니다.

03차시 · 지도 모델

Board는 좌표를 주면 지형 참조를 돌려주는 모델입니다

모델은 화면 그림과 독립적으로 게임의 데이터를 표현합니다. Board는 Dictionary라는 사전에 좌표와 지형 참조를 연결합니다. 키인 Vector2Int는 정수 x, y 한 쌍이고 값인 TerrainType은 지형 객체입니다.

// 타입 읽기 예시: 키는 좌표, 값은 지형 참조
Dictionary<Vector2Int, TerrainType> cells;
// 개념 예시: 존재하는 좌표에서만 규칙 조회
if (board.Contains(cell))
    terrain = board.GetTerrain(cell);

Contains는 좌표가 존재하는지, GetTerrain은 그 위치의 지형이 무엇인지 묻습니다. 지도 밖에는 조회할 항목이 없으므로 존재 여부를 먼저 검사합니다. Board 자체는 타일을 그리거나 유닛을 움직이지 않습니다.

03차시 · 셀과 객체의 개수

사전을 복사해도 그 안의 지형은 계속 공유합니다

Board 생성자는 전달받은 사전을 복사하여 자신의 좌표별 항목을 보관합니다. 그러나 각 항목이 가리키는 TerrainType 객체까지 새로 만들지는 않습니다. 바깥 사전 항목을 교체해도 Board의 항목은 그대로 남습니다.

원본 사전 (0,1) ───┐
                   ├──→ 동일한 Forest 객체
Board 사전 (0,1) ──┘

복사됨: 좌표와 참조를 연결한 사전 항목
복제되지 않음: 항목이 가리키는 지형 객체

120칸 지도라면 좌표별 항목은 여전히 120개입니다. 같은 네 종류를 쓴다면 규칙 객체 네 개를 공유할 수 있다는 뜻이지 지도 전체 메모리가 정확히 30분의 1이라는 뜻은 아닙니다. 좌표와 화면 객체는 별도로 필요합니다.

03차시 · 이동 비용의 정의

출발 칸은 0, 새로 들어가는 칸부터 비용을 냅니다

탐색에서 누적 비용은 출발 이후 지금까지 들어간 지형들의 비용 합입니다. 시작 칸은 이미 서 있는 곳이므로 비용 0으로 등록합니다. 출발점이 숲이어도 숲 비용을 먼저 청구하지 않습니다.

경로 입력계산예산 4에서
시작 숲 → 평지0 + 1 = 1허용
시작 → 산 → 평지0 + 3 + 1 = 4허용
시작 → 숲 → 산0 + 2 + 3 = 5거부

예산 4에서 산과 평지를 차례로 밟으면 3+1=4여서 허용됩니다. 다음 평지까지 가면 5가 되어 거부됩니다. 이동 횟수가 적은지보다 경로의 진입 비용 합이 예산 이하인지가 판단 기준입니다.

지형 탐색의 기준

출발에서 얼마를 지불했는가?

하지만 숲이 섞이면 같은 두 번의 이동도 비용이 달라집니다. 처음 발견했다는 이유만으로 방문을 끝내면 싼 경로를 놓칠 수 있습니다. 이번 탐색은 발견 순서 대신 지금까지의 누적 비용으로 다음 조사 대상을 고릅니다.

03차시 · 예시 B · 가중치 지도

같은 목표로 가는 두 길을 숫자로 비교합니다

앞서 해석한 2×2 지도를 사용합니다. 출발 S=(0,0), 목표 T=(1,1), 예산은 3이며 상하좌우로만 이동합니다. A는 숲, B와 T는 평지입니다. 아래 숫자는 각 칸에 들어가는 비용입니다.

y=1    A:숲 2        T:평지 1
       (0,1)         (1,1)

y=0    S:출발 0      B:평지 1
       (0,0)         (1,0)
입력 예산=3 / 대각선 이동 없음

위로 먼저 가면 S→A→T의 비용은 2+1=3입니다. 오른쪽으로 먼저 가면 S→B→T의 비용은 1+1=2입니다. 둘 다 두 번 이동하지만 싼 길은 B를 거칩니다. 이제 이 결론을 코드가 얻는 과정을 보겠습니다.

03차시 · 후보 선택의 이유

다익스트라는 가장 싼 후보의 이웃부터 조사합니다

후보는 발견했지만 아직 이웃을 조사하지 않은 좌표입니다. 다익스트라는 이 후보 중 누적 비용이 가장 작은 곳을 먼저 꺼냅니다. 이웃을 조사하여 새 도달 비용을 계산하는 과정을 확장이라고 부릅니다.

예: 후보 B의 비용 1, A의 비용 2 → 먼저 B 확장 → B의 이웃에 들어갈 비용을 더해 비교

현재 지형 비용은 모두 양수이므로 경로를 더 이어도 비용이 줄지 않습니다. 이 성질 덕분에 싼 후보부터 확장하는 방식이 맞습니다. 예산을 이미 넘긴 경로 역시 더 진행해 예산 안으로 돌아올 수 없습니다.

같은 좌표라도 세 기록의 질문이 다릅니다. frontier에서 제거해도 가격과 경로 정보는 필요하므로 costs와 previous에서는 지우지 않습니다. 비용만 저장하면 경로 순서를 잃고, 이전 위치만 저장하면 가격을 비교할 수 없습니다.

03차시 · 예시 B · 초기 상태

초기에는 출발점 하나만 후보에 넣습니다

아직 어떤 길도 걸어 보지 않았으므로 S의 비용은 0입니다. S를 후보 집합에 넣고 previous는 비워 둡니다. 출발점 이전의 위치는 없기 때문에 S의 이전 셀을 억지로 만들 필요가 없습니다.

처리 시점frontiercostsprevious
시작 전{S}S:0없음
S를 꺼낸 직후{}S:0없음

다음 단계에서는 후보 S를 꺼내 상하좌우 이웃을 봅니다. 지도 밖의 아래와 왼쪽은 제외하고, 지도 안에 있는 A와 B의 지형 비용을 읽습니다. 대각선 T는 S의 직접 이웃이 아닙니다.

S에서 A로 들어갈 후보 비용은 0+2=2이고 B는 0+1=1입니다. 둘 다 예산 3 이내이며 아직 기록이 없으므로 costs에 저장합니다. 두 곳의 직전 위치는 모두 S입니다.

S 확장 후A=(0,1)B=(1,0)
costs21
previousSS
frontierA 포함B 포함 · 다음 선택

실제 이웃 조사 순서는 위·오른쪽·아래·왼쪽이지만 다음 선택은 이 순서를 따르지 않습니다. A를 먼저 발견했어도 비용 1인 B가 비용 2인 A보다 먼저 확장됩니다. 여기가 단순한 발견 순서와 다른 핵심입니다.

03차시 · 예시 B · 싼 후보 선택

B를 먼저 확장하여 목표 비용 2를 찾습니다

B를 frontier에서 꺼내도 costs[B]=1은 유지됩니다. 위쪽 T는 평지이므로 후보 비용은 1+1=2입니다. 아직 T의 기록이 없어서 비용 2와 previous[T]=B를 저장하고 T를 새 후보로 넣습니다.

B 확장 후내용
frontier: 후보 좌표{A, T} · 비용은 costs에서 조회: A=2, T=2
costsS:0, B:1, A:2, T:2
previousA←S, B←S, T←B

B에서 왼쪽 S로 돌아가면 후보 비용은 1+1=2입니다. 이미 아는 S의 비용 0보다 비싸므로 이 기록은 버립니다. 되돌아오는 길을 매번 새로 등록하지 않아 같은 셀 사이를 끝없이 오가지 않습니다.

03차시 · 예시 B · 기존 기록 비교

A에서 찾은 비용 3은 기존 비용 2를 덮지 않습니다

A와 T는 비용 2로 동점입니다. 여기서는 A를 먼저 꺼내는 한 가지 순서를 보여 줍니다. A에서 T에 들어가는 후보 비용 2+1=3은 예산 안이지만 기존 T의 비용 2보다 비쌉니다.

T에 도착하는 길후보 비용기존 비용판정
S→B→T2기록 없음2와 B 저장
S→A→T32기존 2와 B 유지

그래서 costs[T]=2와 previous[T]=B를 그대로 둡니다. 실제 HashSet의 동점 선택 순서는 보장되지 않아 T가 먼저 나와도 됩니다. 이 예시에서는 어느 순서든 가장 싼 목표 비용 2와 B를 거치는 경로가 같습니다.

마지막 T를 확장하면 B로 가는 후보 비용은 2+1=3으로 기존 1보다 비쌉니다. A로 가는 후보 비용은 2+2=4로 예산을 넘습니다. 새 후보가 추가되지 않으면 frontier가 비어 탐색이 끝납니다.

03차시 · 코드로 읽는 완화

비용과 이전 위치는 한 묶음으로 갱신합니다

새 후보가 기존 기록보다 더 나을 때 도달 정보를 바꾸는 일을 완화라고 부릅니다. 아래는 실제 계산식과 저장 부분의 발췌입니다. 가운데에서는 예산 초과 여부와 기존 비용보다 싼지를 검사합니다.

// 실제 소스 발췌: 중간 검사는 다음 슬라이드
int candidateCost = costs[current] + terrain.MovementCost;
// 예산과 기존 기록 검사 통과 후
costs[next] = candidateCost;
previous[next] = current;
frontier.Add(next);

candidateCost는 현재까지의 비용에 다음 지형의 비용을 더한 값입니다. 허용된 새 기록에는 비용과 이전 위치를 함께 넣습니다. 한쪽만 바꾸면 가격은 싼 경로를 가리키고 경로 목록은 다른 길을 따르는 모순이 생깁니다.

03차시 · 검사 순서의 의미

continue는 이번 이웃만 건너뛰라는 뜻입니다

각 이웃에서는 먼저 지도 안인지, 통행 가능한지 검사합니다. 그다음 누적 비용이 예산을 넘거나 이미 아는 비용 이상이면 건너뜁니다. continue는 탐색 전체를 끝내지 않고 다음 이웃의 조사로 넘어갑니다.

// 실제 조건을 축약: 중괄호 생략
if (candidateCost > budget)
    continue;
if (costs.TryGetValue(next, out int knownCost) &&
    knownCost <= candidateCost)
    continue;

TryGetValue는 next의 기록이 있는지 반환하고, out은 찾은 비용을 knownCost에 넣습니다. >이므로 예산과 같은 비용은 허용하며, <=이므로 기존과 같은 비용이면 기록을 유지합니다. 모든 동점 경로를 모으지는 않습니다.

03차시 · 예시 B · 입력 변화

예산을 줄이면 같은 지도에서도 범위가 달라집니다

지형 배치는 그대로 두고 예산만 3에서 1로 줄여 봅시다. S를 확장할 때 A의 후보 비용 2는 제외되고 B의 비용 1만 남습니다. B에서 T의 비용 2도 초과하므로 최종 범위는 S와 B입니다.

동일한 2×2 지도남는 좌표와 비용T 도달
예산 0S:0불가
예산 1S:0, B:1불가
예산 2S:0, B:1, A:2, T:2가능

예산 2라면 A와 T까지 모두 들어옵니다. 예산 0은 유효한 입력이며 출발점만 남습니다. 시작 셀 자체가 지도 밖이거나 통행 불가라면 실제 Calculate는 출발점도 넣지 않은 빈 결과를 반환합니다.

03차시 · 예시 B · 경로 역추적

previous를 따라가면 목표에서 출발로 돌아갑니다

최종 costs[T]=2는 가격만 알려 줍니다. 실제 지나갈 순서는 previous를 이용해 복원합니다. 먼저 목표 T를 목록에 넣고 previous[T]=B를 따라 B를 추가한 뒤 previous[B]=S를 따라 S를 추가합니다.

역추적 단계현재 좌표따라갈 기록모인 목록
시작Tprevious[T]=B[T]
한 번 이동Bprevious[B]=S[T, B]
출발점 도달S반복 종료[T, B, S]

출발 S에 도착하면 반복을 멈춥니다. 지금 얻은 목록은 [T, B, S]로 원하는 이동 방향의 반대입니다. 경로를 한꺼번에 저장하지 않고 각 셀의 직전 위치 하나만 저장해도 이 연결을 따라 전체 길을 찾을 수 있습니다.

03차시 · 예시 B · 복원 결과

목록을 뒤집으면 출발부터 목표까지의 경로가 됩니다

GetPathTo는 역추적 목록에 Reverse를 적용하여 [S, B, T]를 반환합니다. 좌표가 세 개여도 첫 항목은 출발점이므로 이동 횟수는 두 번입니다. 비용은 새로 들어가는 B와 T의 1+1=2입니다.

역추적 [T, B, S]→ Reverse →경로 [(0,0), (1,0), (1,1)]
좌표 3개 · 이동 2번 · 지형 비용 2

도달하지 못한 목적지는 빈 목록을 반환합니다. 도달 가능한 출발점을 목적지로 주면 [S] 하나가 나옵니다. 경로 목록, 이동 횟수, 누적 비용은 서로 다른 값이므로 화면이나 다른 기능에서 혼동하지 않아야 합니다.

03차시 · 계산 결과와 실행의 경계

복원한 경로가 자동으로 이동 애니메이션이 되지는 않습니다

MovementRangeResult는 범위와 비용을 제공하고 요청하면 경로를 복원합니다. 이 결과는 이동을 설명하는 데이터입니다. 좌표 목록을 얻었다는 사실만으로 유닛이 그 순서대로 걸어가는 동작이 생기지는 않습니다.

// 실제 MoveUnitCommand.Execute
public void Execute()
{
    _unit.MoveTo(_board, _toCell);
}

현재 MoveUnitCommand는 목적지로 MoveTo를 호출하며 Unit은 위치를 즉시 바꿉니다. 경로를 따라 시간에 걸쳐 이동하는 기능은 구현되어 있지 않습니다. 따라서 경로 계산은 맞아도 화면에서는 곧바로 도착지로 옮겨집니다.

03차시 · 지형과 점유의 구분

강은 지형 자체가 통행 불가이므로 MovementRange가 후보에서 제외합니다. 다른 유닛이 서 있는 평지는 지형 비용이 그대로 1입니다. Lesson3의 탐색은 유닛 점유를 입력받지 않으므로 그 칸도 비용 범위에 포함될 수 있습니다.

BoardView.CanMoveTo가 다른 유닛이 있는 최종 목적지를 거부합니다. 따라서 현재 규칙에서는 점유 칸을 경유한 비용 계산이 가능하며, 점유를 경로 전체의 장애물로 처리하지는 않습니다. 빨간 표시와 강을 같은 의미로 읽으면 안 됩니다.

03차시 · 화면에서 읽는 규칙

RangeHighlighter는 ReachableCells를 읽고 각 좌표에 다른 유닛이 있는지 BoardView에 묻습니다. 비용으로 도달 가능한 셀에 점유 정보를 덧붙이면 표시 담당이 빈 칸은 초록, 점유 칸은 빨강으로 그립니다.

03차시 · 예시 C · 이동과 이력

성공한 이동만 기록되어 Undo의 의미가 유지됩니다

가상의 빈 평지에서 S→B 이동 후 B→T 이동에 성공했다고 합시다. 이력에는 출발·도착 좌표를 기억하는 명령 두 개가 쌓입니다. Undo 한 번은 가장 최근 B→T를 꺼내 B로, 두 번은 S로 돌려보냅니다.

입력 순서유닛 위치이력: 오래된 것 → 최근
S→B 성공B[S→B]
강 클릭 실패B[S→B]
B→T 성공T[S→B, B→T]
Undo 한 번B[S→B]

중간에 강이나 점유 목적지를 눌러 실패했다면 명령을 만들지 않으므로 이력이 늘지 않습니다. Undo는 탐색을 거꾸로 수행하는 알고리즘이 아니라 명령에 저장된 출발 좌표를 사용하는 동작입니다.

공유 지형은 반복되는 규칙을 한곳에 모으고, 지도 모델은 그림 없이 비용을 읽게 합니다. 다익스트라는 지형별 비용을 비교하고 previous는 그 결과를 경로로 설명합니다. 각 장치는 서로 다른 문제를 해결합니다.

어떤 길로 왔는가?previous → GetPathTo

현재 후보 선택은 HashSet을 매번 훑어 최저 비용을 찾습니다. 큰 지도에서는 우선순위 큐 같은 개선을 고려할 수 있지만, 이번 구현이 그것을 사용하지는 않습니다. 점유 경유 제한과 경로 애니메이션도 별도 설계가 필요한 부분입니다.
