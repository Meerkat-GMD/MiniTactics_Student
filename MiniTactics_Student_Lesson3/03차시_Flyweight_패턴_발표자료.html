이전 차시의 성공

2강에서는 이동을 기록하고 되돌렸다

  • 선택한 유닛을 유효한 목적지로 이동한다.
  • 명령은 출발 셀과 도착 셀을 기억한다.
  • 이동 이력에서 최근 명령을 꺼내 Undo한다.

잘 해결한 문제

Command는 이동 한 건을 실행하고 복원하는 방법을 묶었다. 지형별 가격이 같을 때는 칸 수로 이동 범위를 정해도 충분했다.

오늘은 이동 기록 앞에 있는 질문, “이 목적지까지 갈 수 있는가?”가 더 복잡해진다.

새 요구

숲과 산은 더 비싸고 강은 막힌다

“평지는 1, 숲은 2, 산은 3만큼 쓰게 해 주세요.
강은 건널 수 없어야 해요.”

이동 예산은 한 번의 이동에 쓸 수 있는 총비용의 상한이다. 예산 3이면 평지 두 칸은 1+1=2로 가능하지만, 숲 두 칸은 2+2=4라서 불가능하다.

관찰

지도에는 같은 규칙이 계속 등장한다

숲 (0,1)
이름: 숲
비용: 2 / 통행: 가능
＝
숲 (1,1)
이름: 숲
비용: 2 / 통행: 가능

두 칸은 위치는 다르지만 지형 규칙은 같다. 지도에 숲이 많아질수록 같은 이름·비용·통행 여부를 반복해서 다루게 된다. 먼저 이 반복을 어떻게 표현할지 생각하자.

첫 시도 · 가상 설계

첫 생각: 칸마다 지형 객체를 만들자

var leftForest =
    new TerrainType("숲", 2, true);
var rightForest =
    new TerrainType("숲", 2, true);

작은 지도에서는 충분하다

각 칸이 자기 규칙을 가지므로 조회하기 쉽다. new는 객체를 새로 만든다는 뜻이며, 여기서는 같은 내용의 숲 객체 두 개가 생긴다.

숲 두 칸이라면 단순하다. 그런데 같은 규칙을 쓰는 숲이 수백 칸이라면 어떨까?

공유가 필요한 이유를 보이는 가상 예시 · 현재 MapLoader의 구현이 아님

첫 시도의 한계

값이 같아도 객체는 따로 존재한다

같은 숲 규칙을 사용칸마다 생성하나를 공유
숲 2칸숲 객체 2개숲 객체 1개
숲 200칸숲 객체 200개숲 객체 1개

필요한 것은 숲 200개의 서로 다른 위치이지,
똑같은 숲 규칙 200벌이 아니다.

서로 다른 규칙이 필요한 칸은 따로 표현하면 된다. 같은 규칙이 반복되는 부분을 찾아 공유하는 것이 이번 설계의 출발점이다.

데이터의 경계

공통 규칙과 칸별 상태를 나눈다

함께 써도 되는 정보

  • 지형 이름: 숲
  • 진입 비용: 2
  • 통행 가능 여부: true

각 장소에 남길 정보

  • 셀 좌표: (0,1), (1,1)
  • 그 칸에 서 있는 유닛

점유 상태까지 숲 규칙에 넣으면 한 유닛이 올라섰을 때 모든 숲이 점유된 것처럼 보일 수 있다. 함께 변하지 않는 정보끼리 묶어야 한다.

패턴의 이름

Flyweight는 반복되는 공통 데이터를 공유한다

여러 칸이 하나의 지형 규칙 객체를
함께 가리키도록 만든다.

참조란?

객체 내용을 복사한 것이 아니라 그 객체를 가리키는 연결이다. 두 숲 좌표가 같은 규칙 객체를 참조해도 좌표는 각각 남는다.

Flyweight란?

반복되는 공통 데이터를 분리해 공유하는 패턴이다. 이번 구현에서는 많은 셀이 읽는 지형 규칙이 공유 대상이다.

현재 구현 · 에셋의 의미

ScriptableObject는 공유 데이터를 에셋으로 저장한다

ScriptableObject

Unity에서 데이터를 담아 .asset 파일로 저장하고 재사용할 수 있는 객체다. 씬의 GameObject에 붙여 움직이는 MonoBehaviour와 역할이 다르다.

이 지도의 두 종류

MapData는 지도 크기와 셀별 에셋 참조를 저장한다. TileData는 지형 규칙과 화면에 쓸 Tile을 저장한다.

현재 씬은 map01.asset을 읽는다. 그 안의 여러 셀이 같은 Forest.asset을 연결하면 공유의 출발점이 생긴다.

실제 구조: MapData.cs · TileData.cs · Scenes/Lesson03.unity

역할 연결

배치·에셋·규칙·조회는 역할이 다르다

MapData각 좌표가 어떤 TileData를 사용할지 저장한다.
TileData지형 값과 표시 Tile을 보관하고 규칙 객체를 재사용한다.
TerrainType탐색이 읽는 이름·비용·통행 규칙을 표현한다.
Board좌표별로 공유 규칙 참조를 보관하고 돌려준다.

공유 기준은 같은 TileData 에셋이다. 이름과 비용이 같더라도 서로 다른 에셋 두 개를 만들면 런타임 규칙 객체도 따로 생길 수 있다.

실제 코드 · TileData

같은 에셋은 만든 규칙을 다시 돌려준다

public TerrainType RuntimeTerrain
{
    get
    {
        Validate();
        return _runtimeTerrain ??= new TerrainType(
            _displayName, _movementCost, _isWalkable);
    }
}

처음 한 번만 생성

??=는 왼쪽이 null일 때만 오른쪽 값을 만들어 저장한다. 캐시는 이렇게 한 번 만든 결과를 다음 요청에서도 재사용하는 보관소다.

동일한 Forest 에셋의 첫 요청은 숲 객체를 만든다. 캐시가 유지되는 동안 두 번째 요청은 그 객체 그대로 반환한다.

실제 발췌: TileData.cs · RuntimeTerrain (줄바꿈 조정)

공유와 변경의 경계

공유하는 규칙은 읽기 전용으로 공개한다

public string Name { get; }
public int MovementCost { get; }
public bool IsWalkable { get; }

왜 set이 없을까?

같은 객체를 읽는 칸이 많으므로 한 칸의 코드가 비용을 바꾸면 전체가 영향을 받는다. TerrainType은 생성자에서 값을 정한 뒤 외부 재대입을 막는다.

TileData 에셋과 이미 생성한 규칙은 구별한다. OnEnable·OnValidate는 캐시를 비우지만 기존 Board의 참조까지 교체하지는 않는다. 에셋 변경이 모든 실행 중 셀에 즉시 반영된다는 뜻은 아니다.

실제 발췌: TerrainType.cs · 속성 / TileData.cs · 캐시 초기화

보조 경로 · 선언 읽기

static과 readonly는 서로 다른 제한이다

public static readonly TerrainType Forest =
    new TerrainType("숲", 2, true);

static

개별 Board마다 생기지 않고 클래스에 속하는 필드다. TerrainTypes.Forest로 같은 참조를 읽는다.

초기화 뒤 필드의 재대입을 제한한다. 객체 내부까지 불변으로 만들지는 않으므로 get 전용 속성과 구분한다.

실제 값: Maps/Plain.asset · Forest.asset · Mountain.asset · River.asset

설명용 2×2 지도

배열의 첫 행은 지도 위쪽 행이다

MapData의 셀 배열

0: Forest    1: Plain
2: Plain     3: Plain

폭 2, 높이 2의 설명용 배치다. 실제 map01 전체를 축소한 지도는 아니다.

셀 좌표로 읽기

y=1   (0,1) F   (1,1) P
y=0   (0,0) P   (1,0) P
         x=0       x=1

F는 Forest 에셋, P는 Plain 에셋을 짧게 쓴 표기다.

인덱스 = (높이−1−y)×폭+x. (0,1)은 (2−1−1)×2+0=0, (1,0)은 (2−1−0)×2+1=3이다.

실제 좌표 규칙: MapData.cs · GetTile / 배치는 설명용 예시

실제 코드 · 지도 로딩

for (int y = 0; y < mapData.Height; y++)
for (int x = 0; x < mapData.Width; x++)
{
    var cell = new Vector2Int(x, y);
    cells.Add(cell, mapData.GetTile(cell).RuntimeTerrain);
}

지도 모델

Board는 좌표별 연결을 보관한다

_cells =
    new Dictionary<Vector2Int, TerrainType>(cells);

사전이란?

키로 값을 찾는 자료구조다. 여기서 키는 정수 x,y 좌표인 Vector2Int이고, 값은 지형 규칙 참조다. Contains로 존재를 확인한 뒤 GetTerrain으로 읽는다.

Board 생성자는 사전 항목을 복사하지만 규칙 객체는 복제하지 않는다. 앞의 2×2 배치는 좌표 항목 4개, 공유 규칙 객체 2개다. 원본 사전의 항목 교체도 Board 항목을 바꾸지 않는다.

실제 발췌: Board.cs · 생성자 (줄바꿈 조정). 모델은 데이터를 표현하며 직접 타일을 그리지 않는다.

이동 비용의 정의

출발은 0, 새 칸에 들어갈 때 비용을 낸다

예산 4인 이동누적 비용판정
시작 숲 → 평지0+1=1가능
시작 → 산 → 평지0+3+1=4가능
시작 → 숲 → 산0+2+3=5초과

누적 비용은 출발 이후 들어간 지형 비용의 합이다. 시작 칸은 이미 서 있는 곳이므로 0이다. 출발점이 숲이어도 먼저 2를 청구하지 않으며, 예산과 정확히 같은 비용까지 허용한다.

탐색의 첫 시도 · BFS

첫 생각: 가까운 칸부터 차례로 찾자

한 번 이동한 칸, 두 번 이동한 칸…
적게 움직여 도착한 곳부터 조사한다.

BFS · 너비 우선 탐색

가까운 단계부터 넓혀 가는 탐색이다. 보통 먼저 넣은 후보를 먼저 꺼내는 큐를 사용한다.

잘 작동하는 조건

모든 진입 비용이 1이면 두 번 이동한 길은 항상 비용 2다. 이동 횟수와 가격이 같아서 먼저 찾은 최소 횟수 경로를 쓸 수 있다.

지형 비용이 같을 때 가능한 개념적 첫 시도 · 현재 MovementRange는 비용 기준으로 탐색한다.

첫 시도의 한계 · 숫자로 비교

두 번 이동해도 가격은 3과 2로 갈린다

y=1   A:숲 2       T:평지 1
      (0,1)        (1,1)

y=0   S:출발       B:평지 1
      (0,0)        (1,0)

같은 2×2 배치

출발 S, 목표 T, 예산 3이다. 상하좌우로만 이동한다. S의 지형은 평지지만 시작 비용은 0이다.

위쪽 길 S→A→T는 2+1=3, 오른쪽 길 S→B→T는 1+1=2다. 위쪽 길을 먼저 발견하고 끝내는 BFS라면 더 싼 오른쪽 길을 놓친다.

설명용 예시 · 이후 탐색 기록도 이 지도와 예산 3을 사용

필요한 기준에서 알고리즘으로

다익스트라는 누적 비용이 작은 후보를 고른다

바꿔야 할 기준

“먼저 발견했는가?” 대신 “지금까지 얼마로 도착했는가?”를 비교한다. 더 싼 길을 찾으면 이전 기록도 바꿔야 한다.

다익스트라 탐색

후보 중 누적 비용이 가장 작은 곳의 이웃을 조사한다. 이웃에 들어갈 비용을 더해 새 기록과 기존 기록을 비교한다.

확장은 한 후보의 이웃을 조사하는 일이다. 현재 비용은 모두 양수여서 길을 더 가도 가격이 줄지 않는다. 이 성질이 싼 후보부터 확장하는 방식과 예산 초과 제외를 뒷받침한다.

데이터의 역할

탐색은 세 가지 기록을 따로 관리한다

기록답하는 질문예시
frontier · 후보 집합어디의 이웃을 더 조사할까?{A, T}
costs · 비용 사전현재까지 찾은 최저 비용은?T: 2
previous · 이전 셀 사전그 비용으로 어디서 왔는가?T: B

집합은 같은 원소를 중복 보관하지 않는다. 후보를 꺼낸 뒤에도 가격과 경로 기록은 남겨야 한다. 그래서 frontier에서만 제거하고 costs와 previous에서는 지우지 않는다.

실제 코드 · 초기화와 선택

처음에는 출발점 하나만 후보가 된다

HashSet<Vector2Int> frontier =
    new HashSet<Vector2Int> { start };
costs.Add(start, 0);

Vector2Int current = FindLowestCost(frontier, costs);
frontier.Remove(current);

시작 상태

frontier={S}
costs={S:0}
previous={}

출발점 이전의 셀은 없으므로 previous는 비어 있다.

위 두 초기화 문장 다음에는 반복문이 이어진다. FindLowestCost는 후보 전체를 살펴 가장 싼 좌표를 고르고, 그 후보만 집합에서 꺼낸다.

실제 발췌: MovementRange.cs · Calculate (초기화와 반복문 안의 두 부분, 줄바꿈 조정)

수치 추적 1 · 첫 확장

S를 조사하면 A는 2, B는 1이다

S의 이웃후보 비용저장할 이전 셀처리
A · 위쪽 숲0+2=2S후보에 추가
B · 오른쪽 평지0+1=1S후보에 추가
아래·왼쪽지도 밖없음제외

처리 뒤 후보는 {A,B}, 비용은 S:0, A:2, B:1이다. 실제 조사 순서는 위→오른쪽→아래→왼쪽이지만 다음 확장은 비용 1인 B다. 대각선 T는 S의 직접 이웃이 아니다.

수치 추적 2 · 가장 싼 후보

B를 먼저 조사하면 T의 비용은 2다

B의 누적 비용 1
＋
T의 진입 비용 1
→
costs[T] = 2
previous[T] = B
후보에 T 추가

현재 후보는 {A,T}, 비용은 S:0, B:1, A:2, T:2다. B에서 S로 돌아가면 1+1=2지만 기존 S의 비용 0보다 비싸므로 저장하지 않는다. 왕복한 길이 더 좋은 기록을 덮지 않는다.

수치 추적 3 · 비교와 종료

비싼 길을 버리면 최저 비용만 남는다

남은 조사후보 비용비교 결과
A → T2+1=3기존 2보다 비싸므로 유지
A → S2+1=3기존 0보다 비싸므로 유지
T → B2+1=3기존 1보다 비싸므로 유지
T → A2+2=4예산 3 초과로 제외

A와 T는 비용 2로 동점이라 어느 쪽이 먼저 나올지는 보장하지 않는다. 표는 A를 먼저 처리한 경우다. 둘을 모두 처리하면 후보가 비고 S:0, B:1, A:2, T:2가 남는다. T의 이전 셀은 계속 B다.

실제 코드 · 기록 갱신

좋은 경로의 비용과 이전 셀은 함께 저장한다

int candidateCost =
    costs[current] + terrain.MovementCost;

// 예산과 기존 비용 검사 통과 후
costs[next] = candidateCost;
previous[next] = current;
frontier.Add(next);

완화란?

새 경로가 기존 기록보다 나으면 도달 정보를 갱신하는 일이다. 처음 발견한 좌표도 비용과 이전 셀을 함께 기록한다.

가격만 바꾸면 previous가 더 비싼 옛길을 가리킬 수 있다. “얼마로 왔는가”와 “어디서 왔는가”는 같은 경로를 설명해야 한다.

실제 발췌: MovementRange.cs · Calculate (중간 검사 생략, 주석 추가, 줄바꿈 조정)

실제 조건 · continue

건너뛰기는 이번 이웃만 제외한다

if (candidateCost > budget)
    continue;
if (costs.TryGetValue(next, out int knownCost) &&
    knownCost <= candidateCost)
    continue;

TryGetValue와 out

next의 기록이 있으면 true를 반환하고, 찾은 비용을 knownCost에 넣는다. 처음 발견한 곳은 기존 비용 비교를 건너뛴다.

두 부등호의 의미

>라서 예산과 같으면 허용한다. <=라서 기존과 같거나 비싸면 유지한다. 모든 동점 경로를 모으지는 않는다.

그 전에 지도 밖과 통행 불가도 제외한다. continue는 탐색 종료가 아니라 다음 이웃으로 넘어가라는 뜻이다.

실제 조건을 축약: MovementRange.cs · Calculate (중괄호 생략)

예측과 답

예산 1이면 T까지 갈 수 있을까?

같은 지도에서 예산만 3에서 1로 줄인다.
답: T는 제외되고 S와 B만 남는다.

예산도달 좌표와 최저 비용T
0S:0불가
1S:0, B:1불가
2S:0, B:1, A:2, T:2가능

예산 1에서는 S→A의 2와 B→T의 2가 모두 초과다. 예산 0도 유효하다. 다만 시작점이 지도 밖이거나 통행 불가면 출발점조차 없는 빈 결과가 나온다.

경로 복원 1 · 역추적

previous를 따라가면 지나온 길이 연결된다

현재 위치읽는 이전 셀모인 목록
Tprevious[T] = B[T]
Bprevious[B] = S[T, B]
S출발점이므로 종료[T, B, S]

costs[T]=2는 가격만 알려 준다. 길의 순서는 T부터 previous를 따라가며 모은다. 셀마다 직전 위치 하나만 기억해도 연결을 따라 전체 길을 복원할 수 있다.

계산 결과의 경계

경로 데이터와 이동 실행은 다른 일이다

public void Execute()
{
    _unit.MoveTo(_board, _toCell);

현재 화면에서 일어나는 일

명령은 최종 목적지로 MoveTo를 호출하고, Unit은 위치를 즉시 바꾼다. 계산한 [S,B,T]를 시간에 따라 걷는 애니메이션은 아직 없다.

도입 판단

공유와 비용 탐색에도 대가가 있다

가치가 큰 조건

  • 같은 규칙이 많은 셀에 반복된다.
  • 규칙을 공통 에셋으로 관리한다.
  • 지형마다 진입 비용이 다르다.
  • 최저 비용과 경로를 함께 알고 싶다.

함께 드는 비용

  • 공유 정보와 개별 상태를 구분해야 한다.
  • 에셋·규칙 캐시의 생명주기를 다룬다.
  • 후보·비용·이전 셀 기록이 필요하다.
  • 현재는 후보를 매번 전부 훑는다.

120칸이 규칙 4개를 공유해도 좌표 항목은 120개다. 전체 메모리가 정확히 1/30로 줄지는 않는다. 큰 지도라면 가장 싼 후보를 효율적으로 꺼내는 우선순위 큐를 고려할 수 있다.

가져갈 핵심

같은 규칙은 공유하고 다른 길은 비용으로 비교한다

  1. Flyweight는 반복되는 지형 규칙을 공유하고 좌표별 상태를 분리한다.
  2. TileData 에셋은 읽기 전용 규칙 객체를 캐시하고 여러 셀이 재사용한다.
  3. 다익스트라는 가장 싼 후보부터 조사하며 비용과 이전 셀을 함께 기록한다.
  4. 이동 명령은 검사를 통과한 이동을 실행하고 출발 셀로 되돌린다.

왜 두 칸 이동인데 T의 비용은 3이 아닌 2일까?
평지 B를 거친 1+1이 숲 A를 거친 2+1보다 싸기 때문이다.
