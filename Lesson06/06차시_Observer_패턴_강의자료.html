CHAPTER 01 · 문제와 책임

변화와 반응의 구조

학습 목표: 직접 호출이 늘어나는 이유를 설명하고, 발행자·이벤트·구독자를 구분한다. 이전 차시의 패턴과 이번 패턴이 맡는 문제를 연결한다.

1.1 한 번의 공격에서 여러 일이 일어난다

적에게 피해 5를 주는 순간을 생각해 봅시다. 적의 HP가 10에서 5로 바뀌고 머리 위의 초록색 바가 절반으로 줄어야 합니다. HP가 0이 되었다면 그 유닛은 사라지고, 마지막 적이었다면 승리라는 결과가 확정됩니다. 전투 로그나 효과음도 같은 순간을 사용할 수 있습니다. 하나의 상태 변화에 여러 기능이 연결되는 셈입니다.

가장 먼저 떠오르는 방법은 Unit의 피해 함수에 모든 호출을 적는 것입니다. 이 방식은 반응이 적을 때 이해하기 쉽지만 화면이나 연출을 바꿀 때도 Unit을 고쳐야 합니다. 게임 규칙을 검토하려고 열어 본 클래스에서 HP 바의 모양과 결과 화면의 동작까지 알아야 한다면 책임이 넓어집니다.

핵심 구분상태는 “현재 무엇인가”를 저장합니다. 사건은 “무엇이 바뀌었는가”를 알립니다. 반응은 “그 변화에 대해 무엇을 할 것인가”를 결정합니다.

1.2 Observer는 변화 전달을 분리한다

발행자는 자기 상태를 바꾸고 알림을 보냅니다. 구독자는 관심 있는 사건에 콜백을 등록합니다. Unit은 어떤 HP 바가 붙었는지, 승리 화면이 어떻게 생겼는지 몰라도 HpChanged와 Died를 발행할 수 있습니다. 새 기능은 같은 알림에 반응하는 구독자로 추가할 수 있습니다.

공격 판단→Unit 상태 저장→HpChanged / Died→HP 바 · GameManager

이 분리는 모든 의존성을 없애는 마법이 아닙니다. 구독자는 어느 Unit을 관찰하는지 알아야 하고 이벤트의 인수와 의미를 이해해야 합니다. 장면에서 참조를 연결하는 작업도 남습니다. 줄어드는 것은 발행자가 구독자의 구체적인 표현과 동작을 알아야 하는 부담입니다.

CHAPTER 02 · 전달 계약

C# 이벤트의 계약

학습 목표: Action의 인수와 event의 발행 권한을 구분한다. 이름 있는 콜백으로 등록과 해제를 짝지으며, 동기 호출이 갖는 영향을 설명한다.

2.1 event와 Action은 무엇을 표현하는가

Action은 반환값 없이 호출할 수 있는 메서드의 모양을 표현합니다. Action<Unit>이라면 Unit 하나를 받아 아무 값을 반환하지 않는 메서드가 연결됩니다. 그 앞의 event는 외부 코드가 이 연결을 통째로 덮어쓰거나 마음대로 발행하지 못하게 합니다. 외부의 역할은 반응을 더하거나 빼는 것이고, 사실의 발행은 선언한 클래스의 책임입니다.

발췌 ① · Unit이 공개하는 세 가지 사건

public event Action<Unit> HpChanged;
public event Action<Unit, Vector2Int, Vector2Int> Moved;
public event Action<Unit> Died;

HpChanged와 Died는 “어떤 Unit인가”를 전달합니다. Moved의 두 Vector2Int는 순서대로 출발 셀과 도착 셀입니다. 인수의 타입뿐 아니라 의미와 순서도 계약입니다.

2.2 메시지에 모든 상태를 복사해야 할까

이번 HpChanged는 이전 HP와 새 HP를 따로 전달하지 않습니다. Unit을 받은 구독자가 CurrentHp와 MaxHp를 읽습니다. 그러므로 발행자는 알림 전에 값을 저장해야 합니다. 이전 값이나 피해량이 필요한 전투 로그를 확장한다면 사건의 인수를 바꾸거나 별도 이벤트 자료형을 만들 수 있지만, 이번 수업에서는 기존 API를 유지합니다.

이벤트는 결과를 조회하는 함수와도 다릅니다. “현재 HP가 몇인가”는 프로퍼티로 읽고, “HP가 바뀌었으니 다시 읽어라”는 이벤트로 받습니다. 바가 매 프레임 HP를 확인하는 방식도 가능하지만, 변화 시점과 구독 책임을 드러내는 연습에는 이벤트가 잘 맞습니다.

2.3 등록한 콜백을 정확히 해제한다

발췌 ② · 같은 대상, 같은 이벤트, 같은 콜백

_unit.HpChanged += HandleHpChanged;
_unit.Died += HandleDied;

// 관찰을 마칠 때의 짝
_unit.HpChanged -= HandleHpChanged;
_unit.Died -= HandleDied;

+=와 -=의 대상 Unit이 같아야 합니다. Bind에서 _unit을 새 대상으로 먼저 바꾸면 해제할 때 옛 Unit을 놓칠 수 있습니다. 또한 등록과 해제에 각각 새 람다식을 만들면 같은 콜백을 가리키지 않을 수 있어 이름 있는 메서드를 사용합니다.

구독은 한 번만 이루어진다고 가정하지 않습니다. Unity에서 오브젝트를 껐다 켜거나 Bind를 다시 호출하면 등록 경로가 반복될 수 있습니다. 구독 플래그와 정확한 해제를 함께 사용해야 같은 알림을 여러 번 처리하는 문제를 피할 수 있습니다.

2.4 알림은 동기적으로 실행된다

발췌 ③ · 구독자가 없을 때도 안전한 발행

HpChanged?.Invoke(this);

?.는 구독자가 없어서 이벤트가 null일 때 호출을 생략합니다. 구독자가 있다면 그 콜백들은 Invoke 흐름 안에서 동기적으로 실행됩니다. 콜백을 등록했다고 별도 스레드나 다음 프레임에서 실행되는 것은 아닙니다. 따라서 콜백에서 오래 걸리는 일을 하거나 예외를 던지면 발행자의 실행에도 영향을 줄 수 있습니다.

설계 주의서로 다른 Died 구독자의 등록 순서를 게임 규칙으로 사용하지 마세요. 모든 구독자는 이미 저장된 HP와 생존 상태를 읽어 독립적으로 판단해야 합니다. 이번 구조는 임의의 구독자 예외를 격리하는 전역 이벤트 버스가 아닙니다.
연습Moved를 구독해 이동 기록을 남길 때, 콜백의 Unit과 두 셀은 각각 어떤 문장을 완성하나요? 같은 셀로 MoveTo를 호출했을 때도 기록을 남겨야 할까요?
해설 보기

“이 Unit이 출발 셀에서 도착 셀로 이동했다”라는 문장입니다. 이번 사건의 의미는 실제 셀 변경이므로 출발과 도착이 같으면 발행하지 않습니다. 이동 시도를 기록하는 별도 요구는 다른 사건으로 구분할 수 있습니다.

CHAPTER 03 · 상태와 시간

HP와 사망의 순서

학습 목표: HP 값의 범위를 유지하고, HP 변경과 사망을 구별한다. 사망 알림 중 생존 판정과 오브젝트 활성 상태가 다른 이유를 설명한다.

3.1 상태는 한 곳에서 보존한다

Unit은 MaxHp, CurrentHp, AttackPower, Defense를 읽기 전용 프로퍼티로 공개합니다. ConfigureCombat은 최대 HP를 최소 1로, 현재 HP를 0부터 최대 HP 사이로, 공격력과 방어력을 0 이상으로 제한합니다. 외부에서 화면을 바꾼다고 HP가 바뀌지 않으며, 전투 상태를 바꾸는 진입점은 TakeDamage입니다.

발췌 ④ · 생존 상태는 현재 HP에서 나온다

public int CurrentHp => _currentHp;
public int MaxHp => _maxHp;
public bool IsAlive => _currentHp > 0;

IsAlive를 별도 bool로 저장하지 않으면 HP 0인데 살아 있다고 표시하는 불일치를 줄일 수 있습니다. 다만 오브젝트의 활성 여부는 별도 속성입니다. 잠시 비활성화된 살아 있는 유닛도 있을 수 있고, 사망 처리 도중에는 HP 0이면서 활성인 순간도 있습니다.

3.2 피해는 저장, 알림, 사망 전이로 나눈다

TakeDamage는 damage가 0 이하이거나 이미 죽은 Unit이면 종료합니다. 유효한 피해는 현재 HP에서 빼되 0 아래로 내려가지 않게 합니다. 이후 HpChanged를 발행하면 관찰자는 정확한 새 상태를 읽습니다. 사망 여부는 이전 HP가 양수였고 현재 HP가 0인지로 판단합니다.

발췌 ⑤ · 변경 전후를 비교하는 핵심

int previousHp = _currentHp;
_currentHp = Mathf.Max(0, previousHp - damage);
bool didDie = previousHp > 0 && _currentHp == 0;
HpChanged?.Invoke(this);

예를 들어 HP 3에 피해 9를 받으면 0을 저장합니다. 알림을 받은 HP 바는 0을 읽으며, didDie는 이번 호출에서 생존→사망 전이가 일어났다는 뜻입니다. 단순히 매번 CurrentHp==0만 보고 발행하면 반복 피해에 사망 알림이 중복될 수 있습니다.

유효 피해→HP 저장→HpChanged→필요 시 Died→비활성화

3.3 Died를 들을 때 오브젝트는 아직 존재한다

발췌 ⑥ · 사망 알림을 마친 뒤 비활성화

if (didDie)
{
    Died?.Invoke(this);
    gameObject.SetActive(false);
}

HP 바는 Died를 받아 자기 오브젝트를 숨길 수 있고 GameManager는 남은 팀원을 셀 수 있습니다. 모든 사망 구독자는 Unit이 비활성화되기 전에 호출됩니다. 따라서 팀원을 셀 때 activeInHierarchy만 보면 방금 죽은 Unit까지 셀 수 있습니다. 반드시 IsAlive를 함께 검사해야 합니다.

보드 점유와 공격 대상 탐색에도 같은 기준이 필요합니다. 사망 알림 도중에 다음 판정을 하더라도 HP가 0인 유닛은 길을 막거나 공격 대상이 되어서는 안 됩니다. 완성 Teacher의 BoardView, TurnManager, AttackTargeting, ObjectiveZone은 이 기준을 사용합니다. Unit에서 HP를 먼저 저장하는 이유가 화면 갱신을 넘어 게임 전체 판정으로 이어집니다.

3.4 이동도 저장된 사실을 알린다

발췌 ⑦ · MoveTo의 두 시점

Vector2Int sourceCell = board.WorldToCell(transform.position);
transform.position = board.CellToWorld(targetCell);
if (sourceCell != targetCell)
    Moved?.Invoke(this, sourceCell, targetCell);

null 보드 검사는 이 발췌 앞에서 합니다. 이동 전 셀을 보존하고 위치를 바꾼 다음 알립니다. 같은 셀에서는 사건이 없으며, MoveUnitCommand가 되돌릴 때도 MoveTo를 사용하므로 Undo 이동 역시 관찰 가능합니다.

CHAPTER 04 · 화면 관찰자

HP 바와 구독 수명

학습 목표: UnitHealthBar의 데이터 참조와 시각 참조를 구분한다. 활성화·비활성화·대상 변경 때 구독이 정확히 한 번 유지되도록 설계한다.

4.1 이번 HP 바는 무엇으로 이루어져 있는가

장면에는 다섯 전투 유닛마다 자식 Health Bar 오브젝트가 있습니다. 어두운 배경과 초록 채움은 SpriteRenderer이며 채움 그림은 Fill Transform 아래에 있습니다. UnitHealthBar의 _unit은 데이터 원천, _fill은 표현 대상입니다. 둘 중 하나가 없으면 올바른 상태를 화면에 반영할 수 없습니다.

HP 바는 HP를 복사해서 별도 저장하지 않습니다. Refresh할 때 Unit의 현재 비율을 읽어 Fill의 가로 크기에 적용합니다. 그래서 유닛이 10/10이면 1, 5/10이면 0.5, 0/10이면 0이 됩니다. y와 z는 보존하여 바의 높이와 깊이가 갑자기 바뀌지 않도록 합니다.

발췌 ⑧ · 현재 값을 표현으로 변환

Vector3 scale = _fill.localScale;
scale.x = _unit.MaxHp > 0
    ? Mathf.Clamp01(_unit.CurrentHp / (float)_unit.MaxHp)
    : 0f;
_fill.localScale = scale;

앞에는 Unit과 Fill의 null 검사가 필요합니다. float 변환은 5/10을 0으로 만드는 정수 나눗셈을 피합니다. MaxHp가 양수가 되도록 데이터가 제한되어 있어도 화면 쪽의 방어 검사는 유효합니다.

4.2 OnEnable은 구독과 즉시 갱신을 함께 한다

켜진 HP 바는 변화를 들어야 하고, 과거 알림을 놓쳤더라도 현재 값에 맞게 표시해야 합니다. 따라서 OnEnable은 Subscribe 후 Refresh합니다. 단순히 다음 HpChanged를 기다리면 잠시 꺼져 있는 동안 HP가 바뀐 바가 오래된 모양으로 남을 수 있습니다.

발췌 ⑨ · 활성 수명과 등록 수명 맞추기

private void OnEnable()
{
    Subscribe();
    Refresh();
}

private void OnDisable() => Unsubscribe();

Subscribe는 Unit이 있고 컴포넌트가 활성화되어 있으며 아직 구독하지 않은 경우에만 등록해야 합니다. 실제로 +=를 한 뒤 _isSubscribed를 true로 바꿉니다. Unsubscribe는 같은 Unit에서 같은 핸들러를 -=하고 플래그를 false로 돌립니다. 비활성화된 바에서 Bind를 호출해도 불필요한 구독이 시작되지 않아야 합니다.

4.3 Bind의 순서는 옛 대상 정리부터

발췌 ⑩ · 구독 대상의 교체

Unsubscribe();     // 옛 Unit의 콜백 연결을 해제한다.
_unit = unit;      // 새 데이터 원천을 저장한다.
Subscribe();       // 활성 상태일 때 새 Unit을 관찰한다.
Refresh();         // 새 대상의 현재 값을 즉시 표시한다.

참조 저장을 먼저 하면 Unsubscribe가 새 Unit을 바라보게 됩니다. 옛 Unit에는 콜백이 남고 새 Unit에는 해제할 콜백이 없을 수 있습니다. 이 문제는 처음 실행할 때보다 재사용·재활성화·대상 변경 때 드러납니다. 따라서 정상 시작뿐 아니라 회복 경로까지 설계해야 합니다.

4.4 콜백도 자기가 받을 사건인지 확인한다

HandleHpChanged는 구독 중인지, 전달된 Unit이 null이 아닌지, 실제 _unit과 같은지 확인하고 Refresh합니다. HandleDied도 같은 조건을 확인한 뒤 바 오브젝트를 비활성화합니다. 그 비활성화는 다시 OnDisable을 불러 구독을 해제합니다. 이 과정에서 Unit의 다른 사망 구독자인 GameManager까지 해제하지는 않습니다.

CHAPTER 05 · 규칙 관찰자

사망 관찰과 전멸 결과

학습 목표: GameManager가 Died로 전멸을 판단하는 과정을 설명한다. 대상 목록과 실제 구독 목록을 구분하고 기존 목표 승패와 최초 결과 보존을 유지한다.

5.1 화면과 결과는 같은 사망을 다르게 해석한다

HP 바는 사망 사건을 받으면 자신을 숨깁니다. GameManager는 그 유닛이 어느 팀인지와 남은 생존 전투 유닛 수를 확인합니다. Unit은 두 반응을 구별할 필요가 없습니다. 자기 상태를 저장하고 Died를 발행하는 것으로 역할이 끝납니다.

완성 장면의 GameManager에는 _combatUnits로 다섯 명이 직렬화되어 있습니다. Start에서 ObserveUnits를 호출하여 실제 구독 목록을 만들며, null과 중복을 제외합니다. 목록을 새로 관찰할 때는 기존 구독을 먼저 해제합니다. Fixed Blocker는 장면에 Unit 컴포넌트가 있어도 전투 명단과 전멸 집계에 포함되지 않습니다.

발췌 ⑪ · 관찰 시작과 단일 구독의 의미

private void Start() => ObserveUnits(_combatUnits);

// 유효하고 아직 관찰하지 않은 Unit을 찾은 뒤
_observedUnits.Add(unit);
unit.Died += HandleObservedUnitDied;

실제 ObserveUnits에는 이전 대상 해제, null 컬렉션 처리, null 항목·중복 확인이 필요합니다. 공개 목록에 같은 유닛이 두 번 있어도 하나의 사망을 두 번 처리하면 안 됩니다.

5.2 생존 전투 유닛의 의미

집계 대상은 null이 아니고, 활성 상태이며, IsAlive가 true이고, IsTurnUnit이며, 지정한 팀인 유닛입니다. 단순히 Enemy 타입의 개수나 활성 오브젝트 개수를 세지 않습니다. IsAlive는 Died가 비활성화보다 먼저 온다는 계약을 반영하고, IsTurnUnit은 고정 장애물을 전멸 조건에서 제외합니다.

발췌 ⑫ · 집계에서 함께 읽어야 하는 상태

unit != null
    && unit.gameObject.activeInHierarchy
    && unit.IsAlive
    && unit.IsTurnUnit
    && unit.Team == team

HandleObservedUnitDied는 아직 Playing인지, 전달된 Unit이 관찰 목록의 대상인지, 전투 참여자인지 먼저 검사합니다. 죽은 대상이 적이면 적 생존 수가 0일 때 PlayerWon, 아군이면 아군 생존 수가 0일 때 PlayerLost를 요청합니다. 이미 끝난 전투에는 뒤늦은 알림이 새 결과를 쓰지 못합니다.

5.3 최초 결과와 목표 점령을 보존한다

발췌 ⑬ · Lesson05부터 유지되는 결과 확정

    return;
Result = result;

전멸은 새로운 승패 조건이지만 기존 목표는 사라지지 않습니다. 아군이 적 소유 목표 (11,6)에 진입하면 승리, 적이 아군 소유 목표 (0,4)에 진입하면 패배입니다. TurnManager.CheckGoal은 현재 셀과 목표 셀을 비교한 뒤 ObjectiveZone의 팀 규칙을 사용합니다. 목표가 결과를 확정했다면 공격 선택을 이어가지 않아야 합니다.

GameManager가 결과를 저장하면 플레이어 공격 완료나 적 행동 뒤 TurnManager가 이를 읽고 Finished로 전환합니다. PhaseHud는 턴 변화에 따라 VICTORY 또는 DEFEAT를 표시합니다. 서로 다른 사건이 거의 연속해서 일어나도 TryFinish가 첫 결과를 지켜 줍니다.

5.4 관찰자의 수명은 컴포넌트마다 다르다

GameManager는 OnDestroy에서 StopObservingUnits로 Died 구독을 정리하고 자신이 Instance인 경우에만 Instance를 비웁니다. 같은 수명 동안 관찰 대상을 교체할 때도 StopObservingUnits를 사용합니다. HP 바와 달리 현재 GameManager는 OnDisable에서 자동 해제·OnEnable에서 자동 재구독하는 구조가 아닙니다. 화면 컴포넌트의 수명을 모든 관찰자에게 그대로 복사하지 않습니다.

재시작과 정적 참조이번 GameManager는 DontDestroyOnLoad로 영구 보존하지 않습니다. R은 Build Settings에 등록된 활성 장면을 새로 불러오며 옛 구독과 Singleton 참조는 이전 장면의 파괴 과정에서 정리됩니다.

CHAPTER 06 · 입력과 행동 경계

공격 상태와 행동 경계

학습 목표: 이동 후 공격 선택의 흐름을 설명한다. HasMoved와 보류 행동을 구분하고, 공격·건너뛰기·Undo·적 턴 진입의 경계를 정한다.

6.1 클릭의 의미를 상태에 맡긴다

Idle에서는 아군 선택, UnitSelectedState에서는 이동할 칸 선택, AttackState에서는 공격 대상 선택이 중요합니다. 같은 클릭이라도 의미가 달라지므로 모든 조건을 한 Update에 겹쳐 넣는 대신 입력 상태로 나눕니다. BattleController는 실제 보드와 전투 행동의 실행을 맡고, 상태는 현재 입력을 어떤 요청으로 바꿀지 결정합니다.

Idle→UnitSelectedState→이동 성공→목표 확인→AttackState 또는 즉시 완료

현재 학생판의 이동 경로는 앞 차시대로 바로 행동을 마칩니다. 전투를 구현할 때 이동 후 인접 적이 있는 경우에만 AttackState를 열도록 연결합니다. 적이 없거나 목표로 결과가 확정된 경우에는 공격 선택을 기다릴 이유가 없습니다.

6.2 대상 선정은 공간 규칙이다

상하좌우 인접은 두 셀의 맨해튼 거리 1로 표현합니다. 대각선은 가로와 세로 차이의 합이 2이므로 제외됩니다. 제공된 AttackTargeting은 다른 팀의 활성·생존 대상을 중복 없이 모읍니다. 호출자는 전투 명단과 행동 자격도 검사합니다. 장면의 Fixed Blocker는 전투 목록에 없으므로 적의 공격 대상이 아닙니다.

발췌 ⑭ · 직교 인접 판정

Mathf.Abs(cell.x - origin.x)
    + Mathf.Abs(cell.y - origin.y) == 1

대상은 선택할 때만 검사해서는 부족합니다. 실제 피해를 주기 직전에도 현재 위치, 생존, 팀, 진행 중인 게임인지 확인해야 합니다. 사건 콜백이나 이전 행동으로 대상의 상태가 바뀔 수 있기 때문입니다.

6.3 HasMoved와 공격 대기는 별개다

PlayerMoveCommand는 이동에 성공하면 HasMoved를 true로 만듭니다. 그래서 AttackState에 들어온 유닛은 이미 이동한 상태입니다. 그 뒤 공격을 선택하는 시간을 관리하려면 BattleController가 어떤 유닛의 행동을 보류 중인지 별도로 기억해야 합니다. HasMoved가 true라는 사실만으로 즉시 다음 턴을 시작하면 공격 클릭을 할 기회가 없어집니다.

보류 중에는 다른 아군 선택이나 Undo가 끼어들지 못해야 합니다. CompletePlayerAction은 보류한 바로 그 Unit의 요청인지 확인한 뒤 보류 상태를 지우고 Idle로 돌아갑니다. 전투가 끝났으면 Finished를 반영하고, 아직 플레이어 턴이면 전체 아군 행동 완료 여부를 TurnManager에 알립니다.

6.4 전투의 피해는 이동 Undo로 복구되지 않는다

이동 Command의 Undo는 이전 위치와 HasMoved만 복구합니다. 적 HP 감소, 사망, 관찰자 반응까지 되돌리는 기능은 들어 있지 않습니다. 공격 후 위치만 돌아가면 피해를 남긴 채 행동을 다시 할 수 있는 모순이 생깁니다. 그래서 실제 HP가 감소한 공격은 명령 이력을 비웁니다.

발췌 ⑮ · 실제 피해와 이력의 관계

_attackApplied = defender.CurrentHp < previousHp;
if (_attackApplied)
    _history.Clear();

완성 TryAttack은 피해 전 HP를 기억하고, 처리 중 상태를 세워 콜백이 행동 완료에 재진입하지 못하게 합니다. finally에서 실제 피해 여부와 이력을 정리하고 처리 중 상태를 해제합니다. 구독자가 예외를 던져도 이미 감소한 HP를 없던 일로 취급해서는 안 됩니다.

공격을 건너뛰었다면 같은 플레이어 턴에서 이력이 남아 있을 때 이동 Undo가 가능합니다. 다만 마지막 아군의 행동 완료가 적 턴을 시작하면 앞 차시 규칙에 따라 이력은 비워집니다. 따라서 “건너뛰기는 항상 Undo 가능”이라고 외우지 말고 현재 턴과 이력 경계를 확인해야 합니다.

7.1 CombatCalculator는 어떤 질문에 답하는가

CombatCalculator.CalculateDamage(attacker, defender, terrain)은 “이 공격의 피해는 얼마인가”에 답합니다. 계산기는 HP 바를 찾거나 Unit을 비활성화하지 않습니다. 공격 실행자는 대상을 검증하고 지형을 찾은 뒤 계산 결과를 TakeDamage에 전달합니다. 계산과 상태 변경을 나누면 숫자 규칙과 사건 흐름을 각각 이해하기 쉽습니다.

이번 차시의 공식피해 = max(1, 공격력 − 방어력 − 방어 지형 보너스)
숲 보너스 1, 산 보너스 2, 그 외 0. 최소 피해는 1입니다.

유닛의 공격력과 방어력은 음수가 되지 않도록 구성됩니다. 유효한 전투에서 공식의 차이가 0 이하가 되어도 최소 피해 1은 남습니다. 따라서 방어가 높다는 이유만으로 무한히 피해를 받지 않는 상태가 되지는 않습니다. 이것은 이번 전투의 의도된 게임 규칙이며, 다른 게임에서는 다른 규칙을 선택할 수 있습니다.

10.1 180분에서 마지막 30분의 역할

수업은 0–30분 개념과 구조, 30–150분 전체 구현, 150–180분 Play 미션과 복습입니다. 120분 구현에는 피해·발행·HP 바·전멸·공격 상태·지형·적 AI가 모두 포함됩니다. 마지막 활동은 구현을 대신하는 시연이 아니라 이미 연결한 게임의 실제 결과를 설명하는 시간입니다.

150–170분에는 짝과 조작자·관찰자를 나눕니다. 관찰자는 클릭 전에 결과를 예측하고 실제 HP, 바, 턴을 기록합니다. 170–180분에는 어떤 알림이 어떤 책임으로 이어졌는지 설명하고 오류를 예방하는 규칙을 정리합니다.

10.2 통합 Play 미션

  1. 기본 공격: Player 3을 (8,6)에서 (9,7)로 이동한 뒤 (9,8)의 Enemy 1을 공격합니다. 평지 피해 5로 HP가 10→5, 바가 절반인지 관찰합니다. 공격 이후 Undo로 위치만 돌아가지 않아야 합니다.
  2. 건너뛰기: R로 초기화하고 같은 이동 뒤 빈 공간을 클릭합니다. 다른 아군이 아직 행동하지 않아 플레이어 턴이 유지될 때 Undo로 위치와 HasMoved가 복구되는지 확인합니다.
  3. 지형 비교: 방어자를 숲과 산의 유효한 비점유 셀에 놓고 같은 공격의 피해 4와 3을 비교합니다. 필요하면 Play 전 Inspector에서 위치·현재 HP를 조정하고 실험 뒤 원래 장면 값을 회복합니다.
  4. 적 행동: 인접한 적은 제자리 공격, 멀리 있던 적은 접근 후 대상 재검색을 하는지 봅니다. 아군 전체 행동 후 적 둘이 순서대로 행동하며 적 턴에 플레이어 입력·Undo가 막히는지 확인합니다.
  5. 전멸 결과: 적 둘을 잃으면 VICTORY, 아군 셋을 잃으면 DEFEAT입니다. 사망 유닛은 보드 점유·대상·다음 행동에서 빠지고 Fixed Blocker는 결과를 지연시키지 않습니다.
  6. 기존 목표와 회복: 아군의 적 소유 목표 (11,6) 진입은 승리, 적의 아군 소유 목표 (0,4) 진입은 패배입니다. 종료 후 이동과 Undo가 막히고 R로 10/10 HP와 플레이어 턴이 새로 시작됩니다.

전멸 직전 상황을 짧게 관찰하려면 재생 전에 Inspector에서 현재 HP를 1로 줄여 시작할 수 있습니다. 이것은 공격이나 전멸 구현을 생략하는 방법이 아니라 완성된 반응을 관찰할 상황을 준비하는 방법입니다. 실험 후 10/10 상태로 회복합니다. HP 바를 비활성화했다가 켜는 회복과 Bind 대상 교체도 순서표로 점검합니다.

10.3 스스로 설명하는 다섯 질문

  1. Unit이 HP 바의 메서드를 직접 호출하지 않아도 되는 이유는 무엇인가요?
  2. HP 저장과 HpChanged의 순서를 바꾸면 어떤 관찰자가 잘못된 값을 읽나요?
  3. Died 처리 중 활성 상태만으로 남은 유닛을 세면 왜 틀릴 수 있나요?
  4. 구독자의 OnEnable/OnDisable과 Bind에서 반드시 짝지어야 하는 것은 무엇인가요?
  5. 공격 후 이력을 비우고, 적 이동 뒤 대상을 다시 검색하는 이유는 무엇인가요?
핵심 답 확인

Unit은 사실의 발행자이고 바는 그 사실의 구독자이므로 표현 타입을 몰라도 됩니다. HP를 나중에 저장하면 바와 결과 관찰자가 이전 값을 읽습니다. Died 때는 HP 0인데 오브젝트가 아직 활성일 수 있어 IsAlive가 필요합니다. 구독 대상·이벤트·콜백을 정확히 맞춰 해제해야 하며 새 Bind 전에 옛 대상을 정리합니다. 이동 Undo는 피해를 복원하지 않기 때문에 공격 후 이력을 비우고, 이동 후 위치와 상태가 달라졌기 때문에 대상을 다시 찾습니다.

10.5 필수 구현 이후의 확장

전투 로그는 HpChanged 또는 새 피해 사건을 듣고, 효과음은 Died를 들으며, 이동 카메라는 Moved를 들을 수 있습니다. 새로운 관찰자를 붙였을 때 Unit의 HP 코드에 UI·오디오 참조를 추가해야 한다면 책임이 다시 섞이고 있는지 점검합니다. 사건의 인수가 새 구독자의 요구를 충분히 설명하는지도 따져 봅니다.

비동기 피격 연출, 피해 숫자, 사거리 자료형, 보호 중심 AI, 오브젝트 풀링은 후속 과제입니다. 비동기 연출에는 알림과 완료 시점이 다를 수 있다는 정책이 필요하고, 풀링에는 재활성화와 재바인딩 수명 설계가 필요합니다. 이번 수업의 필수 전투·바·전멸·지형·적 AI를 모두 완성한 뒤 선택 확장으로 진행합니다.

수업의 기준값의 소유자는 Unit, 표현의 소유자는 HP 바, 결과의 소유자는 GameManager입니다. 한 번 화면이 바뀌는 것뿐 아니라 순서·수명·입력 경계까지 설명할 수 있어야 전투 흐름을 이해한 것입니다.
