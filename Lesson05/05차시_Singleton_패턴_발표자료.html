개념과 공개 창구

유일한 Singleton: GameManager

public static GameManager Instance { get; private set; }
public BattleResult Result { get; private set; }
    = BattleResult.Playing;
public bool IsPlaying =>
    Result == BattleResult.Playing;

static은 클래스에서 접근하는 창구이고, private set은 외부의 인스턴스 교체를 제한한다. 유일성은 Awake의 검사로 지킨다.

이 수업에서 Instance를 갖는 MonoBehaviour는 GameManager 하나다.

05 / 26

수명

중복 생성과 파괴를 함께 생각한다

// Awake의 핵심: 이미 주인이 있으면 중복은 빠진다.
if (Instance != null && Instance != this)
{
    // 실행 중에는 Destroy(gameObject);
    // 제거 예약 뒤에는 반드시 return;
}
Instance = this;

// OnDestroy의 핵심
if (Instance == this) Instance = null;

주석은 수명 구조를 설명한 발췌다. 완성본은 실행 중 Destroy, 편집 모드 DestroyImmediate로 분기한다.

DontDestroyOnLoad는 사용하지 않는다. 재시작할 때 새 장면의 객체가 새 주인이 된다.

작은 공개 API

결과는 한 번만 확정한다

public void TryFinish(BattleResult result)
{
    if (!IsPlaying || result == BattleResult.Playing)
        return;
    Result = result;
}

Playing → PlayerWon 또는 PlayerLost. 이미 종료된 결과를 나중의 호출이 덮어쓰지 않는다.

승리 직후 패배 요청이 들어오면 결과는 무엇일까? 조건식으로 설명하자.

참조로 협력하기

TurnManager는 일반 객체다

TurnManager는 자신의 유닛 목록, 적 AI 목록, 보드와 목표를 안다. 장면에 배치하고 참조를 연결한다.

[SerializeField] private GameManager _gameManager;
[SerializeField] private TurnManager _turnManager;

위 코드는 BattleController의 연결이다. 실제 소비자는 Inspector 참조를 사용한다. Instance가 있다고 모든 호출을 전역 접근으로 바꿀 이유는 없다.

전투 보드를 두 개 띄운다면 전역 TurnManager는 어느 보드를 가리켜야 할까?

Game Loop 이론 코너

프레임 반복과 턴 반복

프레임: 입력 확인 → 상태 갱신 → 화면 표시 → 반복

턴: Player → Enemy → Player → …
목표 도달: 어느 쪽에서든 Finished

적 대기 중에도 프레임은 계속된다. 턴은 게임 규칙이고 Unity의 매 프레임 실행과 같은 단위가 아니다.

await는 화면을 멈추는 잠금이 아니다. 다음 적 행동의 시작 순서를 정한다.

HasMoved

한 번 움직였다는 사실

public bool HasMoved => _hasMoved;
public bool IsTurnUnit => _canMove;
public void SetMoved(bool moved) => _hasMoved = moved;
  • CanMove: 이동 가능한 종류의 유닛인가?
  • HasMoved: 해당 팀의 이번 턴에 이미 행동했는가?
  • 고정 장애물은 CanMove=false, 턴 집계에서 제외된다.

Team은 Player/Enemy 두 값이다. 회색 장애물은 저장상 Player지만 행동 유닛은 아니다.

입력 경계

선택 허용은 여러 조건의 교집합

return Phase == BattlePhase.Player
    && IsGamePlaying()
    && unit != null
    && unit.isActiveAndEnabled
    && unit.Team == Team.Player
    && unit.IsTurnUnit

12 / 26

PlayerMoveCommand

이동과 행동 소모를 한 명령으로

public void Execute()
{
    _movement.Execute();  // MoveUnitCommand: 위치 이동
    _unit.SetMoved(true); // 이번 턴 행동 소모
}
public void Undo()
{
    _movement.Undo();     // 원래 칸
    _unit.SetMoved(false);// 다시 행동 가능
}

Undo가 위치만 복원하면 유닛은 돌아왔지만 다시 선택할 수 없다. 두 상태를 함께 복구한다.

관찰: 한 명만 이동한 뒤 Undo하여 위치와 재선택을 확인한다.

13 / 26

기록과 턴

Undo에도 시간의 경계가 있다

Player 시작: 기록 비우기 · HasMoved 초기화
↓ 이동 명령 기록 / 현재 턴 Undo
모든 활성 아군 행동 완료 또는 Enter
↓ 기록 비우기 · 적 HasMoved 초기화 · Enemy 진입
적 순차 행동 → 다음 Player

마지막 아군의 일반 이동은 자동 전환을 일으킨다. 그 뒤에는 이전 Player의 Undo를 할 수 없다.

Enter(기본·숫자패드)는 남은 행동을 넘기는 필수 조작이다. OnEndTurnRequested가 선택·표시를 정리하고 RequestEndPlayerPhase를 호출한다.

평지→숲→평지의 진입 비용 합계는? 시작 칸 비용은 더하지 않는다.

명령 전 검증

표시와 실행이 같은 규칙을 쓴다

선택 → BoardView.GetMovementRange → 범위 표시
목적지 클릭 → CanPlayerAct + CanMoveTo
→ PlayerMoveCommand → 목표 확인 → 완료 통지

CanMoveTo는 최신 점유와 이동 범위를 다시 확인한다. 표시가 남아 있다고 무조건 이동시키지 않는다.

기본 MoveUnitCommand는 위치 변경을 맡는다. 적법성은 호출 전에 확인한다.

관찰: Player 2 옆 (6,4)의 회색 장애물로 이동을 시도한다.

결정적 AI

적도 같은 이동 규칙 위에서 판단한다

.Where(pair => pair.Key != start)
.OrderBy(pair => ManhattanDistance(pair.Key, goalCell))
.ThenBy(pair => pair.Value)
.ThenBy(pair => pair.Key.y)
.ThenBy(pair => pair.Key.x);

EnemyAI.ChooseDestination의 우선순위: 목표까지 맨해튼 거리 → 실제 이동 비용 → y → x.

완전한 동률 해소가 있어 같은 보드·위치·목표에서는 같은 목적지가 나온다.

탐욕 규칙의 한계

대기도 하나의 결정이다

후보가 없거나, 가장 좋은 후보도 현재보다 목표 거리를 줄이지 못하면 시작 칸을 반환한다.

잠깐 목표에서 멀어져야 우회할 수 있는 길에서는 멈출 수 있다. 이 AI는 전체 경로의 최적성을 보장하지 않는다.

도달 가능한 후보 있음?
→ 없음: 대기
→ 있음: 거리가 엄격히 감소할 때만 이동

“결정적이다”와 “항상 똑똑하다”는 왜 다른 말일까?

UniTask와 순서

적은 한 명씩 행동한다

// RunEnemyPhaseAsync 반복문 중 발췌
EnemyTurnStarted?.Invoke(unit);
await enemyAi.TakeTurnAsync(
    unit, _enemyGoalCell, cancellationToken);
if (CheckGoal(unit)) return;

TakeTurnAsync는 즉시 칸을 옮기고 행동 표시 후 기본 350ms를 기다린다. 다음 적은 이 대기가 끝나야 시작한다.

Enemy 진입 시 활성 적의 HasMoved=false, 각 행동 후 true. Units와 Enemy Ais의 순서를 맞추고 실행 가드로 중복 시작을 막는다.

취소와 수명

장면이 사라지면 기다림도 끝난다

CancellationToken lifetimeToken = destroyCancellationToken;
RunEnemyPhaseForLifetimeAsync(lifetimeToken).Forget();

// EnemyAI 안의 대기
await UniTask.Delay(
    TimeSpan.FromMilliseconds(_turnDelayMilliseconds),
    cancellationToken: cancellationToken);

R 재시작으로 객체가 파괴되면 토큰이 취소된다. 옛 장면의 작업을 계속 실행하지 않는다.

수명 래퍼는 자기 토큰이 취소된 OperationCanceledException만 처리한다. 다른 오류까지 삼키지 않는다.

종료와 화면

경기가 끝나면 함께 멈춘다

목표 도착 → CheckGoal → MarkFinished
→ GameManager.TryFinish + Phase=Finished
→ PhaseChanged → PhaseHud.Refresh

종료 후 보드 입력·Undo·Enter는 거절된다. PhaseHud는 켜질 때 구독하고 꺼질 때 구독을 해제한다.

실제 화면: VICTORY는 승리, DEFEAT는 패배. PLAYER PHASE와 ENEMY PHASE는 각각 아군 턴과 적군 턴이다.

재시작

R로 새 경기를 시작한다

GameManager.Update가 Input System의 R 키를 읽어 RestartCurrentScene을 호출한다. 승패 뒤에도 사용할 수 있다.

Scene activeScene = SceneManager.GetActiveScene();
// buildIndex가 음수면 경고 후 반환
SceneManager.LoadScene(activeScene.buildIndex);

Lesson05 장면이 활성 빌드 장면 목록에 있어야 한다. 재로드로 위치·기록·경기 결과·턴 상태가 초기화된다.

적 대기 중 재시작할 때 20번 슬라이드의 토큰이 왜 필요한가?

150–180분

플레이로 증명하는 완성 미션

  1. 한 아군 이동·재선택 거절·Undo·재선택을 확인한다.
  2. 점유 칸과 강 이동 거절, 세 아군 행동 후 적 순서를 관찰한다.
  3. 이동 전 선택 중 Enter로 턴을 넘기고 선택 정리·적 턴 클릭·Undo·Enter 거절을 확인한다.
  4. 아군이 적 소유 목표를 점령하면 승리, 적이 아군 소유 목표에 진입하면 패배임을 각각 확인한다.
  5. 종료 후 입력 차단과 R 재시작을 확인한다.

짝과 예상·실제·원인을 기록한다. 패배 경로에서는 아군으로 적의 접근을 막지 않는다.

회고와 다음 질문

편리함의 비용까지 설명하자

  • Singleton: 공통 창구가 간편하지만 숨은 의존성과 수명 결합이 생긴다.
  • 일반 참조: 연결이 드러나고 다른 전투 인스턴스로 바꾸기 쉽다.
  • 결정적 AI: 재현이 쉽지만 장기 우회 판단은 부족하다.
  • 턴 경계: 행동 플래그·기록·입력 허용이 함께 바뀐다.

GameManager에 넣지 말아야 할 책임 하나와 이유를 말해 보자.

확장: 턴 로그, 다른 목적지 평가 규칙. 필수 미션을 완성한 뒤 시작한다.
