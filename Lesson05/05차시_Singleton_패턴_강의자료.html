1장 / 전체 10장

한 경기로 묶이는 규칙

이번 차시의 결과물은 목표 점령으로 승패가 정해지는 턴 게임이다. 패턴의 이름보다 먼저, 여러 객체가 같은 경기 상태를 어떻게 공유하는지 이해하자.

1.1 이전 차시에서 이어지는 것

4차시의 입력 상태, 이동 범위 표시, 지형 비용, 이동 명령과 Undo를 그대로 사용한다. 이전에는 “선택한 유닛이 저 칸으로 갈 수 있는가”가 중심이었다. 이제 “지금 그 팀이 행동할 차례인가”, “이미 행동했는가”, “경기가 끝났는가”라는 조건이 더해진다. 이 조건은 한 유닛의 위치만으로 답할 수 없다.

여러 유닛과 화면이 각자 Playing 값을 복사해 가지면 한쪽은 종료되고 다른 쪽은 이동을 허용할 수 있다. 공통 결과를 소유하는 GameManager와 진행 순서를 관리하는 TurnManager가 필요한 이유다.

1.2 실제 완성 장면

대상초기 칸게임 규칙
아군 1 / 2 / 3(2,2) / (5,4) / (8,6)각 아군 턴에 한 번 이동
적군 1 / 2(9,8) / (9,3)목록 순서대로 자동 행동
회색 고정 장애물(6,4)점유하지만 턴에 참여하지 않음
아군 목표 / 적군 목표(0,4) / (11,6)상대 팀이 진입하면 경기 종료

보드는 12×10이다. 이동 유닛 예산은 4이며 Player 2는 숲에서 시작한다. 아군은 파란색, 적군은 빨간색이다. 회색 장애물의 Team은 저장상 Player이지만 CanMove=false이므로 행동 수에 넣지 않는다. Team 열거형은 Player와 Enemy 두 값이다. 목표는 공격해서 파괴하는 대상이 아니라 도착 칸이다.

1.3 책임 지도

GameManager — 경기 결과·재시작
↕ 참조
TurnManager — 턴·목록·목표 판정
↙　　↓　　↘
Unit　EnemyAI　ObjectiveZone

BattleController → CommandHistory → PlayerMoveCommand
　　　　　　↘ BoardView → MovementRange
TurnManager.PhaseChanged → PhaseHud

화살표는 협력 관계를 요약한다. 모든 작업이 GameManager를 지나지는 않는다. BattleController는 입력을 규칙 검사와 명령 실행으로 연결하고, BoardView는 좌표·지형·점유 정보를 제공한다. TurnManager는 해당 장면의 유닛들을 알고 순서를 정한다.

Singleton의 유일성과 수명

2.1 전역 접근과 유일성은 별개의 약속

Singleton은 인스턴스 하나를 관리하고 공통 접근 창구를 제공하는 패턴이다. C#의 static 프로퍼티만 선언했다고 장면 객체가 자동으로 하나가 되지는 않는다. GameObject를 두 개 만들 수 있기 때문에 Awake에서 중복을 검사해야 한다. 이 수업의 GameManager만 Instance를 제공하며 TurnManager는 일반 MonoBehaviour다.

// GameManager: 외부에서는 읽고, 교체는 내부에서만 한다.
public static GameManager Instance { get; private set; }
public BattleResult Result { get; private set; }
    = BattleResult.Playing;
public bool IsPlaying => Result == BattleResult.Playing;

Instance는 객체로 가는 창구, Result는 그 객체가 소유하는 경기 상태다. private set은 다른 코드가 임의로 다른 매니저를 대입하는 것을 막는다. 하지만 Instance가 언제 준비되는지는 여전히 객체 수명에 달려 있으므로 아무 시점에서나 존재한다고 가정하면 안 된다.

2.2 생성할 때와 파괴할 때의 조건

// Awake의 실제 중복 방어 부분
if (Instance != null && Instance != this)
{
    if (Application.isPlaying)
        Destroy(gameObject);
    else
        DestroyImmediate(gameObject);
    return;
}
Instance = this;

실행 중 Destroy는 파괴를 예약한다. 그러므로 제거 요청 뒤 return이 있어야 중복 객체가 Instance를 차지하지 않는다. 완성본은 편집 모드에서도 검증할 수 있도록 DestroyImmediate 분기가 있다. 이 분기를 일반 게임 실행에서 무조건 사용하는 방식으로 바꾸지 않는다.

// OnDestroy: 정상 인스턴스의 참조만 해제한다.
if (Instance == this)
{
    Instance = null;
}

중복 객체도 파괴되므로 무조건 Instance=null을 쓰면 살아 있는 정상 객체의 창구가 사라질 수 있다. “현재 주인이 나인가”라는 조건이 필요한 이유다. 생성 방어와 파괴 해제는 한 쌍으로 읽는다.

2.3 장면 범위의 Singleton

이 구현에는 DontDestroyOnLoad가 없다. R로 현재 장면을 다시 읽으면 기존 GameManager가 사라지고 새 GameManager가 만들어진다. 이전 경기의 Result도 새 Playing 값으로 시작한다. 전역 접근 창구가 있다는 사실과 여러 장면 동안 영구 보존한다는 주장은 다르다.

이익은 공통 결과를 찾는 창구가 단순하고 유일한 소유자가 명확하다는 점이다. 비용은 호출부만 보았을 때 의존성이 숨고, 객체 생성·파괴 순서와 결합되며, 동시에 여러 경기 인스턴스를 두기 어렵다는 점이다. 그래서 이동 경로 계산, 개별 유닛, 모든 UI를 Singleton으로 만들지 않는다.

확인 질문과 해설: 중복 객체가 파괴될 때 무엇을 보존해야 할까?

처음 정상 등록된 Instance를 보존한다. 중복의 Awake는 제거 후 return하고, 중복의 OnDestroy는 Instance==this가 아니므로 null을 대입하지 않는다.

참조와 상태로 표현하는 턴 구조

3.1 일반 TurnManager가 더 자연스러운 이유

턴은 특정 보드, 유닛 집합, 적 AI, 목표와 관련된다. 이 의존성을 직렬화 필드로 드러내면 Inspector에서 장면 구성을 확인할 수 있다. TurnManager.Bind는 목록과 목표 칸·GameManager·CommandHistory를 전달하는 API이며 BindObjectives는 보드와 목표 목록을 전달한다. 이 API가 있다고 씬의 직렬화 참조를 생략해도 된다는 뜻은 아니다.

// BattleController의 실제 의존성 일부
[SerializeField] private BoardView _board;
[SerializeField] private GameManager _gameManager;
[SerializeField] private TurnManager _turnManager;

// TurnManager가 관리하는 현재 차례
public BattlePhase Phase { get; private set; }
    = BattlePhase.Player;
public event Action<BattlePhase> PhaseChanged;

완성본의 소비자는 GameManager 참조를 직접 연결한다. GameManager.Instance를 제공하는 것과 모든 객체가 그것을 호출하도록 만드는 것은 다른 선택이다. 연결이 보이면 빠진 참조를 점검하기 쉽고, 같은 역할의 다른 객체를 전달하기도 쉽다.

3.2 두 상태의 의미

상태의미값
BattlePhase현재 진행 구간Player, Enemy, Finished
BattleResult경기의 결론Playing, PlayerWon, PlayerLost

PlayerWon은 “누구 차례인가”에 대한 답이 아니다. Finished는 “승리했는가”에 대한 답이 아니다. 두 정보를 분리하면 HUD, 입력, 다음 턴 진행이 각자 필요한 조건을 읽을 수 있다. 실제 결과가 확정되면 MarkFinished가 두 상태를 연결한다.

3.3 Game Loop 이론 코너

Unity는 프레임마다 입력과 갱신을 처리하며 화면을 계속 그린다. 턴 게임도 프레임 반복 위에서 실행된다. 플레이어가 생각하는 동안에도 프레임은 진행하지만 BattlePhase는 Player로 유지된다. Enemy 동안 UniTask.Delay를 기다려도 화면은 계속 갱신된다.

프레임 시간: 입력 → 갱신 → 표시 → 입력 → 갱신 → 표시 …
게임 규칙: Player ─────────→ Enemy ──→ Player
종료 규칙: 목표 도착 → Finished

바쁜 while 루프로 기다리면 메인 스레드를 붙잡을 수 있다. await는 완료 후 이어갈 작업을 표현하므로 적 순서를 읽기 쉽게 만든다. 이 수업의 순차 await가 자동 병렬 처리를 의미하지는 않는다.

연습: 상태 표 채우기

시작, 첫 아군 이동 후, 세 번째 아군의 일반 이동 후, 적 전원 행동 후, 아군이 적 소유 목표를 점령한 후의 Phase와 Result를 적어 보자. 일반 이동은 목표에 닿지 않는 이동이다.

해설 보기

Player/Playing → Player/Playing → Enemy/Playing → Player/Playing → Finished/PlayerWon이다. 마지막은 “아군이 적 소유 목표에 도달”한 상황이다. 목표 판정이 턴 완료 통지보다 앞서므로 마지막 이동이 승리라면 Enemy로 넘어가지 않는다.

유닛의 행동 권한과 명령

4.1 가능 여부와 이번 턴의 소모 여부

Unit.CanMove는 유닛이 움직일 수 있는 종류인지를 나타내고 IsTurnUnit은 같은 값을 사용한다. Unit.HasMoved는 이번 아군 턴에서 이미 행동했는지를 나타낸다. 고정 장애물은 HasMoved를 억지로 true로 만드는 대신 CanMove=false로 턴 참여에서 제외한다.

// TurnManager.CanPlayerAct의 조건
return Phase == BattlePhase.Player
    && IsGamePlaying()
    && unit != null
    && unit.isActiveAndEnabled
    && unit.Team == Team.Player
    && unit.IsTurnUnit
    && !unit.HasMoved;

조건은 모두 참이어야 한다. “이동하지 않았다”만 확인하면 적도 선택될 수 있다. “아군이다”만 확인하면 적 턴이나 승리 뒤에도 아군을 움직일 수 있다. BattleController.CanAcceptPlayerInput은 연결된 GameManager가 Playing이고 TurnManager가 Player일 때만 입력을 허용한다. 입력 상태에서도 같은 경계를 확인해 직접 상태 호출로 우회되지 않게 한다.

4.2 위치와 행동 소모를 함께 되돌리기

// PlayerMoveCommand: MoveUnitCommand를 감싸는 역할
public void Execute()
{
    _movement.Execute();
    _unit.SetMoved(true);
}
public void Undo()
{
    _movement.Undo();
    _unit.SetMoved(false);
}

MoveUnitCommand는 생성할 때 출발 칸을 저장하고 실행·되돌리기에 Unit.MoveTo를 사용한다. PlayerMoveCommand는 여기에 행동 상태 복원을 더한다. 기본 이동 명령은 위치 변경 책임이며 적법성 검사는 BattleController나 AI가 호출 전에 수행한다. CommandHistory는 실행한 명령을 스택에 넣고 마지막 명령부터 Undo한다.

4.3 클릭이 명령이 되는 과정

보드 클릭 → 입력 허용 확인 → 입력 상태
→ 아군 선택 → 이동 범위 표시
→ 목적지 클릭 → CanPlayerAct + CanMoveTo
→ 공유 기록에 PlayerMoveCommand 실행
→ CheckGoal → 종료하지 않았다면 완료 통지

UI 위의 클릭은 보드 클릭 처리에서 제외된다. Undo 버튼이 눌렸을 때 뒤의 타일까지 동시에 선택되면 입력 경계가 무너진다. 성공한 이동 뒤에는 Idle 상태로 돌아가 선택 표시를 정리한다.

Play Mode 관찰

한 아군만 일반 칸으로 옮긴다. 같은 유닛 재선택은 거절되어야 한다. Undo를 누르면 원래 칸으로 돌아오고 다시 선택할 수 있어야 한다. 다른 아군이 아직 행동하지 않아 현재 Player가 유지되는 조건에서 관찰한다.

실패 진단

위치는 돌아오지만 선택되지 않으면 HasMoved 복원을 본다. 계속 여러 번 이동하면 PlayerMoveCommand 대신 기본 MoveUnitCommand만 기록했는지 확인한다. 클릭이 전부 막히면 Scene의 GameManager·TurnManager 참조, Phase와 Result, 유닛 팀과 활성 상태를 순서대로 본다.

턴 경계와 Undo의 유효 구간

5.1 새 Player 구간의 시작

BeginPlayerPhase는 Finished라면 바로 반환한다. 경기 결과가 종료라면 그 결과를 Phase에 반영한다. 정상 시작에서는 활성 아군 행동 유닛의 HasMoved를 false로 돌리고 CommandHistory를 비운 뒤 Phase를 Player로 설정한다. 움직이지 않는 장애물은 초기화·행동 완료 집계 대상이 아니다.

// BeginPlayerPhase의 핵심 부분
foreach (Unit unit in _units)
{
    if (IsActivePlayerTurnUnit(unit))
        unit.SetMoved(false);
}
_commandHistory?.Clear();
SetPhase(BattlePhase.Player);

실제 완성본의 팀 행동 집계 보조 함수는 null, activeInHierarchy, 팀, IsTurnUnit을 확인한다. 직접 선택 허용 검사는 isActiveAndEnabled도 확인한다. 수업 기본 장면은 행동 유닛 컴포넌트를 활성 상태로 유지한다.

5.2 모든 아군 행동 완료

NotifyPlayerActionCompleted는 Player인지 확인하고 모든 활성 아군 행동 유닛이 HasMoved인지 살핀다. 모두 끝났다면 RequestEndPlayerPhase를 호출한다. 기본 장면에는 별도 턴 종료 버튼이 없으므로 세 명의 일반 이동으로 자동 전환을 관찰한다. 조기 종료 API는 확장할 때 연결할 수 있다.

// BattleController.ExecuteMove에서 발췌
_turnManager.BindCommandHistory(_history);
_history.Execute(new PlayerMoveCommand(unit, _board, targetCell));
if (!_turnManager.CheckGoal(unit))
    _turnManager.NotifyPlayerActionCompleted();

명령이 기록된 바로 그 History를 TurnManager에도 전달한다. 서로 다른 History를 지우면 Undo가 다음 턴까지 남는 오류가 생긴다. 목표 판정이 먼저이므로 승리하는 마지막 이동 뒤 적이 출발하지 않는다.

5.3 적 턴 진입이 되돌리기 경계다

TryEnterEnemyPhase는 종료 여부를 검사한 뒤 기록을 비우고 즉시 Phase를 Enemy로 바꾼다. 그 다음 비동기 적 행동을 시작한다. 이 순서로 첫 await 전에 아군 입력과 Undo가 막힌다. 적 행동 명령은 플레이어 History에 넣지 않는다.

6장 / 전체 10장

지형·점유·도달 경로

6.1 칸 수와 이동 비용은 다르다

평지는 비용 1, 숲은 2, 산은 3, 강은 통행 불가다. 예산 4로 갈 수 있는 칸은 직선 거리만으로 결정되지 않는다. 시작 칸 비용은 0이고 새로 진입하는 지형 비용을 더한다. 평지→숲→평지에 각각 진입하면 총 4를 사용한다.

MovementRange.Calculate는 현재 알려진 비용이 낮은 칸을 먼저 확장하여 도달 비용과 이전 칸을 기록한다. 양의 가중치를 다루는 최단 비용 탐색 방식이다. MovementRangeResult.Costs는 도달 칸별 비용, GetPathTo는 이전 칸을 따라 복원한 경로를 제공한다. 범위 계산은 경로 자료를 만들지만 현재 MoveTo는 도착 칸 중심으로 즉시 위치를 바꾼다.

6.2 장애물은 탐색 확장을 막는다

// BoardView.GetMovementRange의 반환 부분
return MovementRange.Calculate(
    Board,
    start,
    selectedUnit.MoveBudget,
    GetOccupiedCells(selectedUnit));

GetOccupiedCells는 움직이는 자신을 제외한 활성 Unit의 현재 칸을 모은다. 같은 팀도 막고 적 팀도 막으며 고정 장애물도 막는다. 목표 표시는 Unit이 아니므로 그 자체로 진입을 막지 않는다. 살아 있는 점유 정보를 매번 구하므로 아군이 비킨 칸은 다음 행동에서 열릴 수 있다.

// MovementRange.Calculate의 이웃 확장 중 발췌
if (blockedCells != null && blockedCells.Contains(next))
    continue;
TerrainType terrain = board.GetTerrain(next);
if (!terrain.IsWalkable)
    continue;
int candidateCost = costs[current] + terrain.MovementCost;
if (candidateCost > budget)
    continue;

이 부분은 보드 내부인지 확인한 뒤 실행된다. 점유 칸에서 확장을 중지하므로 도착과 통과가 모두 금지된다. 최종 목적지의 점유만 검사하면 그 뒤 칸으로 장애물을 뛰어넘을 수 있어 규칙이 맞지 않는다.

6.3 표시와 실행 사이의 재검증

선택 때 표시한 범위는 그 시점의 정보다. BattleController는 이동 실행 전에 BoardView.CanMoveTo를 다시 호출한다. CanMoveTo는 출발 칸과 같은지, 다른 유닛이 점유하는지, 최신 범위에 들어오는지 확인한다. 보기 좋은 강조 표시가 실제 규칙을 대신하지 않는다.

실험

Player 2 옆 (6,4) 고정 장애물의 칸을 눌러 보자. 목적지는 거절되어야 한다. 장애물 뒤의 칸이 표시된다면 다른 합법 우회 경로가 예산 안에 있는지 먼저 살핀다. 표시 자체만으로 “장애물을 통과했다”고 단정하지 않는다.

진단과 복구

범위와 이동 가능 여부가 다르면 양쪽이 GetMovementRange를 공유하는지 본다. 모든 지형이 평지처럼 보이면 BoardView의 mapText와 네 지형 Tile 참조를 확인한다. 예산과 다르게 보이면 시작 칸 비용을 더했는지, x/y 셀 좌표 대신 월드 위치를 직접 비교했는지 확인한다.

재현 가능한 적 의사결정

7.1 후보 생성과 선택을 분리한다

EnemyAI.ChooseDestination은 BoardView.GetMovementRange가 제공한 합법 도달 칸을 후보로 사용한다. 먼저 규칙이 가능한 칸을 만들고, 그 안에서 목표에 유리한 칸을 고르는 구조다. 그래서 적도 아군과 같은 지형 예산·강·점유 제약을 따른다.

// EnemyAI.ChooseDestination의 후보 정렬
var orderedCandidates = movementRange.Costs
    .Where(pair => pair.Key != start)
    .OrderBy(pair => ManhattanDistance(pair.Key, goalCell))
    .ThenBy(pair => pair.Value)
    .ThenBy(pair => pair.Key.y)
    .ThenBy(pair => pair.Key.x);

맨해튼 거리는 |목표.x−칸.x|+|목표.y−칸.y|다. 4방향 보드에서 단순한 목표 근접도 기준이지만 지형 비용이나 장애물을 포함한 전체 경로 길이는 아니다. pair.Value는 이번 이동에 필요한 실제 비용이며 거리 동률일 때 사용한다. 이후 y, x로 동률을 완전히 해소한다.

7.2 손으로 정렬해 보기

후보 칸목표 거리이동 비용
(2,3)33
(1,2)32
(0,1)32

위 표는 정렬 원리를 연습하는 가상 후보 자료다. 거리 동률에서 비용 2인 두 칸이 우선이고, 그중 y가 1인 (0,1)이 선택된다. y까지 같으면 x가 작은 칸을 고른다. 실제 게임에서는 이 값들을 보드와 목표로 계산한다.

7.3 아무 이동도 하지 않는 경우

// 후보가 없는 경우에는 start를 반환한 다음,
// 최선 후보가 있어도 거리 감소가 없으면 대기한다.
if (ManhattanDistance(bestCandidate.Key, goalCell) >=
    ManhattanDistance(start, goalCell))
{
    return start;
}

더 가까워질 수 없으면 제자리다. TakeTurnAsync는 이 경우 이동 명령을 실행하지 않지만 행동 표시와 대기는 수행한다. 정지했다고 곧바로 비동기 오류라고 판단하지 말고 도달 후보와 거리 감소를 확인해야 한다.

이것은 탐욕적 규칙이다. 우회하려면 잠시 목표에서 멀어져야 하는 지도에서는 멈출 수 있다. 결정성은 같은 입력에서 같은 결과라는 뜻이며, 장기 최적성이나 반드시 목표에 도달한다는 보장은 아니다.

재현 실험

R 후 같은 순서로 아군을 같은 칸에 이동시키고 적 도착 칸을 기록한다. 다시 R 후 같은 행동을 반복해 비교한다. 아군 점유가 바뀌면 AI 입력 자체가 달라진 것이므로 결과가 달라도 비결정성의 증거는 아니다.

복습: 목표 거리 대신 이동 비용을 첫 정렬 키로 쓰면?

이번 이동에 싼 칸을 먼저 고르게 되어 목표 접근보다 적은 이동 비용을 우선한다. 동작이 달라지는 설계 변경이다. 필수 구현의 정렬을 확인한 뒤 확장 실험으로 비교한다.

UniTask: 순서·중복·취소

8.1 순차 행동의 의미

TurnManager.RunEnemyPhaseAsync는 Units 목록을 돌며 적과 대응하는 EnemyAI를 고른다. 적을 발견한 순서로 AI 인덱스를 진행하므로 Units의 적 부분과 Enemy Ais 목록을 일치시킨다. 장면은 Enemy 1, Enemy 2 순서다. 비활성·고정·AI 누락 대상은 행동에서 건너뛴다.

// 적 한 명씩 진행하는 실제 반복문 내부
EnemyTurnStarted?.Invoke(unit);
await enemyAi.TakeTurnAsync(unit, _enemyGoalCell, cancellationToken);
if (CheckGoal(unit)) return;

첫 적의 await가 끝나야 다음 적으로 간다. 각 적 후 목표를 검사해 패배가 되면 즉시 반환하므로 두 번째 적의 불필요한 행동을 막는다. 모든 적이 끝나고 경기 진행 중이면 BeginPlayerPhase로 돌아간다.

8.2 행동은 즉시, 간격은 비동기

// EnemyAI.TakeTurnAsync 일부
if (destination != start)
    new MoveUnitCommand(enemy, _board, destination).Execute();

enemy.SetMoved(true);
await UniTask.Delay(
    TimeSpan.FromMilliseconds(_turnDelayMilliseconds),
    cancellationToken: cancellationToken);

기본 _turnDelayMilliseconds는 350이다. 유닛이 350ms 동안 부드럽게 이동하는 코드가 아니다. 칸 이동 후 다음 행동까지 간격을 둔다. 적 HasMoved는 표시되지만 적 행동 자격은 아군 CanPlayerAct를 사용하지 않으므로 다음 적 턴에서도 수행된다.

8.3 중복 시작과 수명 종료는 다른 문제

Phase를 Enemy로 먼저 바꾸면 아군 입력은 즉시 막힌다. _isEnemyPhaseRunning은 적 루프가 두 번 시작되는 것을 막으며 finally에서 해제한다. 수명 취소는 재시작·장면 파괴로 더 이상 소유 객체가 존재하지 않을 때 남은 대기를 끝내는 문제다. 둘 중 하나만 있어서는 두 문제를 모두 해결하지 못한다.

// RequestEndPlayerPhase가 객체 수명 토큰을 전달
CancellationToken lifetimeToken = destroyCancellationToken;
RunEnemyPhaseForLifetimeAsync(lifetimeToken).Forget();

// 수명 래퍼의 예외 처리 조건
catch (OperationCanceledException)
    when (lifetimeToken.IsCancellationRequested)
{
}

Forget은 반환된 작업을 기다리지 않고 시작하는 호출 경계다. 내부 래퍼는 RunEnemyPhaseAsync를 await한다. 취소 토큰은 바깥에서 받기만 해서는 부족하고 실제 UniTask.Delay까지 전달해야 한다. 자기 수명 토큰이 취소된 경우의 취소 예외만 예상 종료로 처리한다.

실험과 복구

적 턴이 시작되면 보드와 Undo를 눌러 입력이 무효인지 본다. 대기 중 R을 눌러 새 경기로 돌아간 뒤 옛 루프가 새 턴을 바꾸지 않는지 확인한다. 예외가 보이면 처음 발생한 오류부터 읽고, 토큰 전달·파괴 수명·finally를 확인한다. catch(Exception)으로 모든 오류를 숨기는 방식은 원인을 해결하지 못한다.

목표·HUD·재시작의 데이터 흐름

9.1 공간 판정과 소유 규칙

ObjectiveZone은 Owner와 Cell을 갖는다. GetResultFor는 활성 행동 유닛이 상대 소유 목표에 들어온 경우 결과를 돌려준다. 실제로 같은 칸에 있는지는 TurnManager.CheckGoal이 먼저 확인한다. 소유 규칙 메서드만 호출해 목표 진입을 판정했다고 생각하면 안 된다.

// CheckGoal의 공간 확인 부분
Vector2Int cell = _board.WorldToCell(unit.transform.position);
foreach (ObjectiveZone objective in _objectives)
{
    if (objective == null || objective.Cell != cell) continue;
    BattleResult result = objective.GetResultFor(unit);
    if (result == BattleResult.Playing) continue;
    MarkFinished(result);
    return true;
}

Enemy Goal (11,6)에 Player가 도착하면 PlayerWon, Player Goal (0,4)에 Enemy가 도착하면 PlayerLost다. 같은 팀 목표는 종료를 만들지 않는다. Fixed Blocker는 IsTurnUnit=false라 목표 판정 대상이 아니다.

9.2 결과를 확정하고 화면에 전달하기

// GameManager.TryFinish의 한 번 확정 규칙
if (!IsPlaying || result == BattleResult.Playing)
    return;
Result = result;

// TurnManager.MarkFinished에서
_result = result;
_gameManager?.TryFinish(result);
SetPhase(BattlePhase.Finished);

완성 게임 흐름은 CheckGoal이 경기 진행 중인지 검사하고 실제 종료 결과만 MarkFinished에 전달한다. MarkFinished를 Playing으로 호출하는 것은 종료 API의 정상 사용이 아니다. 결과 확정 뒤 PhaseChanged가 발생하여 PhaseHud.Refresh가 텍스트를 갱신한다. PhaseHud는 OnEnable에서 구독하고 OnDisable에서 해제해 수명과 이벤트 연결을 맞춘다.

게임 장면의 위 표기는 실제 화면을 알아보기 위한 인용이다. 종료 후에는 CanAcceptPlayerInput이 거절되어 보드 이동과 Undo가 차단된다. 텍스트만 바꾸는 것으로 게임을 끝내지 않는다.

9.3 재시작은 새로운 장면 수명

GameManager.Update는 Input System의 Keyboard.current가 있고 R 키가 그 프레임에 눌렸는지 확인한다. 종료 뒤에도 RestartCurrentScene을 호출할 수 있다. 현재 Scene의 buildIndex가 음수면 경고 후 반환하고, 유효하면 SceneManager.LoadScene으로 다시 읽는다.

Scene activeScene = SceneManager.GetActiveScene();
// 완성본은 buildIndex < 0을 먼저 검사해 경고한다.
SceneManager.LoadScene(activeScene.buildIndex);

Lesson05 장면이 활성 빌드 장면 목록에 있어야 한다. 재로드는 위치만 되돌리는 Undo와 다르다. 유닛, GameManager, TurnManager, 명령 기록이 새 경기 수명으로 시작하며 옛 비동기 대기는 파괴 토큰으로 취소된다.

복구 예시

통합 미션·오류 사전·복습

10.1 완료를 관찰로 증명하기

두 사람이 조작자와 관찰자를 번갈아 맡는다. “예상 / 실제 / 원인 / 수정 후 결과” 네 칸으로 기록한다. 목표는 성공 화면 하나가 아니라 규칙 경계들이 함께 작동하는 상태다.

  1. 초기 아군 세 명·적 두 명·회색 장애물과 목표 위치를 확인한다. 적·고정 장애물 선택은 거절되어야 한다.
  2. 한 아군 이동 뒤 재선택 거절, Undo 뒤 위치·행동 권한 복원을 확인한다.
  3. 강·점유·예산 초과 목적지가 거절되는지 확인한다. 우회 경로가 있다면 비용 안인지 구분한다.
  4. 세 아군을 각각 일반 칸으로 이동한다. 적 1→적 2→다음 Player와 행동 초기화를 관찰한다. Enemy 중 보드·Undo는 무효다.
  5. R 후 Player 3에서 (11,6)까지 합법 범위를 확인하여 승리를 만든다. Finished에서 보드·Undo가 막히는지 본다.
  6. R 후 적의 접근 경로를 막지 않게 아군을 이동하며 턴을 반복한다. 적이 (0,4)에 도착해 패배하면 종료와 R 초기화를 확인한다. 적 정지는 더 가까운 후보 유무로 진단한다.

10.3 설명하는 연습

  1. Instance의 private set과 Awake 중복 검사가 각각 무엇을 막는가?
  2. TurnManager를 Singleton으로 만들지 않은 이유를 장면 의존성으로 설명하라.
  3. 세 번째 아군 일반 이동 뒤 Undo가 불가능한 이유는 무엇인가?
  4. 목표 판정과 완료 통지 순서를 바꾸면 어떤 잘못된 진행이 가능한가?
  5. 결정성과 최적성을 구분하고 AI가 멈출 수 있는 지형을 설명하라.
  6. R 재시작 시 결과 초기화와 비동기 취소가 어떻게 연결되는가?
핵심 답안 확인

1: 외부 대입 제한과 장면 객체 중복 방어다. 2: 보드·유닛·목표의 연결을 명시하고 전투마다 다른 객체를 둘 수 있다. 3: Enemy 전환과 공유 기록 초기화가 일어난다. 4: 승리가 이미 가능한데 적 턴을 먼저 시작할 수 있다. 5: 같은 입력에서 같은 선택은 하지만 일시적으로 목표에서 멀어져야 하는 우회는 거절한다. 6: 장면 재로드가 새 상태를 만들고 기존 객체 파괴가 기존 대기를 취소한다.

10.5 요약과 확장

한 경기의 결과는 GameManager가 소유하고, TurnManager는 참조로 연결된 유닛과 목표의 진행을 관리한다. 명령은 위치와 행동 소모를 함께 복구하며 Undo는 현재 Player 구간에 한정된다. 보드 규칙 위에서 적이 결정적으로 선택하고, 순차 await와 수명 취소가 행동 순서와 장면 종료를 지킨다. 목표 판정은 결과·Phase·HUD·입력 차단으로 이어진다.

필수 미션 뒤에는 RequestEndPlayerPhase에 대기 버튼을 연결하는 설계, 턴 로그, 다른 AI 평가 순서, 의존성 전달 방식을 비교한다. 새 기능을 GameManager에 바로 넣기 전에 “경기 결과 소유자의 책임인가”를 먼저 묻는다.
