위치 대입은 이전 위치를 덮어쓴다. Unit 객체가 사라진다는 뜻은 아니다. 직접 호출만으로는 “누가 어디에서 어디로 이동했는가”라는 별도의 기록이 생기지 않는다.

호출은 그 순간 일을 요청한다. 기록은 그 요청을 나중에도 구분할 수 있게 남긴다. 취소가 필요해졌을 때는 현재 결과만 보는 대신 실행 전 상태의 어느 부분이 필요한지 먼저 찾는다.

Chapter 02

한 칸 기억의 성과와 한계

출발 셀 하나만 기억해 볼까?

설계 비교용 가상 코드 — 현재 구현에 없는 첫 시도

lastCell = board.WorldToCell(unit.transform.position);
unit.MoveTo(board, targetCell);

해결한 것

이동 전에 출발 셀 값을 보존했다. 항상 같은 대상 하나만 다루면 유용한 시작이다.

남은 질문과 답

어느 Unit을 돌릴까? 목적지와 대상도 요청에 속한다. 여러 이동 대상이 있는 가상 상황이라면 셀 하나로 대상을 구별할 수 없다.

lastUnit과 lastCell이면 한 번은 되돌린다

설계 비교용 가상 코드 — 현재 구현에 없는 첫 시도

lastUnit = unit;
lastCell = board.WorldToCell(unit.transform.position);
unit.MoveTo(board, targetCell);
// 한 번 되돌릴 때
lastUnit.MoveTo(board, lastCell);

가상 첫 시도는 마지막 행동 하나만 취소하는 요구에는 충분할 수 있다. 현재 Teacher에는 이 lastUnit/lastCell 필드가 없다. 여러 번 취소할 때의 보관 방법은 아직 없다.

같은 유닛을 두 번 움직이면 첫 기록이 덮인다

시점실제 위치가상 lastCell
시작(5,4)없음
첫 이동(5,5)(5,4)
둘째 이동(4,5)(5,5) · 앞 값 덮음
한 번 취소(5,5)첫 출발 (5,4)는 이미 소실

두 이동은 같은 Blue에 대한 요청이다. 값 한 칸을 계속 덮어쓰는 대신, 이동마다 별도 기록과 취소 행동을 묶어야 한다.

생각해 볼 답: lastUnit과 lastCell은 마지막 한 번이라는 작은 요구에는 합리적이다. 여러 이동을 되돌리려면 이전 값을 덮지 않는 별도 기록이 필요하다. 여러 유닛이 움직이는 사례는 가상 확장이고 현재 장면은 이동 가능한 Blue 하나와 고정 Black 하나다.

Chapter 03

요청 객체와 책임의 경계

한 요청에 속한 것들을 한곳에 모은다

함께 기억할 것

  • 수신자: 어느 Unit인가
  • 협력자: 어느 BoardView인가
  • 출발 셀과 목적지 셀

함께 제공할 행동

  • Execute: 저장한 목적지로 요청
  • Undo: 저장한 출발 셀로 요청

수신자는 실제 작업을 수행하는 객체다. 이력은 이동의 세부를 직접 계산하지 않고 이 묶음에 실행이나 취소를 요청한다.

Command는 요청을 객체로 표현한다

누가 무엇을 할지에 필요한 정보와
실행 행동을 하나의 객체에 담는다.

이동 요청 객체

MoveUnitCommand 하나가 Unit 참조, 좌표와 실행·취소 방법을 기억한다. 이동마다 새 객체를 만든다.

분리되는 책임

요청을 만드는 쪽, 보관하고 호출하는 쪽, 실제 위치를 바꾸는 쪽을 구분할 수 있다.

실제 클래스는 어떤 역할을 맡을까?

Client · 생성
BattleController
검사한 이동 요청을 만든다.
Command · 요청
MoveUnitCommand
정보와 실행·취소를 묶는다.
Invoker · 호출/보관
CommandHistory
실행하고 이력을 보관한다.
Receiver · 작업

MoveTo로 위치를 바꾼다.

BoardView는 셀 변환을 돕는 협력자다. 역할은 설계상의 관점이며 클래스 이름을 반드시 Client나 Receiver로 지어야 하는 규칙은 아니다.

요청과 알림은 방향이 다르다

Command · 해 달라

“이 Unit을 이 셀로 이동해 달라.”
실행할 대상과 매개변수를 가진 요청이다.

이벤트/알림 · 일어났다

“이동이 끝났다.”
이미 일어난 사실의 전달이다. 알림 자체가 원상 복구 방법을 제공하지는 않는다.

개념 비교다. Lesson2에 새 이벤트 API가 있는 것은 아니다. 요청을 객체로 만들어야 실행 전에 보관하거나 실행 뒤 취소 정보와 함께 다루기 쉽다.

요청을 묶으면 이력은 좌표 계산을 몰라도 된다. 단, 생성하는 Client는 어느 대상과 매개변수를 넣을지 여전히 알아야 한다. Command는 의존성을 없애는 마법이 아니라 각 책임이 알아야 할 것을 정리하는 경계다.

실행과 취소의 계약

ICommand는 실행할 수 있다는 약속이다

public interface ICommand

    void Execute();
}

void Execute()

매개변수와 반환값이 없다. 실행에 필요한 정보는 이 계약을 구현한 객체가 가진다.

계약의 한계

bool 성공 결과가 아니다. 이 선언만으로 이동 허용 검사나 취소 가능성까지 보장하지 않는다.

취소할 요청은 Undo도 제공한다

public interface IUndoableCommand : ICommand
{
    void Undo();
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/IUndoableCommand.cs

IUndoableCommand는 ICommand를 이어받으므로 Execute와 Undo를 모두 약속한다. 이력은 구체 이동 클래스 대신 이 계약으로 요청을 보관한다. 실제 이동 방법은 MoveUnitCommand가 구현한다.

참조와 좌표를 요청 객체가 보관한다

private readonly Unit _unit;
private readonly BoardView _board;
private readonly Vector2Int _fromCell;
private readonly Vector2Int _toCell;

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/MoveUnitCommand.cs

멤버기억하는 뜻
_unit / _board작업할 Unit / 좌표 변환 협력자
_fromCell / _toCell되돌릴 출발 / 실행할 목적지

readonly는 생성 후 이 필드에 다시 대입하지 않는다는 뜻이다. 참조한 Unit 전체가 불변이 되는 것은 아니다. Unit의 현재 위치는 실행으로 바뀐다.

다형성: 이력은 IUndoableCommand의 Execute/Undo를 부른다. 실제 연결된 객체가 자기 구현을 수행한다. 현재 구체 요청은 MoveUnitCommand다. 새로운 요청 종류를 넣으려면 그 작업의 취소 정보와 의미도 직접 설계해야 한다.

Chapter 05

출발 셀을 언제 보관하는가

이 구현은 생성자에서 출발 셀을 잡는다

public MoveUnitCommand(Unit unit, BoardView board, Vector2Int toCell)
{
    _unit = unit;
    _board = board;
    _fromCell = board.WorldToCell(unit.transform.position);
    _toCell = toCell;
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/MoveUnitCommand.cs

new MoveUnitCommand가 실행되는 순간, BoardView.WorldToCell로 현재 위치를 셀로 바꿔 저장한다. Controller는 생성 직후 실행한다. 생성과 실행 사이에 Unit이 별도로 이동하면 저장한 출발 셀은 실행 직전 위치와 달라질 수 있다.

이 생성자는 수신자 Unit의 현재 월드 위치를 BoardView.WorldToCell로 셀로 해석한다. 목적지도 셀 값으로 받는다. 즉 현재 구현의 취소 기준은 생성 시점이다. 생성 직후 실행하는 Controller 경로에서는 이동 전에 출발을 잡는다.

생성 후 오래 보관했다가 실행하는 설계라면 그 사이의 이동을 어떻게 취급할지 정해야 한다. 실행 직전 캡처를 선택하는 다른 설계도 가능하다. 현재 코드가 그 정책을 이미 제공한다고 읽지 않는다.

Chapter 06

Execute와 Undo가 요청하는 실제 작업

실행은 저장한 목적지로 요청한다

public void Execute()
{
    _unit.MoveTo(_board, _toCell);
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/MoveUnitCommand.cs

누구에게?

선택을 다시 조회하지 않고, 생성할 때 저장한 _unit에게 요청한다.

어디로?

지금 마우스 위치가 아니라 저장한 _toCell이다. 구체 위치 대입은 Unit.MoveTo가 맡는다.

취소는 저장한 출발 셀로 요청한다

public void Undo()
{
    _unit.MoveTo(_board, _fromCell);
}

Execute와 같은 Unit.MoveTo 통로를 사용한다. 방향만 반대로 계산하는 것이 아니라 기억한 _fromCell로 복원한다. Command 안에 프레임 보간이나 애니메이션 역재생은 없다.

답: Undo는 그림을 역재생하는가? 아니다. 루트 위치를 저장한 출발 셀로 즉시 바꾼다. 표현 컴포넌트가 독립적으로 변화를 관찰한다. 같은 MoveTo를 사용하므로 양방향 모두 같은 좌표 변환 경계를 따른다.

Chapter 07

검사·실행·이력의 순서

허용되지 않은 시도는 기록 앞에서 멈춘다

if (SelectedUnit == null || !_board.CanMoveTo(SelectedUnit, targetCell))
{
    return false;
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/BattleController.cs · TryMoveSelectedUnit 앞부분

선택 없음 또는 목적지 거절이면 false다. Command를 만들거나 이력에 넘기기 전이므로 유령 기록이 생기지 않는다. 기존 선택이 있었다면 선택과 범위 표시도 유지한다. 필수 참조는 연결되어 있다는 전제다.

검사 뒤에 생성하고 실행을 맡긴다

MoveUnitCommand command = new MoveUnitCommand(SelectedUnit, _board, targetCell);
_history.Execute(command);
SelectedUnit = null;
_highlighter.Hide();
return true;

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/BattleController.cs · 앞의 선택/목적지 검사 생략

허용된 경우에만 Command를 만들고 이력에 실행을 맡긴다. 그 뒤 선택을 null로 하고 표시를 숨긴다. 성공한 이동이 이전 선택 상태까지 기록하는 것은 아니다.

실행이 끝난 다음 이력에 넣는다

public void Execute(IUndoableCommand command)
{
    command.Execute();
    _commands.Push(command);
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/CommandHistory.cs

순서의 의미

Execute가 정상 반환한 뒤 Push한다. 실행 중 예외가 나면 이 요청은 Push에 도달하지 않는다.

검사의 주인

Execute는 void다. 이력은 이동 허용 여부를 판정하지 않는다. Controller의 사전 검사를 전제로 한다.

가장 나중 요청부터 꺼낸다

위 · m2 : (5,5) → (4,5)
아래 · m1 : (5,4) → (5,5)

Stack은 넣은 곳에서 거꾸로 꺼내는 자료구조다. Last In, First Out = LIFO. m1 다음 m2를 실행했다면 첫 Undo 대상은 m2다. m1/m2와 항목 수는 설명용 표기이며 공개 Count API가 아니다.

허용 여부는 Controller가 BoardView에 묻는다. CommandHistory.Execute는 void이므로 그 반환값으로 이동 성공을 다시 판단할 수 없다. 받은 요청을 실행하고 정상 반환 뒤 Push하는 역할이다. 임의의 잘못된 Command를 스스로 검증하는 범용 안전장치가 아니다.

답과 이유: m2가 가장 위이므로 먼저 취소한다. 각 Command가 자기 출발 셀을 보관했기에 앞선 출발 값이 덮이지 않는다. Black은 어떤 요청의 수신자도 아니므로 움직이지 않는다.

비어 있으면 false, 있으면 꺼내서 Undo한다

public bool UndoLast()
{
    if (_commands.Count == 0)
    {
        return false;
    }

    _commands.Pop().Undo();
    return true;
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/CommandHistory.cs

Count는 내부 Stack에서만 사용한다. CommandHistory가 Count/Clear/Redo를 공개하는 것은 아니다. 빈 이력은 정상 결과이며 Unit에 Undo 요청을 보내지 않는다.

검산: 시작 (5,4)에서 첫 목적지 (5,5)는 한 칸, 다음 (4,5)도 한 칸이다. 거절 시도 (6,4)는 고정 Black이 있는 셀이다. 두 성공 후 m2의 출발은 (5,5), m1의 출발은 (5,4)다. 이 순서로 꺼내면 원래 셀로 돌아간다. 이력 길이는 설명용 표기이며 공개 조회 메서드를 가정하지 않는다.

현재 구현은 같은 셀로의 허용된 이동도 실행하고 기록한다. 위치 차이가 없다는 사실만으로 이력이 비어 있다고 추론하면 안 된다. 허용 여부와 기록 정책은 실제 호출 흐름으로 판단한다.

선택 갱신과 복원의 한계

Undo 뒤의 선택 표시는 어디까지 바뀔까?

public void OnUndoClicked()
{
    if (_history.UndoLast() && SelectedUnit != null)
    {
        Select(SelectedUnit);
    }
}

현재 실제 코드 발췌 — MiniTactics_Teacher_Lesson2/Assets/Lesson02/Scripts/BattleController.cs

UndoLast가 true이고 현재 선택이 있을 때만 Select로 범위를 다시 계산한다. 빈 이력이면 재선택하지 않는다. 이전 이동 유닛을 자동 선택하거나 과거 선택·UI 상태를 통째로 복원하지 않는다.

위치 취소는 게임 전체의 시간 되감기가 아니다

현재 복원 범위

저장한 Unit을 저장한 출발 셀로 옮긴다. LIFO로 최근 이동을 먼저 취소한다.

별도 정책이 필요한 것

외부에서 중간에 바꾼 상태, 사라진 수신자, 다른 부작용, 과거 UI와 애니메이션 시간은 자동 복원되지 않는다.

정확한 Undo에는 “무엇을 저장하고 어떤 순서로 바꿀 것인가”라는 정책이 필요하다. 요청 객체 하나가 모든 상태 변경을 알아서 추적하지는 않는다.

성공 이동은 선택을 지우고 표시를 숨긴다. 이후 Undo를 눌러도 자동으로 그 Unit이 선택되지는 않는다. 별도로 현재 선택이 있으면 성공 Undo 뒤 Select로 현재 위치의 범위를 갱신한다. Undo가 false면 이 갱신도 일어나지 않는다.

저장한 위치로 되돌리는 것은 전체 상태 스냅샷을 복구하는 것과 다르다. 외부 변경, 삭제된 대상, 별도 부작용이 있다면 적용 가능한 취소 순서와 수명 규칙을 정해야 한다.

확장 가능성과 적용 판단

보관한 요청은 다른 설계로 확장할 수 있다

가능한 확장 · 현재 미구현추가로 정할 것
지연 실행 / 다른 Client(예: AI)생성·실행 사이 상태 변화와 유효성 검사 시점
Redo취소 이력과 새 행동 발생 시 분기 처리
Replay적절한 시작 상태, 안정된 참조·매개변수, 재현 가능한 실행

Unity 참조를 담은 C# 객체는 자동으로 파일/네트워크 형식이 되지 않는다. Command를 사용했다고 결정적 재현이나 직렬화가 보장되는 것도 아니다.

기록이 필요한 요청인지 먼저 판단한다

유용할 때

행동별 이력과 취소, 요청 보관, 다른 생성자/입력 주체의 연결이 실제로 필요하다.

부담과 대안

요청마다 객체·저장 상태·연결·수명 정책이 늘어난다. 단순 UI 패널 표시 한 번이면 직접 호출로 충분할 수 있다.
