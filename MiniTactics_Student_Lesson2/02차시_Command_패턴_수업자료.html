Command 패턴

잘못 이동한 유닛을 되돌리려면, 게임은 무엇을 기억해야 할까?

Yesterday's Success

1차시 코드는 목표를 정확히 달성했다

  • 이동 가능한 유닛을 마우스로 선택한다.
  • 이동거리 2의 범위를 계산해 표시한다.
  • 점유 셀은 빨간색으로 구분한다.
  • 유효한 목적지를 클릭하면 셀 중심으로 이동한다.

중요한 관점

Undo가 요구되지 않았던 1차시에는 직접 이동 호출이 단순하고 충분한 설계였다.

Actual Code · BattleController

이동 가능하면 MoveTo()를 직접 호출한다

public bool TryMoveSelectedUnit(Vector2Int targetCell)
{
    if (!_board.CanMoveTo(SelectedUnit, targetCell))
        return false;

    SelectedUnit.MoveTo(_board, targetCell);
    SelectedUnit = null;
    HideRange();
    return true;
}

Observation

직접 호출은 결과를 만들지만 요청을 남기지 않는다

남는 것

  • 유닛의 새로운 월드 위치
  • 이동이 끝난 화면

남지 않는 것

  • 어떤 유닛이 이동했는가
  • 어디에서 출발했는가
  • 어디로 이동했는가
  • 어떤 순서로 이동했는가

실행된 행동과 행동의 기록은 서로 다른 문제다.

Actual Code · Unit

MoveTo()는 현재 위치를 새 위치로 덮어쓴다

public void MoveTo(BoardView board, Vector2Int targetCell)
{
    transform.position = board.CellToWorld(targetCell);
}

대입이 끝난 뒤 transform.position만 살펴보면 출발 위치를 복구할 수 없다.

출발 셀과 도착 셀

First Attempt

첫 생각: lastCell만 저장하자

private Vector2Int lastCell;

lastCell = _board.WorldToCell(SelectedUnit.transform.position);
SelectedUnit.MoveTo(_board, targetCell);

한 유닛의 마지막 이동 한 번만 취소한다면 작동할 수 있다. 아직 틀린 해결책은 아니다.

More State

그런데 어떤 유닛인지도 기억해야 한다

private Unit lastUnit;
private Vector2Int lastCell;

lastUnit = SelectedUnit;
lastCell = _board.WorldToCell(SelectedUnit.transform.position);

현재 행동

BattleController가 이동을 검증하고 실행한다.

추가된 책임

이제 과거 이동의 유닛과 위치까지 관리한다.

Overwrite Again

두 번 이동하면 첫 번째 기록이 사라진다

순서이동lastUnitlastCell
1A: (5,4) → (5,6)A(5,4)
2B: (2,2) → (3,2)B(2,2)

두 번째 저장이 첫 번째 기록을 덮어쓴다. 이제 A의 이동은 취소할 수 없다.

Think · Predict

Undo를 세 번 지원하려면 필드가 몇 개 필요할까?

lastCell1, lastCell2, lastCell3…
이 방향이 계속 가능할까?

  • 기록 개수만큼 필드가 늘어난다.
  • 유닛과 위치의 짝을 맞춰야 한다.
  • 실행 순서도 따로 관리해야 한다.
  • Redo가 추가되면 기록 이동도 필요하다.

우리는 이미 “이동 한 건”이라는 새로운 데이터 단위를 찾고 있다.

Data Boundary

필요한 것은 위치 하나가 아니라 완전한 이동 기록이다

이동 기록 = 유닛 + 보드 + 출발 셀 + 도착 셀 + 실행/취소 방법

서로 항상 함께 사용되는 정보와 행동을 하나의 객체로 묶으면 기록 한 건을 통째로 저장하고 꺼낼 수 있다.

Command Pattern

Command는 요청을 객체로 만든다

“이 유닛을 이 셀로 이동해라”라는 메서드 호출을, 저장하고 전달할 수 있는 객체로 바꾼다.

직접 호출

unit.MoveTo(board, to);

명령 객체

ICommand command =
    new MoveUnitCommand(...);

참고: Game Programming Patterns, Command — 메서드 호출을 객체로 다루는 설명

What Changes?

호출을 객체로 만들면 시간에서 분리할 수 있다

직접 호출명령 객체
호출하는 순간 실행된다.지금 만들고 나중에 실행할 수 있다.
실행이 끝나면 호출 자체는 사라진다.실행 후에도 객체를 기록으로 보관할 수 있다.
과거 상태는 호출자가 따로 저장한다.명령이 실행과 취소에 필요한 상태를 가진다.

핵심은 간접 호출 자체가 아니라, 요청이 데이터가 되었다는 점이다.

Roles

Command 패턴은 네 역할을 분리한다

Client필요한 정보를 모아 명령을 만든다.
Command실행할 요청과 관련 상태를 표현한다.
Invoker명령을 실행하고 순서를 관리한다.
Receiver실제 작업을 수행하는 객체다.

역할 이름보다 중요한 질문은 “누가 만들고, 누가 보관하고, 누가 실제로 움직이는가?”이다.

Execution Contract

ICommand는 실행할 수 있다는 약속이다

public interface ICommand
{
    void Execute();
}

호출자는

구체적인 이동 방법을 몰라도 Execute()를 호출한다.

명령은

자신이 가진 정보로 Receiver에게 실제 작업을 요청한다.

Undo Contract

IUndoableCommand는 되돌릴 수 있다는 약속을 더한다

public interface IUndoableCommand : ICommand
{
    void Undo();
}

Execute()와 Undo()가 한 객체 안에 있으므로 실행할 때 사용한 상태와 되돌릴 때 사용할 상태가 분리되지 않는다.

Concrete Command

MoveUnitCommand는 이동 한 건의 상태를 가진다

public sealed class MoveUnitCommand : IUndoableCommand
{
    private readonly Unit _unit;
    private readonly BoardView _board;
    private readonly Vector2Int _fromCell;
    private readonly Vector2Int _toCell;
}

이 네 값이 하나의 객체에 묶이면서 여러 이동 기록을 같은 형태로 보관할 수 있다.

Capture Timing

출발 셀은 명령을 만들 때 확정한다

public MoveUnitCommand(
    Unit unit, BoardView board, Vector2Int toCell)
{
    _unit = unit;
    _board = board;
    _fromCell = board.WorldToCell(unit.transform.position);
    _toCell = toCell;
}

Record Rule

성공한 명령만 History에 기록한다

실행 가능

  1. 명령을 실행한다.
  2. Undo 스택에 Push한다.

기록하지 않는 경우

  • 점유된 목적지
  • 이동 범위 밖
  • 선택된 유닛 없음

History는 “시도한 입력”이 아니라 실제로 일어난 상태 변화를 기록한다.

LIFO

CommandHistory는 스택으로 최근 이동을 찾는다

TOP · C: (8,7) → (9,7)
B: (3,2) → (3,4)
A: (5,4) → (5,6)

가장 나중에 실행한 행동부터 되돌려야 상태가 자연스럽게 이전 단계로 돌아간다.

Beyond Undo

기록이 생기면 Redo와 Replay도 같은 구조에서 나온다

Redo

Undo한 명령을 별도 스택에 보관했다가 다시 Execute()한다.

Replay

저장된 명령 순서를 처음부터 실행해 같은 행동 흐름을 재현한다.

새 기능의 기반은 좌표가 아니라 시간 순서가 있는 명령 기록이다.

Judgment

모든 호출을 Command로 만들 필요는 없다

도입 가치가 큰 경우

  • Undo·Redo가 필요하다.
  • 실행을 나중으로 미뤄야 한다.
  • 행동을 기록·재생해야 한다.
  • 입력과 실행 주체를 분리한다.

비용

  • 명령 클래스와 객체가 늘어난다.
  • 어떤 상태를 언제 캡처할지 정해야 한다.
  • 실패한 명령의 기록 규칙이 필요하다.

생각하기: 단순한 UI 패널 열기와 유닛 이동 중 어느 쪽에 기록 가치가 더 큰가?

Takeaway

새 요구가 생기면 요청을 기억해야 할 때가 온다

  1. 1차시의 직접 호출은 이동을 잘 실행하지만 과거를 기록하지 않는다.
  2. Undo에는 유닛·출발·도착·실행 순서가 필요하다.
  3. Command는 요청과 필요한 상태를 객체로 묶는다.
  4. History는 명령을 순서대로 보관하고 최근 행동부터 취소한다.

Command 패턴의 핵심은 “실행할 행동”을 저장하고 다룰 수 있는 데이터로 만드는 것이다.
