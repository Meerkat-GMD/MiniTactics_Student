# Mini Tactics 발표자료 형식 규약

2026-09-15에 사용자가 선택한 형식을 이후 세션과 새 차시에서도 유지하기 위한 프로젝트 규약이다. 차시별 발표 HTML의 신규 작성·수정·검토에 적용한다.

## 사용자가 확정한 방향

- “2차시 수업자료 구성으로 다시 다 바꿔줘.”
- 발표자료만 읽어도 처음 배우는 사람이 공부할 수 있어야 한다.
- 발표자는 화면에 있는 내용을 바탕으로 개념과 이유를 설명할 수 있어야 한다.
- 슬라이드 화면 중심의 구성을 유지하고 실습을 별도로 덧붙이지 않는다.
- “앞으로 다른 세션에서 작업하더라도 해당 형식을 유지할 수 있도록 기록 남겨줘.”

이 문서는 이미 정해진 방향을 기록한다. 작업할 때마다 형식을 다시 선택하거나 승인을 요청하지 않는다. 사용자가 이후 명시적으로 변경을 요청하면 그 요청을 따르고 이 규약도 갱신한다.

## 실제 기준 파일

**화면 서식과 설명 전개의 기준**은 [2차시 Command 수업자료](../MiniTactics_Student_Lesson2/02차시_Command_패턴_수업자료.html)다. 설명을 읽고 비슷하게 다시 만드는 대신, 이 파일의 실제 HTML과 CSS를 열어 재사용한다. 서식 일치 검사를 통과시키려고 기준 파일 자체를 임의로 바꾸지 않는다.

같은 형식으로 수정한 사례는 다음과 같다. 기준 반영 커밋은 `dd3a5149882fa9703c8573396490580dfaecc9a7`이다.

- [1차시 객체지향](../MiniTactics_Student_Lesson1/01차시_객체지향_수업자료.html)
- [3차시 Flyweight](../MiniTactics_Student_Lesson3/03차시_Flyweight_패턴_발표자료.html)
- [4차시 State](../MiniTactics_Student_Lesson4/04차시_State_패턴_발표자료.html)
- [5차시 Singleton](../MiniTactics_Student_Lesson5/05차시_Singleton_패턴_발표자료.html)
- [6차시 Observer](../MiniTactics_Student_Lesson6/06차시_Observer_패턴_발표자료.html)

2차시의 기본 서식에 더해, 위 수정본에는 모바일 화살표 정렬·긴 식별자 줄바꿈·목차가 열린 동안의 키보드 처리·인쇄·JavaScript 비활성화 대응이 포함되어 있다. 새 자료에는 수정본의 공통 프레임을 복사하고, 2차시의 기본 디자인과 일치하는지 확인한다. 이 문서나 특정 세션의 임시 생성 스크립트보다 저장소의 실제 기준 HTML을 우선 확인한다.

## 화면 구성

1. 데스크톱에서는 16:9 슬라이드 한 장을 화면 중앙에 표시한다. 본문 전체가 한 화면에 들어가야 한다. 분량이 많으면 장을 나누고, 글자를 계속 줄이거나 내용을 감추지 않는다.
2. 하단에는 `←`, `목차`, `현재 / 전체`, `→`만 둔다. 목차는 버튼을 눌렀을 때 대화상자로 열린다. 좌우 방향키, PageUp/PageDown, Home/End와 슬라이드 해시 이동을 지원한다.
3. 표지, 제목, 짧은 주제 표시, 본문, 우측 상단 장 번호의 위치와 위계를 유지한다. 표지의 “미니 택틱스로 이해하는” 문구를 중복으로 넣지 않는다.
4. 2차시의 글꼴 목록(`Pretendard`, `Noto Sans KR`, system-ui), 어두운 배경, 청록·보라·노랑 강조, 여백, 테두리와 모서리를 유지한다. 글꼴을 내려받는 외부 의존성은 추가하지 않는다.
5. 사이드바, 대시보드형 화면, 교재처럼 모든 장이 이어지는 기본 화면, 발표/학습 모드 전환, 숨겨진 해설 영역을 새로 붙이지 않는다. JavaScript를 끈 경우의 순차 표시와 인쇄는 예외다.
6. 모바일에서는 세로로 재배치하고 필요한 세로 스크롤을 허용한다. 가로 넘침이나 글자·화살표 겹침이 없어야 하며 탐색 버튼에 접근할 수 있어야 한다.

공통 프레임은 `.app > .stage > .deck`, 각 장은 `.slide`와 활성 장의 `.is-active`를 사용한다. 탐색 ID는 `prevBtn`, `tocBtn`, `slideCounter`, `nextBtn`, `tocDialog`, `tocCloseBtn`이다. 제목 ID·장 번호·목차·해시는 실제 장 수에 맞춰 함께 갱신한다.

새 레이아웃을 만들기 전에 다음 **2차시의 기존 구성 요소**에서 적절한 것을 고른다.

| 목적 | 기존 구성 요소 |
|---|---|
| 두 관점 비교 | `.two`, `.panel`과 `teal` / `violet` / `amber` / `redline` |
| 짧은 코드와 이유 설명 | `.wide`, `pre > code`, `.code-focus` |
| 핵심 문장과 해석 | `.quote`, `.big`, `.callout`와 `warning` / `danger` |
| 예상 질문과 풀이 | `.question`, 같은 장 또는 바로 다음 장의 명시적 답 |
| 실행 흐름 | `.flow`, `.node`, `.arrow` |
| 변경 전후 | `.state-board`, `.coord`, `.arrow` |
| 역할 대응 | `.role-map`, `.role` |
| 입력·출력·조건 비교 | `table.compare` |
| 이력의 실행 순서 | `.stack`, `.stack-item` |

기본 `.flow`는 노드 4개와 화살표 3개, `.role-map`은 역할 4개에 맞춰져 있다. 억지로 항목을 늘리지 말고 표나 다른 기존 구성을 사용한다. 모바일 흐름도 화살표는 중앙 정렬 후 회전해야 글자와 겹치지 않는다. 짧은 코드 뒤에 이유를 붙이거나, 질문과 답을 나란히 놓는 등 내용에 맞춰 배치를 바꾼다. 모든 장을 “긴 문단 두 개 + 표 하나”로 반복하지 않는다.

## 설명의 전개

차시의 주제에 맞춰 다음 흐름을 구성한다. 모든 차시를 같은 장 수로 맞출 필요는 없다.

1. **이전의 성공 또는 작은 시작점:** 지금 구조로 무엇을 잘 해결했는지 보여 준다. 1차시는 간단한 동작 예시로 시작할 수 있다.
2. **구체적인 새 요구:** 게임에서 무엇이 달라져야 하는지 사용자의 행동과 결과로 설명한다.
3. **첫 해결 시도:** 조건문·필드·직접 호출 등 초보자가 떠올릴 수 있는 방법을 보여 주고, 어느 범위에서는 충분한지 인정한다.
4. **한계의 관찰:** 요구가 늘 때 어떤 값이 사라지거나, 규칙이 중복되거나, 책임이 섞이는지 예시로 확인한다.
5. **필요한 경계:** 함께 기억할 정보와 행동, 나누어 맡길 책임을 도출한다.
6. **개념 또는 패턴의 이름:** 앞에서 찾은 해법에 이름을 붙이고 실제 클래스와 역할을 대응시킨다. 이름과 정의만 나열하며 시작하지 않는다.
7. **짧은 코드와 수치 추적:** 관련된 부분만 보여 주고 입력, 실행 순서, 바뀐 값과 결과를 따라간다. 생략하거나 재구성한 코드는 표시한다.
8. **예상 질문과 답:** 학습자가 결과를 예측한 뒤 스스로 확인할 수 있게 답과 이유를 화면에 적는다.
9. **적용 기준과 비용:** 언제 유용하고 무엇까지 해결하지는 않는지, 다음에 같은 문제를 만났을 때 어떤 판단을 할지 정리한다.

복합 주제는 이 흐름을 두 번 사용할 수 있다. 예를 들어 3차시는 “지형 규칙의 반복과 공유”를 설명한 뒤 “가중치가 있는 이동 경로 탐색”의 문제를 별도로 도출한다.

## 슬라이드만으로 공부할 수 있는 기준

- 새로운 용어는 처음 사용할 때 뜻을 설명한다. 클래스 이름을 먼저 나열하고 의미를 말로 보충하는 방식에 의존하지 않는다.
- 코드에는 해당 문장이 필요한 이유와 실행 후의 결과를 붙인다. 전체 구현을 붙여 분량을 늘리지 않는다. 대체로 9줄 이내의 관련 코드로 나누되 의미를 훼손하며 자르지 않는다.
- 수치 예시는 출발 상태, 입력, 조건, 결과를 밝힌다. 좌표·비용·체력·이력 등을 실제로 계산하고 질문의 답을 검증한다.
- 실제 코드 발췌, 읽기 편한 축약, 설계 비교용 가상 코드, 이전 차시의 구현을 구분한다. 가상 실패 사례를 현재 코드의 결함처럼 설명하지 않는다.
- 현재 Teacher 구현과 Student의 학습용 미완성 지점을 대조한다. 오래된 문서의 API나 동작을 그대로 옮기지 않는다. 예를 들어 실제 지도는 공유 TileData 에셋과 RuntimeTerrain을 사용하므로 정적 TerrainTypes 예시를 현재 지도의 유일한 구현으로 설명하면 안 된다.
- 기존 개념 범위와 중요한 예외를 보존한다. 재구성하면서 Command와 알림의 차이, Undo 범위, 구독 해제, 실패 입력 처리 같은 원래 설명을 누락하지 않는다.
- 내용 개선 요청에는 **기본 화면의 본문과 설명 순서**를 수정한다. CSS만 바꾸거나 이전 본문 뒤에 해설을 추가한 것으로 완료 처리하지 않는다.

## 실습과 다른 산출물의 범위

발표자료에는 별도 실습 장, 작업 절차 부록, TODO 채우기, 전체 완성 코드, Inspector 조작 안내를 덧붙이지 않는다. 짧은 개념 코드와 계산 예시, 답이 있는 이해 확인 질문은 사용할 수 있다.

이 결정은 발표자료의 구성에 관한 것이다. 180분 수업의 구현 활동, Teacher 완성 게임, Student 학습 과제와 별도 교재형 강의 HTML 요구를 없애거나 축소하지 않는다. 사용자가 별도로 요청하지 않은 코드 작성 순서 HTML도 새로 만들지 않는다.

## 수정 후 검수

- 기준 파일과 수정본을 직접 렌더링해 표지, 글꼴, 여백, 색상, 비교 상자, 코드 영역과 하단 탐색을 비교한다. 화면 비율만 같다는 것으로 형식 일치를 판정하지 않는다.
- 모든 장을 1440×900, 1280×720, 390×844에서 확인한다. 데스크톱 본문에는 내부 스크롤이나 잘림이 없어야 하고, 모바일에는 가로 넘침이 없어야 한다.
- 다음/이전, 목차 선택과 닫기, 키보드 이동, 처음/마지막 장, 유효·잘못된 해시를 확인한다. 목차가 열린 상태에서 키보드가 뒤의 슬라이드를 바꾸지 않아야 한다.
- 중복 ID, 끊어진 목차, 장 번호 불일치, 외부 런타임 요청, 숨겨진 본문과 불필요한 실습 부록이 없는지 확인한다. 인쇄 시 모든 장, JavaScript 비활성화 시 전체 내용에 접근할 수 있어야 한다.
- 원래 개념의 포함 여부, 코드와 동작의 일치, 숫자 예시의 계산, 질문의 답을 내용 관점에서 검토한다.
- 새 세션에서도 저장소 안의 이 문서와 실제 기준 HTML만으로 형식을 재현할 수 있어야 한다. 이전 대화나 특정 로컬 임시 폴더를 필수 자료로 삼지 않는다.
